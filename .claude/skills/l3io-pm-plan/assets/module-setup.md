# Module Setup

**Canonical source: `skills/_shared/module-setup.md`.** Per-skill copies under `assets/`
are generated by `npm run sync:scripts` — never edit them directly.

Records this module's project-level settings in the BMad central config. Module identity
(`code`, `name`, `module_version`, `variables`) comes from `module.yaml`, a sibling of the
skill's `assets/` directory.

## When this runs

Only when the user explicitly asks: they passed `setup`, `configure`, or `install`, or
they asked to reconfigure the module.

**A missing `modules.{module-code}` section is not a trigger.** None of the l3io modules
declare required settings, so a correct install has no section at all — treating its
absence as a first-run made every invocation detour into setup. See
`references/config-resolution.md` §5.

## What this writes, and what it must not

BMad merges four config layers. The installer regenerates `_bmad/config.toml` and
`_bmad/config.user.toml` on every install, so anything written there is lost. Setup writes
only to the two human-authored layers, which the installer never touches:

- **`{project-root}/_bmad/custom/config.toml`** — team-scoped, committed. Module settings
  land under `[modules.{module-code}]`.
- **`{project-root}/_bmad/custom/config.user.toml`** — user-scoped, gitignored. Receives
  any variable marked `user_setting: true` in `module.yaml`.

Setup does **not**:

- write `_bmad/config.yaml` or `_bmad/config.user.yaml` — BMad has no such files, and
  creating them forks config into a file no resolver reads;
- collect or write core settings (`user_name`, `communication_language`,
  `document_output_language`, `output_folder`) — the installer owns those, and asking again
  invites an answer that silently loses on the next install;
- write a help CSV — the installer assembles `_bmad/_config/bmad-help.csv` from each
  module's own `module-help.csv` at install time.

`{project-root}` is a **literal token** in config values — never substitute an actual path.
It tells the consuming skill the value is relative to the project root.

## 1. Verify the base install

```bash
uv run --python 3.11 {project-root}/_bmad/scripts/resolve_config.py --project-root {project-root}
```

If this fails or the script is missing, BMad core is not installed here. Stop and tell the
user to run the BMad installer — do not proceed and do not write config. These skills
extend BMad; they cannot stand in for it.

Otherwise, note whether `modules.{module-code}` is already present in the output. If it is,
tell the user this is a reconfiguration and show the current values as the defaults.

## 2. Collect settings

Read `variables:` from `module.yaml`. For each entry with a `prompt`, ask using that prompt
and show the default in brackets. Present every question at once so the user can answer
with only what they want changed ("set implementation_artifacts to X, rest are fine").
Never tell them to "press enter" or "leave blank" — in a chat interface they must type
something.

Default priority (highest first): value already in the resolved config → `module.yaml`
default.

Question types supported by `module.yaml`:

| Shape | How to present |
|---|---|
| `prompt` + `default` (+ optional `result`, `required`, `regex`, `example`) | free text |
| `single-select:` array of `value`/`label` | pick one |
| `multi-select:` array | pick any; default is an array |
| boolean `default` | Yes/No |

Apply `result` templates when storing — a template of `{project-root}/subdir/{value}`
prepends the token. Entries marked `user_setting: true` go to the user layer.

If the user supplied answers inline, or asked for defaults ("accept all defaults",
`--headless`), map what they gave, default the rest, and skip the questions — but still
show the confirmation in step 4.

**If `module.yaml` declares no `variables:`, there is nothing to collect.** Say so, skip to
step 4, and report the module as usable as installed. This is the current state of every
l3io module — it is a normal outcome, not a failure.

## 3. Write

Write the collected answers to a temp JSON file shaped as
`{"module": {"key": "value", ...}}`, then:

```bash
uv run {skill-root}/scripts/write-module-config.py \
  --project-root {project-root} \
  --module-yaml  {skill-root}/module.yaml \
  --answers      {temp-file}
```

The script splits team- from user-scoped keys using `module.yaml`, writes each to the right
layer, and replaces the module's table wholesale so a key dropped from `module.yaml` cannot
survive as a stale entry. Other modules' settings and all file comments are preserved. It
prints a JSON summary; if it exits non-zero, surface the error and stop.

Pass `--dry-run` to preview without writing. Omit `--answers` when nothing was collected.

## 4. Create output directories

Resolve the `{project-root}` token to a real path **for filesystem operations only** — the
values stored in config keep the literal token. Create any configured path that does not
exist yet (`mkdir -p`): `output_folder`, plus any module variable whose value starts with
`{project-root}/`. If `module.yaml` has a `directories:` array, create those too, resolving
any `{field_name}` references from the collected values.

## 5. Confirm

From the script's JSON output, show: which layer each key was written to, whether this was
a fresh registration or an update, and any directories created. Then display
`post-install-notes` from `module.yaml` if present (showing only notes matching the user's
selected values, when conditional), followed by `module_greeting`.

## 6. Return to the skill

Setup is done. Resume the skill's normal activation — re-resolve config per
`references/config-resolution.md` so the new values are bound, then continue with whatever
the user originally asked for.
