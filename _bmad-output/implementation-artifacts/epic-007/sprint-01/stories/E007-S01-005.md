# Integrate Pull Requests, Local Act, and Workflow Governance

As a contributor,
I want pull requests and local `act` runs to execute the same verification graph safely,
So that issues are found before merge without exposing credentials or modifying my worktree.

Depends on: `E007-S01-003`, `E007-S01-004`.

## Acceptance Criteria

**Given** a pull request, including one from a fork
**When** `ci.yaml` executes
**Then** it calls `verify-build.yaml` with read-only contents permission
**And** no publisher secret, OIDC identity, registry login, push, release, or alias job is
available (CI-AR2, CI-AR32)

**Given** a dirty worktree
**When** `just test-local workflow=ci` runs
**Then** `act` executes against a disposable clone/worktree
**And** the developer's branch, index, tracked changes, and untracked files are unchanged
(CI-AR33)

**Given** workflows or action references change
**When** validation runs
**Then** pre-commit, `actionlint`, and workflow contract tests pass
**And** no step branches on the `ACT` environment variable (CI-AR2)

**Given** the new topology is cut over
**When** workflow files are enumerated
**Then** the pipeline contains exactly `ci.yaml`, `dev.yaml`, `release.yaml`, and
`verify-build.yaml`, with no legacy trigger capable of duplicate publication (CI-AR5)

## Technical Acceptance Criteria

### Workflow and local interfaces

- `ci.yaml` triggers on pull requests, sets workflow-level `contents: read`, uses cancellable
  ref-scoped concurrency, and calls the verifier at job level.
- PR inputs are derived from the checked-out head SHA without accepting an untrusted version or
  publication target as executable configuration.
- `just test-local workflow=...` validates the selector against an allowlist and maps it to a
  checked-in workflow path.
- The local runner creates a safe temporary location, clones the requested commit, and runs
  `act` there with only synthetic/local configuration.

### Safety and trust boundaries

- Temporary cleanup is scoped to the validated temporary path and runs on success, failure, and
  signal; it never targets repository root, `$HOME`, `~`, an empty variable, or caller input.
- `.actrc` and sample var/secret files contain no real endpoints or credentials; local secret
  files are ignored.
- Production publisher secret names are rejected or explicitly unavailable in `test-local`.
- Fork pull requests cannot choose a protected runner label, environment, reusable workflow
  ref, or artifact consumed later by a protected publisher run.

### Action governance

- Approved official and LiquidLogicLabs actions use a documented floating major alias where
  available; new third-party exceptions are pinned to a reviewed commit and recorded (CI-AR3,
  CI-AR4).
- Dependabot covers GitHub Actions and Poetry dependencies.
- Action updates must pass workflow contract tests and local/GitHub verification before merge.

### Error handling and observability

- Missing `act`, unsupported workflow selector, clone failure, and workflow failure return
  distinct actionable messages and non-zero status.
- The local runner reports temporary path, workflow, event fixture, and final result without
  printing secret files or environment contents.
- Cleanup failure is reported and does not mask the original workflow result.

### Test anchors

- Contract tests prove trigger exclusivity: PR -> `ci`, main push -> `dev`, exact tag ->
  `release`; reusable verifier has no direct publish trigger.
- YAML tests prove PR job permissions and absence of publisher secrets/actions.
- A dirty-worktree integration test snapshots status and file hashes before/after local `act`.
- Failure tests cover invalid selector, interrupted run, clone cleanup, and a malicious workflow
  attempting to reference production secrets.
- A topology test fails if any obsolete workflow remains after the cutover story is marked done.

## Deliverables

- `ci.yaml`, safe `test-local` recipe/helper, event fixtures, and documentation.
- Workflow/action governance tests and Dependabot configuration.

## Out of Scope

- Development/stable publishers, which are implemented in Epic 8.
- Gitea runner infrastructure, which is implemented in Epic 9.
