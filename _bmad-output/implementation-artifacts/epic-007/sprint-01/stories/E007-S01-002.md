# Execute a Guarded Semantic Release Transaction

As a maintainer,
I want `just release major|minor|patch` to perform a guarded, atomic release transaction,
So that the application version, release commit, repository tag, and later publications cannot
drift.

Depends on: `E007-S01-001`.

## Acceptance Criteria

**Given** `PART` is not exactly `major`, `minor`, or `patch`
**When** release input validation runs
**Then** it fails before changing a file, creating a Git object, or contacting a remote

**Given** the worktree/index is dirty, `HEAD` is detached, the branch is not the configured
default branch, upstream is absent, or local/upstream commits differ
**When** preflight runs
**Then** it reports the failed invariant and leaves version, commit, and tags unchanged (CI-AR9)

**Given** the target exact tag exists locally or remotely
**When** the target version is calculated
**Then** release fails and never force-moves, deletes, or overwrites the existing tag

**Given** version `1.2.3`, a clean/current default branch, and green verification
**When** `just release patch` completes
**Then** the committed Poetry authority becomes `1.2.4`
**And** lock and built metadata agree with `1.2.4`
**And** commit `release: v1.2.4` and annotated tag `v1.2.4` are created
**And** the branch plus exact tag are pushed atomically (CI-AR8–CI-AR10)

**Given** the atomic push fails
**When** the transaction stops
**Then** it reports the recoverable local commit/tag state and no non-atomic fallback is tried

## Technical Acceptance Criteria

### Interface contracts

- `just release PART` invokes one tested release-transaction entry point with the part, remote,
  and default branch as explicit arguments.
- The entry point supports a dry-run/plan mode that performs all read-only checks and prints the
  proposed version/commands without mutation.
- The version reader is shared with CI and returns strict normalized SemVer without a leading
  `v`; tag formatting is a separate operation.
- Git subprocesses use argument arrays and explicit repository cwd; no `shell=True`, `eval`, or
  command interpolation is permitted.

### Transaction and data model

- The plan records current version, target version, source SHA, branch, upstream SHA, remote,
  exact tag, and planned files without credentials.
- Bump rules follow SemVer for major/minor/patch, including `0.x` input, and discard any
  unsupported prerelease/local suffix rather than guessing.
- Mutation order is version update -> lock consistency -> verification -> commit -> annotated
  tag -> `git push --atomic <remote> <branch-ref> <tag-ref>`.
- The commit contains only expected version/lock files; unrelated staged changes are impossible
  because dirty state is rejected before mutation.

### Error handling and recovery

- Every precondition is rechecked immediately before mutation where a race is possible.
- A version/lock/build mismatch after the bump aborts before commit and reports the changed local
  files; no destructive reset is performed.
- Commit or tag failure reports the current local state. Push failure retains the local commit
  and tag and provides safe retry/inspection instructions.
- Remote checks distinguish missing tag from auth/network failure; an unverifiable remote is a
  hard failure, not treated as an unused tag.

### Observability and security

- Normal logs show versions, branch, remote name, commit SHA, and tag; remote URLs are sanitized
  to remove embedded credentials.
- No Git credential helper contents, token, environment dump, or command containing a secret is
  printed.
- The transaction never uses force push and never deletes a remote reference.

### Test anchors

- Unit tests cover all bump parts, malformed/current prerelease versions, and tag formatting.
- Repository integration tests cover clean, dirty, detached, wrong branch, no upstream,
  behind/ahead/diverged branch, existing local/remote tag, verification failure, and push
  rejection using disposable bare remotes.
- A success test proves the remote receives the version commit and exact tag together and that
  the annotated tag resolves to the release commit.
- A failure-injection test proves no remote ref changes when atomic push rejects either ref.
- Workflow tests prove `release.yaml` validates the tag and never calls Poetry version bump or
  creates the exact stable tag.

## Deliverables

- Guarded release transaction implementation and unit/integration tests.
- `just release PART` recipe and maintainer runbook.

## Out of Scope

- Floating repository tags (`vX`, `vX.Y`), which are finalized in E008-S01-003.
- Publishing packages, images, or forge Releases.
