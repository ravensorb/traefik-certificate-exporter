As a pipeline maintainer,
I want version, build-manifest, publication-plan, and release-receipt contracts plus a reusable
secret-free verifier,
So that every adapter agrees on inputs, outputs, failure semantics, and evidence.

Depends on: `E007-S01-001`.

## Acceptance Criteria

**Given** `verify-build.yaml` is invoked directly or as a reusable workflow
**When** its public interface is inspected
**Then** its only semantic inputs are channel, package version, and source SHA
**And** it requires no publisher secret, protected environment, OIDC write, package write, or
contents write permission (CI-AR5, CI-AR18, CI-AR32)

**Given** a stable exact tag
**When** validation compares tag, committed Poetry version, lock state, and built metadata
**Then** any mismatch fails before artifact production (CI-AR11)

**Given** a development version
**When** validation runs
**Then** it accepts only the planned next-patch PEP 440 `.devN` form and does not mutate the
committed version or repository (CI-AR12)

**Given** a build manifest, publication plan, or release receipt
**When** it is produced or consumed
**Then** it passes a checked-in strict versioned schema and contains no credentials or secret-
derived data (CI-AR15, CI-AR22, CI-AR30)

## Technical Acceptance Criteria

### Workflow interface

- `verify-build.yaml` supports `workflow_call` and `workflow_dispatch` with the same required
  inputs: `channel`, `package-version`, and `source-sha`.
- Workflow-scope permissions are `contents: read`; no job requests `id-token: write`,
  `packages: write`, or `contents: write`.
- Checkout selects the supplied full SHA, fetches required history/tags, and disables persisted
  credentials.
- Outputs contain artifact names and non-sensitive hashes/digests only.

### Schema and application contracts

- `build-manifest-v1.schema.json` requires channel, source SHA, package version, lock hash,
  distribution filenames/hashes, platforms, and observed image digest.
- `publication-plan-v1.schema.json` supports per-target enabled state, endpoint/registry,
  repository, credential mode, immutable identities, aliases, forge/run context, and optional
  development distance.
- `release-receipt-v1.schema.json` supports planned identity, observed destination outcomes,
  release reference, alias movements, timestamps, and errors safe for artifact retention.
- Schemas reject additional properties unless explicitly reserved and enforce SHA-256, OCI
  digest, SemVer/PEP 440, URL/host, and strict boolean formats.
- One library/composite action validates and normalizes these contracts for local and workflow
  callers; no workflow embeds an alternate JSON parser or version authority.

### Error handling and edge cases

- Unsupported channel, malformed SHA/version, missing schema, unknown field, and hash/digest
  mismatch fail with field-scoped diagnostics.
- Tag validation accepts only exact `vMAJOR.MINOR.PATCH`; floating, prerelease, malformed, and
  multiple conflicting exact tags fail stable planning.
- Development validation proves source ancestry/base tag and rejects an unverifiable distance.
- Contract validation rejects credential-like field names and documented secret patterns.

### Observability and security

- Safe manifests may be rendered in the job summary; validation errors redact values for fields
  classified as sensitive.
- Evidence records source/version/hash identity but the reproducible build manifest excludes
  run IDs and timestamps that would change for identical source.
- The publication plan/receipt may include run correlation because they describe a transaction,
  not reproducible build output.

### Test anchors

- Unit tests cover valid dev/stable examples and a mutation test for every required/schema-bound
  property.
- Redaction tests seed token-shaped values, private-key markers, passwords, and certificate
  material and assert none appears in logs/artifacts.
- Workflow tests parse YAML to prove permissions and exact reusable interface parity.
- Dependency tests prove each present/future publisher has `verify-build` and plan/preflight in
  its transitive prerequisites.
- Compatibility fixtures pin the schema examples used by E008 stories.

## Deliverables

- Reusable `verify-build.yaml` interface skeleton.
- Version/contract libraries or composite actions.
- Three strict JSON schemas, fixtures, and tests.

## Out of Scope
