# Establish the Reproducible Local Package and Image Workflow

As a maintainer,
I want a discoverable `just` interface over the existing Poetry, test, Docker, and workflow
tools,
So that local work uses the same entry points and artifact contracts as CI.

Depends on: none.

## Acceptance Criteria

**Given** a supported machine with `just`, Poetry, Python, Git, and Docker
**When** `just --list` is run from the repository root or a child directory
**Then** documented recipes exist for `setup`, `lint`, `test`, `test-local`, `package`, `image`,
`build`, `verify`, and `release PART` (CI-AR7)

**Given** `just package` runs in a clean or dirty developer worktree
**When** Poetry completes the package build
**Then** exactly one wheel and one sdist are produced in a repository-owned output directory
**And** the committed version, filenames, and package metadata agree
**And** the developer's source files and index are not modified

**Given** the wheel and sdist exist
**When** package verification runs
**Then** their SHA-256 values are recorded
**And** the wheel installs in an empty environment
**And** the installed CLI starts and reports the planned version

**Given** `just image` or `just build` runs
**When** the Docker build resolves application input
**Then** it consumes the exact wheel created by `just package`
**And** it does not build the Python project or independently resolve Poetry dependencies
inside the container (CI-AR13, CI-AR14)

**Given** `just verify` runs
**When** any lint, test, package, install, image, or smoke check fails
**Then** the recipe graph stops non-zero before any publish, tag, commit, or remote mutation

## Technical Acceptance Criteria

### Interface contracts

- The root `justfile` sets an explicit fail-fast shell and a root-relative working directory.
- `package` accepts an optional output directory but rejects paths outside the project-owned
  artifact root; its default is deterministic.
- `image` accepts wheel path, wheel SHA-256, expected package version, and a local image tag.
- `build` composes `package` and `image`; `verify` composes lint, test, build, package-install,
  and container smoke checks without reimplementing their commands.
- `release PART` is declared but delegates its mutation semantics to E007-S01-002.

### Data and artifact contracts

- The package output layout contains the wheel, sdist, `SHA256SUMS`, and a machine-readable
  staging manifest; filenames are enumerated rather than selected with an unconstrained glob.
- The staging manifest contains source SHA, committed version, filenames, hashes, and lock hash,
  and contains no environment dump or credentials.
- The Docker build context receives only the selected wheel and required container files.

### Error handling and safety

- Missing tools are reported by name with a setup hint before work begins.
- Cleanup operates only on an explicit validated artifact directory and never on the repository
  root, `$HOME`, `~`, an empty variable, or a broad glob.
- User-controlled recipe parameters are quoted and validated before they reach a subprocess.
- A hash/version mismatch fails before Docker build; an image smoke-test mismatch fails the
  overall recipe even when `docker build` succeeded.

### Observability and security

- Recipe output names the source SHA, version, output filenames, hashes, and local image tag.
- Logs never print environment-wide values, registry credentials, PyPI tokens, or certificate
  material.
- Local build recipes never log in to a registry and never invoke a publish action.

### Test anchors

- Contract tests parse `just --summary` and assert every required recipe is present.
- Tests prove `build` and `verify` transitively invoke package and image verification once.
- Tests cover missing wheel, extra distribution, changed hash, wrong metadata version, failed
  clean install, and failed container smoke test.
- A dirty-worktree test snapshots `git status --porcelain=v1 -z` before/after `package` and
  requires exact equality.
- Documentation examples are exercised in CI with publication disabled.

## Deliverables

- Root `justfile` and developer documentation.
- Minimal tested helper(s) needed for deterministic package/image staging.
- Contract and smoke tests for the local interface.

## Out of Scope

- Stable version mutation and push (E007-S01-002).
- External package or image publication (Epic 8).
