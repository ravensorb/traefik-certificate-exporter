# Load .env only for the standalone CLI: settings.loaddotenv, off in the image

## Context

**Maintainer decisions:** `_bmad-output/implementation-artifacts/epic-015/maintainer-decisions.md`, MD-24 (`.env` loading, maintainer decision D1, 2026-10-13/14) and MD-25 (`appriseurls` stays `any-source` as an accepted residual risk, D2, 2026-10-13/14). Both were accepted on 2026-10-14.

**Binding constraint (2026-10-12), verbatim:** "for the root fix -- do NOT break lsio and the way they do things". This story changes no LinuxServer init script, no `/config` ownership and no s6 script. The image change is one `ENV` line, next to the pinned `DATAPATH`/`OUTPUTPATH`.

**Supersedes:** BL-E015-052 asked the maintainer to ratify the root-mode `.env` narrowing (ADR-0049 amendment of 2026-10-12) and to restate PRD FR-18. MD-24 ratifies the narrowing for CLI root runs (item 4) and replaces the container case. FR-18 was restated on 2026-10-14, so BL-E015-052 was resolved `obsolete` with ref E015-S02-005.

**Evidence, re-probed 2026-10-14 against `traefik-certificate-exporter:local` (built 2026-10-12 from `main`, S01-001 merged):**

- **The s6 service does not run in `/config`.** The image sets `WORKDIR /config` (`docker/Dockerfile:158`). The service's `/proc/<pid>/cwd` was `/run/s6-rc:s6-rc-init:<id>/servicedirs/svc-traefik-certificate-exporter`. A planted `/config/.env` containing `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_DRYRUN=true` left the service at `dryRun: false` (DEBUG settings dump).
- **`docker exec <c> traefik-certificate-exporter -c /config/config.yaml` runs in `/config` and reads `/config/.env`.** The same container logged `Loading Configuration from Local Environment File` and `dryRun: true`. A one-off `docker run <image> traefik-certificate-exporter …` uses the same `WORKDIR`.
- So today `/config/.env` reaches only one-off invocations. These run as root, so the S01-001 any-source filter applies to them. The service is unaffected only because s6 happens to start it in its service directory. Nothing documents or tests that.
- ADR-0049's 2026-10-12 amendment says "The exporter's working directory in the image is `/config`". `docs/operational.md:353` and `docs/upgrading.md:42-43` say "(in the image, `/config/.env`)". All three are inaccurate for the service, and this story corrects them.
- `SettingsManager.loadFromFile` also reads a `.env` from the installed package's own folder: `self.modulePath.joinpath(".env")`, `settings.py:464-472`. That is `/app/.venv/lib/python3.*/site-packages/traefik_certificate_exporter/.env` in the image. The folder is under the `abc`-owned `/app`, a known open risk (BL-E015-002). MD-24 item 5 removes this source.

**D2, `appriseurls` (BL-E015-032, RT-4).** Apprise `json://`, `xml://` and `form://` (and their TLS forms) can send a request with any method, path, query and headers to any host the container can reach. **Example: a POST to a docker-socket-proxy's `/containers/<id>/stop` needs no body.** So `appriseurls: ["json://docker-socket-proxy:2375/containers/traefik/stop?method=POST"]` in `config.yaml` lets the `PUID` account stop a container through a proxy that allows `CONTAINERS` and `POST`. The maintainer keeps `appriseurls` `any-source` "for now" (MD-25). This story only corrects the claim "Network egress only" in `ROOT_SETTING_TRUST` and in ADR-0049 to state that residual risk. BL-E015-032 was resolved `wontfix` with the revisit condition in MD-25.

**Options evaluated (MD-24):**

| Option | Verdict |
|---|---|
| (a) Remove `.env` support entirely | **Rejected** by the maintainer: the CLI may be installed from PyPI and run outside a container, where a cwd `.env` is the normal convenience. |
| (b) Keep loading `/config/.env` in the image, filtered as today | **Rejected**: `/config` is `PUID`-writable, the service's cwd makes the behaviour accidental, and Docker's own `env_file:` covers the container use case without the exporter reading any file. |
| (c) **A switch, `settings.loaddotenv` (default `true`), taken only from the environment or the CLI, set `false` by the image `ENV`** | **Adopted.** |
| (d) Decide by detecting a container (`/.dockerenv`, cgroups) | **Rejected**: it is heuristic and untestable across runtimes, and it adds a hidden rule where an explicit `ENV` line already exists for `DATAPATH`/`OUTPUTPATH`. |

## Acceptance Criteria

1. **New setting `settings.loaddotenv`, default `true`, in the single key registry.** `src/traefik_certificate_exporter/config_default.yaml` gains `loaddotenv: true` under `settings:`, with a two-line comment: "Read a `.env` file from the current working directory. Environment or command line only, never a file. The image sets it false." The environment name is `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_LOADDOTENV`, derived by the existing `_env_name` rule. The CLI flag is `--no-dotenv`, defined in `libs/cli_args.py` like `--no-validate-keys`: `action="store_const"`, `const=False`, `dest="settings.loaddotenv"`, `default=None` (product AD-6 opt-out convention), so an absent flag never overrides the environment. `Settings` gains `loadDotenv: bool`, a keyword argument with default `True` so that callers which build `Settings` directly keep working.
2. **A third trust class enforces "environment or CLI only" in every mode** (MD-24 item 1). `settings.py` adds `ROOT_TRUST_ENVIRONMENT_ONLY_EVERY_MODE = "environment-only-in-every-mode"`, and `ROOT_SETTING_TRUST` maps `("settings", "loaddotenv")` to it, with the comment "decides whether a .env file is read; no file may choose it". The block comment above the map names the three classes. `tests/test_settings_surface.py::_root_trust_violations` accepts the third constant, so the completeness guard keeps failing on an unclassified, non-leaf or unknown entry. The enforcement reads the class from the map and never names `loaddotenv` directly (AC 5), so a second key put in this class is enforced with no code change.
3. **The switch is decided before any `.env` is read, from the environment and the command line only.** `loadFromFile` decides the switch before its first `load_dotenv` call:
   - confuse 2.3.0 evaluates it over a throwaway `confuse.RootView` with exactly three sources: the packaged default source, a `confuse.EnvSource(_ENV_PREFIX, sep="_")` read at that moment (the real environment, since no `.env` is loaded yet) and `set_args(cmdLineArgs, dots=True)`;
   - the value is `view["settings"]["loaddotenv"].get(bool)`, using confuse's own truthiness. `false`, `no`, `off` and `False` are false. Probed 2026-10-14.
   - A value confuse rejects (`0`, `garbage`, empty) **fails closed**: no `.env` is read, and one ERROR names `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_LOADDOTENV` without its value.
   - No hand-written boolean parser and no second precedence implementation. The file sources are absent from the throwaway view by construction.
   - `Settings.loadDotenv` is the decided value. A unit test asserts that it equals confuse's merged `settings.loaddotenv` after AC 5 has run, in every mode.
4. **When `loaddotenv` is true, only the working-directory `.env` is read, as today** (MD-24 items 4, 5):
   - the module-folder `.env` (`self.modulePath.joinpath(".env")`, `settings.py:464-472`) is no longer read in any mode, and its DEBUG line is deleted. `modulePath` stays, because confuse and other callers may use it; `grep` confirms its remaining uses at dev time.
   - `Path(os.getcwd(), ".env")` loads as today. Non-root uses `load_dotenv(path)`. Root uses `_loadDotenvAsRoot(path)`, unchanged from S01-001: any-source names only, every other newly added name removed with one ERROR per file, `interpolate=False`, legacy names left to the S01-004 WARNING.
   - `_warn_if_group_or_world_writable` still runs for the cwd `.env`.
5. **A file can never set an every-mode environment-only key** (MD-24 item 1), in every mode (euid 0 and non-zero):
   - **Config file and confuse user config.** After all sources are merged, a new `SettingsManager._withholdEveryModeSettings()` runs before `_withholdFileSourcedRootSettings()`. For each `ROOT_TRUST_ENVIRONMENT_ONLY_EVERY_MODE` key, it removes the key from **every** file source that carries it, using the S01-001 mechanism: pop from `self._config.sources`, never `view.set()`. It logs one ERROR per file that carried the key. Unlike the when-root rule, this happens whether or not the file value would have won, because a file value for this key is always a misconfiguration and the image's `ENV` would otherwise hide it silently.
   - **A `.env` file.** If `load_dotenv` newly adds the variable of an every-mode key, the variable is removed from `os.environ` and one ERROR names the `.env` file. Non-root runs need a name snapshot around `load_dotenv`, the same snapshot `_loadDotenvAsRoot` already takes. In root mode the name is reported by this ERROR, not in the generic "Ignoring N variable(s)" list. A name the real environment already held is untouched.
   - After the removal, `sourceOf(("settings", "loaddotenv"))` returns `environment`, `command line` or `default`, never a file.
6. **The image switches it off** (MD-24 item 2). The `ENV` block of `docker/Dockerfile` (`:123-130`) gains `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_LOADDOTENV=false` beside `…_DATAPATH=/data` and `…_OUTPUTPATH=/certs`. Its comment says that `/config/.env` is not read in the image, and that variables go in the container's `environment:`/`env_file:` and settings in `config.yaml`. Nothing else in `docker/` changes: no s6 script, no `init-adduser`, no ownership step, no `WORKDIR`.
7. **One WARNING when a `.env` is present but not read** (MD-24 item 3). When the decided value is false, `loadFromFile` checks, with `os.path.isfile` only (the file is never opened):
   - `Path(os.getcwd(), ".env")`;
   - the `.env` beside the configuration file, `Path(fileName).parent / ".env"`, whether or not the configuration file exists.

   The second path is needed because the s6 service's cwd is its service directory, not `/config` (Context), so a cwd-only check would never see `/config/.env` from the service. That deviates from the literal wording of MD-24 item 3, and the reason is recorded in MD-24. Paths are de-duplicated by `os.path.realpath`. If any exist, **one** WARNING is logged at start-up, before the `starting....` line, with no correlation id. It lists each path and never a name or value from the file (Observability). Without a `.env` there is no line. The WARNING never fires while `loaddotenv` is true.
8. **The legacy-name check (E015-S01-004) is unchanged in behaviour.** `check_setting_names` still receives `os.environ` plus `_legacyDotenv`. With `loaddotenv` false, a legacy name inside an unread `.env` is not reported, because the file is not read and the AC 7 WARNING is the only line about it. `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_LOADDOTENV` is a valid name through the existing registry derivation (`legacy_settings.valid_env_names()`), so the image's `ENV` produces no "unknown name" WARNING. A unit test asserts this.
9. **`appriseurls` rationale corrected** (MD-25). The `ROOT_SETTING_TRUST` comment for `("settings", "appriseurls")` changes from "Network egress only: Apprise loads no plugins and reads no local attachment." to state the accepted residual risk: "Outbound requests to any host the container reaches: json/xml/form can choose method, path and headers (RT-4). Accepted residual risk, MD-25; no local file or process reach." The class stays `ROOT_TRUST_ANY_SOURCE`.

## Business acceptance criteria

### Outcome

- **Container users.** `/config/.env` is never read, by the service or by a `docker exec` one-off, in root mode or dropped mode. If one is present, the start-up log has one WARNING that says it is ignored and where to put the variables. Docker's `env_file:` keeps working, because Docker applies it. No setting changes for a deployment that has no `/config/.env`. The service never read it in 0.3.0 either (Context).
- **CLI users (PyPI, `pipx`).** A `.env` in the current directory keeps loading as in 0.3.0. One `.env` location stops working: the one inside the installed package folder. `--no-dotenv` or `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_LOADDOTENV=false` turns `.env` loading off. Under `sudo` the S01-001 rule stays: setting names of `any-source` settings only, no `${VAR}` expansion.
- **Nobody can choose the switch from a file.** A `loaddotenv` in `config.yaml`, the confuse user config or a `.env` is ignored with one ERROR, in every mode.
- **The `appriseurls` risk is written down.** The code comment, ADR-0049 and the spine state plainly that a `config.yaml` Apprise URL can send requests to any reachable host. A POST to a docker-socket-proxy's `/containers/<id>/stop` needs no body. The maintainer accepts that risk for 0.3.1 (MD-25).
- LinuxServer's init, `/config` ownership and s6 scripts are unchanged.

Put variables in the container's `environment:` or Docker's `env_file:` (Docker applies it), and settings in `/config/config.yaml`. ### Non-goals

- No change to LinuxServer's init (`init-adduser`, `lsiown`), `/config`/`/app`/`/defaults` ownership, any s6 script, or the image's `WORKDIR`.
- No removal of CLI `.env` support, and no change to `.env` parsing (python-dotenv `load_dotenv`, unchanged).
- No change to the S01-001 root-mode rules (the three environment-only-when-root keys, the any-source `.env` filter, `interpolate=False`) beyond routing the new key's ERROR.
- No search for `.env` beside the configuration file when `loaddotenv` is true. That path is only checked for the AC 7 WARNING.
- No change to `appriseurls` behaviour or class (MD-25). Only its rationale text changes.
- No change to the hook's cwd or inherited environment (RT-6, RT-3).
- No new start-up INFO line for the switch. `Settings.loadDotenv` appears in the DEBUG settings dump.

### Error and edge case handling

- **`.env` in another working directory (CLI):** the `.env` of the directory the CLI is started from is read. A `.env` next to `-c /elsewhere/config.yaml` is not read when `loaddotenv` is true. When it is false, that `.env` gets the AC 7 WARNING.
- **The switch in `config.yaml`:** ignored, with one ERROR naming `settings.loaddotenv` and `configuration file '<path>'`, in every mode. This holds even when the environment also sets it, which is always the case in the image. The effective value comes from the environment, the CLI or the default.
- **The switch in a `.env`:** the variable is removed after that `.env` was loaded, with one ERROR naming the `.env` file. The decision was already taken before the file was read.
- **The switch in the confuse user config** (`$HOME/.config/traefik_certificate_exporter/config.yaml`): handled like `config.yaml`.
- **Docker `env_file:` / `docker run --env-file`:** Docker puts the variables in the process environment, so they are the environment, not a `.env` read by the app. They load in every mode. A `LOADDOTENV=true` in an `env_file:` re-enables cwd `.env` reading. In the service that cwd is the s6 service directory, so `/config/.env` stays unread; a `docker exec` from `/config` would read it under the root-mode filter. This is the operator's explicit choice through the container's configuration; the docs say not to.
- **An invalid value** (`TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_LOADDOTENV=0`): fail closed (no `.env` read), one ERROR without the value. The `Settings` build then reports it as confuse does for any malformed boolean. The dev agent records the observed behaviour in the notes and keeps it unchanged for the other booleans.
- **No `.env` anywhere and `loaddotenv` false:** no WARNING, no ERROR.
- **Windows (no `os.geteuid`):** the switch and AC 5 apply. Only the root filter is inactive, as today.
- **The init resolver** (`init-traefik-certificate-exporter-config/run`, root) runs the same `loadFromFile` with the image `ENV`, so it reads no `.env` either. Its stdout is `/dev/null`, so its copy of the WARNING is not visible. Only the service's copy reaches `docker logs`.

### Observability requirements

All lines are logged once per start through `globalLogger`, before the `starting....` line, with no correlation id. No line contains a value from any `.env` or file.

- AC 5, file source:

  `Ignoring settings.loaddotenv from <configuration file '<path>'|.env file '<path>'>: it decides whether a .env file is read, so it is taken only from the environment (TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_LOADDOTENV) or the command line (--no-dotenv). Using the <environment|command line|default> value (ADR-0049).`

  The env name and flag are derived (`_env_name`, and the argparse option for the dest), not typed per key.
- AC 3, invalid value:

  `Ignoring TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_LOADDOTENV: not a boolean. No .env file is read (ADR-0049).`
- AC 7:

  `Not reading .env file(s) <'path'[, 'path']>: settings.loaddotenv is false (the container image sets TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_LOADDOTENV=false). Set variables in the container's environment: or env_file:, and settings in config.yaml.`

  The level is WARNING. In `tests/test_s6_privilege_drop.py`, the "exactly one WARNING" invariant counts init stdout only, so this service line does not touch it.
- Paths are passed through `sanitize_for_log` (RT-5 class).

### Security considerations

- **Closes the remaining container path for `/config/.env`.** A `PUID`-writable `.env` can no longer feed variables to any exporter process in the image: service, init resolver, `docker exec` or one-off `docker run`. Today only the one-off root invocations read it, through the S01-001 any-source filter.
- **The module `.env` is gone.** A file under the `abc`-owned `/app` (BL-E015-002) can no longer add variables to a root process, filtered or not.
- **The switch cannot be flipped by the account it protects against.** It is every-mode environment-only (AC 2, AC 5), and the guard is derived from the trust map.
- **What is mechanically checked:**
  - the class completeness (`test_settings_surface.py`, extended allowed set);
  - every-mode withholding from every file source the loader opens, derived from the map, with a planted second key (Testability);
