# setup-buildx-action: rename config input to buildkitd-config, with a guard

## Context

**Maintainer decisions:** `_bmad-output/implementation-artifacts/epic-015/maintainer-decisions.md` — none for this story.

Promoted from BL-E014-108 (Medium, seen in v0.3.0 release run [38281339396](https://github.com/ravensorb/traefik-certificate-exporter/actions/runs/38281339396)). Both multi-arch `publish-image` jobs hand the private-CA BuildKit config to `docker/setup-buildx-action` under an input name the pinned action no longer has:

- `.github/workflows/dev.yaml:409-412` and `.github/workflows/release.yaml:477-480`: `uses: docker/setup-buildx-action@f87e5991a6d7451dcb8d9637bfbc97413f497069 # v4.4.1` with `config: ${{ steps.ca.outputs.buildkit-path }}`.
- `.github/workflows/build.yaml:154` uses the same pin with `driver: docker` only; it is not affected.
- The action's `action.yml` at `f87e599` declares the inputs `version`, `driver`, `driver-opts`, `buildkitd-flags`, `buildkitd-config`, `buildkitd-config-inline`, `use`, `name`, `endpoint`, `platforms`, `append`, `keep-state`, `cache-binary` and `cleanup`. There is no `config` input. In v3.12.0, `config` carried `deprecationMessage: 'Use buildkitd-config instead'`, and v4.0.0 (2026-03-05) removed it ("Remove deprecated inputs/outputs", docker/setup-buildx-action#464).
- `src/context.ts:74-77` at the same SHA adds `--config <file>` to `docker buildx create` only when `buildkitd-config` (or `-inline`) is non-empty. An empty value adds nothing, so the no-CA path (today's only path) is unchanged by the rename.
- Effect: a run with `PUBLISH_CA_CERTIFICATE` set imports the CA into the runner, but BuildKit never receives it, so a push to a private-CA registry fails TLS. Every image job warns `Unexpected input(s) 'config'` (closure notes `_bmad-output/implementation-artifacts/epic-014/sprint-02/closure/notes-E014-S02-007.md`, AC 6 row).
- Until the 2026-10-12 consolidation the CI spine prescribed the defect: AD-18 said setup-buildx "receives that step's `buildkit-path` output as `config`". The consolidated AD-18 (Target 0.3.1) states `buildkitd-config` and the guard below. `docs/ci/gitea-runners.md:40` and `:47-48` still say `config`.

**Why no check caught it (research §5, `_bmad-output/planning-artifacts/research/research-2026-10-12-release-0.3.1.md`).** actionlint checks `with:` keys only for its embedded popular-actions data, and only for a `owner/repo@vN` major-tag spec. Its `docs/checks.md` (v1.7.12) says: "it only supports the case of specifying major versions like `actions/checkout@v4`". A probe with the hook's own binary flagged `config` on `docker/setup-buildx-action@v4` and passed the same step pinned by SHA and by `@v4.4.1`. AD-5 SHA-pins every non-LiquidLogicLabs action, so actionlint validates the inputs of **no** third-party step in this repository. No maintained tool fills the gap:

- zizmor 1.30.1's audit list has no input audit.
- ghalint v1.5.6's policies cover permissions, secrets and pinning only.
- action-validator v0.9.0 checks SchemaStore schemas and path globs only.
- gha-workflow-linter 1.8.1 checks that refs exist (network plus a GitHub token) and documents no `with:` validation. It would also be a new tool outside AD-4's list.

The only component that validates every step's `with:` against the pinned `action.yml` is the GitHub runner itself, which emits `Unexpected input(s)` as a warning annotation.

**Guard decision (retro A5: AD-4 checked first).** AD-4 allows only standard tools' configuration, with `pygrep` named. So the guard is the smallest compliant one:

- **Static.** A `repo: local` pygrep hook `workflows-no-removed-buildx-inputs` refuses a `config:` or `config-inline:` key in any workflow or composite-action YAML. pygrep is line-based and cannot tie a key to its step, so the key is refused for every action. Today no other step uses either name; the current tree has exactly the two offending lines.
- **Runtime, scope from the source of truth.** The per-release checklist gains "zero `Unexpected input` lines in the release run log", checked on the live GitHub run by E015-S02-004.

The runtime check is not CI-gating, and that limit is stated where the rule lives (global rule 3). A maintained validator for SHA-pinned inputs, if one appears, is the revisit condition.

## Acceptance Criteria

1. **The input is renamed.** `.github/workflows/dev.yaml` and `.github/workflows/release.yaml` each pass `buildkitd-config: ${{ steps.ca.outputs.buildkit-path }}` to their `publish-image` `docker/setup-buildx-action` step. No workflow passes `config:` or `config-inline:`. The pin, the `if: env.PUBLISH_IMAGE == 'true'` gate and the step order (AD-18) are unchanged.
2. **The CA reaches BuildKit.** Under act, with a test CA in `PUBLISH_CA_CERTIFICATE` and a TLS registry whose certificate that CA signs, `dev.yaml` `publish-image` runs `docker buildx create … --config <file>`. The multi-arch push to that registry succeeds. The same run on the pre-story tree fails the push with an x509 error; that fail-first run is recorded in the notes.
3. **The no-CA path is unchanged.** With nothing configured, `dev.yaml` and `release.yaml` succeed under act with no destination warning and no `enabled` line, exactly as before.
4. **The guard exists and covers its scope.**
   - `.pre-commit-config.yaml` carries a `repo: local`, `language: pygrep` hook with id `workflows-no-removed-buildx-inputs`, entry `^\s*(?:-\s+)?["']?config(?:-inline)?["']?\s*:` and `files: ^\.github/(workflows|actions)/.*\.ya?ml$`, placed beside the other `workflows-*` guards.
   - Its comment cites AD-18 and BL-E014-108, states that actionlint does not validate inputs of SHA-pinned actions, and states its coverage limit: the two removed key names only, in block style; a flow-style `with: {config: x}` is not matched, and other actions' removed inputs are not seen.
   - Planted violations in a throwaway clone: a `config:` key in a workflow, and a `config-inline:` key in `.github/actions/x/action.yml`, each fail the hook. The current tree's two lines fail it before the fix.
5. **Spine and docs match.**
   - AD-18 says `buildkitd-config`.
   - AD-3's required-hook list names `workflows-no-removed-buildx-inputs` (AD-18).
   - The spine `## Changelog` has a dated E015 line.
   - `docs/ci/gitea-runners.md` (`:40`, `:47-48`) says `buildkitd-config`.
   - `docs/ci/pipeline-walkthrough.md` §"What polices the pipeline" lists the hook and states that actionlint does not validate inputs of SHA-pinned actions.
   - The walkthrough's per-release checklist (§"Releasing") gains "the release run log has zero `Unexpected input` lines (the runner checks every step's `with:` against the pinned action; not CI-gating)".
6. **`just check` is green.** No new zizmor suppression. Every row of `## Verification` passes.

## Business acceptance criteria

### Outcome

A maintainer or fork that publishes to a private-CA registry (`PUBLISH_CA_CERTIFICATE` set) gets a working multi-arch image push. The release log loses its two `Unexpected input(s) 'config'` warnings. A future edit that reintroduces the removed input names fails `just check` and CI before it merges. The maintainer has a per-release check that catches any other action's unknown input, which no static tool here can see.

#### 0.3.1 release notes

- "Publishing to a registry behind a private CA now works: the imported CA is passed to BuildKit (`docker/setup-buildx-action` v4 renamed its `config` input to `buildkitd-config`)." (Maintainer- and fork-facing.)
- Internal-only (no upgrade note): the new pygrep guard; the per-release `Unexpected input` checklist item.

## Technical acceptance criteria

### Interface contracts

- Step contract, both `publish-image` jobs: `docker/setup-buildx-action@f87e5991a6d7451dcb8d9637bfbc97413f497069 # v4.4.1`, `if: env.PUBLISH_IMAGE == 'true'`, `with: buildkitd-config: ${{ steps.ca.outputs.buildkit-path }}`. The value is `''` when the CA step is skipped. The action then adds no `--config` (`src/context.ts:74`).
- Hook contract: id `workflows-no-removed-buildx-inputs`, `language: pygrep`, the entry and `files` of AC 4.
- Sibling conventions for the hook:
  - Every `workflows-*` guard is `repo: local`, `language: pygrep`, with a preceding comment naming its AD/BL key and its "Coverage limit:".
  - Hooks whose subject can live in a composite action use `files: ^\.github/…` (as `workflows-lll-major-tag` does).
  - The hook is listed in AD-3's required-hook list next to the AD it enforces.
- Shared publish logic lands in `dev.yaml` and `release.yaml` in the same commit, and the PR says so (AD-1, ADR-0047).

Spec: none — l3io-plan run, no spec index bound

### Error and edge case handling

- **CA unset** (normal case): `buildkitd-config: ''`, no `--config`, identical behaviour to today minus the warning.
- **CA set, `buildkit-path` empty or missing file:** the action fails at `buildx create` ("config file not found"). That is a loud failure before any push, which is correct. It is not reachable unless the CA action changes its output contract.
- **A later Dependabot bump removes or renames another input:** the static guard does not see it. The runner's `Unexpected input` warning appears on the next dev/release run, and the per-release checklist catches it. Recorded as the guard's coverage limit.
- **Another action legitimately takes an input named `config`:** the guard refuses it. The fix is to narrow the hook in the same change, with a comment. This is accepted as a false positive, because pygrep cannot see step context.
- **Gitea/act:** whether they print `Unexpected input` is not relied on. AC 2's act row proves the input is honoured by the `--config` line and the TLS push, not by the absence of a warning.

Spec: none — l3io-plan run, no spec index bound

### Security considerations

- The test CA and registry key in the act row are generated per run under `/tmp`, valid for one day, and deleted afterwards. They never enter the repository or a forge.
- `PUBLISH_CA_CERTIFICATE` reaches act only through the process environment (`-s NAME` with no value), never argv.
- The change restores the AD-18 control: with a private CA, BuildKit trusts exactly the imported CA, instead of the push failing or an operator being tempted to mark the registry insecure.

### Testability approach

There is no pytest and no custom policy code (AD-4). The checks are:

- the pygrep hook, with planted violations in a throwaway clone, attacking scope: a composite action under `.github/actions/` and the second key name;
- actionlint and zizmor via `just check`;
- one act run with a test CA and a TLS `registry:2`, in the throwaway-clone pattern of E014-S02-002.

The act clone's copy of `dev.yaml` sets `if: false` on the Gitea `docker/login-action` step and the `git-action-docker-test` step. The test registry has no auth, and the host Docker daemon (which performs `docker login` and the test pull) does not trust the test CA. Only BuildKit, the component under test, must trust it. These edits are clone-only and never committed; the notes record them.
