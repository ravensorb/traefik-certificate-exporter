**This story is HITL.** The agent prepares and verifies. The maintainer:
- tags (`just release patch`);
- approves and edits anything on a forge;
- approves every write on the production host.

The agent never tags, pushes, stores a secret or edits a forge setting. On rwusdckrls6 it runs only read-only commands, unless the maintainer approves a specific write in the session; each approval is recorded in the evidence file. Realistic maintainer time: about **3–3.5 hours** over three sittings, plus up to 1 hour of contingency for first-push fix-ups or a rollback.

**Production today** (`epic-014/sprint-02/closure/live-host-test-rwusdckrls6-2026-10-12.md`; GHCR read 2026-10-12):
- rwusdckrls6 runs container `traefik-certificate-exporter` from `ghcr.io/ravensorb/traefik-certificate-exporter:latest`, which is 0.2.0 (`sha256:2e2cf7f7…536f`). Watchtower is active.
- It sets `TRAEFIK_RESOLVERID_INOUTPUTPATHNAME=1`.
- It runs as root, because the ACME store files are `0600 root`.
- Outputs go to `/mnt/certificates/traefik/resolver-*`. `/mnt/certificates` is a CIFS share with a fixed `file_mode=0755`, so `chmod` there is a silent no-op: 0.3.1 logs one summary WARNING per store per pass about it (BL-E015-068), not a line per file.
- `traefik` and `cert-distributor` run beside it.
- Access: SSH as `svc.claude` (password from Infisical `CLAUDE_AD_*`; Kerberos login refused), with passwordless sudo for Docker.

0.3.1 changes what the operator sees there:
- E015-S01-001: a root exporter takes `postexportcommand` and `outputpath` only from the environment or CLI; a value from `config.yaml` or a `.env` is ignored with one `Ignoring settings.<key> from …` ERROR. `/config` ownership is unchanged: it stays `PUID`/`PGID`-owned (LinuxServer `init-adduser`). New start-up line: `Post-export command: <set|not set> (source: …), runs as uid <n>`. If production runs as root with `postexportcommand` in `/config/config.yaml`, move it to the compose `environment:` before the upgrade, or the hook stops and the post-check's no-`ERROR` condition fails.
- E015-S01-002: the `validatekeys` setting and `.pfx` fingerprint change detection, with its first-pass behaviour as that story specifies.
- E015-S01-003: watch detects rename-replaced stores.
- E015-S01-004: a legacy warning for `TRAEFIK_RESOLVERID_INOUTPUTPATHNAME`.
- **One-time first-pass effect of 0.2.0 → 0.3.1** (`docs/upgrading.md` 0.2.0 → 0.3.0, "One-time post-upgrade effect"). Production skips 0.3.0, so 0.3.1's "verify once, rewrite nothing" upgrade (MD-06) does not apply to its output: that covers 0.3.0 output only. The first 0.3.1 pass over 0.2.0 output finds every `.pfx` different (0.3.0 added the intermediates), so it rewrites every `.pfx` (with key validation on: about one RSA-4096 build per domain, ~74 here, so this pass is slow) and writes every fingerprint file. It reports every domain once, so the post-export hook and Apprise notifications fire once if configured, and every container carrying the restart label restarts once (0 such containers on rwusdckrls6 at the 2026-10-12 live test; the pre-check records the current count). For a domain whose chain has intermediates, `fullchain.pem` is unchanged and `cert.pem` and `chain.pem` are rewritten once with the same certificates: 0.2.x ended them with a blank line, 0.3.x with one newline (BL-E015-069; the rehearsal saw 134 such files, 67 domains). For a single-certificate chain, 0.3.0 corrected `cert.pem` (final newline kept) and `chain.pem` (empty when the store holds no intermediates) (`docs/upgrading.md`, 0.2.0 → 0.3.0, PKCS12), so those two files may differ once. A `.pfx` left in `/mnt/certificates` by a domain that is no longer in the store is not touched: the exporter never prunes (AD-8), so it gets no rewrite and no fingerprint file. `cert-distributor` may react to the rewritten `.pfx` files; the pre-check records what triggers it. This pass's duration is not comparable with the 0.2.0 baseline; the steady-state duration is measured on a second pass (row 19a).

**Watchtower risk (research §8).** `containrrr/watchtower` is archived (GitHub `archived: true`; last release v1.7.1, 2023-11-11). Docker Engine 29.0–29.2 rejects its old API client ("client version … is too old"; containrrr/watchtower#2122, #2124, #2126). The live test saw API 1.56 on this host. So a working Watchtower is not assumed. The pre-check records its image, state, interval and recent log, and the upgrade is done deliberately (`docker compose pull && docker compose up -d`) whatever Watchtower would do. Watchtower polls the registry digest of the tag (default every 86400 s) and honours `com.centurylinklabs.watchtower.enable`.

**Rule: test containers never touch production.**
- No test container on rwusdckrls6 mounts a production path writable, joins a production network, or carries a restart or Watchtower label.
- Any test follows the E014 live-test pattern: scratch copy under a `0700` directory, `--network none`, name `tce-test-031-*`, removed afterwards with the scratch data.
- Production is changed only by the maintainer-approved compose edits in this story.

### Error and edge case handling

- **A publish job fails** (token scope, 429, network):
  - fix it, then `gh run rerun <id> --failed`;
  - uploads skip existing files (PyPI `--skip-existing`, the Gitea files check);
  - image tags re-point to the re-run's digest (ADR-0036 §5);
  - the release updates in place;
  - never re-push the tag.
- **GHCR 403 on push:** the workflow token may not write the existing package. In the package's settings (github.com/users/ravensorb/packages/container/traefik-certificate-exporter → Package settings → Manage Actions access), give this repository the Write role, then re-run `publish-image`. Fallback: set `PUBLISH_GHCR_TOKEN` (classic, `write:packages`) in `release`.
- **A partial-configuration warning or a missing `enabled` line:** set the missing item in `release` and re-run. Do not announce until there are six `enabled` lines and zero warnings.
- **Digests differ across registries:** stop. Re-run `publish-image`, which re-points all three, then re-check row 14. Never fix it with a workstation push.
- **The release is cancelled while pending** (AD-14): re-run only while no newer tag has released.
- **Production post-check fails:** roll back (AC 11). Data under `/mnt/certificates` is not rolled back: 0.3.1 writes the same layout, and the pre/post fingerprint diff shows any change.
- **An `Ignoring settings.postexportcommand` ERROR, or a `Post-export command:` line that shows a configuration-file source with `runs as uid 0`, after the upgrade:** the first is the hook still in `config.yaml` in root mode; move it to the compose `environment:` and restart. The second is an S01-001 defect; file it and roll back. `/config` ownership changing from the pre-check owner is also an S01-001 defect; file it. Roll back only if the exporter fails or its privilege line contradicts ADR-0030.
- **Watchtower upgrades production before sitting 3 despite the pin** (the pin was not applied): record it, then run the post-checks at once.
- **A certificate is renewed between the pre-check and the post-check:** its PEM fingerprints differ. The new `cert.pem` must match the current Traefik store entry, which is checked through the exporter's own log line for that domain.
