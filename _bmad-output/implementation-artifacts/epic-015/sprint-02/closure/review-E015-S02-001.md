## Findings

### M-1 — Docs still say the private-CA path makes BuildKit trust the CA

- Severity: medium. Kind: doc-accuracy (global rule 3: prose must not overstate coverage).
- Location: `docs/ci/gitea-runners.md:40-41` (diagram: `setup-buildx buildkitd-config: …`, then
  `build-push BuildKit trusts the CA for registry pushes`), `docs/ci/gitea-runners.md:46-48`
  ("writes a BuildKit config that `docker/setup-buildx-action` receives as `buildkitd-config`"),
  `docs/ci/pipeline-walkthrough.md:615-616` ("set `PUBLISH_CA_CERTIFICATE` and the publish jobs
  trust it, BuildKit included"). The hook comment at `.pre-commit-config.yaml:190-191` ("passing
  the old name silently drops the private-CA BuildKit config") implies the same thing: that the correct name delivers a
  working config.
- Problem: the story edited these passages, or the sections around them, so that they describe the
  corrected path. Notes row 8 shows the path still does not work after the rename. The CA action v3.0.7 writes
  `[worker.oci.registry…]`, which is not in the buildkitd.toml schema. A builder created with that file
  still fails with `x509: certificate signed by unknown authority`. An operator who follows these docs
  sets `PUBLISH_CA_CERTIFICATE` and gets a failed image push.
- Fix: until BL-E015-054 is decided, add a known-limitation line in both places. Wording:
  "BuildKit does not yet trust the CA: the action's generated file is not a buildkitd.toml config
  (BL-E015-054); image pushes to a private-CA registry fail with x509." In the diagram, replace
  "BuildKit trusts the CA" with that caveat or a `(BL-E015-054)` marker. Also change "writes a
  BuildKit config" to "writes a file intended as a BuildKit config". `pipeline-walkthrough.md:615-616` is outside this
  story's listed sections. If it is not edited here, name it explicitly in BL-E015-054's scope.

### L-1 — The guard misses case variants of the key, and the comment does not say so

- Severity: low. Kind: correctness (guard reach) / doc-accuracy.
- Location: `.pre-commit-config.yaml:203` (entry), `:196-198` (coverage limit).
- Problem: the regex is case-sensitive. Probed under Python `re`: `Config: x` and
  `CONFIG-INLINE: x` do not match. The runner compares `with:` keys to `action.yml` inputs
  case-insensitively, and `@actions/core` reads `INPUT_<NAME uppercased>`. So a case variant is the same removed
  input, and it gets past the guard. This is the "one-character respelling" class that global rule 3
  calls out. Confidence: high that the regex misses these keys (probed). Medium that GitHub treats them
  as the same input (runner/toolkit source behaviour from memory, not re-fetched here).
  The runner's `Unexpected input` warning would still flag it on the next run.
- Fix: prefix the entry with `(?i)`, giving `'(?i)^\s*(?:-\s+)?["'']?config(?:-inline)?["'']?\s*:'`.
  Add a third plant (`Config: x`) to the planted-violation table. If `(?i)` is rejected,
  add "case variants (`Config:`) are not matched" to the coverage-limit line instead.

### L-2 — The actionlint description differs from the spine and from actionlint's documented behaviour

- Severity: low. Kind: doc-accuracy.
- Location: `.pre-commit-config.yaml:191-192`, `docs/ci/pipeline-walkthrough.md:595`.
- Problem: both say actionlint checks `with:` keys "only for an `owner/repo@vN` spec". AD-18
  (spine line 328) and the story Context say it checks them only for **popular actions in its embedded
  dataset** at a major tag. actionlint also validates local `./path` actions by reading their
  `action.yml`. As written, a reader would conclude that any `@vN` third-party action is validated. The
  conclusion the docs draw ("no SHA-pinned action is validated") is still correct.
- Fix: in both places, use the spine's wording: "actionlint validates `with:` keys only for popular
  actions in its embedded data, referenced at a major tag (and local `./` actions); it checks no
  SHA-pinned step here." In the same comment, change "silently drops" (`:191`) to "drops (the runner
  only warns `Unexpected input(s)`)", because the runner does warn. That warning is what BL-E014-108 was raised from.

### L-3 — The `files:` scope is a hand-listed pair of directories, and the comment does not state it

- Severity: low. Kind: scope (global rule 4).
- Location: `.pre-commit-config.yaml:204`.
- Problem: `^\.github/(workflows|actions)/` matches AC 4 exactly. But a `with:` key can live in
  any composite action that a workflow references by `uses: ./<path>`, and that path can be anywhere in the
  repository. The siblings whose subject can live in a composite action (`workflows-lll-major-tag`,
  `workflows-no-auth-header-argv`) use `^\.github/.*\.ya?ml$`, and the story's own interface
  contract cites that convention. Today `.github/actions/` does not exist, and every local `uses: ./`
  is a reusable workflow under `.github/workflows/`, so the tree has no gap. Only the stated reach is
  incomplete. The comment states no file scope, and the notes' out-of-scope plant
  (`.github/dependabot-extra.yml` passes) is recorded only in the notes.
- Fix: add to the coverage-limit comment: "files under `.github/workflows/` and `.github/actions/`
  only; a composite action elsewhere is not seen." AD-18 already words it that way. The alternative
  is to widen to `^\.github/.*\.ya?ml$` to match the siblings. `just check` must stay green, because
  `dependabot.yml`/`zizmor.yml` carry no `config:` key today.
