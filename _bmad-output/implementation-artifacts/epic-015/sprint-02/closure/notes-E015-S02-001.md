### Row 8 (CA path): fail-first, post-fix, and the cause

- **Fail-first** (clone of the pre-story tree; D-4 and D-5 applied): the overall chain exited 1.
  - `buildx create` ran without `--config`:
    `docker buildx create --name builder-… --driver docker-container --buildkitd-flags --allow-insecure-entitlement security.insecure --allow-insecure-entitlement network.host --use`
  - The push failed: `failed to push 10.0.1.184:5443/tce-test:0.3.1-dev.13: … tls: failed to verify certificate: x509: certificate signed by unknown authority`, then `Error: Job 'publish-image' failed`.
- **Post-fix** (story tree): the overall chain exited 1. The rename works, because `buildx create` now gets `--config`:
  `docker buildx create … --use --config /tmp/docker-actions-toolkit-…/tmp-1142-…`.
  The push still fails with the same `x509: certificate signed by unknown authority`.
- **Cause.** `install-certificate.sh:277-305` at `f0f9116` (tag v3.0.7 = v3) writes this file:

  ```toml
  [worker.oci]
    image = "moby/buildkit:latest"
    [[worker.oci.registry]]
      mirrors = ["*"]
      [worker.oci.registry.tls]
        ca = ["<system cert path>"]
  ```

  None of these keys exist in buildkitd.toml, and BuildKit ignores unknown keys. A per-registry CA in
  BuildKit's schema is `[registry."<host>"] ca = ["<file>"]`, and there is no wildcard host.
- **Direct proof** (no act; same test registry, same CA): two builders were created with
  `docker buildx create --driver docker-container --config <file>`, and each pushed a `FROM scratch` image.
  - With the action's file: push rc=1, `x509: certificate signed by unknown authority`.
  - With `[registry."10.0.1.184:5443"] ca = ["<ca.pem>"]`: push rc=0.
- Conclusion: AC 2 needs a valid BuildKit config as well as the rename. The story's non-goals
  exclude both ways of producing that config from this repository: adding `buildkitd-config-inline`,
  or otherwise changing the publish path. Changing the LiquidLogicLabs action means a change in
  another repository and a release, which is outside this story.

## Deviations from the story's Verification text (decided and recorded)

- **D-1: `grep` in the agent shell.** This agent's Bash shell defines `grep` as a function
  that runs ugrep, and ugrep treats a mid-pattern `$` as an anchor. So row 2's
  `grep -c 'buildkitd-config: ${{ …'` counted 0 on correct code; that run is recorded with rc=1.
  The rows are written for GNU grep, as CI uses, so the shorthands file starts with `unset -f grep`
  (`/usr/bin/grep` is GNU grep 3.12). Every later run used GNU grep. This is a harness fact, not a
  repository defect.
- **D-2: row 4 as written is a false green.** `poetry -C "$R"` *changes directory* to `$R`
  (Poetry 2.4.2: `poetry -C $R run pwd` prints `$R`), so `pre-commit` checks the real repository,
  not the clone with the plant. On correct code the command exits 1, and it would also report
  "Passed" when the hook is broken. That run is recorded as rc=1. The corrected command uses `poetry -P "$R"`
  (project without chdir; `run pwd` prints the clone) and is recorded rc=0. No other E015 story uses `poetry -C`.
- **D-3: row 5 pattern vs the new wording.** The pattern `config: <buildkit-path` is unanchored, so it
  matches `buildkitd-config: <buildkit-path`. I reworded the doc line instead of changing the row.
- **D-4: `strip` writes `if: false`.** actionlint (run inside the clone's `build` job)
  rejects a constant condition (`constant expression "false" in condition [if-cond]`), so the
  whole run failed in `build`. The clone-only replacement is `if: env.E015_CLONE_ONLY == 'never'`:
  never true, but not constant. The count check now tests for that string (2 lines: the Gitea
  `docker/login-action` step and the `git-action-docker-test` step). This is clone-only and never committed.
- **D-5: a Sprint 01 test fails under root in act.**
  `tests/test_app.py::test_sigterm_during_the_run_at_start_sweep_exits_cleanly` fails in act's
  `build` job, which runs as uid 0. ADR-0049 makes root ignore config-file `datapath`, `outputpath`
  and `postexportcommand`, so the sweep finishes before SIGTERM (`assert 0 is None`). Rows 7, 8 and 9
  ran act with `--env PYTEST_ADDOPTS=--deselect=tests/test_app.py::test_sigterm_during_the_run_at_start_sweep_exits_cleanly`.
  No file was edited, and each `build` job reports `593 passed, 11 skipped, 1 deselected`. The defect
  is filed as **BL-E015-055 (Medium)**. GitHub-hosted runners are non-root, and `just check` here
  (non-root) passes that test.

### Changes

- `.github/workflows/dev.yaml`, `.github/workflows/release.yaml`, `publish-image`:
  - The job env gains `GITEA_REGISTRY`, built exactly like `GITEA_IMAGE`: the same five-term
    enablement expression, yielding `vars.PUBLISH_GITEA_REGISTRY` or `''`. The host list is
    therefore derived from the destination configuration, not kept by hand.
  - The CA step passes `generate-buildkit: ${{ env.GITEA_REGISTRY != '' }}` and

    empty and `buildx create` gets no `--config`. This also avoids v3.1's
    "buildkit-registries not set" warning.
  - The action stays at `@v3`.
- `publish-package` (both files) and the `release` job (`release.yaml`) drop `generate-buildkit: true`.
  Those jobs run no BuildKit, and with v3.1 a CA-configured run would otherwise emit that warning
  on every run, breaking the per-release zero-warning checklist. Their CA import (system store, `twine`) is unchanged.
- `tests/test_app.py::test_sigterm_during_the_run_at_start_sweep_exits_cleanly` (BL-E015-055):
  - `datapath`, `outputpath` and `postexportcommand` now come from
    `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_*` environment variables, not `config.yml`.
    ADR-0049 ignores those file settings for a root process, and honours the environment for any euid.

  - The test asserts the same sweep for root and non-root; nothing is skipped.
