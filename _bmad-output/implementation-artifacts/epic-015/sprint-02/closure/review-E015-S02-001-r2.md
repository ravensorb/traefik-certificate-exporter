## Checked and sound (no finding)

- **`GITEA_REGISTRY` expression.** `dev.yaml:254`, `release.yaml:319`. It uses the same
  four-term enablement conjunction as `PUBLISH_GITEA` and `GITEA_IMAGE`, then
  `&& vars.PUBLISH_GITEA_REGISTRY || ''`. So it is non-empty exactly when `PUBLISH_GITEA` is
  `'true'`. It derives from secrets and vars in the job env, as AD-9 requires. The CA step's
  `if:` still tests the one flag `env.PUBLISH_CA == 'true'`. The new expression sits in `with:`,
  not in `if:`.
- **`'true'`/`'false'` strings.** `${{ env.GITEA_REGISTRY != '' }}` yields a boolean, and the
  runner passes it to the input as the string `true` or `false`. `install-certificate.sh` tests
  `[ "$INPUT_GENERATE_BUILDKIT" = "true" ]`, so the comparison matches.
  - Empty `buildkit-registries` with `generate-buildkit` false: no file, no output, and no
    warning. The warning fires only when hosts are set without generate, or generate is set
    without hosts.
  - Act row 8 shows the file being generated for `10.0.1.184:5443`.
- **Excluding GHCR and Docker Hub hosts.**
  - Their hosts are fixed and publicly certified.
  - BuildKit's per-registry `ca` appends to the system pool; it does not replace it. A Gitea host
    that turns out to be publicly certified while the CA is meant for another host (for example
    the PyPI URL) therefore still verifies.
  - The value is shape-validated by the action before it is interpolated into TOML. Wildcard,
    scheme and bad port all exit 1 before anything is installed, so no hand-rolled validation
    is needed here.
- **Dropping `generate-buildkit` from `publish-package` and `release`.** Nothing in either job
  reads `steps.ca.outputs.buildkit-path`. The only consumers are `dev.yaml:417` and
  `release.yaml:485`, both in `publish-image`. The system-store import and `REQUESTS_CA_BUNDLE`
  are unchanged. With v3.1, keeping it would emit a `::warning` on every CA-configured run. Nothing
  is lost.
- **Test (BL-E015-055).** ADR-0049 Decision 1/3/6 makes `datapath`, `outputpath` and
  `postexportcommand` environment-only when root. The environment is admissible for every euid,
  so the env-var form drives the same sweep for both euids.
  - The test was not weakened. The 1 s liveness assertion (`proc.poll() is None` before SIGTERM)
    still fails if the hook does not run, so a dropped setting gives a red result, not a false
    green.
  - The three SIGTERM assertions are unchanged: no traceback, the shutdown line, and rc 0.
  - Setting the variables explicitly also overrides any inherited `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_*`, which is more robust than before.
- **Spine AD-18 and `.memlog.md`.** Both match what ships: v3.1.0+, generate only in
  `publish-image`, driven by `GITEA_REGISTRY`, one `[registry."<host>"]` table each, no
  wildcard, and no `--config` on the no-CA and no-Gitea paths.
- **Deletion check (kind: deletion).** The removed lines are:
  - three `generate-buildkit: true` lines (justified above);
  - the old "BuildKit included" claim in the walkthrough, replaced by a narrower and accurate one;
  - the BL-E015-054 limitation text in `gitea-runners.md`, now fixed;
  - three `config.yml` lines in the test, moved to the environment and not lost.

  Nothing else was removed.

## Findings

### L-1 (low, kind: claim): the "must match the image's registry part" rule is prose-only and does not say so
- **File:** `docs/ci/gitea-runners.md:50-51`
- **Defect:** the doc states "it must match the registry part of `PUBLISH_GITEA_IMAGE` exactly,
  port included" but no check enforces it, and the doc does not say what a mismatch does
  (global rule 3).
  - For example, `PUBLISH_GITEA_REGISTRY=git.example.com:443` with
    `PUBLISH_GITEA_IMAGE=git.example.com/o/i` writes a `[registry."git.example.com:443"]` table,
    and BuildKit pushes to `git.example.com` without the CA.
  - The failure is loud: the push to the image host also lacks the login credential.
    Nothing says so, though.
- **Fix:** append "Not checked by the pipeline: a mismatch fails the push (x509 or
  unauthorized), before anything is published to that registry." Also add the same constraint
  to the `PUBLISH_GITEA_REGISTRY` row of the variable table in
  `docs/ci/pipeline-walkthrough.md:123`, so an operator sees it where the value is set.

### L-2 (low, kind: claim): the doc names the generated file `buildkitd.toml`; the action writes `buildkit.toml`
- **File:** `docs/ci/gitea-runners.md:47`
- **Defect:** "it also writes a `buildkitd.toml`". `install-certificate.sh` (v3) sets
  `BUILDKIT_PATH="buildkit.toml"`, and its log line says `buildkit.toml trusts the CA for: …`.
  `buildkitd.toml` is the format, not the file name. An operator grepping the log or the
  workspace for the doc's name finds nothing.
- **Fix:** "it also writes `buildkit.toml` (a buildkitd config) with one `[registry."<host>"]`
  CA entry …".

### L-3 (low, kind: claim): story interface contract and edge cases not updated for the no-Gitea and malformed-host paths
- **File:** `_bmad-output/implementation-artifacts/epic-015/sprint-02/stories/E015-S02-001.md:82`, `:94-98`
- **Defect:** the step contract says the `buildkitd-config` value "is `''` when the CA step is
  skipped". It is now also `''` when the CA step runs and no Gitea registry is enabled
  (`generate-buildkit` false).
  - "Error and edge case handling" also has no entry for a CA set with a
    `PUBLISH_GITEA_REGISTRY` that is not a bare `host[:port]` (for example with `https://` or a
    trailing `/`). The CA step then exits 1 in `publish-image`, before any login.
  - Previously, with a CA aimed at another host, such a value let `docker/login-action` and
    the push proceed.
  - The behaviour is acceptable and loud, but the story's contract no longer describes what
    ships.
- **Fix:** in the step contract, write "`''` when the CA step is skipped or no Gitea registry is
  enabled". Add an edge-case bullet: "CA set, `PUBLISH_GITEA_REGISTRY` not a bare host[:port]:
  the CA step fails with the action's `buildkit-registries: … is not a valid host[:port]` error
  before any login; the variable's documented shape is `host, no scheme`
  (pipeline-walkthrough variable table)."

### L-4 (low, kind: claim): BL-E015-054 and BL-E015-055 still read `status: backlog` and "Blocks E015-S02-001"
