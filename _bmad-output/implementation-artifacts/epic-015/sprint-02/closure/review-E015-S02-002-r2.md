## R2-1: medium: the walkthrough cites a one-forge checklist item that does not exist

- **Location:** `docs/ci/pipeline-walkthrough.md:299-300` ("Not mechanically enforced: the
  per-release checklist compares secret names on both forges"); also spine AD-12 ("a release
  is acceptable only when ... the one-forge check finds no `PUBLISH_*` name on the
  non-publishing forge"); story §Scope line 103 ("the one-forge and digest checklist items").
- **What is wrong:** the walkthrough's per-release checklist has four items (destination
  warnings, `Unexpected input`, one digest, token expiry). None compares `PUBLISH_*` names on
  the two forges. The only mitigation named for a not-mechanically-enforced rule points at
  nothing (global rule 3). It matters: `PUBLISH_PYPI` and `PUBLISH_RELEASE` are secret-only
  flags (`release.yaml:109`, `:528`), so a single `PUBLISH_PYPI_TOKEN` left on Gitea makes a
  mirrored tag run there upload a second, different build to PyPI.
- **Fix:** add a "Per-release checklist: one forge" item. Make it list names, never values,
  on GitHub repository level (`gh secret list`/`gh variable list` without `--env`), on Gitea
  repository (`GET /api/v1/repos/{owner}/{repo}/actions/secrets` and `.../variables`), on
  Gitea user variables (`GET /api/v1/user/actions/variables`) and, if the repository is in an
  organisation, the organisation's secrets and variables. It must also say that Gitea user-level
  **secrets** have no list endpoint (this instance's `swagger.v1.json`, version 28.0.0, has
  only `PUT`/`DELETE` on `/user/actions/secrets/{secretname}`), so that part is a UI check
  (`/user/settings/actions/secrets`). Alternatively, remove the sentence and state that
  there is no check.

## R2-2: medium: checklist step 6 writes the Gitea publish token to `~/.docker/config.json`

- **Location:** notes §"Maintainer checklist" step 6; ADR-0052 D6 ("through the process
  environment (`docker login --password-stdin`)").
- **What is wrong:** the checklist's header rule is that a token never goes into a file.
  `docker login --password-stdin` keeps the value off argv, but it then stores the value in the
  Docker config. On this workstation `~/.docker/config.json` has no `credsStore` or
  `credHelpers`, so the token is written base64-encoded in plain text and stays there until
  `docker logout`. If the `create` fails midway, the step says to re-run it, and a maintainer
  who stops there never reaches `logout`. ADR-0052 D6 calls this "the process environment",
  which is wrong.
- **Fix:** run step 6 with a throwaway Docker config that is removed on every path, and say
  plainly that the token is on disk for the duration:
  `( export DOCKER_CONFIG="$(mktemp -d -p "$HOME")"; trap 'rm -rf "$DOCKER_CONFIG"' EXIT; read -rsp 'Gitea publish token: ' T; echo; printf '%s' "$T" | docker login git.ravenwolf.org -u ravensorb --password-stdin; unset T; docker buildx imagetools create --dry-run ...; docker buildx imagetools create -t ... )`.
  Correct the D6 wording to match.

## R2-3: low: step 7a does not state GitHub's 30-day re-run window

- **Location:** notes §"Maintainer checklist" step 7 (a); ADR-0052 D7.
- **What is wrong:** the step and D7 give the `dist` artifact's retention (2027-01-10) as the
  limiting date. GitHub allows a re-run only up to 30 days after the initial run. Run
  38281339396 was created on 2026-10-12T17:00:36Z (`gh run view`), so option (a) stops being
  possible after about 2026-11-11, two months before the artifact expires. The re-run also
  runs the release job as defined at `046016b3` (the `v0.3.0` tag). That definition uses
  `environment: release` and `PUBLISH_RELEASE_TOKEN`, so it is compatible, but the step does
  not say so.
- **Fix:** add "re-run possible until 2026-11-11 (30 days after the run); after that use (b)"
  to step 7 and D7, and note that the re-run executes the `v0.3.0` workflow definition.

## R2-4: low: step 5's agent check cannot see Gitea user-level secrets, and does not say so

- **Location:** notes §"Maintainer checklist" step 5 ("Agent check: ... no `PUBLISH_*` name
  in the repository's Actions secrets or variables").
- **What is wrong:** the maintainer is asked to clear repository, user and organisation
  levels, but the agent checks only the repository level. User-level variables are listable
  (`GET /user/actions/variables`, which needs a `user: Read` scope the `agent-read` token does
  not have). User-level secrets have no list endpoint at all. A user-level
  `PUBLISH_PYPI_TOKEN` is enough to publish from a mirrored run (see R2-1). The step does not
  say that this part goes unverified.
- **Fix:** state in step 5 that the user-level secrets part is the maintainer's record only.
  Either add `user: Read` to `agent-read` and include `GET /api/v1/user/actions/variables` in
  row 8, or state that user-level variables go unchecked too.

## R2-5: low: step 4's secret loop gives three identical prompts

- **Location:** notes §"Maintainer checklist" step 4,
  `for s in PUBLISH_GHCR_TOKEN PUBLISH_GITEA_TOKEN PUBLISH_RELEASE_TOKEN; do gh secret set "$s" ...; done`.
- **What is wrong:** `gh secret set` without `--body` prompts with the same masked "Paste your
  secret" text for each name. Nothing tells the maintainer which secret is being asked for,
  so pasting two tokens in the wrong order is silent. Row 8 checks names only, so it would
  not catch this. The first sign would be a failed 0.3.1 publish.
- **Fix:** print the name before each prompt: `...; do echo "value for $s:"; gh secret set "$s" --env release -R "$GH"; done`.

## R2-6: low: step 3's agent check does not verify the two tokens step 3 creates

- **Location:** notes §"Maintainer checklist" step 3, "Agent check".
- **What is wrong:** the check reads the package's visibility and linked repository. Those
  values are already `public ravensorb/traefik-certificate-exporter` today (run read-only on
  2026-10-14), so the check passes whether or not the maintainer does anything. Nothing
  verifies the GHCR classic token's scopes or the fine-grained release token's permissions,
  and the step does not say when they are first proven.
- **Fix:** state that the agent cannot read token scopes. The release token is first proven
  by step 7 (a), when the re-run logs `Forge release enabled` and creates the release. The
  GHCR token is first proven by the 0.3.1 release run (E015-S02-004).
