## F-1 — high — `just act` still injects the maintainer's `gh` token as `secrets.GITHUB_TOKEN`

- **Location:** `justfile:66-67` (the `act` recipe). The same overstatement is in
  `justfile:52-60` (comment), `docs/developer.md` §"Validate CI locally" ("No secrets or
  variables are passed"; "act's ambient secret sources are ignored"),
  `docs/ci/pipeline-walkthrough.md` §"Releasing" bullet, §"Running locally" paragraph and the
  `just act dev.yaml` table row, ADR-0052 Context and D5 ("Not mechanically prevented"
  list), CI spine AD-16 line 298 ("passes no secrets and reads none of act's ambient
  sources"), and the spine changelog line "no deviation".
- **What is wrong:** when no `GITHUB_TOKEN` secret is given, act 0.2.89 runs `gh auth token`
  and uses the result as `secrets.GITHUB_TOKEN` (and so `github.token`). `gh` reads its token
  from the system keyring over D-Bus (and from `GH_TOKEN`/`GITHUB_TOKEN` in the environment),
  not from `$HOME`, so the fresh `HOME`/`XDG_CONFIG_HOME` do not stop it. Reproduced on this
  workstation, 2026-10-14, with the recipe's exact isolation (`HOME=$(mktemp -d)
  XDG_CONFIG_HOME=$(mktemp -d) act push ... -P ubuntu-latest=... --secret-file /dev/null
  --var-file /dev/null`), a one-step workflow printing `${{ secrets.GITHUB_TOKEN != '' }}`:
  `TOKSET=true`. With a stub `gh` (exit 1) first on `PATH`: `TOKSET=false`, so the token comes
  from `gh`. `gh auth status` reports that token's scopes as `admin:org`, `delete:packages`,
  `repo`, `workflow`, `write:packages` (among others). Every `just act` run therefore hands an
  account-wide token that can push to GHCR and administer the org to every step, including the
  `LiquidLogicLabs/*` actions at mutable major tags and the mutable
  `catthehacker/ubuntu:act-latest` image — the exact exposure RT-2 describes. Nothing in the
  workflows publishes with `GITHUB_TOKEN` (AD-9), so this is credential exposure, not
  publication; but AC 2 ("`just act` cannot pick up ambient secrets") and every doc claim
  above are false. AC 3's scope attack planted only the three hand-enumerated sources
  (`.secrets`, `.vars`, `~/.actrc`), so it could not see a fourth (global rule 4: the scope
  was enumerated, not derived from act's source).
- **Fix:** stop act's `gh` fallback in the recipe. Both of these were verified to give
  `TOKSET=false`: `-s GITHUB_TOKEN=` (an explicitly empty secret; act skips the `gh` lookup
  when the key exists), or `GH_HOST=none.invalid` in the recipe's environment prefix. Prefer
  `-s GITHUB_TOKEN=` (act's own flag, no `gh` behaviour assumed) and amend AD-16's "no
  `--secret` arguments" to "no `--secret` argument except the empty `GITHUB_TOKEN=`"; record
  the deviation in the notes' `## Spine/ADR amendments` and correct the spine changelog line.
  Add the source to ADR-0052 Context/D5, the recipe comment, `docs/developer.md` and the
  walkthrough. Extend Verification row 3 with a plant that attacks this source: a workflow or
  step that fails when `secrets.GITHUB_TOKEN != ''` (or grep the act log for a step echoing
  the boolean) under the recipe, and a fail-first run against the current recipe.

## F-2 — medium — digest command's count guard cannot fail as shipped; prose claims it does

- **Location:** `docs/ci/pipeline-walkthrough.md` §"Releasing", "Per-release checklist: one
  digest on every registry" (the `onedigest 9 {ghcr.io,docker.io,git.ravenwolf.org}/...`
  block and the sentence "an unset image name drops refs and fails").
- **What is wrong:** the prose says to look up "each `PUBLISH_*_IMAGE` value" and that the
  `3 ×` count "fails" when an image name is unset. The shipped command hard-codes three image
  names and the literal `9`, so the ref count is always 9 and the count test is a tautology;
  the set of registries checked is a hand-kept list, not derived from the forge variables
  (global rule 4). If a `PUBLISH_*_IMAGE` value changes or a registry is added, the command
  keeps passing over the stale set. (Brace expansion itself is correct: braces expand before
  `$V`/`$M`, giving 9 refs.)
- **Fix:** either build the refs from the source of truth, e.g.
  `mapfile -t imgs < <(gh variable list --env release -R ravensorb/traefik-certificate-exporter --json name,value -q '.[] | select(.name|test("^PUBLISH_.*_IMAGE$")) | .value')`
  with the Docker Hub value prefixed `docker.io/` if it has no host, then
  `onedigest 9 "${imgs[@]/%/:$V}" "${imgs[@]/%/:$M}" "${imgs[@]/%/:latest}"` (the literal
  `9` stays the expected count, so a dropped variable fails); or keep the literal list and
  replace the "(an unset image name drops refs and fails)" clause with a stated limit: "the
  image names are listed by hand; update the command when a `PUBLISH_*_IMAGE` value changes".

## F-3 — low — `mktemp` failure fails open to the real `$HOME`

- **Location:** `justfile:67`.
- **What is wrong:** `HOME="$(mktemp -d)" XDG_CONFIG_HOME="$(mktemp -d)" act ...` is a simple
  command with assignment prefixes; under `bash -euo pipefail` a failing command substitution
  in a prefix does not abort the line (the status is the command's), so act runs with
  `HOME=""`/`XDG_CONFIG_HOME=""`. act resolves its home through a fallback when `$HOME` is
  empty (passwd lookup), which would read the real `~/.actrc` — the source the recipe exists
  to neutralise. Plausible, not reproduced (needs an unwritable `$TMPDIR`).
- **Fix:** make the directories standalone assignments in the same line so `-e` applies:
  `h="$(mktemp -d)" && x="$(mktemp -d)" && HOME="$h" XDG_CONFIG_HOME="$x" act ...`.

## F-5 — low — digest checklist does not cover the `X` tag from 1.0, and does not say so

- **Location:** `docs/ci/pipeline-walkthrough.md` "Per-release checklist: one digest on every
  registry".
- **What is wrong:** AD-8 has `release.yaml` write `X` when X ≥ 1. The checklist (and AD-12)
  check only `X.Y.Z`, `X.Y`, `latest`, so from 1.0 a split digest on `:1` passes the check.
  Harmless for 0.x, but the item presents the three tags as "every" tag of the release
  without stating the limit (global rule 3).
- **Fix:** add "from 1.0 also `X` (4 × the registries)" or state the limit in the item.
