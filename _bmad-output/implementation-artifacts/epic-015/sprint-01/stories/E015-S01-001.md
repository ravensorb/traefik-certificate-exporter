# Close the /config root-escalation: the service account must not control what runs as root

## Context

**Maintainer decisions:** `_bmad-output/implementation-artifacts/epic-015/maintainer-decisions.md` — MD-01, MD-02, MD-03, MD-04, MD-05. The story proceeds on each recommendation until answered.

Promoted from deferred finding(s):
- BL-E014-119 (High, epic-redteam (RT-1)) — See _bmad-output/implementation-artifacts/epic-014/epic-closure/redteam-report.md. Deferred to E015 (0.3.1) per epic-closure directive: only BLOCKER/CRITICAL fixed at E014 closure; 0.3.0 released. Not ADR-accepted.

**Evidence:** `_bmad-output/implementation-artifacts/epic-014/epic-closure/redteam-report.md` §RT-1. It was demonstrated on the released `ravensorb/traefik-certificate-exporter:0.3.0`: uid 911 replaced `/config/config.yaml`, and the next boot ran `postexportcommand` as `uid=0(root)`. It recommends four steps: take the paths back in init, a loader ownership check, a container test, and doc corrections.
**Research:** `_bmad-output/planning-artifacts/research/research-2026-10-12-release-0.3.1.md` §1 "LinuxServer base image init and /config ownership". Every base-image fact below was read from the digest-pinned base image and its upstream source.

**Problem.**

- The base image is `ghcr.io/linuxserver/baseimage-alpine:3.24@sha256:d2deff7a…fea` (`docker/Dockerfile:6`, label `org.opencontainers.image.version=4bf86442-ls13`, revision `f6b732b1`). Its `/etc/s6-overlay/s6-rc.d/init-adduser/run:53-57` runs on every boot unless `LSIO_READ_ONLY_FS` or `LSIO_NON_ROOT_USER` is set:
  ```
  lsiown abc:abc /app
  lsiown abc:abc /config
  lsiown abc:abc /defaults
  ```
  `lsiown` without `-R` is `find <path> -maxdepth 0 … -exec chown abc:abc` (`/usr/bin/lsiown:30`), so it changes the three directories themselves and not their contents.
- s6-rc order, read from the image's `dependencies.d`: `init-migrations → init-adduser → init-device-perms → init-os-end → init-config → init-traefik-certificate-exporter-config` (ours, `docker/root/etc/s6-overlay/s6-rc.d/init-traefik-certificate-exporter-config/dependencies.d/init-config`) `→ init-config-end → init-mods… → init-custom-files → init-services → svc-traefik-certificate-exporter`.
  - Our init therefore always runs after the chown.
  - Docker mods and `/custom-cont-init.d` scripts run after our init, as root.
  - Every oneshot runs again on each container start. Probe: `chown 0:0` the three paths in a running 0.3.0 container, `docker restart` it, and they are `1000:1000` again.
- Our init (`init-traefik-certificate-exporter-config/run:38-41`) only seeds the sample config. Nothing in the repository takes `/config` back. On a booted 0.3.0 container with `PUID=1000`, `stat` shows `/config`, `/app` and `/defaults` as `1000:1000`, while `/config/config.yaml`, which init seeded as root, is `0:0`. The account owns the directory, so it can rename a file of its own over `config.yaml`.
- The only loader check is `_warn_if_group_or_world_writable` (`src/traefik_certificate_exporter/libs/settings.py:275-292`). `loadFromFile` (`:313-346`) calls it for the module `.env` (`:331`), the cwd `.env` (`:338`) and the config file (`:343`). A `0644` file owned by uid 911 passes it silently. Two sources are never checked: confuse's packaged default and its user source (`:321`, `:323`).
- Three documents claim the opposite of what ships:
  - `docs/adr/0030-conditional-privilege-drop.md:89-91`: "`/config` is deliberately **not** chowned: it stays root-owned …";
  - `docs/operational.md:417-420`: "`/config` deliberately stays root-owned …";
  - `docs/operational.md:296`: "it must be root-owned".
  `tests/test_s6_privilege_drop.py` executes only this repository's scripts, so it never sees the base image's init (global rules 3 and 4).
- Nothing in the image needs `abc` to own `/config`, `/app` or `/defaults`. Each was checked:
  - init seeds the sample as root;
  - the run-mode and privilege state live in `/run/traefik-certificate-exporter`;
  - the base image ships no `/migrations` and no `/defaults/crontabs`;
  - the service's working directory is its s6 service directory (`/run/s6-rc:s6-rc-init:…/servicedirs/svc-traefik-certificate-exporter`, read from `/proc/<pid>/cwd` on 0.3.0), not `/config`.
  So a relative file-log path does not land in `/config`. The "Known limitation" paragraph at `docs/operational.md:422-426` is therefore inaccurate, but it is out of scope (Non-goals).

**Options evaluated** (research §1):

| Option | Verdict |
|---|---|
| (a) Our init takes `/config`, `/app`, `/defaults` and `/config/config.yaml` back to `root:root` after `init-adduser` | **Adopted.** It is ordered after the chown by the existing `init-config` dependency, and it heals existing deployments, whose host `/config` directory 0.3.0 already gave to the PUID. On its own, though, it leaves a window on every boot. Between `init-adduser` and our init, a host process running as the PUID uid can `inotify`-watch `/config`, rename its own `config.yaml` in, and have init chown it to root. |
| (a′) Neutralise the three `lsiown` lines of the base image's `init-adduser/run` at image build | **Adopted with (a).** It removes the per-boot window. A build-time count assertion fails the build loudly if a base bump changes those lines. `usermod`/`groupmod` (PUID/PGID) are untouched. |
| (b) Move the config file out of `/config` | **Rejected.** It breaks the documented mount and `-c /config/config.yaml` (`svc-…/run:46,51`), and it still needs (d) to protect the new path. |
| (c) `LSIO_READ_ONLY_FS` / `LSIO_NON_ROOT_USER` | **Rejected.** Both also skip the `usermod`/`groupmod` that apply PUID/PGID (`init-adduser/run:7-15`). LinuxServer documents that "The PUID & PGID variables will not have any effect" in both modes. `LSIO_NON_ROOT_USER` means running the whole container as `--user`, which rules out root mode (`restartcontainers`). |
| (d) The loader refuses a configuration source not owned by root when the process is root | **Adopted** as defence in depth. It catches anything that runs after our init (Docker mods, custom init scripts), a take-back that failed (read-only or remote mount), a symlinked config whose target init does not touch, and PyPI installs run as root. |

## Acceptance Criteria

1. **Build: the base image no longer hands the paths to `abc`.** `docker/Dockerfile`'s runtime stage rewrites `/etc/s6-overlay/s6-rc.d/init-adduser/run`.
   - Before rewriting, it asserts that exactly 3 lines match `^[[:space:]]*lsiown abc:abc /(app|config|defaults)$`. Otherwise the build fails with `base contract: init-adduser no longer chowns /app /config /defaults as expected (ADR-NNNN)`.
   - Each matching line becomes a no-op `:` carrying a comment that names the ADR. A deleted line would leave an empty `then … fi` body, which is a bash syntax error.
   - The build then runs `bash -n` on the file and asserts that no `lsiown abc:abc /config` remains.
   - The `usermod`/`groupmod` block (`:7-15`) is unchanged.
2. **Init takes the paths back on every start, in both modes, before the resolver runs.** `init-traefik-certificate-exporter-config/run` declares `ROOT_OWNED_DIRS=(/config /app /defaults)` on one line. Before the sample-config seed (`:38`), it does the following:
   - For each directory that exists and is not a symlink: `chown -h root:root` and `chmod go-w`.
   - If `${CONFIG_FILE}` is a regular file and not a symlink: `chown -h root:root` and `chmod go-w`.
   - A symlinked `${CONFIG_FILE}` is left untouched, and the loader judges its target (AC 4).
   - Nothing is recursive, and nothing follows a symlink.
   - A failed `chown` or `chmod` prints one `INFO:` line naming the path. The script carries on: the decision and the run-mode answer are unaffected, and AC 4 is the fail-closed backstop.
3. **The take-back is visible.** Each path whose owner or mode actually changed gets one stdout line: `INFO: took <path> back to root:root from <uid>:<gid> (mode <old> -> <new>); /config holds execution-equivalent configuration (ADR-NNNN)`. Nothing is printed when a path is already root-owned and not group- or world-writable. No new `WARNING:` line is ever emitted, so the "exactly one WARNING" invariant of ADR-0030 holds.
4. **The loader refuses an untrusted source when running as root.** When `os.geteuid() == 0`, `SettingsManager.loadFromFile` checks every file it hands to confuse or `load_dotenv` before loading it:
   - the packaged default;
   - the confuse user config path, if it exists;
   - the module `.env`;
   - the cwd `.env`;
   - the config file.

   For each source it takes `os.path.realpath`, then checks the resolved file and the resolved file's parent directory. A source is refused when either of them:
   - has `st_uid != 0`, or
   - is world-writable (`S_IWOTH`), unless it is a directory with the sticky bit set.

   On refusal the process logs one ERROR (text in Observability) and exits `1` through `sys.exit(1)`, the same way `require_existing_path` (`app.py:41-48`) reports a start-up failure (ADR-0044). Group-writable stays a WARNING (the existing `_warn_if_group_or_world_writable`, unchanged). When the euid is not 0, the new check does nothing.
5. **The check's scope is derived from the loads, not from a list.** Every path passed to `load_dotenv` and every `filename` used to construct `confuse.core.YamlSource` during `loadFromFile` has passed the check first. A unit test enforces this by recording those calls (Testability). A source added later without the check fails that test.
6. **The running image proves the boundary** in `tests/test_container_config_ownership.py` (new, opt-in), against `${TCE_IMAGE:-traefik-certificate-exporter:local}` with `PUID=1000 PGID=1000` and a named `/config` volume:
   - (i) After start, `/config`, `/app`, `/defaults` and `/config/config.yaml` are `0:0` and not group- or world-writable.
   - (ii) As uid `1000`, creating a file in `/config`, replacing `config.yaml`, and writing to `config.yaml` in place all fail.
   - (iii) A volume pre-seeded as 0.3.0 left it (`/config` and a `0664` `config.yaml` owned by `1000:1000`) is taken back on boot, and the log carries the AC 3 INFO lines.
   - (iv) Scope attack: the root exporter exits `1` with the AC 4 ERROR and the hook never runs in this case. Setup: `config.yaml` is a symlink into a `1000`-owned subdirectory `/config/sub/`, outside the non-recursive take-back, and the target sets `postexportcommand: "/bin/sh -c 'id > /certs/pwned'"`. The run is run-once with an empty `/data` and stays root (no store file).
   - (v) A `1000`-owned `/config` mounted `:ro`, so the take-back fails, also makes the root exporter exit `1` with the AC 4 ERROR.
   - (vi) The image's `init-adduser/run` contains no `lsiown abc:abc /(app|config|defaults)` line and passes `bash -n`.
7. **Script-level tests** in `tests/test_s6_privilege_drop.py` execute the init copy through the existing `_run_init` harness. Its substitution table gains the `ROOT_OWNED_DIRS=` line, pointed at directories under `tmp_path`, so no test touches the real `/config`. The tests cover:
   - the take-back in both decision outcomes;
   - the take-back runs before the resolver;
   - a symlinked config is not followed;
   - a failing `chown` leaves the decision unchanged and emits no `WARNING:`;
   - the INFO line names the previous owner.
8. **Docs state what ships.**
   - `docs/adr/0030-conditional-privilege-drop.md:89-91` is replaced by a dated amendment. It says the base image's `init-adduser` used to hand `/config` to `abc` (0.3.0, BL-E014-119), and that from 0.3.1 the image neutralises that, init takes the paths back, and the loader refuses. It points to the new ADR.
   - `docs/operational.md:294-298` and `:417-420` say the same and name `init-adduser`. They also give the operator consequence: the host `/config` directory and `config.yaml` become `root:root` and lose group/other write, so edit them with `sudo` or override settings through `TRAEFIK_CERTIFICATE_EXPORTER_*` environment variables.
   - `docker/README.md`'s "Which user does the exporter run as?" section (`:90-99`) carries the same operator consequence and names `init-adduser`.
   - No shipped doc keeps the sentence "deliberately **not** chowned".
9. **New ADR** `docs/adr/NNNN-config-trust-boundary-enforced-at-runtime.md`; the number is reserved at dev time (ADR and spine routing). It records:
   - the base-image mechanism and its s6 order;
   - options (a), (a′), (b), (c), (d) with the verdicts above;
   - the race that (a) alone leaves open;
   - the accepted costs: the build-time patch of a base file, owned by this project, fails loudly on drift and is revisited if LinuxServer adds a supported opt-out; operators lose PUID-owned config editing;
   - the refusal rule, and which cases refuse and which warn.
10. **No regression.** The existing `tests/test_s6_privilege_drop.py`, `tests/test_s6_run_mode.py`, `tests/libs/test_settings.py` and the three existing container tests pass unchanged except for the `_run_init` substitution added in AC 7.

## Business acceptance criteria

### Outcome

- The account the exporter drops to (`abc`, i.e. `PUID`) cannot change what the exporter runs as root. It cannot write into the container. On the host, a process running as the PUID's uid cannot write into the bind-mounted `/config`. It cannot get a file of its own read as configuration by a root exporter. The RT-1 replay (rename a `config.yaml` with `postexportcommand` into `/config`, then restart) no longer yields `uid=0` on the image: the rename is denied.
- An operator upgrading from 0.3.0 needs to do nothing for the fix to apply. The first 0.3.1 start takes the paths back and logs, once per changed path, what it changed and why.
- A deployment the fix cannot secure fails closed and says why, rather than running a root hook from an untrusted file. Examples: a read-only or remote `/config` owned by another uid, or a config symlinked elsewhere.
- ADR-0030, `docs/operational.md` and `docker/README.md` describe the boundary that actually ships, and an image test proves it on every run of the integration suite.

#### 0.3.1 release notes

The release story generates `docs/upgrading.md` from this list. Every bullet is a user-visible change.

- "**Security (BL-E014-119): `/config` is root-owned again.** In 0.3.0 the LinuxServer base image's start-up gave `/config`, `/app` and `/defaults` to the `PUID` account on every start. That account could therefore rewrite `config.yaml` (e.g. `postexportcommand`) and have the next start run it as root. The image no longer does this. On every start it takes `/config`, `/app`, `/defaults` and `/config/config.yaml` back to `root:root` and removes group/other write. Each change is logged as an `INFO:` line."
- "**Host-side editing of `config.yaml` now needs root.** If you mount `/config` from the host, the directory and `config.yaml` become owned by root after the first 0.3.1 start. Edit them with `sudo`, or override settings with `TRAEFIK_CERTIFICATE_EXPORTER_*` environment variables, which outrank the file."
- "**A root exporter refuses a configuration file it cannot trust.** When it runs as root (the image's root mode, or a PyPI install run as root), the exporter exits with code 1 and one ERROR if any configuration file it loads is not owned by root or is world-writable, or if that file's directory is. The files are the config file, a `.env`, the confuse user config and the packaged default. A symlinked config is judged by its target. Fix: `chown root:root <file> <its directory> && chmod o-w <file> <its directory>`. Group-writable files still only warn."

Spec: none — l3io-plan run, no spec index bound

### Non-goals

- No change to the privilege decision itself (ADR-0030 rows): what makes the service drop or keep root is unchanged.
- `/data` and the output path are not taken over. `/data` is never chowned (ADR-0030), and the output path's ownership walk to `abc` in dropped mode is unchanged.
- Not recursive. Files under `/config` other than `config.yaml` are left alone, because nothing else there is read. A symlinked `config.yaml` target is judged by the loader, not chowned.
- Ancestors above the immediate parent directory of a configuration file are not checked.
- No protection against code the operator chooses to run as root after our init: Docker mods and `/custom-cont-init.d`. AC 4 still refuses a config those leave untrusted.
- No change for a container run with `--user` / `LSIO_NON_ROOT_USER`. It is never root, so AC 4 is inactive, and init's `chown` fails harmlessly with an INFO line.
- No fix for the inaccurate file-logging "Known limitation" paragraph (`docs/operational.md:422-426`; the cwd is the s6 service directory, not `/config`). Raise it as a separate backlog item.
- No change to the hook's inherited environment (RT-3) or to argv secrets (RT-4).
- No setting or environment variable to opt out of the take-back or the refusal.

### Error and edge case handling

- **Read-only, remote or root-squashed `/config`:** `chown` fails. Init prints INFO and continues. A root exporter then refuses (AC 4) and exits `1`. In watch mode s6 respawns it and logs the ERROR on each attempt; in run-once mode `finish` stops the container with exit code `1` (ADR-0044). This is fail-closed by design and documented in `operational.md` with the remedy: make the host directory and file root-owned, or mount them `:ro` already owned by root.
- **Dropped mode (service runs as `abc`):** the take-back still happens in init, so the path (a) attack (code execution as `abc` inside the container) gains no root on the next start. The exporter's own loader check is inactive, because the euid is not 0. The init resolver, which runs as root, is subject to AC 4. A refused resolver writes nothing, so the decision fails safe to root, and the root service then refuses. The result is a container that refuses to run, not a root hook.
- **`config.yaml` absent:** the seed (`:38-41`) runs after the take-back, so the seeded file is root-owned as before. No INFO line is printed for a path that does not exist.
- **`config.yaml` is a symlink:** init does not touch it. The loader resolves it and checks the target and the target's directory.
- **`/config` is itself a symlink** (unusual for a volume): it is skipped by the `! -L` guard, and the loader checks the resolved parent.
- **`LSIO_READ_ONLY_FS` set (read-only root filesystem):** the base already skips its `lsiown`. Our `chown` of `/app` and `/defaults` fails on the read-only root filesystem and prints INFO; the `/config` volume is still taken back.
- **A base image bump changes `init-adduser/run`:** the AC 1 count assertion fails the image build with the `base contract:` message. Dependabot's base bump PR cannot go green until a maintainer re-reads the base init.
- **Docker mods or `/custom-cont-init.d` re-chown `/config` after our init:** the root exporter refuses (AC 4).
- **The `inotify` race at boot:** with (a′) there is no window, because `/config` is never handed to the PUID during boot. On the first 0.3.1 start of an upgraded deployment, the 0.3.0-era ownership persists until our init runs. That one-time window is recorded as a residual risk in the ADR.
- **PyPI install run as root over a user-owned venv or config:** it refuses with the ERROR. The account that owns them already controls the code root runs, so the remedy is to run as that account or make the files root-owned. This is in the release notes.
- **Windows (no `os.geteuid`):** the check is inactive.

Spec: none — l3io-plan run, no spec index bound

### Security considerations

- **Closes BL-E014-119 / RT-1 paths (a) and (b).** In the container, `abc` no longer owns any directory or file that a root process loads as configuration or code (`/config`, `/app`, `/defaults`, `config.yaml`). On the host, the bind-mounted `/config` stops being writable by the PUID's host uid.
- **Defence in depth with a derived scope.** AC 4/5 bind the refusal to every file the loader actually reads, so a new configuration source cannot silently escape it. The container test attacks the scope of the take-back (a symlink into a subdirectory it does not walk) and of the patch (a read-only mount where `chown` cannot act), not only the rule.
- **The guard's scope is the running image** (global rule 4). AC 6 runs the built image, including the base image's own init. A future base init, mod or ordering change that hands `/config` back fails (i)/(ii) even if every repository script is unchanged.
- **No symlink dereference anywhere** in the take-back (`chown -h`, `! -L` guards, no `-R`). This avoids the arbitrary-chown primitive that `:147-150` already guards against.
- **Residual risks (in the ADR):**
  - the one-time first-boot window on upgrade;
  - group-writable sources still only warn;
  - a symlinked config whose target is root-owned but sits in a root-owned directory where another file is attacker-controlled is out of scope;
  - `/defaults/crontabs` does not exist today, so the base `init-crontab-config`, which imports `/config/crontabs/root` into root's crontab when it exists, is inert. AC 6 asserts `! -e /defaults/crontabs` so that a future change that adds it is caught.
- No new secrets. The ERROR carries no setting values.

### Testability approach

- **Unit, `tests/libs/test_settings.py`.** These tests monkeypatch `settings.os.geteuid` and the `_stat` seam, so they pass under any runner uid, including root in CI:

### Existing-library check

- **Ownership and mode checks:** stdlib `os.stat`, `os.path.realpath` and `stat.S_IWOTH`/`S_ISVTX`, as the existing `_warn_if_group_or_world_writable` uses. No library offers a "trusted config file" predicate that fits a confuse plus dotenv loader. The check is about 20 lines, and it is not in a domain that global rule 1 lists (no parsing, crypto or path matching).
- **Chown in init:** coreutils/busybox `chown -h`, `chmod` and `stat`. The base image's own `lsiown` helper is deliberately not used: `lsiown -R` and its `find … -exec chown` without `-h` follow the semantics this repository already rejected (`init…/run:147-150`).
- **Base init patch:** LinuxServer offers no supported switch that skips only the `/config` chown. `LSIO_READ_ONLY_FS` and `LSIO_NON_ROOT_USER` also skip PUID/PGID, per docs.linuxserver.io "Read-Only Operation" and "Non-Root Operation". A build-time `sed` with a count assertion and `bash -n` is the smallest change. The ADR records it with its revisit condition: LinuxServer ships a supported opt-out.
- **Tests:** pytest and the Docker SDK (`docker` package), already used by `tests/test_container_*.py`. There is no new harness and no new dependency.
