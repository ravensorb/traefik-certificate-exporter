# Watch mode detects store files replaced by rename

## Context

**Maintainer decisions:** `_bmad-output/implementation-artifacts/epic-015/maintainer-decisions.md` — none for this story.

Promoted from deferred finding(s):
- BL-E014-105 (Medium, live-host-test (rwusdckrls6-2026-10-12)) — See _bmad-output/implementation-artifacts/epic-014/sprint-02/closure/live-host-test-rwusdckrls6-2026-10-12.md.

**Evidence.** Live-host test row D (`live-host-test-rwusdckrls6-2026-10-12.md:24`): Traefik writes in place, so in-place writes were detected, and only the changed store file was re-processed. "An atomic-rename replacement of the file was **not detected**." Production is unaffected because Traefik writes in place. Restores, `cp`-then-`mv` scripts, configuration tools and editors that write a temporary file and rename it are missed. Until some later in-place write, the exported certificates stay stale.

**Research:** `_bmad-output/planning-artifacts/research/research-2026-10-12-release-0.3.1.md` §3 "watchdog moved events (E015-S01-003)". The facts below were checked against the installed watchdog 6.0.0 (`poetry.lock`, `pyproject.toml`: `watchdog = "^6.0"`). The released 0.3.0 image runs the same 6.0.0, and its `Observer` is `InotifyObserver`. Both were checked on 2026-10-12.

**Problem (verified against the current tree).**

- `src/traefik_certificate_exporter/libs/certificate_exporter.py:1304`: `AcmeCertificateFileHandler(watchdog.events.PatternMatchingEventHandler)`.
  - `:1341-1346` registers `patterns=[settings.fileSpec]` (default `*.json`), `ignore_directories=True` and `case_sensitive=False`.
  - `:1349-1356` overrides only `on_created` and `on_modified`. Both call `handleEvent`, which queues `event.src_path` (`:1381`).
  - There is no `on_moved`, so the base `FileSystemEventHandler.on_moved` no-op (`watchdog/events.py:228`) receives every rename.
- `src/traefik_certificate_exporter/app.py:240-255`: `watchdog.observers.Observer()`, scheduled with `recursive=False` on `settings.dataPath`.
- **How watchdog reports a rename (installed source, `.venv/lib/python3.11/site-packages/watchdog/`):**
  - `observers/inotify.py:141-151`: a paired `IN_MOVED_FROM`/`IN_MOVED_TO` inside the watched directory becomes one `FileMovedEvent(src_path, dest_path)`, plus two `DirModifiedEvent`s.
  - `observers/inotify.py:155-161`: an unpaired `IN_MOVED_TO` becomes a `FileCreatedEvent(dest)`. This is a file renamed in from outside the watched directory, under the default `generate_full_events=False`.
  - `observers/inotify.py:169-172`: an unpaired `IN_MOVED_FROM` becomes a `FileDeletedEvent`. It is delivered late, after the move-pairing timeout.
  - `events.py:342-365` (`PatternMatchingEventHandler.dispatch`): an event is dispatched when **either** `dest_path` **or** `src_path` matches the patterns (`paths = [dest_path, src_path]`, `match_any_paths`). So `on_moved` is called for a rename **onto** a watched name (only `dest_path` matches), a rename **away** from one (only `src_path` matches), and a rename between two watched names. The handler must decide which case it has. Dispatch does not decide it.
  - `utils/patterns.py:24-45`: the matching is `PurePath.match` (`PureWindowsPath` when `case_sensitive=False`), and the public helper is `watchdog.utils.patterns.match_any_paths` (`:81`).

## Acceptance Criteria

1. **Rename onto a watched name is exported.** A `FileMovedEvent` whose `dest_path` matches the handler's patterns queues `dest_path` and opens or joins the debounce window, exactly as a `created`/`modified` event for that path does. One drain later, `exportCertificatesForFile(dest_path)` is called once.
2. **The destination is matched by the handler, not inferred from dispatch.** `on_moved` re-tests `dest_path` against the handler's own `patterns`, `ignore_patterns` and `case_sensitive`, using `watchdog.utils.patterns.match_any_paths`. Dispatch passes an event when either path matches (`events.py:354-365`), so `src_path` is never queued from a moved event.
3. **The renamed-away source is dropped from the window.** When `src_path` matches, `on_moved` discards it from `pendingPaths` under `self.lock`. It no longer exists under that name, and exporting it would log a spurious `File not found` ERROR. This covers the "matching temporary file renamed onto the store" row of the probe table: the drain exports `acme.json` and never `tmpXYZ.json`.
4. **Rename away from a watched name exports nothing.** If `src_path` matches and `dest_path` does not (for example `acme.json` → `acme.json.bak`), the handler queues nothing, arms no timer, and deletes no exported file. It logs one INFO line (see Observability). If a window is already open, it stays open for its other paths.
5. **Rename between two watched names** (`a.json` → `b.json`) queues `b.json`, drops `a.json` from the window, and exports `b.json` once.
6. **The scope is unchanged.** Directory events (`DirMovedEvent`) are still ignored (`ignore_directories=True`), and the watch stays non-recursive. A rename into the data path from another directory keeps arriving as `FileCreatedEvent` and keeps being handled by `on_created`. A real-observer test pins this.
7. **Existing contracts hold** (ADR-0043, ADR-0045, AD-11):
   - only the store file named by the event is re-processed, and other store files in the directory are not;
   - a rename that installs byte-identical content runs a pass that rewrites nothing and runs no hook or notification (`NO_CHANGE_MESSAGE`);
   - debounce, coalescing, shutdown latch and correlation id behave for a moved event exactly as for a modified one. Every existing test in `tests/libs/test_certificate_exporter_watch.py` passes unchanged.
8. **Both observers are covered.** The real-observer tests run with the platform `Observer` (inotify on Linux, which is what the image uses) and with `PollingObserver`, the fallback watchdog selects when inotify is unavailable.
9. **Docs** state the trigger set: `docs/architecture.md` (`:50` relation label and the `:72` sequence note) and `docs/operational.md` runbook step 1, which gains `Watchdog received moved event`.
10. **Spine:** AD-11 already states the trigger set (consolidated 2026-10-12). The notes file records that the shipped behaviour matches it, or the deviation (see ADR and spine routing).

## Business acceptance criteria

### Outcome

- An operator who restores a store from backup, or a tool that writes the store atomically (write a temporary file, then rename), gets the certificates exported within one debounce window (2 s). Before this story they waited for the next in-place Traefik write, possibly weeks.
- Only the replaced store file is re-processed. If the content is unchanged, nothing is rewritten and no hook, notification or restart follows.
- Renaming a store away (for example to `.bak`) is logged and does nothing else.

#### 0.3.1 release notes

- "Watch mode now detects an ACME store that is replaced by renaming a file onto it (an atomic `write temp + rename`, a restore from backup, many editors). Before 0.3.1 only in-place writes, which is what Traefik does, triggered an export."
- "Renaming a store file away (for example `acme.json` → `acme.json.bak`) is logged at INFO and exports nothing. Exported certificates are left in place, as before."

Spec: none — l3io-plan run, no spec index bound

### Non-goals

- No recursive watching, and no handling of directories moved into the data path.
- No pruning or deletion of exported certificates when a store is renamed away or deleted. Stale-artifact pruning is a separate, unscheduled concern.
- No `on_deleted` handling, and no change to how a deleted store is treated (still ignored).
- No switch to `on_closed` (`IN_CLOSE_WRITE`) as the trigger. watchdog emits `FileClosedEvent` only from `InotifyObserver` (changelog 7.0.0-dev note), so it cannot replace `modified` under polling. The debounce already absorbs the extra events.
- No `generate_full_events=True`. The default already reports an unpaired move-in as `created`, which is the behaviour we want.
- No change to the debounce duration, the drain loop, or shutdown (ADR-0023, ADR-0026).
- No watchdog upgrade. The 7.x pattern change is a risk noted below, not addressed here.

## Technical acceptance criteria

### Interface contracts

- `AcmeCertificateFileHandler` (`libs/certificate_exporter.py`):
  - **new:** `on_moved(self, event) -> None`, which overrides `FileSystemEventHandler.on_moved` and takes the same single-event signature as the other `on_*` methods (`events.py:228`):
    - it returns immediately for `event.is_directory`;
    - it logs DEBUG first;
    - under `self.lock`, it discards `event.src_path` from `pendingPaths` when the source matches;
    - when `dest_path` matches, it queues `dest_path` through the same path that `created`/`modified` take;
    - otherwise it logs the "moved away" INFO line.
  - **new private:** `__queuePath(self, path: str) -> None`. This is the body of today's `handleEvent` from the shutdown check through `__arm()`, parameterised by path. `handleEvent(event)` keeps its signature and calls `self.__queuePath(event.src_path)` after its `is_directory` check, so the existing tests that call `handler.handleEvent(_event(...))` are untouched.
  - **new private:** `__matches(self, path: str) -> bool`, which returns `watchdog.utils.patterns.match_any_paths([path], included_patterns=self.patterns, excluded_patterns=self.ignore_patterns, case_sensitive=self.case_sensitive)`. It reads the handler's own read-only properties (`events.py:308-340`), so the pattern list is never restated.
  - `on_created`, `on_modified`, `doTheWork`, `cancel`, `__processPath`, `__arm` and `__rearm`: unchanged.
- `app.py`: unchanged (`Observer()`, `recursive=False`).
- Sibling conventions:
  - handler methods are `camelCase` apart from the watchdog-mandated `on_*`, and private helpers use `__name`;
  - each `on_*` logs `Watchdog received <kind> event - <path>.` at DEBUG first;
  - comments explain *why*, in the file's existing style;
  - tests stay in `tests/libs/test_certificate_exporter_watch.py`, built with the `_handler(...)` fixture (real `Settings`);
  - new tests construct **real** watchdog event classes (`watchdog.events.FileMovedEvent`, `DirMovedEvent`, `FileCreatedEvent`) and deliver them through `handler.dispatch(...)`, never by calling `on_moved` directly, so that the pattern filtering is what is tested.

Spec: none — l3io-plan run, no spec index bound

### Error and edge case handling

- **`dest_path` matches, `src_path` does not** (temporary file renamed onto the store): `dest_path` is queued.
- **`src_path` matches, `dest_path` does not** (store renamed away): `src_path` is discarded from the window and nothing is queued. One INFO line. No timer is armed. An already-open window is left alone.
- **Both match:** `src_path` is discarded and `dest_path` queued.
- **Neither matches:** unreachable, because dispatch filters it out. `on_moved` still behaves safely (no-op apart from the DEBUG line).
- **The source was the only pending path, and the window is open:** the drain finds the set empty, clears `isWaiting`, and returns (`doTheWork` `:1520-1532`). No export and no lost wakeup.
- **Residual race:** the drain has already taken `src_path` off the queue before the rename arrives. This happens only if the rename lands more than one debounce window (2 s) after the temporary file's own `created` event. That pass logs the existing `File not found: <path>` ERROR for the vanished name, and the moved event queues `dest_path` for the next drain. This is accepted and documented in a code comment: suppressing the ERROR would also hide a store that genuinely vanished mid-pass.
- **Rename after `cancel()`:** `__queuePath` keeps the `shuttingDown` latch check, so nothing is armed.
- **Case:** `case_sensitive=False` applies to `dest_path` exactly as to `src_path`, because the same properties are passed to `match_any_paths`.
- **`ignore_patterns`:** none are set today. If one is added, it applies to the destination too.
- **Unpaired `IN_MOVED_FROM`:** watchdog reports a store moved out of the directory as `FileDeletedEvent`, which stays unhandled (non-goal).
- **Editor-style save** (vim `4913` probe file, `acme.json~` backup): handled. The `acme.json` → `acme.json~` move discards `acme.json` from the window, and the following `created` re-queues it in order, so one export happens. Test `test_editor_style_save_exports_the_store_once`.
- **Network filesystems:** inotify reports only local changes. A store on NFS/SMB changed from another host is not seen by either the old or the new code. This is documented as an existing limitation (one sentence in `docs/operational.md`), not fixed here.

Spec: none — l3io-plan run, no spec index bound

### Observability requirements

- **DEBUG** in `on_moved`: `Watchdog received moved event - <src> -> <dest>.`, with both paths through `sanitize_for_log`.
- A queued destination produces the existing **INFO** `Certificates changed found in file: <dest>` under the window's `correlation_id` (`__logEvent`). It is not duplicated.
- **INFO** on rename away: `Store file <src> was renamed to <dest>, which does not match the watched file pattern; not exported, exported certificates left in place`. It is logged under the open window's correlation id if a window is open, otherwise with the unset placeholder, like the other out-of-pass lines.
- No new WARNING or ERROR. No metrics (the project has none).

Spec: none — l3io-plan run, no spec index bound

### Security considerations

- File names in the data directory are written by Traefik or the operator, but they reach the log. New log lines pass paths through the existing `sanitize_for_log`, so a newline or control character in a renamed file name cannot forge log lines (AD-3).
- No path from a moved event is used for anything except `exportCertificatesForFile(path)`, which already reads only. The watch is non-recursive on `dataPath`, so a `dest_path` outside the watched directory cannot be delivered.
- A hostile writer of the data directory could already trigger passes with in-place writes. Renames add no new capability, and the debounce plus ADR-0045's restart rule bound the resulting work exactly as before.

### Existing-library check

- **watchdog 6.0.0 (already a dependency) covers the whole mechanism:**
  - `FileSystemEventHandler.on_moved` is the extension point;
  - `FileMovedEvent.dest_path` carries the destination;
  - `watchdog.utils.patterns.match_any_paths` does the matching, which is the same function `PatternMatchingEventHandler.dispatch` uses, so the handler and dispatch cannot disagree about what matches;
  - the handler's `patterns`, `ignore_patterns` and `case_sensitive` properties supply the inputs.
  No `fnmatch`/`glob`/`PurePath.match` call is written by hand.
- `PollingObserver` (watchdog) is used as-is for the fallback test. No custom polling.
- Considered and rejected: `generate_full_events=True` (unneeded, see Non-goals); `on_closed` (inotify-only); `RegexMatchingEventHandler` (would restate the file spec as a regex).
- **Risk to record, not to act on:** the watchdog 7.0.0-dev changelog changes pattern matching from `PurePath.match()` to `PurePath.full_match()`, so `*.json` would stop matching absolute event paths. `pyproject.toml` pins `^6.0`, which excludes 7.x. The real-observer tests use absolute paths and fail on such an upgrade, so the break is caught at the dependency bump, not in production.
