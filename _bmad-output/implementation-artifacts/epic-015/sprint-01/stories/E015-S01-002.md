# Fast export on RSA-4096 stores: validatekeys setting and .pfx fingerprint change detection

## Context

**Maintainer decisions:** `_bmad-output/implementation-artifacts/epic-015/maintainer-decisions.md` — MD-06, MD-07, both accepted as recommended on 2026-10-12 (D1–D6 below stand).

Promoted from deferred finding BL-E014-106 (Medium; live-host test on rwusdckrls6, 2026-10-12). Evidence: `_bmad-output/implementation-artifacts/epic-014/sprint-02/closure/live-host-test-rwusdckrls6-2026-10-12.md` ("Timing: ~1–1.5 s per certificate per pass"). The backlog entry adds the numbers: 74 certificates take 74 s on the first pass and 108 s on an unchanged pass, and a one-domain change re-processes its whole store file (~36 s for 22 entries).

**Root cause** (issue note, `_bmad-output/implementation-artifacts/state/events.jsonl` line 1130, measured on cryptography 50.0.2). RSA private-key validation runs on every load and costs ~550 ms for an RSA-4096 key (~52 ms for RSA-2048; under 1 ms with `unsafe_skip_rsa_key_validation=True`). Traefik's keys are RSA-4096. The test fixtures use EC P-256 (`tests/fixtures/acme_fixtures.py:69-93`), so no test ever showed the cost. Research: `_bmad-output/planning-artifacts/research/research-2026-10-12-release-0.3.1.md` §2.

Every pass loads each domain's key several times. Line numbers are against the current tree:

| Load | Where | Pass |
| --- | --- | --- |
| `serialization.load_pem_private_key` (validating) | `src/traefik_certificate_exporter/libs/certificate_exporter.py:976` (`__exportDomain`, step 1) | every pass, every domain |
| `serialization.load_pem_private_key` again (validating) | `certificate_exporter.py:1201` (`PemToPfxConverter.build_pkcs12`, called at `:981`) | every pass, every domain |
| `pkcs12.load_key_and_certificates` (always validates; takes no skip flag) | `certificate_exporter.py:397` (`_pfx_differs`, called at `:1031`) and `:370` (`_loads_without_passphrase`, when a passphrase is set) | every pass in which a `.pfx` exists |
| `pkcs12.load_key_and_certificates` | `certificate_exporter.py:420` (`_log_pkcs12_details`) | only at DEBUG, after a `.pfx` write |

Probe of the current tree (5 domains sharing one RSA-4096 leaf; the throwaway script wraps both loaders with counters; this host, cryptography 50.0.2, Python 3.11.11). A first pass took 5.95 s with 10 key loads and 0 PKCS#12 loads. An unchanged pass took 9.09 s with 10 key loads and 5 PKCS#12 loads (10 with a passphrase). That ratio matches production's 74 s / 108 s.

Matching a key to its certificate is already enforced. `pkcs12.serialize_key_and_certificates` raises `ValueError: Certificate public key and provided private key do not match` (probe, 50.0.2). The `unsafe_skip_rsa_key_validation` flag does not affect that check.

The `.pfx` is compared by content, not by bytes, because two builds of the same input never match. The comment at `certificate_exporter.py:271-276` says so, as do ADR-0043 Decision 2 and `test_encrypted_pfx_builds_differ_byte_for_byte`. The probe found this holds for `NoEncryption()` as well as `BestAvailableEncryption`. The content compare is what costs a PKCS#12 load per domain per pass.

**Maintainer decision 2026-10-12** (verbatim from the issue note): "fix in 0.3.1, not 0.3.0. Scope: (1) setting settings.validatekeys (env TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_VALIDATEKEYS, optional --no-validate-keys), default true; false skips RSA validation, key/cert match stays. (2) No toggle for the .pfx compare: per-.pfx fingerprint sidecar (cert, key, chain, salted passphrase hash), rebuild on mismatch or missing/damaged .pfx; ADR-0043 amendment. (3) RSA-4096 fixtures + pass-time regression test; passphrase-change and damaged-.pfx tests written first."

**Design decisions D1–D6** (accepted 2026-10-12 as MD-06 and MD-07):

- **D1. Lazy key load.** The expensive steps are loading the key and serialising the `.pfx`. They run only when the domain's `.pfx` must be rebuilt or verified. When the sidecar shows the `.pfx` is current, the key is not loaded at all. The cheap steps are unchanged and still run first for every domain: strict base64 decode, chain parse, PEM byte compare. An unchanged pass therefore costs no key load and no PKCS#12 load whatever `validatekeys` is set to, and `validatekeys` only affects passes that build a `.pfx`.
  - Build-first (ADR-0043 Decision 1) still holds: every artifact that will be written is built before the first write.
  - The key is loaded at most once per domain per pass, and `build_pkcs12`'s second load goes away.
  - Alternative rejected: always load the key once. With the default `validatekeys: true`, that leaves 74 × ~550 ms ≈ 41 s on every unchanged production pass.
- **D2. Upgrade from 0.3.0: verify once, rewrite nothing.** Accepted 2026-10-12 (MD-06). When the sidecar is missing or unusable, or the recorded `.pfx` hash differs from the file, the old content compare (`_pfx_differs`) runs once.
  - If the content matches, only the sidecar is written. The `.pfx` keeps its inode and mtime, so no restart, hook or notification follows (ADR-0045).
  - If it differs, or the `.pfx` is damaged, the `.pfx` is rebuilt and the domain is reported.
  - The upgrade pass pays one key load and one PKCS#12 load per domain, once (~80 s for 74 RSA-4096 domains with validation on).
  - Alternative rejected: rebuild every `.pfx` on upgrade. That restarts every labeled container once and fires the hook and notifications for every domain.
- **D3. Sidecar path and name.** `<pfx path>.fingerprint.json`: `cert.pfx.fingerprint.json` in the per-domain layout, `<name>.pfx.fingerprint.json` in the flat layout.
  - It is derived from the `.pfx` path that `_artifact_paths` returns, by one pure helper `_pfx_fingerprint_path(pfxPath)` defined beside `_artifact_paths`. No other code joins this path.
  - It is **not** one of the five recorded artifact paths, so `artifactMtime` and the restart rule never see it.
  - No artifact name ends in `.json`, so the name cannot collide with another domain's files.
- **D4. Passphrase hash.** cryptography's `Scrypt` (`cryptography.hazmat.primitives.kdf.scrypt`) with n=2^14, r=8, p=1, length 32, and a random 16-byte salt per sidecar written. The parameters are stored in the sidecar, and verification uses `Scrypt.verify`, a constant-time compare that raises `InvalidKey`.
  - Cost is ~63 ms per derive on this host. A module-level `functools.lru_cache` (maxsize 4096) keyed on `(passphrase, salt, n, r, p)` means each sidecar costs one derive per process, not one per pass. The passphrase already lives in process memory (`Settings.pkcs12Passphrase`).
  - Alternatives: `hashlib.scrypt`, rejected because it depends on the interpreter's OpenSSL build, not the locked wheel; PBKDF2-HMAC-SHA256 at 600 000 iterations, rejected at ~390 ms per derive.
- **D5. Write order.** Changed PEMs, then the `.pfx`, then the sidecar, each atomically (`_atomic_write_bytes`, mode 0600).
  - A crash between the `.pfx` and its sidecar leaves a stale sidecar whose recorded `.pfx` hash no longer matches. The next pass takes the verify path, finds the content current, writes the sidecar and reports nothing. It never yields a false "unchanged".
- **D6. Start-up logging.** One INFO line next to `Output Path` (`src/traefik_certificate_exporter/app.py:175-177`): `RSA key validation: on` or `RSA key validation: off (settings.validatekeys=false: keys are trusted, not checked)`. It is not a WARNING, because the operator chose the setting and it would repeat on every start.

Sequencing: E015-S01-001 also edits `settings.py` (`loadFromFile`) and owns creating the `## 0.3.0 → 0.3.1` heading of `docs/upgrading.md` (its AC 9), so `depends_on: [E015-S01-001]` is set; this story adds its own `###` subsection under that heading. E015-S02-002 adds another `###` subsection under it in parallel; whichever of the two merges second rebases and keeps both subsections. E015-S01-001 also introduces `ROOT_SETTING_TRUST`, a declared trust class for every key in `config_default.yaml`, with a test that fails on an unclassified key: this story adds `validatekeys` to that table as **any-source** (maintainer-decisions MD-21), and the failing classification test is the guard working as intended, not a regression. E015-S01-003 edits the watch handler in the same module (`AcmeCertificateFileHandler`, `certificate_exporter.py:1304+`), a disjoint region.

## Acceptance Criteria

1. **Fail-first tests.** The tests named in Testability approach are committed and run against the unchanged product code before any product change, and their failing output is pasted into the notes:
   - RSA-4096 fixture;
   - unchanged-pass load-count and time test;
   - first-pass key-load tests;
   - passphrase-change-from-sidecar test;
   - damaged-`.pfx` tests;
   - upgrade test;
   - sidecar-scope test.

   The damaged-`.pfx` tests pass on the current tree as well, because content compare detects the damage. They are regression guards and are marked so.
2. **`settings.validatekeys`.**
   - `config_default.yaml` declares `validatekeys: true` under `settings`.
   - `Settings` gains `validateKeys: bool`, read with `.get(bool)`. Its constructor parameter defaults to `True`, so existing callers and the tests' `_make_settings` keep working.
   - Env `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_VALIDATEKEYS=false` sets it false.
   - CLI `--no-validate-keys` (`action="store_const"`, `const=False`, `dest="settings.validatekeys"`, `default=None`, help text naming the trust caveat) sets it false.
   - Precedence is CLI > env > config file > packaged default.
3. **Key loading honours the setting.** Every private-key load in the export path goes through one helper, `_load_private_key(keyPem: bytes, validate: bool)`. It calls `serialization.load_pem_private_key(keyPem, password=None, unsafe_skip_rsa_key_validation=not validate)`.
   - With `validatekeys: false`, every such call passes `unsafe_skip_rsa_key_validation=True`.
   - With the default, every call passes `False`.
   - The key is loaded at most once per domain per pass. The `.pfx` is serialised from that loaded key through `_serialize_pkcs12(key, certs, passphrase)`, which `PemToPfxConverter.build_pkcs12` also uses.
   - `build_pkcs12` keeps its signature and keeps validating, so external callers are unchanged.
4. **Key/cert match stays in both modes.** A store entry whose key does not match its leaf is not exported under either `validatekeys` value: one ERROR names the `pkcs12` stage, and the domain's existing files are left untouched. `serialize_key_and_certificates` raises for this.
5. **Sidecar.** Every `.pfx` the exporter writes or verifies has a sidecar at `_pfx_fingerprint_path(pfxPath)` (D3), written atomically at mode 0600 after the `.pfx` (D5). Its content is the JSON object specified in Interface contracts. It never contains the passphrase or any key bytes.
6. **Change test for the `.pfx`** (replaces the content compare on the normal path). The `.pfx` is *current* iff all of these hold:
   - the `.pfx` passes `_breaks_write_policy` as today;
   - the sidecar is usable (Error and edge case handling);
   - the SHA-256 of the `.pfx` file's bytes equals `pfx_sha256`;
   - `key_sha256` equals the SHA-256 of the store's decoded key PEM bytes;
   - `certificates_sha256` equals the ordered SHA-256 fingerprints (`Certificate.fingerprint(hashes.SHA256())`) of leaf and intermediates;
   - the passphrase state matches: `null` exactly when no passphrase is configured (`None`/`""`), otherwise `Scrypt.verify` succeeds.

   The outcome for each case:
   - Current: nothing is loaded or built, and the `.pfx` is not written.
   - Usable sidecar with an input mismatch: the `.pfx` is rebuilt. No PKCS#12 load happens.
   - Unusable or missing sidecar, or a `pfx_sha256` mismatch: the verify path (D2) runs.
7. **Damaged or missing `.pfx`.** A missing `.pfx` is rebuilt and the domain reported, as today. So is one truncated to 0 bytes, or one with any byte changed, whether or not its sidecar is current.
8. **Passphrase change.** Changing `pkcs12passphrase` (unset → set, set → other, set → unset) between passes rebuilds only the `.pfx` (plus its sidecar) and reports the domain. Detection performs no PKCS#12 load.
9. **Upgrade from 0.3.0** (D2). Over output written by 0.3.0 (five artifacts, no sidecars), the first pass rewrites no artifact: inode and mtime are unchanged for all five. It writes one sidecar per `.pfx`, reports no domain, and so triggers no restart, hook or notification. The next pass performs zero PKCS#12 loads.
10. **Sidecar is not an artifact.** `artifactMtime` and the recorded artifact index cover exactly the five `_artifact_paths` paths. A sidecar newer than every artifact does not change `artifactMtime`. Writing only a sidecar never makes a domain "changed".
11. **Performance bound (unchanged pass).** For 5 domains with RSA-4096 keys, an unchanged pass over existing output, with a fresh exporter and default settings (`validatekeys: true`), makes **0** calls to `serialization.load_pem_private_key` and **0** to `pkcs12.load_key_and_certificates`, and takes **< 2.0 s** of wall time. The current tree takes 9.09 s here, with 10 and 5 calls.
12. **Performance bound (first pass).** On a first pass over the same 5 domains:
    - `load_pem_private_key` is called exactly 5 times;
    - with `validatekeys: false`, each call passes `unsafe_skip_rsa_key_validation=True`, and the pass takes < 2.0 s;
    - with the default, each call passes `False`.

    The current tree makes 10 calls taking 5.95 s.
13. **`_log_pkcs12_details` loads nothing.** Its DEBUG introspection (subject, issuer, dates, intermediate count) comes from the in-memory `certs`, not from re-loading the written bundle.
14. **Start-up log** per D6: exactly one INFO line, after `Output Path`.
15. **Settings surface and docs.**
    - `README.md` usage block (the `--help` copy) carries `--no-validate-keys`.
    - `config.sample.yml` gains a commented `# validatekeys: true` line with a one-line comment.
    - `docker/README.md`'s env sample gains `# - TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_VALIDATEKEYS=true`.
    - `docs/operational.md` describes the sidecar file next to the `.pfx` and the setting, including the trust caveat.
    - `docs/upgrading.md` § `## 0.3.0 → 0.3.1`, in a `### PKCS12 fingerprint files and validatekeys` subsection, states the one-time verify pass for 0.3.0 output (slower first pass, no rewrite, no restart), that output from 0.2.x still gets the 0.2.x → 0.3.0 one-time `.pfx` rewrite, and the new sidecar files.
    - `tests/test_settings_surface.py` and `tests/libs/test_cli_args.py` pass unchanged; they derive their scope.
16. **ADR.** A new ADR, reserved at dev time (see ADR and spine routing), records the sidecar decision and amends ADR-0043 Decision 2. ADR-0043 gains an `## Amendment (2026-10-…) — ADR-NNNN` section pointing to it. `docs/architecture.md` §6 gains the new ADR's row and an "amended by" marker on the ADR-0043 row, in the same change (the §6 rule).

## Business acceptance criteria

### Outcome

An operator with a production-size Traefik store (tens of RSA-4096 certificates) gets an export pass that costs almost nothing when nothing changed. An unchanged pass performs no private-key or PKCS#12 load, so a 74-certificate store no longer spends ~108 s re-checking itself, and a single renewal no longer re-validates the 21 other entries in its store file. An operator who trusts the keys Traefik writes can set `validatekeys: false` to make passes that do write `.pfx` files fast as well.

Upgrading from 0.3.0 rewrites nothing and restarts nothing. The first pass is slower, once, while each existing `.pfx` is verified.

#### 0.3.1 release notes

- "Export passes over unchanged certificates are fast again on RSA-4096 stores. Each `.pfx` now has a small `.fingerprint.json` file beside it (mode 0600, no secrets: hashes only, and the passphrase only as a salted scrypt hash). The exporter uses it to tell that the `.pfx` is current without opening it. A missing, damaged or edited `.pfx` is still rebuilt."
- "New setting `settings.validatekeys` (env `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_VALIDATEKEYS`, CLI `--no-validate-keys`), default `true`. Set it to `false` to skip RSA private-key validation when the exporter builds a `.pfx` (~0.5 s per RSA-4096 key). Do this only when the ACME store is written by your own Traefik: the keys are then trusted, not checked. The check that a key matches its certificate always runs."
- "Upgrading from 0.3.0: the first pass verifies every existing `.pfx` once and writes its fingerprint file. It rewrites no certificate file and restarts no container."
- Internal only, no upgrade note: the key is loaded once per domain instead of twice; the DEBUG `.pfx` introspection no longer re-opens the file.

Spec: none — l3io-plan run, no spec index bound

### Non-goals

- No toggle for the `.pfx` change test (maintainer decision): the sidecar path is the only path.
- No change to the `.pfx` encryption (`BestAvailableEncryption`, AES-256/SHA-256) or to its algorithm or iteration choices.
- No removal of stale sidecars when a domain leaves the store. The exporter never deletes artifacts either.
- `PemToPfxConverter.export_to_pkcs12` (external API) writes no sidecar. A `.pfx` it writes into the output directory is verified once by the next pass.
- No skip flag for `pkcs12.load_key_and_certificates`; cryptography 50.0.2 offers none. The verify path pays full cost and runs once per `.pfx`.
- No persisted state other than the sidecars. The PEM change test stays a byte compare against the files.
- No live-host change to production. The rwusdckrls6 re-measure is optional HITL evidence in a test container.

## Technical acceptance criteria

### Interface contracts

New and changed module-level functions in `src/traefik_certificate_exporter/libs/certificate_exporter.py`. All are private, typed, and pass `mypy` over `src/`:

| Name | Signature | Contract |
| --- | --- | --- |
| `_load_private_key` | `(keyPem: bytes, validate: bool) -> PrivateKeyTypes` | the only key loader in the export path; passes `unsafe_skip_rsa_key_validation=not validate` |
| `_serialize_pkcs12` | `(key: PrivateKeyTypes, certs: list[x509.Certificate], passphrase: str \| bytes \| None) -> bytes` | the body of today's `build_pkcs12` after its key load: friendly name and encryption choice unchanged; raises `ValueError` on key/cert mismatch |
| `_pfx_fingerprint_path` | `(pfxPath: Path) -> Path` | pure: `pfxPath.with_name(pfxPath.name + ".fingerprint.json")`; defined beside `_artifact_paths` |
| `_pfx_fingerprint` | `(pfxBytes: bytes, keyPem: bytes, certs: list[x509.Certificate], passphrase) -> dict` | the sidecar object for a `.pfx` (new salt when a passphrase is set) |
| `_pfx_state` | `(pfxPath: Path, keyPem: bytes, certs, passphrase, dryRun: bool) -> Literal["current", "rebuild", "verify"]` | per Acceptance Criterion 6; never raises (any I/O or parse error gives `"verify"`, or `"rebuild"` when the `.pfx` is absent) |
| `_passphrase_matches` | `(passphrase: bytes, record: dict) -> bool` | `Scrypt(...).verify` behind `functools.lru_cache(maxsize=4096)`; an unknown `kdf` or bad parameters give `False` |
| `PemToPfxConverter.build_pkcs12` | unchanged signature | `_load_private_key(key_pem, validate=True)` then `_serialize_pkcs12` |
| `_pfx_differs` | unchanged | used only on the verify path |

Sidecar JSON (`json.dumps(obj, sort_keys=True)`, UTF-8, trailing newline):

```json
{
  "certificates_sha256": ["<hex leaf fingerprint>", "<hex intermediate fingerprint>"],
  "format": "traefik-certificate-exporter/pfx-fingerprint",
  "key_sha256": "<hex SHA-256 of the store's decoded key PEM bytes>",
  "passphrase": null,
  "pfx_sha256": "<hex SHA-256 of the .pfx file bytes>",
  "version": 1
}
```

With a passphrase set, the `passphrase` value is instead `{"kdf": "scrypt", "n": 16384, "r": 8, "p": 1, "salt": "<base64 16 bytes>", "digest": "<base64 32 bytes>"}`.

`__exportDomain` flow, replacing steps 1–3 at `certificate_exporter.py:970-1075`:

1. Decode the key and chain strictly and parse the chain. Failure produces one ERROR (stage `key` or `certificate chain`) and the files are untouched.
2. Run the containment check and the directory sweep, as today.
3. Byte-compare the PEMs, as today.
4. Compute `_pfx_state`.
5. If the state is `rebuild` or `verify`, run `_load_private_key(keyPem, settings.validateKeys)` and then `_serialize_pkcs12`. Failure produces one ERROR (stage `key` or `pkcs12`) and **nothing** is written, the PEMs included (build-first). On `verify`, `_pfx_differs` decides whether the `.pfx` joins the changed set.
6. Write the changed PEMs, then the `.pfx`, then the sidecar whenever the `.pfx` was written or verified current.
7. The return value `(changed, paths)` is unchanged in meaning: `paths` stays the five artifact paths.

Settings: `config_default.yaml` `settings.validatekeys: true`; `Settings.validateKeys: bool = True`; `SettingsManager.loadFromFile` reads `self._config["settings"]["validatekeys"].get(bool)`. `cli_args.py` adds `--no-validate-keys` with the sibling conventions: `dest="settings.<key>"`, `default=None` so an absent flag does not override env or file, and help text.

Sibling conventions to keep:
- `_atomic_write_bytes` for every write;
- `_SECRET_FILE_MODE` for key-bearing files and the sidecar;
- `sanitize_for_log` for names in log lines;
- no new global singleton;
- tests in `tests/libs/test_certificate_exporter.py`, named `test_<behaviour>`, with fixtures in `tests/fixtures/acme_fixtures.py` cached in `_CACHE`, as `real_chain()` is.

Downstream consumers:
- `DockerManager`, through `artifactMtime`, which is unchanged;
- `post_export` and `notify`, through the changed-domain list, which is unchanged;
- the image test `tests/test_container_pkcs12.py`, which finds the `.pfx` by suffix `cert.pfx` and is unaffected.

### Error and edge case handling

Unusable sidecar. A sidecar is unusable when it:
- is absent;
- is not a regular file (symlink included);
- fails `_breaks_write_policy` at 0600 after the in-place tighten;
- is larger than 64 KiB;
- is not valid UTF-8 JSON;
- has a `format` or `version` this code does not know, or a field of the wrong type.

An unusable sidecar gives `verify`. It is never an error and never a log line above DEBUG. The atomic write replaces a symlinked sidecar instead of writing through it, as for the artifacts.

- **Missing `.pfx`** → `rebuild`; the domain is reported.
- **`.pfx` present, `pfx_sha256` mismatch** covers truncation, an edited byte, an operator replacement, or a crash between the `.pfx` write and the sidecar write. The result is `verify`, which loads the `.pfx` once:
  - content current → sidecar rewritten, domain not reported;
  - content differs, or the load fails → `.pfx` rebuilt, domain reported.
- **Sidecar write fails after a successful `.pfx` write.** One WARNING names the sidecar path and the error. The domain's changed signal is unaffected, and the next pass takes `verify`. A sidecar write failure on the verify-only path logs the same WARNING and reports nothing.
- **Artifact write failure.** The partial-export handling at `:1046-1063` is unchanged. A `.pfx` that was not written gets no sidecar update.
- **Dry run.**
  - `_pfx_state` and the verify compare run as usual, but no sidecar is written. A dry run over 0.3.0 output therefore verifies every `.pfx` (slow) on every dry run until a real pass has written the sidecars. Document this in `docs/operational.md`.
  - `_breaks_write_policy` keeps its dry-run behaviour.
- **Passphrase `""`** is normalised to none (`_normalize_passphrase`). Sidecar `passphrase: null`.
- **Key PEM re-encoded by Traefik** (same key, different bytes): `privkey.pem` differs and is rewritten, `key_sha256` differs, and the `.pfx` is rebuilt once. This is harmless, and correct for consumers that read the PEM.
- **`validatekeys` toggled between runs**: nothing is rebuilt. The setting changes how inputs are checked, not what is written.
- **Invalid RSA key with `validatekeys: false`.** The cryptography docs: "If you do load an invalid key this way and attempt to use it OpenSSL may hang, crash, or otherwise misbehave". The key/cert match in `serialize_key_and_certificates` still runs. The documented mitigation is the trust statement: only Traefik's own store. The setting stays default-on.
- **Two candidates mapping to one file set** (`__owners`): unchanged. Only the owner writes the `.pfx` and its sidecar.
- **Stale staging files**: the sidecar's `.{name}.{random}.tmp` is collected by `_sweep_stale_temp_files` like any other staging file.
- **Clock and mtime**: the sidecar's mtime is never read.

Spec: none — l3io-plan run, no spec index bound

### Security considerations

- **`unsafe_skip_rsa_key_validation` is only safe for trusted keys** (cryptography docs: "unsafe unless you are certain the key is valid. User supplied keys should never be loaded with this parameter set to True").
  - The default stays `true`.
  - The help text, `config.sample.yml` comment and `docs/operational.md` state: "only when the ACME store is written by your own Traefik".
  - `build_pkcs12`, the public API, always validates.
- **The sidecar is written 0600** next to files of the same sensitivity. It holds hashes of public certificates, the SHA-256 of the private key PEM and of the `.pfx`, and a scrypt hash of the passphrase.
  - A SHA-256 of a 4096-bit key is not invertible.
  - The scrypt hash, with a per-sidecar random salt and n=2^14, r=8, p=1, makes an offline guess cost ~63 ms each here. Anyone able to read the sidecar can already read `privkey.pem`. The hash protects only passphrase reuse elsewhere.
  - A test asserts that neither the passphrase nor any key bytes (PEM or DER) appear in the sidecar.
- **The sidecar is never authoritative alone.** "Current" requires its `pfx_sha256` to equal the hash of the file on disk. An attacker who can rewrite both the `.pfx` and its sidecar could also rewrite `privkey.pem`, so no trust boundary is crossed. This is the answer to ADR-0043's rejection of option B ("a second source of truth that drifts"), and the new ADR states it.
- **Comparison** uses `Scrypt.verify` (constant time) for the passphrase. Hash compares are of public or non-secret values, so a plain `==` is fine.
- **No secret is logged.** The new log lines carry names and reasons only.
