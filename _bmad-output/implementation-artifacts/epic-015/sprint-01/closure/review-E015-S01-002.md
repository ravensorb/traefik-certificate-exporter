## Findings

### R1 — MEDIUM — kind: claim — an edited fingerprint file can rebuild the `.pfx` and report the domain

- **Location:** `docs/operational.md:293-296`; behaviour at
  `src/traefik_certificate_exporter/libs/certificate_exporter.py` `_pfx_state` (the
  `key_sha256` / `certificates_sha256` / passphrase branches after the `pfx_sha256` check).
- **Claim:** "A missing, unreadable or edited fingerprint file makes the next pass verify the
  `.pfx` by content once and write a new fingerprint file; that rewrites no certificate file
  and reports nothing. Deleting the fingerprint files is therefore safe."
- **Evidence:** If the edit keeps a well-formed record and `pfx_sha256` still matches, the
  sidecar is usable. Any other field that differs (`key_sha256`, `certificates_sha256`, the
  passphrase `salt`/`digest`) then gives `"rebuild"`, not `"verify"`. The `.pfx` is rewritten,
  the domain is reported, and the restart, hook and notification follow. Probe (a) sets
  `key_sha256` to 64 zeros, and the next pass reports `['a.example.test']`. The code follows
  the story here: AC 6 says "Usable sidecar with an input mismatch: the `.pfx` is rebuilt".
  The operator doc is what is wrong: it promises an operator who edits the file no restart.
  "Deleting … is therefore safe" is still true.
- **Fix:** Reword the bullet. Example: "A missing, unreadable or malformed fingerprint file,
  or one whose recorded `.pfx` hash no longer matches, makes the next pass verify the `.pfx`
  by content once … and reports nothing. A fingerprint file edited to record different inputs
  makes the next pass rebuild the `.pfx` and report the domain. Deleting the fingerprint files
  is therefore safe; editing them is not." Optionally pin this with a test that edits
  `key_sha256` and expects the domain to be reported, so the doc and the code stay tied.

### R2 — LOW — kind: correctness — a scrypt record with a non-power-of-two `n` counts as usable, so it rebuilds instead of verifying

- **Location:** `src/traefik_certificate_exporter/libs/certificate_exporter.py`,
  `_scrypt_params` (the `n <= 0 or r <= 0 or p <= 0 or 128 * n * r > _SCRYPT_MAX_MEMORY`
  check).
- **Evidence:** `_scrypt_params` accepts any positive `int` `n`. `Scrypt(...)` raises
  `ValueError` when `n` is not a power of 2 greater than 1. That error is caught inside the
  cached `_scrypt_verifies`, which returns `False`. Three things go wrong as a result:
  1. `_read_pfx_fingerprint` treats the record as usable.
  2. `_pfx_state` returns `"rebuild"`, so the domain is reported (probe (b): `n = 3` →
     `['a.example.test']`). The recorded deviation says the opposite: "malformed passphrase
     record ⇒ unusable sidecar ⇒ `verify`".
  3. The malformed record adds an `lru_cache` entry, although the story (D4) and
     `test_passphrase_check_is_cached_on_hashable_values_only` claim that "a record with … a
     non-`int` `n` … gives `False` and adds no cache entry". This shape of malformed record is
     simply missing from the test's list.

  Reaching this needs a hand-edited sidecar.
- **Fix:** In `_scrypt_params`, also require `n > 1 and n & (n - 1) == 0`. Add
  `{**record, "n": 3}` to the malformed list in
  `test_passphrase_check_is_cached_on_hashable_values_only`. Optionally add an
  unusable-sidecar case with that record, expecting no report.

### R3 — LOW — kind: deletion (confidence: high) — a new domain whose key or `pkcs12` build fails now leaves an empty directory behind

- **Location:** `certificate_exporter.py` `__exportDomain`, step 2
  (`if not dryRun: if not directory.exists(): directory.mkdir(...)`). Before this change the
  key load ran ahead of this `mkdir`.
- **Evidence:** The old step 1 loaded the key and built the `.pfx` before any filesystem
  action, so a failing new domain created nothing. That contract was not carried over: the
  key load now comes after the `mkdir`. Probe (c), a new domain with a mismatched key: one
  ERROR (stage `pkcs12`), reported `[]`, and `certs/new.example.test/` exists and is empty.
  - Judgment against the story: this does not break the letter of AC 4 or step 5. No file is
    written and no existing file is touched, and the story keeps "containment check and the
    directory sweep" at step 2. It is still a behaviour regression, and the notes record it
    as a deviation.
  - Impact: a consumer that maps directories to domains sees a domain directory with no
    certificate, and it reappears on every pass while the entry stays broken. Nothing is
    restarted, because the domain is not recorded.
- **Fix:** Keep the containment check and the sweep at step 2, but sweep only when the
  directory already exists. Move `directory.mkdir(...)` to just before the step 6 write loop,
  after a successful build. The `.pfx` build at step 5 then always precedes the first
  filesystem change, as before. Add a test: a new domain with a mismatched key leaves
  `outputPath` without that directory.

### R4 — LOW — kind: observability — the per-domain DEBUG lines can be wrong or missing, and dry runs warn twice

- **Location:** `certificate_exporter.py` `__exportDomain` steps 5–6.
- **Evidence:**
  1. `.pfx for <name> rebuilt: fingerprint mismatch` is also logged when `_pfx_state` returned
     `"rebuild"` because the `.pfx` fails the write policy (a symlink, a non-regular file, or
     a failed `chmod`). In that case no fingerprint was compared, so the reason is false.
  2. In the not-changed branch, `__writeFingerprint(...)` is followed unconditionally by
     `.pfx for <name> verified by content; fingerprint recorded`. When the write failed, the
     WARNING says it was not written and the next DEBUG line says it was recorded.
  3. When the `.pfx` is verified current but a PEM also changed, the `elif verifiedPfx is not
     None` branch writes the sidecar and logs no `verified by content` line at all. The story
     lists that line among the per-domain DEBUG lines.
  4. In a dry run over a `.pfx` wider than 0600 that takes the verify path,
     `_breaks_write_policy` runs twice, once in `_pfx_state` and once in `_pfx_differs`. The
     `[DRYRUN] would tighten mode …` WARNING is therefore logged twice for one file. Outside a
     dry run the first call tightens the mode, so the second call is silent.
- **Fix:**
  1. Have `_pfx_state` hand back the rebuild cause, or recompute it at the log site: `missing`
     when the path does not exist, `unreadable` (or a new `not a regular file`) when it fails
     the write policy, `fingerprint mismatch` otherwise.
  2. Make `__writeFingerprint` return `bool`, and log "fingerprint recorded" only on `True`.
  3. Log the `verified by content` DEBUG line in the `elif` branch too.
  4. Optional: accept the duplicate dry-run WARNING, or skip the write-policy check inside the
     verify path, since `_pfx_state` already ran it.

## Checks with no finding

- **`_pfx_state`:**
  - The AC 6 conditions are evaluated in the specified order: write policy, sidecar usability,
    `pfx_sha256`, `key_sha256`, ordered `certificates_sha256`, then passphrase state.
  - `null` is accepted exactly when no passphrase is configured (`_normalize_passphrase` makes
    `""` none).
  - It never raises: there is an outer `except Exception` returning `"verify"`;
    `FileNotFoundError` gives `"rebuild"` and any other `OSError` gives `"verify"`.
  - A symlinked or non-regular sidecar is unusable through `_breaks_write_policy`. Size is
    capped by both `lstat` and the read length.
  - A dry run keeps `_breaks_write_policy`'s dry-run behaviour.
- **`__exportDomain` flow:**
  - Build-first holds: the key load and `_serialize_pkcs12` both run before the first write,
    and a `key`/`pkcs12` failure returns before any write.
  - The key is loaded at most once per domain per pass, and not at all when the state is
    `current`.
  - On `verify`, `_pfx_differs` decides whether the `.pfx` joins `changed`.
  - The sidecar is written after the `.pfx` (D5), and also when the `.pfx` was verified
    current. A dry run writes no sidecar, and a partial or failed write gives no sidecar
    update.
  - A sidecar write failure produces one WARNING and leaves the changed signal unchanged.
  - Every write goes through `_atomic_write_bytes` with `_SECRET_FILE_MODE`.
- **`_passphrase_matches` / `_scrypt_verifies` split (AG-3):** the record is validated
  uncached, and the cache is keyed only on hashable primitives. `Scrypt.verify` is the
  constant-time compare, and `InvalidKey` gives `False`. The extra memory and `p` caps are
  sound hardening; the deviation is accepted. See R2 for the gap left in the record check.
- **Sidecar content:**
  - It holds hashes only: `json.dumps(sort_keys=True)` plus a newline. The passphrase appears
    only as scrypt output, with a fresh 16-byte `os.urandom` salt for each write.
    `test_sidecar_holds_no_secret` covers the passphrase, the PEM, the PEM body, and the DER
    in raw, hex and base64 form.
- **artifactMtime scope (AC 10):** `_pfx_fingerprint_path` is the only place that derives the
  sidecar path, and the sidecar is not in `_artifact_paths`.
  `test_sidecar_does_not_move_artifact_mtime` and the updated
  `test_artifact_mtime_finds_every_layout` both move the sidecar's mtime into the future and
  confirm that `artifactMtime` does not change.
- **`build_pkcs12`:** its signature is unchanged, and it calls
  `_load_private_key(key_pem, validate=True)` and then `_serialize_pkcs12`, so it still
  validates.
- **Tests:**
  - The spies patch `serialization.load_pem_private_key` and
    `pkcs12.load_key_and_certificates` on the module objects that `certificate_exporter`
    resolves at call time, so every load in the export path is counted. The fail-first output
    in the notes (10 key loads, 5–10 PKCS#12 loads) shows that the spies catch the defect.
  - The relative time bounds are sound. Both passes run in the same test process: about
    2.9 s for the validating first pass, against 0.005–0.285 s unchanged and 0.016 s
    non-validating. That is far below the ¼ and ½ thresholds.
  - `_snapshot` compares `(inode, mtime_ns, bytes)`, so the upgrade and unchanged-pass tests
    do detect rewrites.
- **Existing-library check:** the code matches the story's table. It uses cryptography's
  `Scrypt`, `Certificate.fingerprint(hashes.SHA256())`, `hashlib.sha256`, `json`, `base64`,
  `os.urandom`, `functools.lru_cache` and the existing `_atomic_write_bytes`. Nothing is
  hand-rolled, and the key/cert match is left to `serialize_key_and_certificates`.
- **Deletions:**
  - The `build_pkcs12` body moved verbatim into `_serialize_pkcs12` (confidence: high).
  - `_log_pkcs12_details` no longer reloads the written bundle. AC 13 requires this, and it
    now reads the in-memory `certs`, including in `export_to_pkcs12` (confidence: high).
  - The old ERROR text is kept in `__logBuildFailure` (confidence: high).
  - The old step 1 ordering is covered by R3.
- **Settings and docs:**
  - `--no-validate-keys` uses `store_const` / `False` / `dest="settings.validatekeys"` /
    `default=None`.
  - `.get(bool)` is used.
  - The constructor parameter defaults to `True`.
  - `ROOT_SETTING_TRUST` has the entry with the MD-21 comment.
  - The INFO line comes right after `Output Path`, and the test asserts the index.
  - The README, `config.sample.yml`, the docker README, the upgrading subsection, ADR-0051, the
    ADR-0043 amendment and the §6 rows (0051, plus "amended by 0051" on 0043) are all present.
- **Other recorded deviations:**
  - A non-regular file at the `.pfx` path is rebuilt directly. That is consistent with AC 6
    (the file fails the write policy) and with what the old content compare did.
  - The `_log_pkcs12_details` signature change is private, and both callers were updated.
  - The three extra test-expectation updates follow necessarily from the sidecar's existence,
    and each is explicit.
  - Test placement is justified.

  All accepted.
