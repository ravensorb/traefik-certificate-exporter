## MEDIUM-1 — the composite-action half of CI-AR42's re-pinning ban is not enforced

**File:** `/home/ravenwolf.org/sanderson/source/git/ravensorb/traefik/traefik-certificate-exporter/tests/ci/test_workflow_contracts.py:769`
**Severity:** Medium
**kind:** claim

**Problem:** `test_no_step_re_pins_identity_after_a_ref_free_checkout` opens with

```python
for definition, container, steps in _governed_step_groups():
    if not any(_is_checkout(step) for step in steps):
        continue
```

`_governed_step_groups()` yields composite actions as their own group (`container == "runs"`).
No composite action contains an `actions/checkout` step (verified by grep: every
`actions/checkout@v7` occurrence is in a workflow file), so **every composite-action group is
skipped by this `continue` before a single `run:` body is examined**. A
`git fetch origin "$SHA" && git checkout "$SHA"` planted in
`.github/actions/verified-bundle` or `.github/actions/publication-contract` — which run inside
a job that *did* just check out ref-free, with that job's authority — passes this guard.

That is the precise route the story's interface-contract AC names ("no nested composite action
that re-checks-out") and that the test's own docstring claims to cover: *"Scope is every
governed definition on disk, so a checkout moved into a composite action is covered the moment
it exists."* That claim is true for the `ref:`-key guard above it (MEDIUM-1 does not apply
there) and false for this one.

**Evidence:** `tests/ci/support.py:736` `_governed_step_groups` appends `(name, "runs", steps)`
for non-`jobs` documents; grep for `actions/checkout` returns zero hits under `.github/actions/`.
The guard's `examined` counter is still non-zero (workflow jobs supply it), so the hole is
silent.

**Suggested fix:** scan composite-action step groups unconditionally — a composite action has no
checkout of its own precisely because it inherits the caller's working tree, which is what makes
re-pinning inside it dangerous.

## MEDIUM-3 — `recheck-head` still writes a freshness claim it can no longer substantiate

**File:** `/home/ravenwolf.org/sanderson/source/git/ravensorb/traefik/traefik-certificate-exporter/.github/workflows/dev.yaml:641`
**Severity:** Medium
**kind:** deletion (confidence: high)

**Problem:** This is *not* a re-litigation of the deliberate deletion — the removal of
`ref: github.event.repository.default_branch` and the empty-default-branch refusal is
documented in the step comment, in `docs/ci/ref-free-checkout-walkthrough.md` §"The second thing
that changed", and is being filed to the backlog. That handling is adequate for the design
decision itself.

What is not adequate is the residue. With the checkout now resolving to the run's own
`github.sha`, and `needs.plan.outputs.source-sha` being `plan`'s `git rev-parse HEAD` of an
equally ref-free checkout of the same run, `head_commit != SOURCE_SHA` is unreachable. The
step nonetheless still emits to the permanent run record:

```
Candidate `${SOURCE_SHA}` is still the default-branch head.
```

An operator or auditor reading `GITHUB_STEP_SUMMARY` after a `dev` alias move now sees an
explicit assertion of default-branch-head freshness that the pipeline no longer proves. The
story's observability dimension is about keeping the audit trail truthful; a tautology that
prints a strong claim is worse than a tautology that prints nothing. The step name
("Halt unless the candidate is still that head") carries the same problem.

Secondary, same root: `tests/ci/test_finalization.py:1242`
`test_a_stale_development_candidate_halts_without_moving_dev` still passes, because it drives
the step's `run:` body with a synthetic `SOURCE_SHA` that the workflow can no longer produce.
Its docstring — *"the head is proven again immediately before the alias moves"* — is now false
of the workflow, and the green test reads as coverage of a protection that was removed.

**Evidence:** `dev.yaml:636-653` (ref-free checkout followed by the comparison);
`dev.yaml` `plan` checkout at line 54 is likewise ref-free; the walkthrough explicitly concedes
"the comparison below it can no longer observe a superseding push". Test still green in the
run above.

**Suggested fix:** downgrade the summary line and the step name to what is still true
(defense-in-depth consistency check, not a freshness proof), and mark the behavioural test's
docstring/`xfail`-ish status so it does not advertise coverage of the removed guarantee. Both
belong with the backlog issue already being filed.

## LOW-4 — two narrow evasion gaps in `_repinning_arguments`

**File:** `/home/ravenwolf.org/sanderson/source/git/ravensorb/traefik/traefik-certificate-exporter/tests/ci/test_workflow_contracts.py:708`
**Severity:** Low
**kind:** claim

**Problem:** Two minor holes in the regex-based guard, both only reachable by a future author
who writes the command in a non-obvious spelling:

1. `REPINNING_COMMAND` anchors on `\bgit\s+(?:fetch|checkout|reset\s+--hard)`, so
   `git -C . checkout <sha>` and `git --git-dir=... fetch origin <sha>` are not matched.
2. The body is passed through `_uncommented()`. `tests/ci/support.py:138` documents the
   opposite convention in its own docstring — *"Prohibitions deliberately keep the raw body ...
   stripping there would weaken the rule rather than sharpen it."* This guard is a prohibition.

Neither is a live violation (no workflow contains any matching command in any spelling), and
the line-continuation case is safe by accident — the trailing `\` is itself reported as an
offending token. Flagged because the story's error-handling AC makes this test, not manual
review, the thing standing between the pipeline and a reintroduced re-pin.

**Evidence:** regex read directly; `_repinning_arguments("git -C . checkout deadbeef")`
returns `[]` by inspection of the pattern.

**Suggested fix:** allow optional `git` global options before the verb in the pattern, and drop
`_uncommented()` here to match the documented convention for prohibition guards.
