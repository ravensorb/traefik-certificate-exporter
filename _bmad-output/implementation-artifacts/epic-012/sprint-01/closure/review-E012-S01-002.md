## CRITICAL-1 — `condition = "AND"` does not confine the path allowlist in `gitleaks dir`; the new allowlist still exempts whole files by path

**File:** `.gitleaks.toml:43-58` (both `[[allowlists]]` entries), with
`tests/ci/test_gates.py::test_the_secret_scanner_exempts_no_path_from_content_scanning`
and `docs/adr/0033-secret-scanning-exempts-no-path.md` (Part 1, Decision) as the claims it
breaks.

**What is wrong.** The story's central thesis — "allowlist the value, never the directory",
enforced by requiring `condition = "AND"` on any allowlist carrying `paths` — does not hold
for `gitleaks dir`, which is the mode the `gitleaks` pre-commit hook (`entry: gitleaks dir
--redact --no-banner --config .gitleaks.toml .`) and therefore CI's only tree-content gate
actually runs. In `dir` mode the `paths` criterion exempts the whole file regardless of the
regex criterion.

**Evidence** (throwaway directory, repository's own `.gitleaks.toml`, repository's own
gitleaks binary `v8.30.1` from the pre-commit cache):

```
sub/api-testing-patterns.md  ==  TOKEN = "ghp_016C7e42F292c6912E7710c838347Ae178B4a"  <!-- gitleaks:allow -->
$ gitleaks dir --config <repo>/.gitleaks.toml .
INF no leaks found
```

A live-shaped GitHub PAT in a file whose path ends in `api-testing-patterns.md` is not
reported. The same content in `sub/other.md` is reported. Confirmed independently with a
deliberately impossible regex:

```
[[allowlists]]
condition = "AND"
paths = ['''api-testing-patterns\.md$''']
regexTarget = "secret"
regexes = ['''ZZZNEVERMATCH''']
```

`gitleaks dir` → `no leaks found`. An allowlist whose regex criterion cannot match anything
still exempts the file, so `condition = "AND"` is not what confines the exemption in this
mode.

**Why it matters.** This is the exact failure RT-008 / BL-E011-015 exists for, reintroduced
in a narrower but still open shape, while ADR-0033, `docs/developer.md` and spine CI-AR49
all state that no path is exempt. Two aggravating details:

- The path pattern `api-testing-patterns\.md$` is **unanchored**. It matches any path
  anywhere in the repository ending in that filename — including a new `src/.../api-testing-patterns.md`
  that any pull request can add. The ADR's own table presents it as "confined to the guide
  the findings came from"; it is not.
- `_bmad/_config/files-manifest\.csv$` is anchored, so its blast radius is one file, but it
  is exempt for *every* rule, not just the 64-hex digest column.

The CI self-proving probe cannot catch this: it plants at `_bmad/.scanner-probe/planted.py`,
which matches neither allowlist path, so it exercises the removal of the old `^_bmad/`
allowlist and nothing about the new ones.

`test_the_secret_scanner_exempts_no_path_from_content_scanning` does not prevent a path-only
allowlist returning — it only asserts that the TOML carries `regexes` and `condition`
alongside `paths`, which the probe above shows is not sufficient for the mode the gate runs
in.

**Suggested fix.** Do not rely on `condition = "AND"` to confine a `paths` allowlist. Either
(a) drop `paths` and express the exemptions purely as content constraints that gitleaks
honours in both modes, or (b) scope the allowlists under the specific `[[rules]]` entry
(`generic-api-key`) rather than globally, and in either case extend the `verify-build.yaml`
probe with a fourth leg: plant the same PAT at a path matched by each surviving allowlist
(e.g. `<tree>/probe/api-testing-patterns.md` and a copy of the manifest CSV path) and
require the scan to fail. A guard that asserts the TOML's shape cannot substitute for one
that observes the scanner's behaviour — the job already proves the scanner reads the tree;
it should prove the same about every allowlist it keeps.

## CRITICAL-2 — the new `.gitleaks.toml` makes `verify-build.yaml`'s history-scan step fail; the `gitleaks` job cannot pass

**File:** `.gitleaks.toml:43-58`; the failing step is
`.github/workflows/verify-build.yaml:195-200` ("Scan the repository history for
credentials").

**What is wrong.** The `api-testing-patterns.md` allowlist that works in `dir` mode does not
work in `git` mode, so the history scan the `gitleaks` job runs reports 18 leaks and the
step exits non-zero under `set -euo pipefail`.

**Evidence** (run in the worktree under review):

```
$ gitleaks git --redact --no-banner --config .gitleaks.toml .
INF 217 commits scanned.
WRN leaks found: 18
$ gitleaks git --redact --no-banner --config <(git show HEAD:.gitleaks.toml) .
INF 217 commits scanned.
INF no leaks found
```

All 18 are `generic-api-key` on `.../resources/knowledge/api-testing-patterns.md` in commit
`6bdb5167`, `Match: "expiredToken = '******'"`, `Secret: "******"` — i.e. exactly the class
the second allowlist is supposed to cover. Reproduced minimally in a throwaway git repo
containing only lines 680–700 of
`.agents/skills/bmad-tea/resources/knowledge/api-testing-patterns.md`: `gitleaks dir` →
clean, `gitleaks git` → 1 leak.

Narrowing probes show why: in `git` mode under `condition = "AND"`, the `regexes` criterion
is not evaluated against the secret or the line. With `paths` matching, `regexes = ['''.''']`
and `regexes = ['''api-testing''']` allowlist the finding, while `regexes = ['''\*{6}''']`,
`'''expiredToken'''`, `'''.*\*+.*'''` and `regexTarget = "secret"` / `"line"` / `"match"`
variants all fail to. The regex is effectively being matched against the file path, not the
content — the opposite of what the config, the ADR and the guard assume.

**Why it matters.** This is a hard CI break on the very gate the story strengthens, not a
latent risk: the step fails on every run of `verify-build.yaml` for the current repository
history. It also means the two scan modes disagree about the same config in opposite
directions (CRITICAL-1 is `dir` too permissive; this is `git` too strict), so neither mode's
result currently reflects the policy as written.

**Suggested fix.** Re-derive both allowlists against *both* invocations before merging
(`gitleaks dir` **and** `gitleaks git`), and add a guard or CI step that runs the history
scan against a known-clean expectation so a config change cannot pass review on the `dir`
result alone. If no single allowlist form satisfies both modes, a `commits = [...]` entry
naming the vendored-payload install commit, or a `[[rules.allowlists]]` scoped to
`generic-api-key`, are the two shapes worth testing next.

## MEDIUM-1 — `CREDENTIAL_ACTIONS_ON_MOVING_REFS = {}` and ADR-0031's "neither is handed a credential" overstate what was checked: `actions/download-artifact@v4` runs on a moving ref inside credential-holding jobs

**File:** `tests/ci/support.py:662-683` (`ACTIONS_ON_MOVING_REFS` comment and the empty
`CREDENTIAL_ACTIONS_ON_MOVING_REFS`), `docs/adr/0031-...md` decisions 3 and 4; the
underlying blind spot is `tests/ci/test_action_policy.py:196-209`
(`_definition_step_lists`) and `:259` (`if used and not used.startswith("./")`).

**What is wrong.** `actions/download-artifact@v4` is called from
`.github/actions/verified-bundle/action.yml:82`. That composite action is invoked by
`release.yaml`'s `attest` (holds `id-token: write` / `attestations: write`),
`publish-package-forge` and `publish-package-pypi` (hold `secrets.*` and `id-token: write`).
So a moving ref executes inside the most credentialed jobs in the repository.

The derivation cannot see it. `_definition_step_lists` gives a composite action
`permissions: {}` ("the caller is examined separately"), but the caller's step is
`uses: ./.github/actions/verified-bundle`, which `_credential_handling_actions` skips as a
local reference. Credential scope therefore never propagates into a composite action, and
`actions/download-artifact` is never a candidate.

**Why it matters.** ADR-0031 decision 4 explicitly counts *ambient* holders —
`actions/checkout`, `actions/attest-build-provenance`, `docker/setup-buildx-action`,
`docker/setup-qemu-action` — as credential-handling and pins them for that reason. By that
same standard `actions/download-artifact@v4` qualifies and is not pinned. The registry's
"this repository currently takes none of that risk" and ADR-0031's "Neither action is handed
a credential" are therefore claims the code does not support; `test_every_credential_handling_action_is_pinned_or_its_risk_is_recorded`
passes because of a gap in the derivation, not because the risk is absent. The *decision* to
hold the artifact pair at `@v4` is accepted and out of scope; the honesty of the record is
not.

**Suggested fix.** Either propagate the calling job's `permissions`/`secrets` into local
composite actions in `_credential_handling_actions` (resolve `uses: ./...` and inherit the
caller's ambient set), or amend the `ACTIONS_ON_MOVING_REFS` comment and ADR-0031 decision 3
to say plainly that `actions/download-artifact@v4` runs ambiently inside jobs holding
`id-token: write` and the forge/PyPI secrets, and that the derivation does not currently see
it.

## MEDIUM-2 — the `index_digest` fast path is never taken; the lock header, ADR-0032 and AD-09's remedy claim a cost saving the gates do not realise

**File:** `vendored-trees.lock:21-24` (`[index]` comment),
`scripts/vendored_trees.py:84-96` and `:259-276` (`main --check`),
`docs/adr/0032-...md` decision 3.

**What is wrong.** `main(["--check"])` computes `expected = render(PROJECT_ROOT,
DECLARED_TREES)` unconditionally, and `render` calls `scan()`, which SHA-256s all 2,391
files from disk. `test_the_vendored_lock_and_its_codeowners_caveat_regenerate_from_one_command`
calls that on every run of `tests/ci`, which is what the `workflow-policy` pre-commit hook
(`entry: poetry run pytest -q tests/ci`) runs on every commit, and what the `actionlint`,
`supply-chain` and `untracked-coverage` jobs each run in CI.

So the `[index]` fast path in `test_the_vendored_trees_match_the_repository_lock` saves one
of two full hash passes, in the same pytest session, every time. AD-09 / BL-E011-021's
complaint that "integrity gates hash ~4,700 files per commit" is unaddressed by this
mechanism.

**Why it matters.** Not a correctness hole — the fast path's reasoning about `git ls-files
-s` is sound, and the full `--check` pass is strictly stronger than the fast path (it reads
the working tree, so it also catches an unstaged edit the index digest cannot see). The
problem is that the lock, the ADR and the spine all state a property the implementation does
not have, in a file whose entire purpose is that its claims are checked.

**Suggested fix.** Either make `--check` take the same `[index]` fast path (compare
`index_digest` and the non-`[files]` header first, rehashing only on mismatch), or delete
the "keeps a routine commit cheap" claim from `vendored-trees.lock`'s `[index]` comment,
`scripts/vendored_trees.py`'s `index_digest` docstring and ADR-0032 decision 3, and say
instead that `[index]` is a mode/membership check.

## LOW-1 — `untracked-coverage`'s `::error::` annotation misattributes any `test_gates.py` failure

**File:** `.github/workflows/verify-build.yaml:355-361`.

The step runs the whole of `tests/ci/test_gates.py` but the annotation says "A file under
src/, tests/ or .github/ is untracked, so every file-scoped gate reported green without
reading it. Run 'git add' on the files named above." `test_gates.py` also holds the vendored

pre-commit-exclude guard; any of those failing produces this annotation. Note the vendored
guards are *also* run by `supply-chain` with their own correct annotation, so the same

**Suggested fix.** Scope the step to the guard it names (`-k "escapes_every_gate or
coverage_guard"`), or soften the annotation to point at the pytest output.

## LOW-2 — on a clean CI checkout the `untracked-coverage` job cannot fail for the reason it is named for

**File:** `.github/workflows/verify-build.yaml:341-361`.

`test_no_file_escapes_every_gate_by_never_having_been_added` reads `git status --porcelain`.
After `actions/checkout` the working tree is clean, so `blocking` is always empty and the
advisory list is always empty. The job is a real gate only because it happens to run the
rest of `test_gates.py` (LOW-1). The value of BL-E000-001's check is entirely in the
pre-commit path. Spine CI-AR50 and ADR-0033 Part 2 both describe `untracked-coverage` as
though it is the enforcement point and describe `-W always` as making "the list appear in
the job log" — in CI that list is always empty.

**Suggested fix.** Record in ADR-0033 Part 2 that the blocking/advisory split is enforced at
commit time and that the CI job is defence against a runner whose checkout is not clean, so
a later reader does not mistake a green job for evidence.

## LOW-3 — `_bmad/` is now declared vendored executable surface but has no CODEOWNERS ownership entry, and `vendored-trees.lock` is not in the owned-surfaces registry

**File:** `.github/CODEOWNERS:33-61` (generated block names `.agents, .claude, _bmad`;
ownership lines below cover only `/.agents/` and `/.claude/`), and
`tests/ci/test_meta.py:293-297` (`required` set in `test_the_authority_surfaces_are_owned`).

The generated prose ends "Refreshing the lock is therefore a reviewed act, and that review
is what this ownership entry exists for", immediately above ownership lines that do not
include `_bmad/`. In practice the review requirement still holds transitively, because any
change under `_bmad/` must also change the code-owned `/vendored-trees.lock` or fail
`test_the_vendored_trees_match_the_repository_lock` — so this is a record gap, not an open
hole. Separately, `test_the_authority_surfaces_are_owned`'s `required` set was not extended
with `/vendored-trees.lock` or `/scripts/vendored_trees.py`, so the two new ownership lines
ADR-0032 calls load-bearing are themselves unguarded and can be deleted silently.

**Suggested fix.** Add `/_bmad/ @ravensorb` beside the other two trees, and add
`/vendored-trees.lock` and `/scripts/vendored_trees.py` to `required` in
`test_the_authority_surfaces_are_owned`.

## What checks out

Mechanically confirmed, not assumed:

- Every `uses:` in all five workflows and both composite actions is either a 40-hex SHA with
  a matching `# vX.Y.Z` comment or the registered `actions/upload-artifact@v4` /
  `actions/download-artifact@v4` pair. `test_every_pinned_action_is_called_at_exactly_the_commit_it_was_reviewed_at`
  really is stronger than the shape check it replaces: it pins *which* commit, rejects a
  missing version comment, and fails on a registry entry no definition calls.
- `test_no_governed_definition_calls_an_action_on_a_moving_ref` handles the bare
  `uses: owner/action` case correctly (`rpartition` returns an empty separator, the code
  re-assigns `action, version = reference, ""`, and the empty version matches neither the
  SHA pattern nor the exception registry), satisfying the story's edge-case criterion.
- `supply-chain` and `untracked-coverage` are both in `distribution.needs`, so they do block
  the promotable artifact set; `distribution` lists all ten gate jobs.
- The gitleaks probe's three legs are the right directions: plant in-tree → must fail, plant
  in `_bmad/` → must fail (the inversion RT-008 required), clean tree → must pass. The
  planted token is a real `ghp_` shape the default ruleset detects, and both occurrences in  <!-- gitleaks:allow -->
  the workflow carry inline `gitleaks:allow`, so the workflow does not self-trip.
- `_unlinted_untracked_paths` returns the blocking/advisory split from inside the classifier,
  and the planted-repository test asserts both halves, so the downgrade is not a deletion of
  the finding. `LINTED_ROOTS` covers exactly the three roots the ACs name.
- The pre-commit-exclude derivation is genuinely reversed: `test_the_pre_commit_exclude_matches_the_declared_vendored_set`
  validates the regex against the lock in both directions (declared-but-not-excluded, and
  excluded-but-not-declared), so the brittle `re.fullmatch(r"\^\((?P<alternatives>.+)\)/")`
  dependency is gone.
- The lock's failure modes are sound: missing file → exit 1 "run --write"; stale text →
  exit 1; added/removed files named before any digest comparison; and the final
  `raise AssertionError` correctly covers "all digests match but `[index]` moved" (a mode or
  membership change).
- `scan()` hashes the working tree while `index_digest` reads the index, so the `--check`
  path catches an unstaged vendored edit that the `[index]` fast path alone would not.
- `SHA_PINNED_ACTIONS = frozenset(PINNED_ACTIONS)` keeps one authority for membership, and
  `_pinned_reference` removes the duplicate literal spellings in `test_finalization.py`,
  `test_image_publication.py` and `test_publication_contract.py`.
- `test_every_granted_privilege_points_at_a_decision` does cover `ACTIONS_ON_MOVING_REFS`
  (unioned at `test_meta.py:328`), so the new exception registry is ADR-backed as claimed.
- `test_the_vendored_integrity_guard_records_what_it_cannot_verify` now reads the counts from
  the lock and unwraps the comment block before matching, so it asserts the claim rather than
  the generator's line breaks; `2,391` / `142` / `2,249` in CODEOWNERS agree with the lock.
- The three accepted deviations are honestly recorded: the artifact-pair exception is in
  `ACTIONS_ON_MOVING_REFS` with ADR-0031 decision 3 and spine CI-AR47; the removal of the
  per-call-site `reviewed` comments is stated in ADR-0031 decision 2; CI-AR4's supersession
  is marked in the spine with its original text retained.
- `pytest -q tests/ci` shows no new failure attributable to this story.
