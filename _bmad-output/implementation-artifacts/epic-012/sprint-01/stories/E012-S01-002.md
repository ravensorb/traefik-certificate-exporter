## Acceptance Criteria

- The deferred finding BL-E011-013 is resolved: Vendored agent-instruction trees: 2,222 files verified against nothing (AI-poisoning foothold)
- The deferred finding BL-E011-014 is resolved: Third-party GitHub Actions pinned to mutable tags in publish jobs holding secrets
- The deferred finding BL-E011-015 is resolved: Secret scanner excludes the vendored trees, leaving an uncovered commit path for credentials
- The deferred finding BL-E011-020 is resolved: Untracked-file gate fails on any scratch file, incentivising git add of unintended files
- The deferred finding BL-E011-021 is resolved: Vendored-integrity gates hash ~4,700 files per commit and assert hand-maintained counts

## Business acceptance criteria

### Outcome

- CI maintainers can tell which trees are vendored, and verify that set, by reading an
  explicit, named manifest (`vendored-trees.lock`) instead of reverse-engineering intent
  from regex patterns — a reviewer can answer "is tree X vendored and accounted for?"
  without reading gate script internals.
- A contributor adding a third-party GitHub Action to any workflow gets an immediate,
  explicit CI failure if they reference it by a floating tag instead of a commit SHA, so a
  supply-chain-compromised action tag cannot silently execute in a workflow holding secrets.
- A secret accidentally committed anywhere in a vendored tree is now caught by the
  secret scanner, closing a previously uncovered credential-leak path, while vendored
  trees remain excluded from lint (so this does not reintroduce lint noise on
  non-project-owned content).
- A contributor who leaves a genuinely scratch/untracked file outside `src/`, `tests/`, or
  `.github/` sees a non-blocking warning instead of a hard CI failure, while untracked
  files inside those three directories still hard-fail the gate as before.
  Spec: none — l3io-plan run, no spec index bound

### Non-goals

- This story does not change what content is vendored, or remove any vendored tree; it
  only changes how the vendored set is declared, verified, and scanned.
- This story does not implement the docker-socket-proxy pattern itself (that documentation
  lives in Story E012-S01-001); it only documents the vendored-tree/CODEOWNERS/secret-scan
  changes described here.
- This story does not relax lint exclusions for vendored trees — lint stays excluded; only
  the secret-scanner exclusion is removed.
- This story does not retroactively audit the history of previously-committed vendored
  content for secrets already merged before this story; it closes the gap going forward.

## Technical acceptance criteria

Files this story adds or changes, and the conventions their siblings establish:
- A new `vendored-trees.lock` manifest at the repository root (or alongside existing CI
  config, matching wherever `CODEOWNERS` and CI gate config already live) — no existing
  sibling lock file of this kind exists in this repo, so its format is newly established
  by this story; it should follow the same plain-text, git-diffable convention as
  `poetry.lock` (already present, already a precedent for a generated-but-committed lock
  file in this repo).
- `.github/workflows/verify-build.yaml` — the action-pinning gate and untracked-file gate
  land here as new jobs alongside the existing channel-agnostic governance jobs
  (`gitleaks`, `actionlint`, `file-hygiene`, `source-integrity`) — per ADR-0029, not in
  `ci.yaml`/`dev.yaml`/`release.yaml`, since those three files are thin per-channel callers
  into this one reusable file once Story E012-S01-003 lands (CI-AR45). New gate steps
  should follow the existing job/step naming convention already used by sibling
  `verify-*`/`*-gate` jobs in this file. Gate script location follows whatever convention
  `tests/ci/test_action_governance.py` and `tests/ci/test_action_policy.py` (existing
  CI-contract test modules) already assume.
- `CODEOWNERS` — range-based count assertions already reference vendored trees by name;
  this story changes the assertion mechanism (named tuple against `vendored-trees.lock`)
  but keeps `CODEOWNERS` itself in its existing location and format.

### Interface contracts

- `vendored-trees.lock`: module input is the output of `git ls-files -s` over the
  repository, cached; its output/contract is an explicit, named list (tuple) of vendored
  tree paths that CODEOWNERS enforcement and the vendored-integrity gate both consume by
  name, replacing the current regex-based reverse-engineering. Consumers (CI gate scripts,
  CODEOWNERS enforcement) read this file as the single source of truth for "what counts as
  vendored."
- The action-SHA-pin gate: input is every `uses:` reference under `.github/workflows/*.yaml`
  with a floating-tag pattern (`@v?\d`); output is a CI failure listing each offending
  `uses:` line and workflow file, consumed as a required status check the same way existing
  gates in `ci.yaml` already are.
- The untracked-file gate: input is `git status --porcelain` (or equivalent) scoped by
  directory; output is a hard failure for untracked paths under `src/`, `tests/`, or
  `.github/`, and a non-blocking warning (not a failure) for untracked paths elsewhere —
  same gate, new directory-scoped severity branching, no new CLI/API surface.
  Spec: none — l3io-plan run, no spec index bound

### Error and edge case handling

- `vendored-trees.lock` cache: a stale or missing lock file causes the gate to fail closed
  (treat as "no vendored trees declared," which then fails the count assertion loudly)
  rather than silently passing with zero vendored trees.
- Action-SHA-pin gate: an action referenced with no version qualifier at all (bare
  `uses: org/action` with no `@`) is also flagged, not just floating-tag references, since
  it is equally unpinned.
- Secret scanner over vendored trees: a false-positive secret match inside a vendored tree
  is handled via the scanner's existing allowlist/suppression mechanism, not by
  re-excluding the tree wholesale.
- Untracked-file gate: a directory rename or move that temporarily shows as untracked
  during a multi-commit PR is still scoped by the same `src/`/`tests/`/`.github/` rule —
  no special-casing for in-flight renames.
  Spec: none — l3io-plan run, no spec index bound

### Observability requirements

- The action-SHA-pin gate failure output names every offending workflow file, step, and
  `uses:` reference, not just a pass/fail summary, so a contributor can fix it without
  re-running CI to find the location.
- The vendored-integrity gate failure output states both the expected tuple (from
  `vendored-trees.lock`) and what was actually found, so a maintainer can tell at a glance
  whether a tree was added, removed, or miscounted.
- The untracked-file gate's downgraded (non-`src`/`tests`/`.github`) warning path still
  surfaces in CI job output (not silently swallowed), consistent with "warning" meaning
  visible-but-non-blocking rather than invisible.
  Spec: none — l3io-plan run, no spec index bound

### Security considerations

- SHA-pinning every third-party action closes the specific supply-chain risk named in
  BL-E011-014: a compromised or re-tagged action version executing inside a workflow that
  holds secrets. This is the primary security-relevant change in this story.
- Removing the secret-scanner's vendored-tree exclusion directly closes an uncovered
  credential-leak path (BL-E011-015); the lint exclusion is deliberately left in place
  since lint findings in third-party content are not a credential-exposure risk.
- The untracked-file gate's directory-scoped severity change is a usability fix, not a
  security control weakening: `src/`, `tests/`, and `.github/` are exactly the trees where
  an unintended untracked file could become unreviewed code or workflow content, so the
  hard-fail scope is unchanged for the security-relevant paths.
  Spec: none — l3io-plan run, no spec index bound

### Testability approach

- New/changed gate behavior is covered by the existing CI-contract test modules under
  `tests/ci/` (e.g. `test_action_governance.py`, `test_action_policy.py`), following their
  existing naming and fixture conventions (see `tests/ci/support.py` for shared helpers)
  rather than introducing a new, differently-structured test module.
- `vendored-trees.lock` generation/caching is verified by a test asserting its content
  matches a fresh `git ls-files -s` computation, named consistently with sibling
  `tests/ci/test_*.py` modules.
- Before any `apply`/merge, the gate changes are exercised via the project's existing
  `act`-based local verification path (`docker/act-build.sh`), not a separate new local
  runner.
  Spec: none — l3io-plan run, no spec index bound

### Existing-library check

- `git ls-files -s` is the existing, standard git plumbing command for this; no new
  dependency is needed to enumerate tracked files for the lock manifest.
- Action SHA-pin enforcement: no third-party GitHub Action in the marketplace is adopted
  for this (e.g. `zgosalvez/github-actions-ensure-sha-pinned-actions` was considered
  implicitly by the backlog item's framing) is ruled in or out here; a regex-based CI gate
  script is warranted given this repo's existing pattern of hand-written `tests/ci/`
  contract checks rather than marketplace actions for governance.
  N/A — no specific marketplace action was pre-approved by prior design discussion; the
  implementer should prefer an existing, already-used secret scanner/governance tool over
  writing new scanning logic where one already covers this.
  Spec: none — l3io-plan run, no spec index bound
