# Publish Stable Packages and Immutable Images

As a package or container user,
I want stable Python and multi-architecture image artifacts promoted from the verified set,
So that every enabled registry exposes byte- or digest-identical release content.

Depends on: `E008-S01-003`.

## Acceptance Criteria

**Given** `PUBLISH_PACKAGE_PYPI` is false or absent
**When** stable publication runs
**Then** no `pypi` environment, OIDC token, API token, PyPI endpoint, or package-publish action is used
**And** the mandatory forge Release can still receive the distribution files later

**Given** PyPI publication is enabled and preflight plus verification succeed
**When** the publisher starts
**Then** it downloads `verified-dist-v1` from the same workflow run and validates canonical layout, `SHA256SUMS`, manifest schema/hash, source SHA, and version before requesting OIDC

**Given** GitHub trusted publishing is configured
**When** upload occurs
**Then** only the top-level protected `pypi` job receives `id-token: write`
**And** `pypa/gh-action-pypi-publish@release/v1` uploads exactly the manifest-recorded wheel and sdist

**Given** the artifact is ready for upload
**When** the stable equality gate runs
**Then** tag without `v`, committed Poetry version, wheel `METADATA`, clean installed runtime version, and planned version are exactly equal
**And** a mismatch prevents OIDC issuance and upload

**Given** the stable version is absent from PyPI
**When** upload and read-back verification succeed
**Then** PyPI reports the expected filenames and SHA-256 hashes
**And** no file is rebuilt, renamed, or recovered from another package index

**Given** the stable version already exists on rerun
**When** remote identity is checked
**Then** exact filename/hash matches are accepted as complete
**And** any mismatch, unverified object, or replacement requirement fails without deletion or upload-overwrite (CI-AR26)

**Given** both stable image toggles are false or absent
**When** stable publication runs
**Then** no registry login, remote image build, push, manifest verification, or OCI alias job executes

**Given** Docker Hub, GHCR, or both are enabled
**When** the immutable image publisher starts
**Then** it validates the stable plan, distribution checksums, build-manifest hash/fingerprint, exact wheel, version, and source SHA before registry authentication
**And** Docker Hub uses its repository-scoped credentials while GHCR uses only a `packages: write` job token

**Given** immutable names are passed to LiquidLogicLabs Docker metadata and Bake
**When** image construction begins
**Then** a single Bake invocation uses the shared target and exact verified wheel
**And** pushes only `M.m.p` to every enabled registry
**And** does not include `M.m`, `M`, or `latest` in the build operation (CI-AR23)

**Given** the build targets `linux/amd64` and `linux/arm64`
**When** BuildKit completes
**Then** one multi-platform manifest is produced from the recorded plan
**And** SBOM and `mode=max` provenance attestations are attached
**And** no credential enters build arguments, cache, logs, SBOM, or provenance (CI-AR13, CI-AR28)

**Given** each enabled remote immutable name
**When** post-push verification runs
**Then** its manifest is resolved by digest, each declared platform is pulled by digest, and native/QEMU tests validate entrypoint, s6 startup, CLI behavior, runtime version, version label, and full revision label
**And** all results match the tag, wheel, build manifest, and publication plan

**Given** the same exact image tag already exists on rerun
**When** its manifest and platform identities are checked
**Then** matching digests and labels are reused
**And** any mismatch fails without overwrite, deletion, retag, or rebuild (CI-AR26)

**Given** any enabled registry or platform fails publication or validation
**When** forge Release and alias dependencies are evaluated
**Then** neither the forge Release nor any mutable OCI or Git alias advances (CI-AR25)

**Given** immutable publication is in flight
**When** a second event or dispatch supersedes the run
**Then** every immutable publication job runs in a non-cancellable concurrency group, so no package upload or image push is interrupted midway
**And** a publication run cancelled mid-publish is precisely how a half-published artifact set arises — some registries written, others not, and no receipt to say which

**Given** immutable publication and alias finalization both need protection from cancellation
**When** their concurrency groups are compared
**Then** they are two separate non-cancellable groups, never one
**And** immutable publication serializes only against another run of the same release identity, while alias finalization is a single-writer lock across every stable run (CI-AR27)

## Technical Acceptance Criteria

### Interface contracts

**Given** the publisher half of `release.yaml`
**When** its job graph is inspected
**Then** it adds `publish-pypi` and `publish-images`, both `needs: [plan, preflight, verify]`, and `verify-images` (`needs: publish-images`)
**And** the finalizer of `E008-S01-005` declares `needs: [publish-pypi, verify-images]` so a failed or skipped-because-disabled publisher is distinguished: `if: always() && !cancelled() && needs.publish-pypi.result != 'failure' && needs.verify-images.result != 'failure'`
**And** a bare `needs:` without that guard would make a disabled destination block the mandatory Release, which contradicts the first acceptance criterion

**Given** `publish-pypi` runs
**When** its interface is inspected
**Then** it declares `permissions: { contents: read, id-token: write }` at job scope only and `environment: pypi`
**And** `environment: pypi` and `environment: testpypi` are distinct protected environments; the same name is never reused across channels
**And** it downloads `verified-dist-v1` with `actions/download-artifact@v4`, revalidates it, runs the equality gate, and only then invokes `pypa/gh-action-pypi-publish@release/v1`
**And** it never runs `poetry build`, `poetry publish`, or any command that could produce a distribution: ARCHITECTURE-SPINE.md forbids publishers rebuilding the Python package, and the deleted legacy publishers violated exactly that (BL-E007-020)

**Given** the stable equality gate
**When** it runs inside `publish-pypi`, before the publish step
**Then** it asserts five values are string-equal: the tag without `v`, the committed Poetry version from the checkout, the wheel `METADATA` `Version` field read from the downloaded wheel, the version reported by an installation of that wheel into a clean virtual environment, and `publication-plan-v1.json`'s `package_version`
**And** it is a distinct step preceding the publish step, so a mismatch fails before the OIDC exchange rather than after it

**Given** `publish-images` runs
**When** its interface is inspected
**Then** it is structurally the same job as `E008-S01-002`'s image publisher with a different tag set: one `docker/bake-action@v7` invocation over `docker-bake.hcl`, `PLATFORMS` `["linux/amd64","linux/arm64"]`, `OUTPUTS` `["type=registry"]`, `ATTESTATIONS` `["type=sbom","type=provenance,mode=max"]`
**And** `TAGS` is built solely from the plan's `tags.immutable`, which for this channel is exactly `["M.m.p"]` per enabled registry
**And** `tags.aliases` is never read by this job

**Given** `publish-pypi` and `publish-images` are the immutable publishers
**When** their concurrency is inspected
**Then** each declares its own job-level `concurrency` block with `cancel-in-progress: false`, grouped per destination and release identity — `stable-immutable-pypi-${{ needs.plan.outputs.package-version }}` and `stable-immutable-images-${{ needs.plan.outputs.package-version }}`
**And** the two publishers take different groups deliberately: one shared group would serialize them against each other inside a single run and halve the fan-out for no safety gain, since they mutate disjoint destinations
**And** neither group is `E008-S01-005`'s `stable-release-finalization`: merging publication into the alias lock would make every release queue behind every other release's alias writes, and would extend a lock held for alias mutation across a multi-minute image push
**And** `release.yaml`'s workflow-level `${{ github.workflow }}-${{ github.ref }}` group from `E008-S01-003` is necessary but not sufficient here — it is already `cancel-in-progress: false`, but it is scoped to one ref, so it does not serialize a `workflow_dispatch` rerun against the tag-push run for the same version

**Given** `verify-images` runs
**When** its interface is inspected
**Then** it emits a non-secret JSON array of `{registry, repository, digest, platforms}` and holds no registry write capability
**And** the finalizer consumes that array as the only source of the digests it will alias

### Data model

**Given** the shared publisher shape between development and stable
**When** the two workflows are compared
**Then** the duplication between `dev.yaml`'s and `release.yaml`'s image publisher is deliberate and must not be resolved by a shared reusable workflow: AD-1 states publication jobs live in the top-level workflows so environment protection, OIDC and forge credentials do not cross the reusable-workflow boundary
**And** what is shared instead is `docker-bake.hcl`, the publication plan and the publication-contract action — data and contracts, not a workflow

**Given** `publication-plan-v1.json`
**When** the publishers consume it
**Then** no schema change is required beyond `E008-S01-003`'s stable additions
**And** no publisher derives a registry, repository, tag or endpoint from anything except the plan

**Given** `release-receipt-v1.json`
**When** this story runs
**Then** the receipt is authored by `E008-S01-006`; this story's obligation is to emit, as job outputs, the per-destination facts the receipt will need: remote filenames and hashes for the package, and registry/repository/digest/platforms for each image

### Error handling and edge cases

**Given** the stable version already exists on PyPI
**When** the publisher reconciles it
**Then** it queries the index for the version's file list and hashes before uploading, and a full match short-circuits with success and no upload
**And** `--skip-existing` style behaviour is prohibited on its own: skipping without comparing hashes accepts a different artifact under the same name, which is precisely the failure CI-AR26 exists to prevent
**And** a partial remote set (wheel present, sdist absent) is uploaded only for the missing file, and only when the index permits adding a file to an existing release

**Given** PyPI is disabled but the image toggles are enabled
**When** the run executes
**Then** `publish-pypi` is skipped, the mandatory Release still proceeds and still receives the wheel, sdist and `SHA256SUMS` as assets from `verified-dist-v1`
**And** this is why the Release's assets come from the verified artifact rather than from the package index

**Given** an immutable `M.m.p` image tag already exists
**When** reconciliation runs
**Then** the existing manifest is resolved by digest and its platform set, version label and revision label are compared to the plan and build manifest
**And** an exact match reuses it; any mismatch fails without overwrite, delete, retag, or rebuild

**Given** one enabled registry succeeds and another fails inside the single Bake invocation
**When** the job ends
**Then** the job fails, the successfully pushed immutable object is left in place (it is immutable and identity-matched, so it is not garbage), and no alias or Release advances
**And** a same-tag rerun reuses the pushed object and completes the missing one

**Given** a maintainer cancels the run while `publish-images` is pushing
**When** the cancellation lands
**Then** `cancel-in-progress: false` does not stop it: the setting prevents supersession-driven cancellation only, so a half-pushed set remains possible and is reconciled by identity on the next same-tag run (`E008-S01-006`)
**And** no publisher may add `continue-on-error`, a cleanup trap, or a "finish quickly" path on cancel — an upload completed under a cancellation signal is indistinguishable in the log from one that completed normally

**Given** a platform smoke test fails under QEMU
**When** the failure is classified
**Then** it is a hard failure, not a warning: no `continue-on-error` may appear on any publication, version check, smoke test, digest check or release step in this workflow

### Observability

**Given** `publish-pypi` completes
**When** its log is read
**Then** it records the five values compared by the equality gate, the endpoint host, each uploaded filename with its manifest SHA-256, and the outcome as `uploaded` or `already-present-identity-matched`
**And** it never logs the OIDC token, its length, or any hash derived from it

**Given** `verify-images` completes
**When** its evidence is read
**Then** each `{registry, platform}` pair reports independently: digest pulled, entrypoint observed, s6 service state, installed runtime version, and both OCI labels read back
**And** the manifest-list digest per registry is printed so the finalizer's inputs are auditable from the log alone

**Given** an operator needs to trace a published artifact back to its run
**When** correlation is followed
**Then** the path is `publication-plan-v1.json`'s `run` object (run id, run attempt, repository, server URL) plus `org.opencontainers.image.revision` on the image and the `source_sha` in the build manifest
**And** the build manifest still carries no run identity, preserving its byte-determinism

### Security

**Given** trusted publishing is the GitHub credential model for PyPI
**When** `publish-pypi` authenticates
**Then** `id-token: write` exists on that one job only, never at workflow scope, and never on `verify`, `plan`, `preflight` or any image job
**And** a long-lived `PYPI_API_TOKEN` is not introduced for the GitHub-hosted path; it is reserved for Epic 9's Gitea host

**Given** Docker Hub is enabled
**When** its credentials are mapped
**Then** `DOCKERHUB_USERNAME` and a repository-scoped `DOCKERHUB_TOKEN` appear only in the `docker/login-action@v4` step whose `if:` enables Docker Hub
**And** GHCR uses the automatic job token with `packages: write` and no stored secret at all

**Given** the SBOM and provenance attestations
**When** they are inspected
**Then** they contain no credential material, and no `secrets.*` expression reaches a Bake variable, a build argument, or a cache key
**And** the wheel enters the build as a bind-mounted file with a caller-supplied SHA-256 (ADR-0008), so no index credential is needed inside the build at all

**Given** the repository-write guards
**When** they run against `release.yaml` after this story
**Then** no job introduced here declares `contents: write`, runs `git push`, runs a `gh release` command, or uses a release-creating action
**And** `RELEASE_FINALIZER_JOBS` is still empty at the end of this story

### Testability

**Given** the no-rebuild guard
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts that no job holding `id-token: write`, `packages: write` or a registry login runs `poetry build`, `poetry publish`, `python -m build`, or `twine upload`
**And** the planted violation adds a `poetry build` step to `publish-pypi`; the guard must fail on it, because that is exactly the shape BL-E007-020 recorded in the deleted publishers

**Given** the equality-gate guard
**When** it is added
**Then** it asserts that in every job invoking `pypa/gh-action-pypi-publish@`, a step comparing the five version values precedes the publish step in the step list
**And** the planted violation reorders the publish step above the gate; the guard must fail on ordering alone, since a gate that runs after the upload gates nothing

**Given** the alias-not-in-build guard from `E008-S01-002`
**When** it is applied to the stable channel
**Then** it additionally asserts that `latest`, a bare major, and a `M.m` form never appear in any `TAGS` assignment
**And** the planted violation appends `:latest` to the stable bake tag list

**Given** the environment-separation guard
**When** it is added
**Then** it asserts that no job declares `environment: pypi` and `environment: testpypi` interchangeably, and that a `dev`-channel workflow never names the `pypi` environment
**And** the planted violation points `dev.yaml`'s publisher at `environment: pypi`

**Given** the non-cancellable-publisher guard
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts that every job that uploads a package or pushes an image declares a `concurrency` block whose `cancel-in-progress` is literally `false`, with the job set derived from the parsed workflows — every job whose steps invoke `pypa/gh-action-pypi-publish@`, `docker/bake-action@` or `imagetools create` — rather than from a hand-listed set of job names
**And** the planted violation sets `cancel-in-progress: true` on `publish-images`; the guard must fail on it
**And** a second planted violation gives `publish-images` the finalizer's `stable-release-finalization` group, which is non-cancellable and would pass a `cancel-in-progress`-only check; the guard must fail on the group collision too, asserting that no publisher shares a group with a job registered in `RELEASE_FINALIZER_JOBS`
**And** a third planted violation adds a new publisher job with no `concurrency` block at all; the guard must fail on the absent block, since inheriting the workflow-level group is not the same as declaring a publication group

**Given** the remote-identity reconciliation logic
**When** it is unit tested in `tests/ci/test_publication_contract.py`
**Then** cases cover: absent remote, full identity match, hash mismatch, filename present with unreadable hash, and partial file set
**And** the planted violation treats "index reports the version exists" as success without comparing hashes; the mismatch case must then pass and the test must catch it

## Open questions

1. **How does the finalizer distinguish "publisher disabled" from "publisher failed"?** GitHub's `needs:` treats a skipped dependency as not-satisfied unless `always()` is used, and `always()` also runs after cancellation. This story specifies `always() && !cancelled() && result != 'failure'`, which is correct but subtle enough to deserve its own guard. If a cleaner shape is preferred — for example a `publication-summary` job that fans in and emits one status — that decision belongs here, not to the implementer at 2am.
2. **Does the equality gate's "clean installed runtime version" duplicate the verifier?** `verify-build.yaml` already installs the wheel into a clean venv and compares versions on the `stable` channel. Re-running it in the publisher costs a minute and defends against artifact substitution between jobs; the alternative is to trust the artifact hash, which is already checked. This story keeps the install because the epic asks for it explicitly; if the maintainer prefers hash-only, the AC needs amending rather than quietly under-implementing.
3. **Is a per-registry retry acceptable when one registry in a multi-target Bake push fails?** "Build once" is an invariant; retrying the push for one name without rebuilding is arguably still one build. This story assumes the whole job fails and a rerun reconciles, which is simpler and provably safe, but slower.
4. **Is forge package publication deliberately removed?** `docs/ci/codex-assesment.md`'s appendix records this as an unreconciled divergence, and it lands on this story. The condensed assessment states that forge package publication is removed, leaving only TestPyPI for development and PyPI for stable; a surviving fragment of the original assessment, and the elaborated Epic 8 stories, both have the owning forge's native package registry always published on Gitea. As written, this story takes the condensed position by omission: the only stable package destination is PyPI, and the forge receives the wheel, sdist and `SHA256SUMS` as Release assets in `E008-S01-005`, not as package-registry uploads. Recorded rather than resolved, because either answer is material scope and neither is the implementer's to pick: if the forge package registry stays, this story needs a third package destination with its own toggle, preflight entry, plan `package_targets` entry, reconciliation case and receipt entry, and `E008-S01-001` needs the development-channel equivalent; if the removal is deliberate, the epic text and the assessment line need the same edit so a later reader does not restore it. Epic 9 is where a Gitea-hosted run would exercise it, so the answer is needed before Epic 9 is planned, not before this story is implemented.
