# Cut Over the Workflow Topology and Document Failed-Jobs-Only Recovery

As an operator, I want one production topology and a safe recovery procedure, so obsolete paths
cannot race delivery and successful immutable uploads are not repeated.

Depends on: `E008-S01-003`.

## Acceptance Criteria

**Given** green staging runs, **when** cutover completes, **then** `ci.yaml`, `dev.yaml`,
`release.yaml`, and `verify-build.yaml` are the only pipeline workflows; each event has one owner;
and every local workflow/action reference resolves.

**Given** one destination fails after another succeeds, **when** the operator follows the
runbook, **then** only failed jobs are rerun against retained verifier evidence. Successful
immutable package uploads are not repeated and aliases remain blocked until all required jobs
succeed (CI-AR38).

**Given** failed-jobs-only rerun is unsupported, evidence expired, or a remote immutable identity
conflicts, **when** recovery is evaluated, **then** the run halts and escalates; development uses a
new version where appropriate. The runbook never presents whole-workflow rerun, force update,
deletion, or overwrite as normal recovery.

**The detector is the destination action's own failure** -- pypa's action rejects a duplicate, a
registry rejects an immutable tag -- **never a pre-upload existence query**. "Check whether this
version already exists before uploading" is retired CI-AR26 under a new name, and a guard rejects
it (`test_no_publisher_queries_a_destination_before_uploading`). Inspecting what you have just
published is a different thing and is required; the guard scopes to steps preceding the upload.

## Files in scope

- `.github/workflows/` (`ci.yaml`, `dev.yaml`, `release.yaml`, `verify-build.yaml`)
- `docs/operational.md`
- `tests/ci/test_workflow_contracts.py`

## Definition of Done

- Operator guidance records exact GitHub and supported Gitea failed-jobs-only procedures.
- Run summaries expose source/tag, version, artifact hashes, image digest/platforms, destination
  conclusions, Release URL, and alias outcomes (CI-AR41).
- Governance tests prove exact topology, trigger exclusivity, verifier-before-publisher ordering,
  action version policy, and no dangling references.
- Staging evidence includes dev, stable, a destination-local failure, failed-jobs-only rerun, and
  aliases-last results before approval.

## Test anchors

Guard, then the violation planted to prove it fires:

- Exact topology: the workflow set is globbed from disk and must equal those four names; plant a
  fifth workflow file, and a rename (scope attack).
- Trigger exclusivity: event and ref-filter pairs parsed from `on:` are unique across workflows;
  plant a push trigger on `release.yaml`.
- Verifier before publisher: every credential-bearing job sits in the verifier's transitive
  `needs`; plant a publisher outside it.
- No dangling references: local `uses:` targets resolve on disk and owners stay inside the
  approved set; plant a missing path, and an unapproved owner.
- Runbook: the recovery section names whole-workflow rerun, force, and delete only as prohibited;
  plant a "rerun all jobs" instruction.

## Out of Scope

- Production Gitea migration, which requires Epic 9 certification.

## Prep finding P2 — the exact topology is five workflow files, not four

Story 001 creates `.github/workflows/publish-image.yaml` as reusable shared surface (gate finding
F8), so this story's topology AC and its "plant a fifth workflow file" anchor would reject story
001's own design. Reconciled here, since this story owns the topology assertion:

The expected set is `ci.yaml`, `dev.yaml`, `release.yaml`, `verify-build.yaml` **and**
`publish-image.yaml`. The meaningful distinction is not the count but the trigger surface:
`verify-build.yaml` and `publish-image.yaml` are **reusable-only** — `workflow_call` and no event
trigger of their own — while the other three each own a disjoint set of events. Assert that
property, derived from each file's parsed `on:` block, rather than a hand-kept name list; a name
list is exactly the hand-enumerated scope that global rule 4 forbids, and it would have to be
edited again by E009.

Trigger exclusivity is unaffected: a reusable-only workflow contributes no event/ref pair, so the
uniqueness check still holds and still catches a `push` trigger added to `release.yaml`.

**Test anchors, revised:** plant a sixth workflow file carrying its own event trigger (must fail);
plant an event trigger added to `publish-image.yaml`, turning a reusable workflow into a second
owner of that event (must fail — this is the scope attack, and a name-list assertion would miss
it entirely); plant a rename.
