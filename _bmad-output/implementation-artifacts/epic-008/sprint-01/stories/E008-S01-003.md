# Validate, Plan, and Preflight a Stable Release

As a release maintainer,
I want exact tags classified, structurally validated, and resolved into a fail-closed destination plan,
So that only one deliberate release identity can authorize stable publication.

Depends on: `E008-S01-001`, `E008-S01-002`.

## Acceptance Criteria

**Given** `.github/workflows/release.yaml` uses the portable `v*` tag trigger
**When** a tag event starts
**Then** the publication-contract action is the sole classifier and emits exactly `exact`, `alias`, or `invalid`
**And** all downstream conditions use that output rather than another regular expression (CI-AR3)

**Given** the event ref is `vMAJOR` or `vMAJOR.MINOR`
**When** classification runs
**Then** it returns `alias`
**And** the workflow completes successfully before verification, credential mapping, checkout with write access, publication, or Release creation

**Given** the event ref is malformed, prerelease-shaped, metadata-suffixed, incomplete, or otherwise not strict `vMAJOR.MINOR.PATCH`
**When** classification runs
**Then** it returns `invalid` and the workflow fails before credentials or publication

**Given** classification returns `exact`
**When** Git-object validation runs against full history
**Then** `git cat-file -t refs/tags/<tag>` returns `tag`
**And** the tag's peeled commit equals the workflow event SHA
**And** a lightweight tag is rejected (CI-AR4)

**Given** an annotated exact tag points to a commit
**When** ancestry and version checks run
**Then** the commit is required to be an ancestor of the fetched remote default branch
**And** the tag without `v` equals the committed Poetry version
**And** either mismatch fails before the verifier or any publisher receives credentials

**Given** the exact tag passes local structural checks
**When** semantic validation runs
**Then** `LiquidLogicLabs/git-action-tag-validate-version@v2` validates the same exact tag contract
**And** no CI job creates, replaces, or retargets the exact release tag

**Given** `release.yaml` reaches verification
**When** it calls `verify-build.yaml`
**Then** the call is job-level, same-run, channel `stable`, and uses the validated version and peeled source SHA
**And** the resulting wheel metadata and installed runtime must equal the tag and committed Poetry version before publication (CI-AR14)

**Given** exact-tag validation succeeds
**When** the non-secret stable planning job runs
**Then** it derives GitHub.com as the current owning forge from runner context
**And** resolves repository owner/name, GHCR coordinates, optional Docker Hub coordinates, package endpoints, version, source SHA, credential modes, and workflow identity without an operator-maintained forge switch (CI-AR1)

**Given** stable toggles are normalized
**When** destination policy is applied
**Then** `PUBLISH_PACKAGE_PYPI` controls public PyPI, `PUBLISH_IMAGE_DOCKERHUB` controls Docker Hub, and `PUBLISH_IMAGE_FORGE` controls GHCR
**And** `PUBLISH_PACKAGE_TESTPYPI` cannot enable a stable destination
**And** the owning forge's native package registry is controlled by nothing: it is published on every stable release, exactly as the owning-forge Release is (maintainer decision, `docs/ci/codex-assesment.md`, "Divergences resolved (2026-09-01)")
**And** the owning-forge Release remains mandatory regardless of toggle values (CI-AR19, CI-AR20)

**Given** stable version `M.m.p`
**When** image tags are planned
**Then** immutable OCI identity is `M.m.p` without `v`
**And** aliases are `M.m`, `latest`, and `M` only when `M >= 1`
**And** Git alias candidates are `vM` and `vM.m`, including for `0.x.y` releases (CI-AR18, CI-AR22)

**Given** all coordinates and destinations are resolved
**When** the publication-contract action writes `publication-plan-v1.json`
**Then** the plan is schema-valid, contains every mandatory and toggle-enabled destination and tag, includes no secret, and is the only downstream source for coordinates and identities (CI-AR21)

**Given** the plan enables only the mandatory GitHub Release
**When** aggregate preflight runs
**Then** it validates repository/tag permissions, the Release credential mode, and the always-on forge package destination's coordinates and credential mode
**And** it performs no PyPI, Docker Hub, or GHCR authentication
**And** "only the mandatory GitHub Release" therefore means only the mandatory destinations: the forge package registry is one of them, and a preflight that iterates toggle-enabled destinations alone would never evaluate it

**Given** PyPI or an image registry is enabled
**When** aggregate preflight runs
**Then** it validates every required endpoint, namespace, protected environment or token pair, job-permission expectation, repository existence/access contract, and CA requirement before any publisher logs in or uploads
**And** one failed destination blocks all stable mutation (CI-AR24)

**Given** preflight succeeds
**When** stable mutation jobs are evaluated
**Then** the only aggregate output is `publication-ready=true`
**And** every mutation job requires planning, preflight, and verified build outputs
**And** each publisher receives only its destination-specific permissions and secrets (CI-AR28)

## Technical Acceptance Criteria

### Interface contracts

**Given** `.github/workflows/release.yaml` is added
**When** its trigger and top-level keys are inspected
**Then** `on:` is exactly `push` with `tags: ['v*']` — the portable glob, not a regular expression, because Git ref filters do not support one
**And** workflow-scope `permissions:` is `contents: read`; the only escalation is the single finalizer job introduced by `E008-S01-005`
**And** `concurrency:` groups on `${{ github.workflow }}-${{ github.ref }}` with `cancel-in-progress: false`, because a release run must never be cancelled by a second event on the same tag

**Given** the job graph
**When** `needs:` edges are resolved
**Then** the order is `classify` -> `validate-tag` -> `plan` -> `verify` -> `preflight`, with every publisher of `E008-S01-004` and the finalizer of `E008-S01-005` declaring `needs: [plan, preflight, verify]`
**And** `verify` is `uses: ./.github/workflows/verify-build.yaml` at job level with `channel: stable`, `package-version` equal to the tag without `v`, and `source-sha` equal to the peeled tag commit
**And** because `release.yaml` is push-triggered, `test_any_push_triggered_workflow_verifies_before_it_ships` requires `verify` in every publisher's transitive needs

**Given** classification is the sole tag decision
**When** the `classify` job runs
**Then** it calls `./.github/actions/publication-contract` with a new `classify` operation, passing the ref, and reads back outputs `tag-class` (exactly `exact`, `alias` or `invalid`), `tag-name` and `package-version`
**And** the action is the only place in the repository holding a tag regular expression; no workflow `if:`, no `run:` block and no second action re-matches the ref
**And** `alias` ends the workflow successfully with every later job skipped by `if: needs.classify.outputs.tag-class == 'exact'`; `invalid` fails the `classify` job itself

**Given** `validate-tag` runs
**When** its steps are inspected
**Then** it checks out with `fetch-depth: 0`, `fetch-tags: true`, `persist-credentials: false`
**And** it asserts `git cat-file -t "refs/tags/${TAG}"` prints `tag`, that `git rev-parse "refs/tags/${TAG}^{commit}"` equals `${{ github.sha }}`, and that `git merge-base --is-ancestor` places that commit on the freshly fetched remote default branch
**And** it asserts the tag without `v` equals the committed Poetry version read through `./.github/actions/setup-poetry-python`
**And** it then runs `LiquidLogicLabs/git-action-tag-validate-version@v2` on the same tag; the local Git-object checks are not replaced by it, because that action validates SemVer shape, not annotated-versus-lightweight or ancestry

**Given** the `plan` job runs
**When** its steps are inspected
**Then** it resolves the committed version through `./.github/actions/setup-poetry-python` and contains no `tomllib` and no `import` in a `run:` block, satisfying `test_the_committed_version_authority_has_one_implementation` for the third `plan` job on disk
**And** it emits `publication-plan-v1.json` through the publication-contract action and uploads it with `retention-days: 30`
**And** its outputs are `package-version`, `source-sha`, `plan-artifact-name`, and per-destination enablement booleans; no coordinate string is an output, because coordinates travel in the plan document

**Given** the `preflight` job runs
**When** its interface is inspected
**Then** its single output is `publication-ready`, whose only success value is `true`
**And** it declares no `id-token: write`, no `packages: write`, no `contents: write`, and performs no registry login
**And** for the mandatory Release destination it validates only that the finalizer's credential mode is the job token and that the tag is not already bound to a conflicting Release; it makes no write call

### Data model

**Given** `publication-plan-v1.json` as extended by `E008-S01-001`
**When** the stable plan is written
**Then** `channel` is `stable`, `development_distance` is absent, and `package_targets` contains the always-present `forge` entry plus, when enabled, `pypi`; a `testpypi` entry on the `stable` channel is a schema-level validation failure, not a runtime `if:`
**And** the `forge` entry's `enabled` is the constant `true` on both channels, so a stable plan missing it is invalid rather than merely incomplete — the same rule `E008-S01-001` states for the development plan, not a second one
**And** `tags.immutable` is exactly `["M.m.p"]` and `tags.aliases` is `["M.m", "latest"]` plus `"M"` when `M >= 1`
**And** a new `git_aliases` array carries `["vM", "vM.m"]`, present for `0.x.y` too, consumed by `E008-S01-005`; it needs a `$defs` entry because the existing `tag` pattern rejects a leading `v`-plus-digits only by accident, not by intent

**Given** the plan's destination set
**When** the mandatory Release is represented
**Then** `destinations` includes `forge-release` unconditionally on the `stable` channel, and the schema enforces that rather than leaving it to a workflow condition
**And** `credential_mode` is per target: `oidc` for PyPI on GitHub, `token` for Docker Hub, and the job-token mode for GHCR, the forge package registry, and the Release

**Given** `build-manifest-v1` and `release-receipt-v1`
**When** this story runs
**Then** neither needs a change here; the receipt is written by `E008-S01-006` and the manifest is unchanged from the verifier

### Error handling and edge cases

**Given** an alias push emits its own `v*` event
**When** `release.yaml` receives `refs/tags/v1` or `refs/tags/v1.2`
**Then** `classify` returns `alias`, the run completes green, and no checkout with credentials, no verifier call and no publisher job starts
**And** this is what prevents `E008-S01-005`'s own alias writes from re-entering the release path recursively

**Given** a lightweight tag matching `vM.m.p`
**When** `validate-tag` runs
**Then** `git cat-file -t` prints `commit` rather than `tag` and the job fails, before the verifier and before any credential-holding job is reachable

**Given** the tag points at a commit that is not on the remote default branch
**When** ancestry is checked
**Then** the job fails; the fetch that establishes the default branch happens inside `validate-tag` and is not inherited from an earlier job's checkout

**Given** the tag version and the committed Poetry version disagree
**When** validation runs
**Then** the job fails naming both values, before the verifier runs — the verifier's `stable` channel would also catch it, but catching it later means a full matrix run before a decidable failure

**Given** a stable destination is enabled but incompletely configured
**When** preflight runs
**Then** the whole fan-out fails, including the mandatory Release, because AD-5 makes required destinations a union and a partial release is worse than no release
**And** the failure names the destination and the missing key, never the value

**Given** two events arrive for the same tag (a re-push, or a rerun)
**When** concurrency is evaluated
**Then** the non-cancellable group serializes them; the second run reconciles rather than duplicating, which is the behaviour `E008-S01-006` specifies

### Observability

**Given** `classify` completes
**When** its log is read
**Then** it prints the ref, the derived tag name, and the class, and nothing else — a classifier that logs a reason string derived from a regular expression tempts a second implementation of the rule into the log line

**Given** `plan` completes
**When** its step summary is read
**Then** the whole plan document is rendered, which is safe by schema, and the plan artifact name and its SHA-256 are printed so a later recovery run can prove it downloaded the same document
**And** the plan's `run` object carries run id, run attempt, repository and server URL (BL-E007-005), giving every stable artifact set a path back to the run that produced it

**Given** `preflight` completes
**When** its output is read
**Then** it lists each required destination and a per-destination `ok` line with the endpoint host and namespace, and emits the single aggregate `publication-ready=true`
**And** it prints no credential value, no credential length, and no hash derived from a credential

### Security

**Given** the tag path can be triggered by anyone who can push a tag
**When** protections are considered
**Then** the workflow assumes, and the operator guide records, that exact stable tag creation is restricted to release maintainers by repository rules; the workflow itself cannot enforce that and must not pretend to
**And** every job up to and including `preflight` holds `contents: read` only, so an unauthorised tag push reaches validation and stops there without touching a credential

**Given** `release.yaml` is a publisher workflow
**When** tier two is evaluated
**Then** it is deliberately outside `SECRET_FREE_WORKFLOWS`, which remains `ci.yaml` and `verify-build.yaml`; ADR-0007's superseded-in-practice note already anticipates this
**And** tier one still governs it: approved owners only, floating `vN` aliases only, no interpolated `uses:`

**Given** the write guards
**When** `test_no_workflow_holds_github_token_write_access_to_contents` runs against `release.yaml` after this story
**Then** it passes with `RELEASE_FINALIZER_JOBS` still empty, because no job in this story declares `contents: write`
**And** the registration happens in `E008-S01-005` and nowhere earlier

### Testability

**Given** the single-classifier guard
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts no workflow `run:` block or `if:` expression contains a `v`-prefixed version regular expression, and that every conditional gating a release job references the classifier's output
**And** the planted violation is an `if: startsWith(github.ref, 'refs/tags/v')` guard on a publisher job; the guard must fail on it, since that is a second, weaker classifier

**Given** the classification unit tests
**When** `tests/ci/test_publication_contract.py` runs
**Then** it covers `exact` for `refs/tags/v1.2.3` and `v0.0.0`; `alias` for `v1` and `v1.2`; and `invalid` for `v1.2.3.4`, `v1.2.3-rc1`, `v1.2.3+build`, `v01.2.3`, `1.2.3`, `vX.Y.Z`, an empty ref, and a ref with a trailing newline or space
**And** the planted violation relaxes the pattern anchor from a full match to a search; `v1.2.3-rc1` must then classify as `exact` and the test must catch it

**Given** the Git-object guard
**When** it is tested
**Then** an integration test builds a scratch repository with one annotated and one lightweight `v0.0.1`, and asserts the validation script accepts the first and rejects the second
**And** the planted violation replaces `git cat-file -t` with `git rev-parse --verify`, which succeeds for both; the lightweight case must then fail the test

**Given** the stable-tag-set rule
**When** it is unit tested
**Then** the alias derivation is asserted for `1.2.3` (immutable `1.2.3`; OCI aliases `1.2`, `latest`, `1`; Git aliases `v1`, `v1.2`) and for `0.4.1` (immutable `0.4.1`; OCI aliases `0.4`, `latest`, and **no** `0`; Git aliases `v0`, `v0.4`)
**And** the planted violation emits the OCI `0` alias for a `0.x.y` release and must be caught — this is CI-AR18's exact asymmetry and the easiest rule in the epic to get backwards

**Given** the channel-exclusion rule
**When** it is tested
**Then** a stable plan containing a `testpypi` package target fails schema validation
**And** the planted violation is such a plan; if the schema accepts it, the exclusion is only a workflow condition and the guard has not fired

## Open questions

1. **Does `LiquidLogicLabs/git-action-tag-validate-version@v2` overlap the local checks enough to replace one of them?** The epic requires both, and this story keeps both because the action's documented contract is SemVer shape, not annotated-versus-lightweight or default-branch ancestry. If the action does cover the Git-object check, the duplication should be removed deliberately with the action's behaviour cited — not left in place "just in case", which is how two classifiers get born.
2. **What does preflight validate for the mandatory Release without writing?** Checking "can this token create a release" without creating one is not directly expressible through the GitHub API. This story assumes preflight validates configuration shape only — the finalizer job exists, is registered, and holds the job token — and that an actual permission failure surfaces at Release creation. If a stronger pre-check is required, the maintainer must accept the API call it implies.
3. **Should `PUBLISH_IMAGE_FORGE=false` on the stable channel be permitted at all?** The epic makes GHCR toggle-controlled and the Release mandatory, so a stable release can legitimately publish no image anywhere. That is representable, but it means `latest` can go stale relative to a released version. Still open, and the 2026-09-01 decision sharpened rather than settled it: that decision's prose says "the owning forge — package and image alike — is always a destination", which read literally removes `PUBLISH_IMAGE_FORGE` too, while the same decision's enumeration of the optional destinations names only `PUBLISH_PACKAGE_TESTPYPI`, `PUBLISH_PACKAGE_PYPI` and `PUBLISH_IMAGE_DOCKERHUB` — and CI-AR20 still defines `PUBLISH_IMAGE_FORGE` as a toggle. These stories change only the *package* destination, because that is the change the decision spells out and scopes; the forge *image* toggle is left exactly as CI-AR20 has it. If the maintainer meant the image registry too, that is a further change across `E008-S01-002`, this story, `E008-S01-004` and `E008-S01-005`, and it also answers this question by making the `false` case unrepresentable.
