# Create the Forge Release and Finalize Stable Aliases

As a release consumer,
I want a verified forge Release followed by forward-only OCI and Git aliases,
So that visible convenience pointers advertise only a complete newest stable release.

Depends on: `E008-S01-004`.

## Acceptance Criteria

**Given** all mandatory and enabled immutable package/image publishers have succeeded or identity-matched existing objects
**When** forge Release creation becomes eligible
**Then** it runs before all OCI and Git alias mutation
**And** a failed enabled immutable destination blocks Release visibility (CI-AR25)

**Given** release notes are generated
**When** `LiquidLogicLabs/git-action-release-changelog-builder@v3` runs
**Then** it uses full release history, targets the exact annotated tag, and sets `fail-on-error: true`
**And** changelog failure prevents Release creation

**Given** no owning-forge Release exists for the exact tag
**When** `LiquidLogicLabs/git-action-release@v2` runs
**Then** it creates a GitHub Release bound to the exact tag/commit with the changelog, wheel, sdist, and `SHA256SUMS`
**And** it sets `artifact-errors-fail-build: true`, `replaces-artifacts: false`, and `remove-artifacts: false`

**Given** a Release or asset already exists on rerun
**When** preflight reconciliation compares it
**Then** the Release tag/commit and every existing asset SHA-256 must match expected identity
**And** matching objects are reused, only missing verified assets are added, and mismatches fail without replacement or deletion (CI-AR26)

**Given** the Release action completes
**When** read-back verification runs
**Then** the Release resolves to the exact annotated tag commit
**And** downloaded wheel, sdist, and checksum asset validate against `SHA256SUMS` and the build manifest
**And** no floating Git tag is treated as the Release identity

**Given** the owning-forge Release and all enabled immutable destinations are verified
**When** stable alias finalization begins
**Then** it enters one non-cancellable single-writer concurrency group shared by all stable release runs
**And** the lock is held across OCI and later Git alias operations (CI-AR27, CI-AR34)

**Given** the finalizer holds the lock
**When** it assesses eligibility
**Then** it refetches all exact stable tags and remote OCI pointers immediately before mutation
**And** the candidate must still be the greatest exact stable SemVer tag
**And** a pre-lock eligibility result is not accepted

**Given** the finalizer holds the lock and an alias already exists in an enabled registry
**When** it decides whether that alias may move
**Then** it resolves the alias to its current remote manifest and reads the source SHA and version recorded on that manifest, rather than inferring the alias target from the tag list
**And** it moves the alias only when this run's candidate is strictly newer than what the alias already points at
**And** an out-of-order older run succeeds without moving the alias: every enabled publisher succeeding proves this run is complete, not that it is newest

**Given** an enabled registry has no stable aliases or has aliases referencing an older eligible version
**When** the candidate is `M.m.p`
**Then** `M.m` and `latest` move to the verified immutable digest
**And** `M` also moves when `M >= 1`
**And** a `0.x.y` release omits the OCI `0` alias

**Given** a stable OCI alias is created or moved
**When** the registry operation runs
**Then** it uses a digest-only manifest copy from the verified immutable object
**And** performs no Dockerfile execution, package install, image rebuild, or unverified cross-registry source operation (CI-AR23)

**Given** an alias already references the candidate or a greater stable version
**When** a same-tag or stale run finalizes
**Then** the matching alias is accepted or the newer alias is left unchanged
**And** no alias ever moves backward

**Given** one enabled registry alias update fails after another succeeds
**When** the run ends
**Then** Git alias mutation does not begin
**And** the release remains explicitly incomplete and eligible for same-tag identity-based reconciliation

**Given** all OCI aliases are updated
**When** read-back verification runs
**Then** every alias resolves to the expected immutable manifest digest before Git aliases become eligible

**Given** the stable finalizer still holds its single-writer lock and all required OCI aliases are verified or not applicable
**When** Git alias eligibility is checked
**Then** full tag history is refetched immediately before mutation
**And** the candidate must be the greatest exact stable SemVer tag and newer than each applicable alias target

**Given** `vM` or `vM.m` already exists on the remote
**When** Git alias eligibility is checked under the lock
**Then** the commit each alias currently points at is read from the refetched remote and mapped back to the exact stable tag that references that commit
**And** the alias moves only when the candidate's version is strictly greater than the version its current target represents
**And** an alias pointing at a commit no exact stable tag references is unverifiable and fails closed without mutation

**Given** Git aliases are eligible
**When** `LiquidLogicLabs/git-action-tag-floating-version@v2` runs
**Then** it receives `prefix: v`, `update-minor: true`, and `ignore-prerelease: true`
**And** `.github/actions/publication-contract/` has already decided that these aliases may move and which they are; the action only executes the write (maintainer decision, `docs/ci/codex-assesment.md`, "Divergences resolved (2026-09-01)")
**And** `@v2` is the pinned major: the upstream repository publishes `v1` and `v2` floating majors with `v2.0.3` the newest release, which settles the `@v1`/`@v2` disagreement between sources empirically rather than by preference
**And** no allowlist change accompanies it: `LiquidLogicLabs` is already a tier-one approved owner and `v2` satisfies the floating-major rule
**And** GitHub checkout configures only the release job token with `contents: write`
**And** no human or other automation identity is granted floating-tag write authority (CI-AR18, CI-AR34)

**Given** release `vM.m.p` completes
**When** alias reconciliation succeeds
**Then** both `vM` and `vM.m` reference the exact release commit, including `v0` and `v0.m` for `0.x.y`
**And** the annotated `vM.m.p` tag object is never changed

**Given** the selected action force-pushes aliases sequentially
**When** failure occurs between alias writes
**Then** the run records incomplete Git alias state
**And** a same-tag rerun rechecks and reconciles both aliases without changing the exact tag or moving either alias backward

**Given** a newer exact stable tag exists or an alias already targets a newer release
**When** an older release run or rerun holds the lock
**Then** it exits successfully without regressing either alias

**Given** the alias push itself emits another portable `v*` event
**When** `release.yaml` receives it
**Then** Story 8.3 classifies it as `alias` and completes as a credential-free no-op

## Technical Acceptance Criteria

### Interface contracts

**Given** ADR-0006's "identity versus artifacts of an identity" amendment
**When** the finalizer is designed
**Then** it is **one** job, not two, because the concurrency lock must be held continuously across Release creation, OCI alias writes and Git alias writes
**And** two jobs sharing a `concurrency` group cannot hold one lock across both: the group serializes jobs, but between the first job ending and the second starting, a different run may acquire the group and interleave — which is precisely the race AD-8's single-writer protocol exists to prevent
**And** the job is named `finalize-release` and that exact name is added to `RELEASE_FINALIZER_JOBS` in `tests/ci/test_workflow_contracts.py`

**Given** the finalizer job
**When** its declaration is inspected
**Then** it declares `permissions: { contents: write, packages: write }` — `contents: write` because GitHub has no `releases:` scope and Release creation plus Git alias pushes both require it, and `packages: write` because the same job writes OCI aliases
**And** it declares `concurrency: { group: stable-release-finalization, cancel-in-progress: false }` — a fixed literal shared by every stable run, with no `github.ref` or `github.run_id` term
**And** it declares `needs: [classify, plan, preflight, verify, publish-forge-package, publish-pypi, verify-images]` with the disabled-versus-failed guard specified in `E008-S01-004`, in which the always-on forge package publisher is tested with `== 'success'` because it can never legitimately be skipped

**Given** the finalizer's step sequence
**When** it is inspected
**Then** the order is fixed and each stage gates the next: (1) checkout with `fetch-depth: 0`, `fetch-tags: true` and the job token persisted, since the Git alias action needs a credentialed remote; (2) download `verified-dist-v1` and the plan; (3) revalidate both; (4) reconcile any existing Release; (5) `LiquidLogicLabs/git-action-release-changelog-builder@v3`; (6) `LiquidLogicLabs/git-action-release@v2`; (7) Release read-back; (8) refetch tags and remote OCI pointers; (9) OCI alias copies; (10) OCI alias read-back; (11) refetch tags again; (12) `LiquidLogicLabs/git-action-tag-floating-version@v2`; (13) Git alias read-back
**And** steps 8 and 11 are two separate refetches, not one hoisted above both: AD-8 requires the check immediately before each mutation class

**Given** the Release action's inputs
**When** they are set
**Then** `artifact-errors-fail-build: true`, `replaces-artifacts: false`, `remove-artifacts: false` are set literally, and the assets are the three files from `verified-dist-v1` — the wheel, the sdist and `SHA256SUMS`
**And** the changelog action's `fail-on-error: true` is set literally
**And** the floating-version action receives `prefix: v`, `update-minor: true`, `ignore-prerelease: true`

**Given** the division of labour between the repository's own action and the two executors
**When** the finalizer's steps are inspected
**Then** `./.github/actions/publication-contract` is the sole classifier: it alone decides what the pushed tag means and therefore which floating aliases — OCI and Git — are eligible to move, and it performs no mutation of its own
**And** the Git aliases are written only by `LiquidLogicLabs/git-action-tag-floating-version@v2`, and the OCI aliases only by `docker buildx imagetools create`; `crane` and `regctl` remain outside the approved-owner allowlist and are not adopted
**And** this is one decider and two executors, and it adds no third-party action outside the existing policy: the alternative — centralising the ref write inside `publication-contract` — would put a credentialed `git push` of a tag ref inside the repository's own composite action, and would still leave the registry-side manifest copy to something else
**And** no `run:` step spells an alias name: `vM` and `vM.m` come from the plan's `git_aliases`, and the OCI alias names from `tags.aliases`, so a shell-derived `v${MAJOR}` is a defect rather than a shortcut

**Given** the compare-before-move read
**When** it is implemented
**Then** each OCI alias is resolved with `docker buildx imagetools inspect <registry>/<repository>:<alias>` at step 8, and the comparison uses `org.opencontainers.image.version` and `org.opencontainers.image.revision` read from that manifest — the same two labels `E008-S01-002`'s `dev` finalizer reads, so one label contract serves both channels
**And** each Git alias is resolved with `git rev-parse refs/tags/<alias>` after the step 11 refetch, and its commit is mapped to a version with `git tag --points-at`, filtered to exact `v<major>.<minor>.<patch>` tags
**And** both reads happen inside the lock and are not hoisted above it: an alias read taken before the lock authorises a move that another run may have made in the meantime, which is the same staleness AD-8's immediately-before-mutation rule closes for tags

**Given** the OCI alias operation
**When** it runs
**Then** it is `docker buildx imagetools create --tag <registry>/<repository>:<alias> <registry>/<repository>@<digest>`, taking the digest from `verify-images`' output array and the alias names from the plan's `tags.aliases`
**And** the finalizer never runs `docker/bake-action`, `docker buildx build`, or any command that could produce a layer

### Data model

**Given** `publication-plan-v1.json`
**When** the finalizer consumes it
**Then** `tags.aliases` supplies the OCI alias set and `git_aliases` (added by `E008-S01-003`) supplies `vM` and `vM.m`
**And** the finalizer spells no alias itself; the `M >= 1` rule for the OCI major alias and the "always emit `v0` for `0.x.y`" rule for Git aliases live in the plan producer and are tested there
**And** that is the whole of the decider/executor split in data terms: `publication-contract` writes the alias sets into the plan, and the floating-version action and `imagetools create` read them and write refs and manifests respectively

**Given** `E008-S01-002` defines alias eligibility as a pure function over the candidate and the observed remote alias identity
**When** the stable channel reuses it
**Then** it is the same function with a SemVer precedence comparator in place of the first-parent-distance comparator, not a second implementation of the forward-only rule
**And** its inputs are the observed remote alias identity together with the candidate, never the greatest remote tag alone: the greatest tag says which release *should* own the alias, the alias's own manifest says which release *does*, and the two can disagree — after a failed finalization, or while a newer run holds the lock
**And** both inputs are required; dropping either is what lets a slow older run move an alias backward while every check it did still passed

**Given** `release-receipt-v1.json`
**When** the finalizer records its results
**Then** the receipt is written by `E008-S01-006`, but this story must emit the facts it needs as job outputs or a step-summary JSON: the Release id and URL, each asset's filename and remote SHA-256, and each OCI and Git alias with its expected and actual target
**And** the existing `reconciliationStatus` enum (`failed`, `matched`, `pending`) is insufficient for the four-way classification the epic requires; the extension is `E008-S01-006`'s to make, and this story must not emit a status the schema cannot represent

**Given** ADR-0006
**When** this story lands
**Then** the ADR gains a short amendment naming `finalize-release` as the registered finalizer, stating the permissions it holds and why, and stating why it is one job rather than two
**And** the amendment records that `RELEASE_FINALIZER_JOBS` is no longer empty, which the existing comment in `tests/ci/test_workflow_contracts.py` explicitly anticipates

### Error handling and edge cases

**Given** a Release already exists for the exact tag
**When** reconciliation runs before the changelog step
**Then** its tag and target commit must equal the validated tag and peeled commit, and every existing asset's SHA-256 must equal the corresponding `SHA256SUMS` entry
**And** matching objects are reused, only genuinely missing assets are uploaded, and any mismatch fails without delete or replace — which is also why `replaces-artifacts: false` and `remove-artifacts: false` are set

**Given** the changelog action fails
**When** the run continues
**Then** it does not: `fail-on-error: true` makes the failure terminal, and no Release is created
**And** this is deliberate — a Release without notes is a visible, hard-to-retract artifact

**Given** one enabled registry's OCI alias write succeeds and another's fails
**When** the run ends
**Then** the finalizer fails at step 9 or 10, Git alias mutation (steps 11-13) never starts, and the release is recorded incomplete
**And** the succeeded alias is not rolled back: it already points at a verified immutable digest for this release, and reverting it would be a backward move

**Given** the floating-version action force-pushes `vM` and `vM.m` sequentially rather than atomically
**When** it fails between the two writes
**Then** the run records incomplete Git alias state, and a same-tag rerun re-checks both aliases and writes only the one still missing or still older
**And** neither alias is ever moved backward, and the annotated `vM.m.p` tag object is never touched

**Given** an alias points at an object whose recorded version equals the candidate but whose digest differs from the verified immutable digest
**When** eligibility is assessed
**Then** it fails closed without mutation: two different artifact sets claiming one release identity is CI-AR26's hard failure, not a move, and overwriting the alias would hide it
**And** an alias whose manifest cannot be resolved, carries no version label, or carries a version that is not an exact stable SemVer is `unverifiable` and also fails closed — never treated as absent, since assuming absence from a failed read is how a rerun overwrites something it could not see

**Given** a newer exact stable tag exists by the time this run acquires the lock
**When** eligibility is re-checked at steps 8 and 11
**Then** the run exits **successfully** without moving any alias, because the immutable objects for the older release are legitimately complete and only the pointers are not this run's to move
**And** the receipt records the aliases as intentionally not advanced rather than as failures

**Given** the finalizer's own Git alias push emits `refs/tags/vM` and `refs/tags/vM.m` push events
**When** `release.yaml` re-triggers
**Then** `classify` returns `alias` and the run is a green, credential-free no-op — the mechanism from `E008-S01-003` that prevents recursion
**And** the alias run acquires no lock, because every job past `classify` is skipped

**Given** the run is cancelled by a maintainer mid-finalization
**When** cancellation lands
**Then** the non-cancellable concurrency group does not protect against a manual cancel; a cancel between the Release and the aliases leaves an incomplete release that a same-tag rerun reconciles
**And** this is an accepted, documented state, not a defect

### Observability

**Given** the finalizer completes or fails
**When** its step summary is read
**Then** it records, in order: the Release id, URL and target commit; each asset filename with expected and remote SHA-256; each OCI alias with registry, expected digest and observed digest after read-back; each Git alias with expected and observed commit; and for every stage not attempted, the reason
**And** "not attempted because a newer release owns the alias" is logged distinctly from "not attempted because an earlier stage failed"

**Given** an alias is deliberately left where it is
**When** the step summary is written
**Then** it records the alias name, the version and revision read from that alias's own current remote manifest or ref, the candidate version, and the comparison outcome
**And** the pre-move comparison is logged distinctly from the post-move read-back, so "declined to move" and "moved and confirmed" are never conflated in the evidence

**Given** an operator inspects a released artifact
**When** they trace it back
**Then** the path is: the Release asset's SHA-256 -> `SHA256SUMS` -> `build-manifest.json`'s `source_sha` -> the plan's `run` object (run id and attempt) -> the workflow run
**And** the image path is the OCI alias digest -> the immutable `M.m.p` digest -> `org.opencontainers.image.revision`

**Given** the eligibility re-checks
**When** they run
**Then** each logs the values it compared — the greatest remote exact stable tag, the candidate, the current remote alias target — so a "did not advance" outcome is explainable from the log without re-running anything

### Security

**Given** `contents: write` is the scope this story introduces
**When** it is justified
**Then** ADR-0006's amendment governs: the committed Poetry version and the exact `vX.Y.Z` annotated tag are chosen only by the local guarded transaction; the Release object, its assets, and the moving `vMAJOR`/`vMAJOR.MINOR` aliases attach to an identity already decided, and an alias is a pointer, not a choice
**And** the finalizer must not run `poetry version`, create or retarget an exact tag, or push to the default branch; the only refs it writes are the two alias tags

**Given** the checkout that credentials the Git remote
**When** it is configured
**Then** `persist-credentials` is true only for the finalizer's checkout, and only the automatic job token is used; no PAT, deploy key or App token is introduced
**And** the operator guide records that repository rules must restrict `vMAJOR`/`vMAJOR.MINOR` write authority to the release publisher identity, and that this is external readiness the workflow cannot enforce

**Given** the behavioural guard `test_no_workflow_writes_refs_or_releases_outside_a_finalizer`
**When** its reach is examined
**Then** a defect must be fixed as part of this story: its `release_actions` tuple is `("action-gh-release", "create-release", "release-action")`, and **none of those substrings occurs in `LiquidLogicLabs/git-action-release@v2`, `LiquidLogicLabs/git-action-release-changelog-builder@v3`, or `LiquidLogicLabs/git-action-tag-floating-version@v2`**
**And** an unregistered job could therefore create a Release or force-push an alias tag with an approved-owner action and pass the guard unnoticed
**And** the tuple must be extended to cover `git-action-release` and `git-action-tag-floating-version`, and the fix must be proven by planting each in an unregistered job

**Given** the permissions guard
**When** it runs after this story
**Then** `test_no_workflow_holds_github_token_write_access_to_contents` passes because `finalize-release` is registered, and fails for any other job declaring `contents: write`
**And** the guard's known blindness to PAT-based pushes is covered by the behavioural guard above, which is why both exist

### Testability

**Given** the finalizer registration
**When** it is proven
**Then** the planted violation is a second job in `release.yaml` declaring `contents: write` without registration; `test_no_workflow_holds_github_token_write_access_to_contents` must fail on it
**And** a second planted violation is a `git push origin HEAD:refs/tags/v9.9.9` step in an unregistered job; the behavioural guard must fail on it while the permissions guard passes — the same two-guard demonstration ADR-0006 already records

**Given** the extended `release_actions` tuple
**When** it is proven
**Then** a planted `uses: LiquidLogicLabs/git-action-release@v2` step in an unregistered job must fail the behavioural guard, and the same for `git-action-tag-floating-version@v2`
**And** the guard must be shown red before the fix and green after, because the current tuple passes both plants today

**Given** the single-lock guard
**When** it is added
**Then** it asserts exactly one job in `release.yaml` writes a Release or a Git alias, that this job's name is in `RELEASE_FINALIZER_JOBS`, and that its `concurrency.group` is a literal with no `${{` and `cancel-in-progress: false`
**And** the planted violation splits Release creation and alias finalization into two registered jobs sharing a group; the guard must fail, because that is the interleaving hazard this story's one-job decision exists to close

**Given** the action-input guard
**When** it is added
**Then** it asserts the literal input values the epic pins: `fail-on-error: true` on the changelog action; `artifact-errors-fail-build: true`, `replaces-artifacts: false`, `remove-artifacts: false` on the release action; `prefix: v`, `update-minor: true`, `ignore-prerelease: true` on the floating-version action
**And** the planted violation flips `replaces-artifacts` to `true`; the guard must fail, since that single input turns a fail-closed rerun into a silent overwrite

**Given** the decider/executor guard
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts that no `run:` step in any workflow constructs a floating alias name or writes a floating ref — no `refs/tags/v${` and no `git tag`/`git push` of a `v<major>` or `v<major>.<minor>` form — with the scope derived from every parsed workflow rather than from `release.yaml` alone, since the next channel to grow aliases would otherwise be uncovered
**And** the planted violation replaces the floating-version action step with `git push --force origin HEAD:refs/tags/v${MAJOR}`; this guard and the extended `release_actions` behavioural guard must both fail on it
**And** a second planted violation keeps the action but adds a `run:` step that computes `V_MAJOR="v${VERSION%%.*}"` and passes it as the action's input; the guard must fail on the derivation even though the write is still the approved action's, because a name the plan did not decide is a second classifier

**Given** the pinned-major guard for approved actions
**When** it is added
**Then** it asserts that every `uses:` of `LiquidLogicLabs/git-action-tag-floating-version` in every parsed workflow is pinned at `@v2`, with the occurrence set derived from the parsed workflows rather than from a list of files
**And** the planted violation downgrades one occurrence to `@v1`; the guard must fail on it, because `@v1` is the version the condensed assessment proposed and is exactly what a later reader would restore from that document

**Given** the compare-before-move guard
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts that in every job writing an OCI alias, an `imagetools inspect` of each alias name appears in the step list before the first `imagetools create`, and that a `git rev-parse refs/tags/` read appears before the floating-version action
**And** the planted violation deletes the inspect step while keeping the tag refetch, so the run still "checks eligibility" but only against the tag list; the guard must fail, because the greatest tag existing says nothing about what the alias currently points at
**And** a second planted violation moves the inspect step above the job's lock-acquiring first step in a two-job split; the guard must fail on ordering, since a pre-lock read authorises a stale move

**Given** the forward-only alias rules
**When** they are unit tested in `tests/ci/test_publication_contract.py`
**Then** the eligibility function is tested over: no remote alias; remote alias on an older version; remote alias on this exact version; remote alias on a newer version; a newer exact stable tag existing; and a malformed remote pointer
**And** the OCI alias set is asserted for `1.2.3` (`1.2`, `latest`, `1`) and `0.4.1` (`0.4`, `latest`, no `0`), and the Git alias set for both (`v1`/`v1.2`, and `v0`/`v0.4`)
**And** the planted violation emits a Git `v0` only when `M >= 1`, mirroring the OCI rule; the `0.x.y` case must fail, because CI-AR18 makes the two rules deliberately asymmetric

**Given** the compare-before-move decision
**When** it is unit tested
**Then** the eligibility function is exercised over observed alias identities rather than tag state alone: alias absent; alias on an older version; alias on the candidate with a matching digest; alias on the candidate with a differing digest; alias on a newer version; alias with an unreadable, unlabelled, or non-SemVer manifest
**And** the planted violation makes the function return "move" whenever the candidate is the greatest exact stable tag, ignoring the version recorded on the alias itself; the "alias on a newer version" case must then move the alias backward and the test must catch it

**Given** the alias-event no-op
**When** it is tested
**Then** the `push-tag-alias.json` fixture from `E008-S01-003` is asserted to classify as `alias`, and a guard asserts `finalize-release` carries an `if:` requiring `tag-class == 'exact'`
**And** the planted violation removes that term from the finalizer's `if:`, which would let an alias event acquire the release lock

## Open questions

1. **One job holding both `contents: write` and `packages: write`, or least privilege?** Holding the lock continuously requires one job, and that job therefore concentrates both scopes. Splitting them restores least privilege but reintroduces the interleave window. This story chooses the single job and records the trade-off; the maintainer should confirm, because it is the widest permission grant in the pipeline and the ADR amendment will cite this reasoning.
2. **Does `LiquidLogicLabs/git-action-release@v2` support identity-preserving reconciliation, or must the finalizer reconcile before calling it?** `replaces-artifacts: false` and `remove-artifacts: false` make it fail-closed, but "existing Release, missing one asset" needs a documented behaviour. This story assumes the finalizer reconciles first and passes only the missing assets. The action's actual behaviour must be verified against its `v2.0.3` documentation before implementation, and the verified release and date recorded per the maintenance convention.
3. **Is a manual cancel between the Release and the aliases acceptable?** The non-cancellable concurrency group does not stop a maintainer pressing cancel. This story treats the resulting incomplete release as a documented, reconcilable state. If it must be prevented, the only mechanism is process, not YAML.
4. **Resolved 2026-09-01 — `publication-contract` decides, the vendor actions execute.** Answered by the maintainer and recorded in `docs/ci/codex-assesment.md`, "Divergences resolved (2026-09-01)". `.github/actions/publication-contract/` remains the sole tag *classifier*: it alone decides what a tag means — exact release, alias, or invalid — and therefore which floating aliases may move. It performs no mutation. The Git aliases `vMAJOR` and `vMAJOR.MINOR` are written by `LiquidLogicLabs/git-action-tag-floating-version@v2`, and the OCI aliases by `docker buildx imagetools create`; `crane` and `regctl` remain outside the approved-owner allowlist and are not adopted.
