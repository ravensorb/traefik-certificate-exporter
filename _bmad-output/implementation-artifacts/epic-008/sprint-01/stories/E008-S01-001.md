# Publish Immutable Development Packages and Images

As a maintainer, I want protected default-branch artifacts published from the verified bundle,
so development delivery creates immutable package and image identities without rebuilding.

Depends on the completed Epic 7 foundation.

## Acceptance Criteria

**Given** a protected default-branch push, **when** `dev.yaml` starts, **then** unknown forges fail
closed; one full-history/tags checkout derives `X.Y.(Z+1).devN`; an exact stable tag on the source
suppresses dev publication; and `verify-build.yaml` is called exactly once for the event SHA.

**Given** a destination receives `verified-dist-v1`, **when** it reaches its first credentialed
step, **then** it has revalidated `SHA256SUMS` and `build-manifest.json`, matched source/version,
and, for images, matched the exact wheel hash to the declared image input (CI-AR36).

**Given** package publication is enabled or required, **when** upload begins, **then**
`pypa/gh-action-pypi-publish@<reviewed-full-commit-sha>` receives only the verified wheel/sdist;
implementation resolves, reviews, and records the actual full SHA. Package OIDC/tokens are
isolated from image jobs (CI-AR24, CI-AR38, CI-AR40).

**Given** development image publication, **when** the image job runs, **then** it consumes the
exact verified wheel and performs one Buildx invocation for `linux/amd64,linux/arm64` with the
immutable `dev-<12sha>` tags for the required forge registry and optional Docker Hub. It never
rebuilds per registry and emits digest/platform inspection as outputs and run summary (CI-AR39,
CI-AR41).

**Given** forge coordinates, **when** `FORGE_REGISTRY` is present, **then** it accepts only
same-forge `host[:port]` with no userinfo, path, query, or fragment. Optional toggles accept only
`true`, `false`, or absence; disabled destinations receive no credentials or requests.

## Multi-platform feasibility — spike complete, do not re-run it

Gate finding F13 required a spike before this story proceeds. It ran on 2026-09-02 and the
answer is **feasible as-is, with no Dockerfile change**. Evidence: `/tmp/f13-spike/` (transient);
numbers and reasoning recorded permanently in ADR-0008, whose second open question this closes.

- `linux/amd64` alone: **50 s**. `linux/amd64,linux/arm64` emulated: **436 s** (8.7×).
- 80% of the wall is two `linux/arm64` steps under QEMU: `apk add gcc cargo` (203 s) and
  `poetry install --only main` (145 s). Nothing compiles Rust from source.
- Budget **12–15 minutes** on a 4 vCPU GitHub-hosted runner (the spike had 8). No second native
  runner is needed on these numbers.
- The wheel is `py3-none-any`, so the same file with the same SHA-256 installs into both platform
  images. Exact-wheel provenance is platform-independent by construction.

### The index assertion this story must write

`ATTESTATIONS = []` — the shipped default — **does not disable attestations**. BuildKit emits
SLSA provenance `mode=min` regardless, so the index carries four descriptors: two platforms plus
two `unknown/unknown` attestation manifests. Adding `type=sbom` keeps it at four; only
`type=provenance,disabled=true` drops it to two. **A count assertion is wrong in three
directions.** Key on the authoritative annotation, not on the `unknown/unknown` convention:

```python
platforms = {
    f"{m['platform']['os']}/{m['platform']['architecture']}"
    for m in index["manifests"]
    if m.get("annotations", {}).get("vnd.docker.reference.type")
    != "attestation-manifest"
}
assert platforms == {"linux/amd64", "linux/arm64"}
```

Nesting differs by source: `imagetools inspect --raw <ref>` returns the manifest list directly,
while an OCI-layout `index.json` sits one level above it, and a single-platform layout has no
nested index at all. Iterating `index.json`'s `manifests[]` reads the wrong level.

### Two bake-interface traps found by the spike

Neither blocks, both cost an hour if rediscovered:

1. Buildx parses env overrides of `list(string)` as CSV, so `OUTPUTS="type=oci,dest=/tmp/x.tar"`
   splits into two elements. It must be CSV-quoted: `OUTPUTS='"type=oci,dest=/tmp/x.tar"'`.
   `PLATFORMS="linux/amd64,linux/arm64"` works naturally because there each comma *is* a
   boundary. The failure is opaque — `ATTESTATIONS="type=provenance,mode=max"` reports
   `Unsuitable value: attestation type not specified`, which does not read as a quoting problem.
2. `type=oci,dest=` writing outside the bake context needs `--allow fs.write=<dir>`, otherwise
   `ERROR: additional privileges requested`. Local and spike use only; irrelevant to
   `type=registry`.

Gate finding F25 (`DOCKER_PLATFORMS` baked into the runtime image's `ENV`) is **already fixed** —
it was read nowhere and has been deleted.

## Destination matrix — channel decides, and channel is the file you are in

`dev.yaml` is always the development channel and `release.yaml` always the stable one, so this
distinction costs no runtime condition (ADR-0011).

| Destination | `dev.yaml` | `release.yaml` |
|---|---|---|
| image -> active forge registry | **always** | **always** |
| image -> Docker Hub | **never** | if `PUBLISH_IMAGE_DOCKERHUB` |
| package -> forge Python index | if supported *(host capability)* | if supported *(host capability)* |
| package -> TestPyPI | if `PUBLISH_PACKAGE_TESTPYPI` | **never** |
| package -> PyPI | **never** | if `PUBLISH_PACKAGE_PYPI` |

No toggle is renamed or removed; each is channel-scoped, so `PUBLISH_IMAGE_DOCKERHUB` is inert in
`dev.yaml`. Development images never reach Docker Hub.

Two reasons a destination may be absent, recorded distinctly because conflating them hides a
regression: **disabled by toggle** (an operator chose it) and **absent by host capability**
(GitHub has no forge Python index, and no toggle can override that).

The enabled set is produced **once**, by the plan job, as a job output -- not a repository-owned
schema (CI-AR41), and reviving neither retired CI-AR22 nor CI-AR23. No publisher re-reads
`PUBLISH_*`; a guard enforces it.

## Shared surface — name it now, before two workflows restate it (F8)

`dev.yaml` and `release.yaml` would otherwise hold near-identical implementations of forge
detection, bundle revalidation, and the image build — then stories 003 and E009-S01-001 would
edit both. Four stories touching two files that should share one implementation is how the
divergence starts. This story owns the shared surface:

- `.github/actions/forge-coordinates/action.yml` — derives forge kind, registry and package-index
  coordinates from action context, fail-closed, with `FORGE_REGISTRY` as the documented override
  (CI-AR6). Also emits whether a forge Python index exists on this host, which is the
  capability half of the enabled set (see the destination matrix above).
- `.github/actions/verified-bundle/action.yml` — downloads `verified-dist-v1`, checks
  `SHA256SUMS`, validates `build-manifest.json`, and matches source SHA, version and the exact
  wheel hash before any login (CI-AR36).
- `.github/workflows/publish-image.yaml` — reusable, taking channel, tags and enabled registries;
  one Buildx multi-platform invocation, no per-registry rebuild (CI-AR39).

`release.yaml` consumes these rather than restating them.

## Validators are Python with tests, not regexes in `run:` blocks (F9)

Two rules need real parsing and are not unit-testable inside a `run:` block:

- **Forge coordinate validation** — rejecting userinfo, path, query and fragment in a
  `host[:port]` override is URL parsing. Use `urllib.parse`, not a hand-written pattern.
- **Annotated-tag peeling and reachability** — `git rev-parse` / `merge-base --is-ancestor`
  wrapped, not pattern-matched.

Both live in `scripts/` (or `src/publication_contract/`) as functions with pytest cases, and the
workflow calls them. Left inline, the only available "test" is grepping the workflow for its own
regex, which asserts nothing about behaviour. This is the same rule that put the release
transaction in `scripts/release_version.py` rather than in a `run:` block.

## The published image must be smoke-tested, not only inspected (F14)

`verify-build.yaml` builds a **single-platform, `--load`ed** image and smoke-tests it. The
publisher then builds a **different** image — multi-platform, pushed — which nothing ever starts.
That is ADR-0008's Option-B objection reappearing one layer up: the artifact that was tested and
the artifact that ships are two different builds. Digest and platform *inspection* is not a smoke
test; it proves the manifest exists, not that the container runs.

After push and before any alias moves: pull the published index by digest, resolve the descriptor
matching the runner's own architecture, and re-run the container smoke test
(`LiquidLogicLabs/git-action-docker-test@v2`) against it.

**Stated limit, because it should not be discovered later:** only the native descriptor is
executed. The non-native platform is covered by the argument ADR-0008 now records — the wheel is
`py3-none-any`, so the *same file with the same SHA-256* is installed into both images, and the
base is digest-pinned — plus platform inspection. That is provenance, not execution, and the
runbook should say so.

## The tag race is accepted, and that acceptance is a record not an oversight (F16)

`just release` pushes the branch and the tag **atomically**, so one operation fires a `push`
event on `main` *and* a tag event. Dev suppression depends on `dev.yaml` observing the exact
stable tag on the source commit — and the forge guarantees no ordering between the two.

If the tag is not yet visible when the dev run's guard job evaluates, an **immutable,
unretractable** `X.Y.(Z+1).dev0` is published for the release commit. It cannot be withdrawn;
the recovery is a new development version.

**This was knowingly accepted** — tagging drives the release, and serialising the two events
would mean giving up the atomic two-ref push that ADR-0006 exists to provide. The superseded
plan recorded that acceptance; the rewrite dropped the record, so the next reader met it as a
bug rather than a decision. It is recorded here again for that reason.

**Cheap hardening, which does not remove the race:** re-run `git fetch --tags` and
`git describe --exact-match` immediately before the **first credentialed dev step**, not only in
the guard job. That shrinks the window from "guard job start → upload" to "check → upload"
without pretending it is closed.

**Test anchor:** plant a tag arriving between the guard job and the upload; suppression must
still fire.

## Definition of Done

- `dev.yaml` owns protected default-branch pushes and uses workflow concurrency to cancel/supersede
  stale candidates.
- Required forge and enabled external immutable publications consume one verified artifact set.
- The image job receives only enabled registry credentials; package credentials remain job-local.
- Tests cover forge fail-closed, full-history derivation, stable-tag suppression, coordinate
  validation, one verifier call, one Buildx invocation, two platforms, and secret isolation.
- Run evidence records run ID/URL, manifest/artifact hashes, published digest/platforms, and
  destination conclusions without adding a schema (CI-AR37, CI-AR41).

## Test anchors

Guard, then the violation planted to prove it fires:

- Forge fail-closed: unknown forge hits a non-zero fallthrough; plant deleting that branch.
- Full-history derivation: parsed checkout keeps full depth and tags; plant deleting the key while
  leaving the comment explaining it.
- Stable-tag suppression: every publisher is transitively gated on the suppression job; plant one
  that is not (scope attack).
- Coordinate validation: `FORGE_REGISTRY` rejects userinfo, path, query, fragment, foreign host;
  plant an unanchored pattern.
- One verifier call: parsed verifier `uses:` in `dev.yaml` counts one; plant a second elsewhere.
- One Buildx invocation: one build-push step carries both platforms and all tags; plant a
  per-registry second build.
- Secret isolation: per-job secret references stay disjoint; plant a registry credential in the
  package job.
