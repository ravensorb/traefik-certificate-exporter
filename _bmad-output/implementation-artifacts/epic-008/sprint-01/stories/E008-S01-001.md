# Plan, Preflight, and Publish a Development Package

As a maintainer,
I want one deterministic development plan that validates destinations and optionally publishes to TestPyPI,
So that default-branch packages are unique, verified, and fail closed before mutation.

Depends on: `E007-S01-005`.

## Acceptance Criteria

**Given** `.github/workflows/dev.yaml` is present
**When** a commit is pushed to the protected default branch
**Then** the workflow starts and checks out full first-parent and stable-tag history
**And** pushes to other branches do not trigger it

**Given** the committed Poetry version is `X.Y.Z` and the matching exact stable tag is present
**When** the planning job calculates the development identity
**Then** it computes `N` once as the first-parent commit count from `vX.Y.Z` to the event SHA
**And** emits the public PEP 440 version `X.Y.(Z+1).devN`
**And** records the full source SHA separately rather than using a `+sha` local-version suffix (CI-AR17)

**Given** the development version has been calculated
**When** downstream jobs execute
**Then** they consume the planned version and recorded `N` without recomputing either value
**And** no Git tag, commit, or persistent repository version change is created

**Given** the event commit is already referenced by an exact stable tag
**When** the plan is evaluated
**Then** the reusable verifier may still run
**And** every development package, image, login, and alias operation is suppressed because the tag event exclusively owns publication for that commit

**Given** publication variables are absent or present
**When** the plan normalizes them
**Then** only `PUBLISH_IMAGE_DOCKERHUB`, `PUBLISH_IMAGE_FORGE`, and development-applicable `PUBLISH_PACKAGE_TESTPYPI` can enable development destinations
**And** absent values normalize to false
**And** case-normalized `true` and `false` are accepted while any other value fails planning (CI-AR19)

**Given** the workflow is executing on GitHub.com or a supported self-hosted host
**When** forge coordinates are planned
**Then** the forge kind is derived from `github.server_url`, owner/repository context, and the documented `FORGE_REGISTRY` override only when safe derivation is impossible
**And** no operator-maintained GitHub/Gitea mode switch or cross-forge target is introduced (CI-AR1, CI-AR20)

**Given** all non-secret values are known
**When** the planning job completes
**Then** the publication-contract action emits schema-valid `publication-plan-v1.json` with package version, source SHA, development distance, normalized coordinates, credential modes, enabled destinations, immutable `dev-<12-character-sha>` tags, and `dev` aliases
**And** the plan is retained for 30 days and passed within the same workflow run (CI-AR21, CI-AR22)

**Given** the development publication plan enables zero optional destinations
**When** aggregate preflight runs
**Then** it succeeds with `publication-ready=true` without reading publisher secrets, requesting OIDC, logging into a registry, or starting a publication job

**Given** TestPyPI, Docker Hub, the active forge registry, or any combination is enabled
**When** preflight evaluates required destinations
**Then** it validates every enabled endpoint, normalized namespace/repository, credential mode, required username/token pair or protected OIDC environment, permission expectation, and CA input before any publisher authenticates (CI-AR24)

**Given** any enabled destination is incomplete, malformed, unreachable under the supported contract, or missing a required credential
**When** preflight runs
**Then** it fails the complete development publication fan-out
**And** no registry login, package upload, image build/push, or alias mutation occurs

**Given** a destination is disabled
**When** jobs and action inputs are evaluated
**Then** that destination's secrets are not mapped, its authentication action does not run, and its endpoint is not contacted

**Given** preflight succeeds
**When** it exposes caller-visible state
**Then** its only success output is the non-sensitive aggregate value `publication-ready=true`
**And** it never prints credential values, token lengths, secret-derived hashes, or secret-derived diagnostics

**Given** a mutation job is part of development publication
**When** its dependencies are inspected
**Then** it declares `needs` on the planning job, aggregate preflight, and successful `verify-build`
**And** it validates the downloaded plan and build manifest before passing credentials to an external action or command (CI-AR28)

**Given** `PUBLISH_PACKAGE_TESTPYPI` is false or absent
**When** `dev.yaml` succeeds
**Then** no TestPyPI environment, OIDC permission, API token, endpoint call, or package publisher executes

**Given** `PUBLISH_PACKAGE_TESTPYPI` is true and preflight plus verification succeed
**When** the TestPyPI publisher starts
**Then** it downloads `verified-dist-v1` from the same workflow run
**And** validates artifact layout, `SHA256SUMS`, build-manifest schema/hash, planned version, and source SHA before requesting credentials

**Given** GitHub.com owns the repository and trusted publishing is configured
**When** upload runs
**Then** only the top-level protected `testpypi` publisher job receives `id-token: write`
**And** `pypa/gh-action-pypi-publish@release/v1` uploads the exact wheel and sdist to TestPyPI
**And** the reusable verifier never receives OIDC permission or environment secrets

**Given** the planned development version is absent remotely
**When** upload succeeds
**Then** TestPyPI exposes exactly the manifest-recorded wheel and sdist hashes under `X.Y.(Z+1).devN`
**And** stable PyPI and every forge Release remain untouched

**Given** the same development version already exists during a rerun
**When** remote identity is checked
**Then** matching filenames and SHA-256 hashes are accepted as already complete
**And** any missing file is uploaded only when the index contract permits it
**And** any hash mismatch or unverifiable existing identity is a hard failure without replacement (CI-AR26)

**Given** TestPyPI publication fails
**When** later development visibility steps are evaluated
**Then** no `dev` image alias advances even if immutable images succeeded
**And** the previous successful development pointers remain intact (CI-AR25)

**Given** the development package publisher is uploading and a newer default-branch push supersedes the run
**When** the workflow-level cancellable concurrency group fires
**Then** the publisher is not interrupted, because it declares its own job-level non-cancellable concurrency group
**And** a workflow-level `cancel-in-progress: true` group cancels the entire superseded run including jobs already executing, so a publisher's position in the `needs:` graph protects nothing (CI-AR27)
**And** an upload cancelled midway is precisely how a half-published development set arises — the wheel accepted by the index, the sdist not, and no receipt to say which

## Technical Acceptance Criteria

### Interface contracts

**Given** `.github/workflows/dev.yaml` is added
**When** its trigger and top-level keys are inspected
**Then** `on:` contains exactly `push` with `branches: [main]` and no `tags:` filter, so an exact stable tag push reaches `release.yaml` and never this workflow
**And** workflow-scope `permissions:` is `contents: read`, with escalation only at job scope
**And** `concurrency:` uses group `${{ github.workflow }}-${{ github.ref }}` with `cancel-in-progress: true`, which is intended for planning and verification: superseding an obsolete plan for the same ref is desirable and is why the workflow-level group stays cancellable
**And** that group does **not** scope cancellation to planning and verification, and no configuration can make it do so: when a new run enters the group GitHub cancels "any currently running job or workflow in the same concurrency group" — the whole superseded run, jobs already executing included
**And** every job that mutates a remote destination therefore declares its own job-level non-cancellable `concurrency` block — `publish-testpypi` here, `publish-images` and `finalize-dev-alias` in `E008-S01-002` — because a job's position in the `needs:` graph confers no protection from that cancellation whatsoever

**Given** the job graph is inspected
**When** `needs:` edges are resolved
**Then** the graph is `plan` -> `verify` -> `preflight` -> `publish-testpypi`, with the image jobs of E008-S01-002 attaching to the same `plan`/`preflight`/`verify` fan-in
**And** `verify` is `uses: ./.github/workflows/verify-build.yaml` at job level with `channel: dev`, `package-version: ${{ needs.plan.outputs.package-version }}`, `source-sha: ${{ needs.plan.outputs.source-sha }}` and no `secrets:` key
**And** `publish-testpypi` declares `needs: [plan, preflight, verify]` so `test_any_push_triggered_workflow_verifies_before_it_ships` resolves the verifier in its transitive needs

**Given** the `plan` job runs
**When** its steps are inspected
**Then** it checks out with `fetch-depth: 0`, `fetch-tags: true`, `persist-credentials: false`, `ref: ${{ github.sha }}`
**And** it resolves the committed version through `./.github/actions/setup-poetry-python`, whose `package-version` output is produced by `scripts/committed_versions.py`; the job contains no `tomllib`, no `import` statement in a `run:` block, and no second version reader, as `test_the_committed_version_authority_has_one_implementation` requires of every `plan` job on disk
**And** it emits outputs `package-version`, `base-version`, `development-distance`, `source-sha`, `suppressed`, `plan-artifact-name`

**Given** the development distance is computed
**When** the plan job derives `N`
**Then** it runs `git rev-list --count --first-parent "v${BASE_VERSION}..${GITHUB_SHA}"` exactly once
**And** an absent `v${BASE_VERSION}` tag, a `${GITHUB_SHA}` that is not a descendant of it, or a non-zero exit fails the job before any downstream edge is taken
**And** the value is written into `publication-plan-v1.json` and is not recomputed by any other job

**Given** `scripts/committed_versions.py` is the single version authority
**When** `development_version(distance)` is called
**Then** it returns `X.Y.(Z+1).devN` derived from the committed `X.Y.Z`, not the current `X.Y.Z.devN`
**And** its docstring no longer names release-please as a version owner (retired by ADR-0006)
**And** the accompanying assertion in `tests/ci/test_workflow_contracts.py::test_the_committed_version_authority_has_one_implementation` is updated to the next-patch form

**Given** the `preflight` job runs
**When** its interface is inspected
**Then** its single output is `publication-ready`, whose only success value is the literal `true`
**And** it declares no `id-token: write`, performs no `docker/login-action`, and issues no authenticated request; it validates only plan-derived non-secret shape plus the presence — never the content — of each required credential

**Given** the `publish-testpypi` job runs
**When** its interface is inspected
**Then** it declares `permissions: { contents: read, id-token: write }` at job scope only, `environment: testpypi`, and an `if:` gated on `needs.plan.outputs.suppressed == 'false'` and the plan's TestPyPI destination being enabled
**And** it downloads `verified-dist-v1` with `actions/download-artifact@v4` and the plan artifact, revalidates both through `./.github/actions/publication-contract`, and only then invokes `pypa/gh-action-pypi-publish@release/v1` with `repository-url` taken from the plan's package endpoint

**Given** `publish-testpypi` is the development channel's immutable package publisher
**When** its concurrency is inspected
**Then** it declares its own job-level `concurrency` block with `cancel-in-progress: false`, grouped per destination and development identity: `dev-immutable-testpypi-${{ needs.plan.outputs.source-sha }}`
**And** this is the same rule `E008-S01-004` states for the stable channel's `publish-pypi` and `publish-images`, applied to the development channel with the same shape and vocabulary rather than a second idiom
**And** the key is the source SHA rather than the planned version, because the source SHA is the development identity the immutable artifacts are named for; a rewritten default-branch history can reproduce a `.devN` version for a different commit, and two different commits must never share one publication lock
**And** the group is distinct from `E008-S01-002`'s `dev-immutable-images-...` publisher group and from its `dev-alias-finalization` single-writer lock: the two publishers mutate disjoint destinations, and holding the alias lock across a multi-minute upload would queue every development run behind every other run's package upload
**And** the workflow-level `${{ github.workflow }}-${{ github.ref }}` group is not a substitute for this block; it is `cancel-in-progress: true`, so it is the hazard the block exists to defend against

### Data model

**Given** `publication-plan-v1.schema.json` as packaged today
**When** the development plan is written
**Then** the schema is extended, because the current document is `additionalProperties: false` over a single `registry`/`repository`/`package_endpoint`/`credential_mode` quadruple and cannot represent a development distance, more than one image registry, or per-destination credential modes and enablement
**And** the extension is additive and keeps `schema_version` at the constant `publication-plan-v1`, which is safe because no producer of this contract exists in any workflow today, so no already-published artifact can be invalidated
**And** the same change updates `src/publication_contract/contract.py`, the action's declared outputs, and `tests/ci/test_publication_contract.py` in one commit

**Given** the extended plan document
**When** its fields are enumerated
**Then** it must be able to express, at minimum: `development_distance` (integer, minimum 0, required when `channel` is `dev`), a `package_targets` array of `{name, endpoint, enabled, credential_mode}`, an `image_targets` array of `{registry, repository, enabled, credential_mode}`, and a `run` object carrying forge kind, server URL, repository, run id and run attempt for correlation
**And** `tags.immutable` for the development channel is exactly `["dev-<first 12 characters of source_sha>"]` and `tags.aliases` is exactly `["dev"]`
**And** no field may hold a credential value, a credential length, or a credential-derived hash

**Given** `build-manifest.json` is produced by the verifier
**When** the development distance is recorded
**Then** it is **not** carried through a new verifier input: `test_verifier_supports_call_and_direct_dispatch_with_the_same_graph` pins the `workflow_call`/`workflow_dispatch` input set to exactly `channel`, `package-version`, `source-sha`, and AD-2 states the verifier "accepts only" that triple
**And** `N` is therefore recoverable from the planned version's `.devN` segment and is recorded authoritatively in `publication-plan-v1.json`
**And** `build-manifest-v1`'s existing optional `development_distance` property remains unset for this story (see the open question below)

### Error handling and edge cases

**Given** a repository variable holds a value other than a case-insensitive `true` or `false`
**When** the plan normalizes toggles
**Then** planning exits non-zero with the offending variable named and the value quoted, before any destination is marked enabled
**And** shell truthiness is never used: normalization happens in `publication_contract`, not in a bash `if [ "$VAR" ]`

**Given** the event commit is already referenced by an exact stable tag
**When** the plan evaluates suppression
**Then** `git tag --points-at "$GITHUB_SHA"` matching strict `v<major>.<minor>.<patch>` sets `suppressed=true`
**And** `verify` still runs, and every publisher and alias job is skipped by `if:`, not by an internal early-return that would still map secrets into the job

**Given** the same commit is pushed twice, or a tag event and a branch event race
**When** two `dev.yaml` runs exist
**Then** the ref-scoped cancellable concurrency group cancels the superseded verification, and suppression prevents a branch run from publishing a commit the tag event owns
**And** that ref-scoped group cancels the *whole* superseded run, jobs already executing included, so it would interrupt `publish-testpypi` mid-upload: sitting behind `plan`, `verify` and `preflight` in the `needs:` graph is not protection, and a non-cancellable finalizer group protects only the finalizer
**And** the publisher survives supersession only because of its own job-level `cancel-in-progress: false` group; that block, not graph position, is what makes "immutable publication is non-cancellable" true

**Given** TestPyPI reports the version already present on a rerun
**When** identity is reconciled
**Then** the publisher compares the remote filenames and SHA-256 values against `build-manifest.json` before deciding
**And** an exact match is reported as already-complete and the job succeeds without upload
**And** a mismatch, a partially present file set that the index refuses to complete, or an unverifiable remote object fails the job without any delete, overwrite, or `--skip-existing` style silent pass

**Given** a required credential for an enabled destination is absent
**When** preflight evaluates it
**Then** the job fails and names the destination and the missing configuration key, never the value
**And** the failure blocks the whole fan-out, not only the affected destination

### Observability

**Given** the plan job completes
**When** its logs and artifacts are inspected
**Then** the full `publication-plan-v1.json` is echoed to the step summary, which is safe because the schema forbids secret material
**And** it is uploaded as an artifact with `retention-days: 30`, matching `verified-dist-v1`'s window so a recovery run has both halves or neither

**Given** BL-E007-005 records that no evidence artifact carries run correlation
**When** the plan is written
**Then** the plan's `run` object closes it for the publication path by recording `github.run_id`, `github.run_attempt`, `github.repository` and `github.server_url`
**And** `build-manifest.json` deliberately does **not** gain those fields: it must stay byte-identical for identical source, and a run id would make every rebuild differ

**Given** the TestPyPI publisher completes
**When** its log is read
**Then** it states the planned version, the wheel and sdist filenames, their manifest hashes, the endpoint host, and whether the outcome was `uploaded` or `already-present-identity-matched`

### Security

**Given** the verifier pair is governed by tier two
**When** `dev.yaml` is added
**Then** `ci.yaml` and `verify-build.yaml` remain the only members of `SECRET_FREE_WORKFLOWS`, and `dev.yaml` is legitimately outside it because a publisher that cannot hold a credential is not a publisher
**And** tier one still applies to `dev.yaml`: every external action must come from `actions`, `docker`, `pypa` or `LiquidLogicLabs` and use a `vN` or `release/vN` alias, and no `uses:` may be expression-interpolated

**Given** trusted publishing is the GitHub credential model
**When** the TestPyPI publisher authenticates
**Then** it uses `id-token: write` scoped to that one job plus a protected `testpypi` environment, and no long-lived API token is stored for the GitHub-hosted path
**And** a long-lived `TESTPYPI_API_TOKEN` remains reserved for the Gitea host of Epic 9 and is not introduced here

**Given** `dev.yaml` is scanned by the repository-write guards
**When** `test_no_workflow_holds_github_token_write_access_to_contents` and `test_no_workflow_writes_refs_or_releases_outside_a_finalizer` run
**Then** no job in `dev.yaml` declares `contents: write`, runs `git push`, runs `gh release`, or uses a release-creating action
**And** no job name from `dev.yaml` is added to `RELEASE_FINALIZER_JOBS`

### Testability

**Given** the guards this story must keep green
**When** the test suite runs
**Then** `test_any_push_triggered_workflow_verifies_before_it_ships` stops passing vacuously and asserts `dev.yaml`'s publishers transitively need `verify`
**And** `test_the_committed_version_authority_has_one_implementation` now examines two `plan` jobs
**And** `test_no_workflow_calls_a_local_workflow_or_action_that_does_not_exist` covers `dev.yaml`'s verifier reference
**And** `test_governance_scope_is_derived_from_disk` picks `dev.yaml` up from the glob with no edit

**Given** a new guard asserting the development identity rule
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts that no job in any workflow recomputes the first-parent distance — that `rev-list --count --first-parent` appears in exactly one `plan` job and nowhere else
**And** the planted violation is a second `git rev-list --count --first-parent` step added to `publish-testpypi`; the guard must fail on it before the guard is accepted

**Given** the toggle-normalization guard
**When** it is added to `tests/ci/test_publication_contract.py`
**Then** it asserts `TRUE`, `True`, `true`, `FALSE`, `False`, `false` and the empty/absent case normalize, and that `1`, `yes`, `on`, ` true ` and `truthy` raise
**And** the planted violation is a normalizer that falls back to Python truthiness; it must turn `yes` into an enabled destination and the test must catch it

**Given** the suppression guard
**When** it is added
**Then** an event fixture `tests/ci/fixtures/workflows/push-main-tagged.json` carries a `sha` that a companion fixture marks as tag-pointed, and the guard asserts every publisher job's `if:` references `needs.plan.outputs.suppressed`
**And** the planted violation removes the `suppressed` term from one publisher's `if:`

**Given** the non-cancellable-publisher guard for the development channel
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts that every job which mutates a remote destination declares a job-level `concurrency` block whose `cancel-in-progress` is literally `false`, with the job set derived from the parsed workflows — every job whose steps invoke `pypa/gh-action-pypi-publish@`, `docker/bake-action@` or `imagetools create` — never from a hand-listed set of job names, since a name-enumerated set silently stops covering the next publisher anyone adds
**And** it is `E008-S01-004`'s guard widened in scope to `dev.yaml` rather than a second parallel guard, so one rule covers both channels and cannot drift between them
**And** the planted violation is a new development publisher job with **no** `concurrency` block at all; a guard that merely checks `cancel-in-progress: true` is absent would wrongly pass it, because an absent block inherits the cancellable workflow-level group and is therefore cancellable
**And** a second planted violation sets `cancel-in-progress: true` on `publish-testpypi`; the guard must fail on it before the guard is accepted

**Given** the schema extension
**When** `tests/ci/test_publication_contract.py` runs
**Then** a fixture development plan validates, and negative fixtures fail for: a missing `development_distance` on the `dev` channel, an immutable tag whose SHA segment is not 12 characters, an alias set other than `["dev"]`, and any property whose name matches the existing credential-name pattern

## Open questions

1. **Where does `N` live for a consumer that has only the build manifest?** AD-3 says `N` is "recorded in `build-manifest.json`", but the verifier's input triple is pinned by AD-2 and by `test_verifier_supports_call_and_direct_dispatch_with_the_same_graph`, so the verifier cannot be told the distance without relaxing a governed contract. This story assumes `N` lives in `publication-plan-v1.json` and is recoverable from the `.devN` segment of the version the verifier already receives. If a consumer genuinely needs it inside the manifest, that is an AD-2 amendment, not a workflow edit.
2. **Is `X.Y.Z.devN` a released defect or merely unimplemented?** `committed_versions.development_version` currently returns `X.Y.Z.devN`, which sorts *below* the released `X.Y.Z` under PEP 440 and would advertise post-release work as older than the release. No workflow calls it today, so nothing has shipped wrong; this story fixes it. Recorded here so the fix is not mistaken for a gratuitous behaviour change.
3. **`FORGE_REGISTRY` override semantics.** The epic permits it "only when safe derivation is impossible". Nothing in the spine or the ADRs defines what makes derivation impossible on GitHub.com, where `github.server_url` is always conclusive. This story assumes the override is accepted but unused on GitHub and is genuinely exercised only by Epic 9; if it must be rejected outright on GitHub.com, that is a policy decision for the maintainer.
