# Publish and Advance Verified Development Images

As a development-image consumer,
I want one verified multi-architecture image published to enabled registries with a forward-only `dev` alias,
So that registry choice and out-of-order completion cannot change or regress the code I run.

Depends on: `E007-S01-005`. Shares `dev.yaml`'s `plan`, `verify` and `preflight` jobs with `E008-S01-001`.

## Acceptance Criteria

**Given** the event commit is already referenced by an exact stable tag
**When** the plan reports suppression from its tags-fetched checkout
**Then** the image publisher, the image verifier, and the `dev` alias finalizer are all skipped, because the tag event exclusively owns publication for that commit
**And** no registry login, image build, image push, or `dev` alias operation occurs, even though the forge image registry is an always-on destination and Docker Hub may also be enabled
**And** `dev` is therefore never dragged onto a commit that `latest` also points at

**Given** an exact stable tag appears for the event commit after the run started
**When** the finalizer takes the alias lock
**Then** it refetches tags and re-evaluates exact-stable-tag ownership inside the lock, not only at plan time
**And** it declines to move `dev` when the commit has become tag-owned, and succeeds without mutation

**Given** the owning forge's image registry — GHCR on GitHub, the local registry on Gitea
**When** the development plan enumerates image destinations
**Then** it is always present and always enabled, and Docker Hub is the only optional image destination on this channel (maintainer decision, `docs/ci/codex-assesment.md`, "2b. The forge IMAGE registry is always on too")
**And** no `PUBLISH_IMAGE_FORGE` variable exists, so there is no `false` normalization path for it, no disabled branch that maps no secrets, and no destination-enabled term in any image job's `if:`
**And** it is not host-conditional the way the forge *package* destination is: every supported forge has an image registry, so this destination exists on GitHub.com and on Gitea alike, and its absence is never a derived host fact
**And** CI-AR20 and CI-AR21a are already amended to say so, so this story consumes the amendment rather than owing it

**Given** `PUBLISH_IMAGE_DOCKERHUB` is false or absent
**When** development publication runs
**Then** no Docker Hub login, credential mapping, Docker Hub tag, or Docker Hub alias operation occurs
**And** the image publisher, the image verifier and the `dev` alias finalizer still run, because that toggle governs one external destination and not the image channel as a whole
**And** there is therefore no configuration in which the three image jobs are skipped for a destination reason; only exact-stable-tag suppression withholds them

**Given** the image publisher runs for the always-on forge registry, and for Docker Hub when it is enabled
**When** the image publisher starts
**Then** it revalidates the publication plan, `verified-dist-v1`, `SHA256SUMS`, build manifest, wheel hash, version, and source SHA before any registry login
**And** each enabled registry login is independently gated and destination-scoped

**Given** the forge image registry is an always-on destination
**When** registry authentication occurs
**Then** GHCR uses the job token with only `packages: write`, and that login is unconditional rather than gated on an enablement value
**And** Docker Hub, when enabled, uses `DOCKERHUB_USERNAME` and a repository-scoped `DOCKERHUB_TOKEN`
**And** disabled registry credentials are not mapped into the job (CI-AR28)

**Given** the immutable image tag list is prepared
**When** LiquidLogicLabs Docker metadata and Bake receive it
**Then** each enabled repository receives only `dev-<12-character-sha>` during the build/push operation
**And** OCI labels include the planned version, full revision, source URL, creation time, title, description, license, and portable workflow-run identity

**Given** the always-on forge registry, plus Docker Hub when it is enabled
**When** publication builds the image
**Then** one `docker/bake-action` invocation consumes the shared `docker-bake.hcl`, exact verified wheel, and combined immutable tag list
**And** it builds `linux/amd64` and `linux/arm64` once and pushes the same manifest inputs to every enabled registry (CI-AR13, CI-AR23)

**Given** the multi-platform build is published
**When** BuildKit output is inspected
**Then** SBOM and `mode=max` provenance attestations exist
**And** caches, attestations, logs, and build arguments contain no registry or package credentials
**And** no `dev` alias is included in the build invocation

**Given** an immutable development tag already exists on rerun
**When** its digest and recorded source/version labels are compared
**Then** an exact identity match is reused
**And** a mismatch fails without overwriting the tag or building a replacement (CI-AR26)

**Given** an immutable development image was published to an enabled registry
**When** remote verification begins
**Then** the manifest list is resolved to its immutable digest
**And** it contains exactly the declared `linux/amd64` and `linux/arm64` platform entries

**Given** each declared platform digest
**When** validation runs on native or configured QEMU support
**Then** the image is pulled by digest rather than mutable tag
**And** its entrypoint, s6 startup, CLI behavior, package runtime version, OCI version label, and full revision label match the build and publication manifests

**Given** Docker Hub is enabled alongside the always-on forge registry
**When** remote manifests are inspected
**Then** both immutable names resolve to the expected manifest identity and equivalent platform digests
**And** verification evidence identifies each registry and platform independently

**Given** a platform is missing, cannot start, reports a wrong version/revision, has an unexpected entrypoint, or resolves to a different digest
**When** verification runs
**Then** development publication fails
**And** no moving `dev` alias is created or updated in any registry

**Given** all declared platforms pass
**When** the image-verification job completes
**Then** it exposes only non-secret verified digest identities to the alias-finalization job
**And** it performs no rebuild or alias mutation

**Given** all enabled development package and immutable image publishers and platform checks succeed
**When** alias finalization becomes eligible
**Then** it enters a dedicated non-cancellable single-writer concurrency group shared by all development runs
**And** a failed enabled publisher prevents alias finalization entirely (CI-AR25, CI-AR27)

**Given** the finalizer holds the concurrency lock
**When** it examines the current remote `dev` manifest
**Then** it reads and validates the source SHA and first-parent distance recorded in that manifest
**And** it refetches protected default-branch history immediately before mutation rather than trusting a pre-lock check

**Given** no `dev` alias exists or the candidate is a greater descendant with a larger first-parent distance
**When** every enabled registry is eligible
**Then** each `dev` alias is created from the verified immutable digest using a manifest-copy operation
**And** no Dockerfile execution, package installation, or image rebuild occurs

**Given** the remote `dev` candidate is newer, unrelated, malformed, or unverifiable
**When** a stale or unsafe run finalizes
**Then** it succeeds without moving the alias backward when the remote is a valid newer descendant
**And** it fails closed without mutation for unrelated, malformed, or unverifiable state

**Given** alias mutation succeeds for one registry but fails for another
**When** the same commit is rerun within the 30-day recovery window
**Then** matching immutable images and already-correct aliases are reused
**And** only missing or older eligible aliases are reconciled
**And** every digest mismatch remains a hard failure without replacement (CI-AR26)

**Given** two default-branch pushes complete out of order
**When** their finalizers run serially
**Then** `dev` ultimately resolves to the greatest successfully published first-parent distance
**And** a newer failed build leaves the previous successful alias unchanged

**Given** development workflow concurrency is configured
**When** a newer run arrives
**Then** superseded planning and verification work may be cancelled before mutation begins
**And** the workflow-level `cancel-in-progress: true` group cancels the entire superseded run — any currently running job included, not only the jobs that have yet to start — so it would otherwise cancel an image push already in flight
**And** immutable image publication is not cancelled mid-push, because the image publisher declares its own job-level non-cancellable concurrency group, per destination and per development identity, distinct from the `dev` alias-finalization group (CI-AR27)
**And** an acquired alias-finalization operation is likewise not cancelled mid-mutation, for the same reason: its own non-cancellable group
**And** a push cancelled mid-write is precisely how a half-published image set arises — one enabled registry written, another not, and no receipt to say which

**Given** development-channel behavior is documented
**When** an operator configures it
**Then** the guide covers the two applicable toggles, the always-on forge image and forge package destinations and why neither has one, required credentials/environments, immutable and moving tag meanings, multi-registry behavior, out-of-order completion, and 30-day identity-based reruns (CI-AR35)

## Technical Acceptance Criteria

### Interface contracts

**Given** the image half of `dev.yaml`
**When** its job graph is inspected
**Then** it adds `publish-images` (needs `plan`, `preflight`, `verify`), `verify-images` (needs `publish-images`) and `finalize-dev-alias` (needs `verify-images`, `publish-forge-package` and `publish-testpypi`)
**And** `finalize-dev-alias` also needs the two package publishers so a failed package publisher blocks the alias, which is the only way the "a package failure stops the `dev` alias" rule can hold in a DAG
**And** its guard distinguishes disabled from failed exactly as `E008-S01-004`'s stable finalizer does, and for the same reason: `needs.verify-images.result == 'success' && needs.publish-forge-package.result == 'success' && needs.publish-testpypi.result != 'failure'`
**And** the two always-on destinations are tested with `== 'success'` rather than `!= 'failure'` precisely because neither can be skipped-because-disabled: `!= 'failure'` also accepts `skipped`, and an always-on publisher that did not succeed is a run that must not advance a visible pointer
**And** every one of the three image jobs is gated by `if:` on `needs.plan.outputs.suppressed == 'false'` and nothing else: with the forge image registry always on there is no destination-enabled term left to carry, and adding one back would be the defect the destination-model guard exists to catch
**And** Docker Hub's enablement is expressed at step scope — on its login step and its contribution to the tag list — never at job scope, so a disabled Docker Hub cannot skip a job the forge registry needs

**Given** the tag event exclusively owns publication for its commit
**When** the three image jobs evaluate suppression
**Then** each reads `needs.plan.outputs.suppressed` — the value `E008-S01-001`'s `plan` job derives from a checkout made with `fetch-tags: true` — and none re-derives it with its own `git tag --points-at`
**And** suppression is expressed as an `if:` on the job, never as an early `exit 0` inside a job that has already mapped registry credentials, because a skipped job maps no secret and an exited one already has
**And** `finalize-dev-alias` carries the suppression term in addition to its concurrency group, so a suppressed run never acquires the `dev` alias lock at all

**Given** `publish-images` runs
**When** its steps are inspected
**Then** the order is: download `verified-dist-v1` and the plan artifact; revalidate both through `./.github/actions/publication-contract` (`verify-checksums`, then `validate --contract build-manifest`, then `validate --contract publication-plan`); assert the wheel hash equals the manifest's `image_plan.build_args.WHEEL_SHA256`; only then `docker/login-action@v4`, once per enabled registry
**And** each login is scoped to its destination: the forge registry's `docker/login-action@v4` step carries no `if:` at all, and Docker Hub's carries the only destination condition in the job
**And** `docker/setup-qemu-action@v4` and `docker/setup-buildx-action@v4` run only inside this job, and run unconditionally within it, because at least one image destination — the forge registry — is always enabled
**And** `LiquidLogicLabs/git-action-docker-metadata@v6` produces labels, and `docker/bake-action@v7` is invoked exactly once with `files: docker-bake.hcl`, `targets: image`

**Given** `docker-bake.hcl` is the sole declarative target
**When** the publisher overrides it
**Then** it sets only the documented dynamic variables: `WHEEL_PATH`, `WHEEL_SHA256`, `VERSION`, `REVISION`, `LABELS_JSON`, `TAGS`, `PLATFORMS`, `OUTPUTS`, `ATTESTATIONS`
**And** `TAGS` is the concatenation of `<registry>/<repository>:dev-<12-character-sha>` across enabled targets, taken from the plan and never assembled from `github.*` context in the publisher
**And** `PLATFORMS` is `["linux/amd64","linux/arm64"]`, `OUTPUTS` is `["type=registry"]`, and `ATTESTATIONS` is `["type=sbom","type=provenance,mode=max"]`
**And** no parallel `docker buildx build` command is introduced anywhere in the workflow

**Given** `verify-images` runs
**When** its interface is inspected
**Then** it needs no registry write capability: it may hold `packages: read` for GHCR and reuse the Docker Hub login only for pulls
**And** its single output is a JSON array of `{registry, repository, digest, platforms}` objects, non-secret, consumed by the finalizer
**And** it uses `docker buildx imagetools inspect` for manifest resolution and `docker run --platform` by digest for the runtime check

**Given** `publish-images` is the development channel's immutable image publisher
**When** its concurrency is inspected
**Then** it declares its own job-level `concurrency` block with `cancel-in-progress: false`, grouped per destination and development identity: `dev-immutable-images-${{ needs.plan.outputs.source-sha }}`
**And** this is the rule `E008-S01-004` states for the stable channel's immutable publishers, applied to the development channel with the same shape and vocabulary rather than a second idiom
**And** the group is deliberately not `dev-alias-finalization`: that is a single-writer lock across every development run, and extending it across a multi-minute multi-registry push would queue every run behind every other run's build, for a lock that exists only to serialize alias writes
**And** it is deliberately not `E008-S01-001`'s `dev-immutable-testpypi-...` group either: the two publishers mutate disjoint destinations, so one shared group would serialize them against each other inside a single run and halve the fan-out for no safety gain
**And** `dev.yaml`'s workflow-level `${{ github.workflow }}-${{ github.ref }}` group is necessary but not sufficient here: it is `cancel-in-progress: true` and cancels the whole superseded run, every executing job included, so it is the hazard this block defends against rather than a substitute for it

**Given** `finalize-dev-alias` runs
**When** its concurrency is inspected
**Then** it declares job-level `concurrency: { group: dev-alias-finalization, cancel-in-progress: false }` — a fixed literal group shared by every development run, deliberately not keyed on `github.ref` or `github.run_id`
**And** the alias write is `docker buildx imagetools create --tag <registry>/<repository>:dev <registry>/<repository>@<digest>`, a digest-only manifest copy — confirmed as the executor by the 2026-09-01 decision, with `crane` and `regctl` remaining outside the approved-owner allowlist and not adopted

### Data model

**Given** the finalizer must read the first-parent distance recorded by the *current remote* `dev` manifest
**When** the label set is planned
**Then** the standard OCI label set cannot carry it, so a project label is added — `org.opencontainers.image.version` already encodes `X.Y.(Z+1).devN` and the finalizer parses `N` from the `.devN` segment rather than introducing a second, drift-prone source
**And** if a distinct label is preferred instead, it must be added to `build-manifest-v1`'s `image_plan.labels` (which already permits additional string properties) *and* to `docker-bake.hcl`'s label merge, in the same change — see the open question

**Given** `publication-plan-v1.json` as extended by `E008-S01-001`
**When** the image jobs consume it
**Then** `image_targets` supplies every registry, repository and credential mode, and no job derives a registry host, namespace or tag from `github.repository`, `github.actor` or a hard-coded string
**And** `tags.aliases` supplies the literal `dev`; the finalizer never spells the alias itself

**Given** `build-manifest-v1`
**When** this story runs
**Then** no schema change is required: `image_plan.fingerprint`, `build_args.WHEEL_SHA256` and `labels` already carry everything the publisher revalidates

### Error handling and edge cases

**Given** `PUBLISH_IMAGE_DOCKERHUB` is false
**When** the run executes
**Then** the Docker Hub login step and its tag contribution are skipped inside a job that still runs for the always-on forge registry, so no Docker Hub credential is ever mapped
**And** there is no longer a "no image job runs" state to test at all: the earlier form of this rule assumed both image destinations could be off at once, which the removal of `PUBLISH_IMAGE_FORGE` makes unrepresentable
**And** the only state in which QEMU, Buildx and every login step live inside skipped jobs is exact-stable-tag suppression

**Given** an immutable `dev-<sha>` tag already exists in an enabled registry
**When** the publisher reconciles it
**Then** it resolves the existing manifest by digest and compares the platform set, `org.opencontainers.image.version` and `org.opencontainers.image.revision` against the plan and build manifest
**And** an exact match skips the build for that registry; a mismatch fails the job and performs no push, retag or delete
**And** when one enabled registry matches and another is absent, the single Bake invocation still pushes only the missing name, so the "build once" rule is preserved rather than becoming a per-registry rebuild

**Given** the finalizer holds the lock and inspects the remote `dev` alias
**When** the remote manifest resolves
**Then** four outcomes are distinguished: absent (create), older descendant on the protected default branch (move), equal or newer valid descendant (succeed without moving), and unrelated/malformed/unverifiable (fail closed without mutation)
**And** "descendant" is decided by refetching default-branch history inside the finalizer — `git fetch --no-tags origin main` followed by `git merge-base --is-ancestor` — never by a value captured in `plan`

**Given** an exact stable tag is pushed for a commit while that commit's default-branch run is already in flight
**When** the two runs overlap
**Then** plan-time suppression cannot see a tag that did not exist when `plan` ran, so the branch run may still publish the immutable `dev-<sha>` object and, if enabled, the TestPyPI distribution for a commit the tag event also owns
**And** the alias half of the hazard is closed inside the lock: `finalize-dev-alias` runs `git fetch --tags --force origin` and re-evaluates `git tag --points-at` against the plan's `source-sha` before any `imagetools create`, and exits successfully without mutation when the commit is tag-owned
**And** the residual immutable-publication window is accepted rather than mitigated (maintainer decision, `docs/ci/codex-assesment.md`, "Divergences resolved (2026-09-01)"): the branch run publishes `dev-<sha>` and, if enabled, `X.Y.(Z+1).devN` to TestPyPI while the tag run publishes `X.Y.Z` to PyPI — two different version strings on two different indexes, nothing overwritten and no ref contended
**And** no second suppression check is added to the publisher: it would narrow the window without closing it, and would buy nothing, because the outcome it narrows is untidy rather than corrupting

**Given** one registry's alias write succeeds and another's fails
**When** the run ends
**Then** the job fails, the succeeded alias is left in place (an alias that already points at a verified newer digest is not rolled back), and the failure is recorded
**And** a same-commit rerun within 30 days reuses the matching immutable images, leaves the already-correct alias alone, and writes only the missing one

**Given** a newer run supersedes an older one
**When** cancellation is evaluated
**Then** `dev.yaml`'s ref-scoped group cancels the entire superseded run — GitHub cancels any currently running job or workflow in the same concurrency group, not merely the jobs that have yet to start — so `plan`, `verify` and `preflight` are cancelled, and `publish-images` would be too
**And** `publish-images` is exempt only because it declares its own non-cancellable group: being downstream of `preflight` in the `needs:` graph confers no protection at all, and a bake push cancelled mid-write leaves one enabled registry written and another not, with no receipt
**And** `finalize-dev-alias` cannot be cancelled by that group for the same reason — its own non-cancellable group, not its position in the graph; a run that has acquired the alias lock always completes or fails on its own terms
**And** neither non-cancellable group stops a maintainer's explicit cancellation of the run: `cancel-in-progress: false` prevents supersession-driven cancellation only, so a half-pushed set remains possible there and is reconciled by identity on the next same-commit run
**And** the two out-of-order pushes therefore serialize through the lock and `dev` settles on the greatest successfully published distance

### Observability

**Given** `publish-images` completes
**When** its log is read
**Then** it names each enabled registry, the immutable tag pushed, the resulting manifest-list digest, and the per-platform digests
**And** it never prints the login step's inputs, the Buildx builder's config, or any `--secret` mount content

**Given** `verify-images` completes
**When** its evidence is read
**Then** each `{registry, platform}` pair has its own line stating the digest pulled, the installed runtime version, the `org.opencontainers.image.version` and `.revision` labels read back, and whether the s6 startup check passed
**And** a single combined pass/fail is never reported for a multi-registry, multi-platform matrix

**Given** an artifact set must be traceable to the run that produced it
**When** correlation is checked
**Then** the plan's `run` object (run id, run attempt, repository, server URL) plus `org.opencontainers.image.revision` on the image are the correlation path
**And** run identity is deliberately absent from `build-manifest.json`, which must stay byte-deterministic

### Security

**Given** GHCR is the forge registry on GitHub
**When** `publish-images` authenticates
**Then** the job declares `permissions: { contents: read, packages: write }` and logs in with the automatic job token
**And** Docker Hub, when enabled, uses `DOCKERHUB_USERNAME` and a repository-scoped `DOCKERHUB_TOKEN` mapped only into the step whose `if:` enables Docker Hub
**And** neither credential is passed as a Bake variable, a build argument, or an environment value visible to the Dockerfile

**Given** attestations are published
**When** SBOM and provenance are inspected
**Then** they contain no credential material and no `secrets.*` expression appears in any Bake input
**And** `attestations: write` is not required, because the attestations are BuildKit's and travel with the image, not GitHub's attestation store — adding that permission would put `dev.yaml` closer to the tier-two prohibitions for no benefit

**Given** the finalizer mutates a registry alias
**When** its permissions are inspected
**Then** it holds `packages: write` and `contents: read` only; it never holds `contents: write`, runs `git push`, or touches a Git ref
**And** it therefore does not belong in `RELEASE_FINALIZER_JOBS`, and `test_no_workflow_writes_refs_or_releases_outside_a_finalizer` must stay green with it unregistered

### Testability

**Given** the shared-alias-lock guard
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts that every job whose steps contain `imagetools create` declares a job-level `concurrency` block whose `group` contains no `${{` expression and whose `cancel-in-progress` is `false`
**And** the planted violation sets `group: dev-alias-${{ github.ref }}`; the guard must fail, because a per-ref group is not a single-writer lock

**Given** the non-cancellable-publisher guard applied to the development image jobs
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts that every job which pushes an image declares a job-level `concurrency` block whose `cancel-in-progress` is literally `false`, with the job set derived from the parsed workflow — every job whose steps invoke a registry login, `docker/bake-action@`, `imagetools create` or a package upload — rather than from a hand-listed set of job names, which is the recurring defect this project keeps finding
**And** it is `E008-S01-004`'s guard widened in scope to `dev.yaml`, not a second parallel guard, so the rule cannot drift between the two channels
**And** it additionally asserts that no image publisher shares a group with a job that writes an alias, so `publish-images` can never be given `dev-alias-finalization` — which is non-cancellable and would therefore pass a `cancel-in-progress`-only check while reintroducing the lock-held-across-a-push hazard
**And** the planted violation is a development image publisher job with **no** `concurrency` block at all; a guard that only checks that `cancel-in-progress: true` is absent would wrongly pass it, since an absent block inherits the cancellable workflow-level group and is cancellable in exactly the way this rule forbids
**And** a second planted violation sets `cancel-in-progress: true` on `publish-images`; the guard must fail on it before the guard is accepted

**Given** the build-once guard
**When** it is added
**Then** it asserts that no workflow step runs `docker buildx build`, and that any step invoking `docker/bake-action@` passes `files: docker-bake.hcl`
**And** the planted violation is a second `docker/bake-action` step for the Docker Hub target; the guard asserts at most one bake invocation per job and must fail on it

**Given** the alias-not-in-build guard
**When** it is added
**Then** it asserts the immutable tag list handed to Bake is derived from the plan's `tags.immutable` and that the literal `:dev` alias never appears in a `TAGS` assignment
**And** the planted violation appends `:dev` to the bake `TAGS` list

**Given** the suppression-reach guard
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it asserts that in `dev.yaml` every job that logs into a registry, pushes an image, or writes an alias carries `needs.plan.outputs.suppressed` in its `if:`, with that job set derived from the parsed workflow — every job whose steps invoke `docker/login-action`, `docker/bake-action` or `imagetools create` — rather than from a hand-listed set of job names
**And** the planted violation is a fourth image job added to `dev.yaml` with a `docker/login-action` step and no suppression term; the guard must fail on it before it is accepted, because a guard enumerating `publish-images`, `verify-images` and `finalize-dev-alias` by name would pass over it
**And** a second planted violation replaces `finalize-dev-alias`'s `if:` suppression term with an `exit 0` in the job's first step; the guard must still fail, since by then the job's credentials are already mapped

**Given** the in-lock tag re-check
**When** it is tested
**Then** `tests/ci/test_workflow_contracts.py` asserts that `finalize-dev-alias`'s step list contains a tag refetch and a `git tag --points-at` evaluation before its first `imagetools create`, reusing `E008-S01-001`'s `push-main-tagged.json` fixture for the tag-pointed case
**And** the planted violation moves the re-check after the first alias write; the guard must fail on ordering alone, since a check that runs after the mutation authorises nothing

**Given** the forward-only rule
**When** it is unit tested
**Then** `tests/ci/test_publication_contract.py` covers the eligibility decision as a pure function over `(candidate_distance, candidate_sha, remote_distance, remote_sha, is_ancestor)` with cases for absent, older, equal, newer-descendant, unrelated, malformed and unverifiable remotes
**And** the planted violation makes the comparison `>=` instead of `>` for the equal case and must be caught, since re-pointing an alias at an equal-distance different SHA is a backward move in disguise

**Given** the destination-model guard applied to the development image jobs
**When** it is added to `tests/ci/test_workflow_contracts.py`
**Then** it is `E008-S01-001`'s guard in scope rather than a second parallel guard: the `vars.PUBLISH_*` references collected from the parsed workflows must equal exactly the optional-destination set `publication_contract` declares, which on this channel is `PUBLISH_IMAGE_DOCKERHUB` and `PUBLISH_PACKAGE_TESTPYPI`
**And** the planted violation restores `vars.PUBLISH_IMAGE_FORGE` on `publish-images`' `if:`; the guard must fail, because the referenced set no longer matches the declared set
**And** a second planted violation attacks the scope rather than the rule: it deletes the forge registry's login step and its tag contribution from `publish-images`, leaving Docker Hub as the only target. No toggle reference changes, so a guard that only collects `vars.PUBLISH_*` passes over it
**And** the guard must therefore also assert that every `image_targets` and `package_targets` entry the contract marks always-enabled is written by some job in the channel's workflow, with that job set derived from the parsed workflow — every job whose steps invoke `docker/bake-action@`, `imagetools create` or a package upload — rather than from a hand-listed set of job names
**And** a third planted violation deletes `publish-images` from `dev.yaml` entirely; the derived-scope assertion must fail on it, because an always-on destination with no publisher is exactly the failure a toggle-reference guard cannot see

**Given** existing guards
**When** the suite runs
**Then** `test_tier_one_actions_use_approved_owners_and_floating_major_aliases` covers the new `docker/*` and `LiquidLogicLabs/*` references, and `test_artifact_actions_remain_on_the_both_forge_v4_pair` still holds for the download side

## Open questions

1. **How does the finalizer learn the remote `dev` alias's first-parent distance?** This story assumes it parses the `.devN` segment of `org.opencontainers.image.version` on the remote manifest, because that label already exists and adding a second source invites drift. A dedicated label (for example `org.ravensorb.dev.first-parent-distance`) would be more explicit but must be threaded through `docker-bake.hcl`, the build manifest's label set, and the metadata action. Maintainer decision; either is implementable, and the choice must be recorded before the finalizer is written.
2. **Resolved 2026-09-01 — `docker buildx imagetools create` performs the digest-only manifest copy.** Answered by the maintainer and recorded in `docs/ci/codex-assesment.md`, "Divergences resolved (2026-09-01)". OCI aliases — `latest`, `MAJOR`, `MAJOR.MINOR` and `dev` — continue to be moved with `docker buildx imagetools create`, which is already on the runner and copies a manifest by digest without repulling. `crane` and `regctl` remain outside the approved-owner allowlist and are not adopted, so no ADR is owed. The related half of the same answer is in `E008-S01-005`: `.github/actions/publication-contract/` decides which aliases may move and the vendor executors write them, which is why no LiquidLogicLabs action is substituted here — the split is deliberate, not a gap.
3. **Resolved 2026-09-01 — the immutable half of the tag race is accepted, not mitigated.** Answered by the maintainer and recorded in `docs/ci/codex-assesment.md`, "Divergences resolved (2026-09-01)". The framing that resolves it is the release model itself: tagging drives the release process, the exact `vX.Y.Z` tag is pushed by the local guarded transaction (ADR-0006) rather than decided by any workflow, and the only ref mutation any workflow performs is moving a floating tag. The race therefore splits into two halves that are not alike. The *immutable* half — a tag landing between `dev.yaml`'s stable-tag check and its publish — means one commit reaches TestPyPI as `X.Y.(Z+1).devN` and PyPI as `X.Y.Z`: two different version strings on two different indexes, nothing overwritten, no ref contended. Untidy, not corrupting, and accepted; the tolerated window is written down in the acceptance criteria above rather than left implied, and no repository rule forbidding tags during an in-flight run is introduced. The *floating alias* half was always the one that mattered, because `dev` and `latest` are mutable and could otherwise land on the same commit or move backwards, and it is already closed by the in-lock compare-before-move rule this story specifies: take the alias lock, read what the alias currently points at, and move only when strictly newer. So the residual window is bounded to a cosmetic double-publish across two channels, and the dangerous half is closed by a mechanism that already exists.
4. **What does "equivalent platform digests" mean across two registries?** Pushing one manifest to two names normally yields identical per-platform digests, but registries may re-compress or differ in manifest media type. The epic asks for "equivalent", not "identical". This story assumes byte-identical per-platform digests are required and a difference is a hard failure; if a registry is later found to legitimately rewrite manifests, the rule needs relaxing deliberately, not by weakening the check when it first fires.
