# Code review — E008-S01-001, "Publish Immutable Development Packages and Images"

Reviewed: the full 2397-line diff, the story, and the named sections of ADR-0009, ADR-0011,
`verify-build.yaml` and `docker-bake.hcl`. Six dimensions plus the four named spot checks.

## What holds up

Recorded so the findings below are read against a correct baseline, not as a verdict on the
change as a whole.

- **Interface contracts line up.** `verify-build.yaml`'s `workflow_call` inputs are exactly
  `channel` / `package-version` / `source-sha` — matched. Every output `verified-bundle` consumes
  (`package-version`, `source-sha`, `file-sha256`, `wheel-filename`, `wheel-sha256`,
  `sdist-filename`, `image-plan-fingerprint`) is declared by `publication-contract/action.yml:50-80`.
  Every bake variable the image job overrides (`TAGS`, `PLATFORMS`, `WHEEL_PATH`, `WHEEL_SHA256`,
  `VERSION`, `REVISION`, `LABELS_JSON`) is declared in `docker-bake.hcl`.
  `committed_versions.py:117` really does expose the `development-version --distance` subcommand
  the setup action now calls.
- **P1 placement is met.** `dev.yaml` contains no `imagetools inspect` / `docker manifest inspect`
  / `skopeo` / `crane`; all four published-image reads live in `publish-image.yaml`, which moves no
  alias. `test_channel_workflows_consume_image_inspection_rather_than_performing_it` derives its
  scope from *who calls the image publisher*, so `release.yaml` is covered the day it lands.
- **ADR-0008 amendment is implemented correctly.** `publish-image.yaml:277-287` keys the platform
  set on `vnd.docker.reference.type != "attestation-manifest"` and asserts set equality against the
  build's own `PLATFORMS`; `descriptors` is emitted as evidence only, never asserted.
- **ADR-0011 single producer holds.** `vars.PUBLISH_PACKAGE_TESTPYPI` is read in exactly one step
  (`dev.yaml:139-165`); no publisher re-reads a toggle; `publish-image.yaml` takes `dockerhub` as a
  boolean input and reads no toggle.
- **Bundle revalidation is strictly before any credential.** In all three publishers the ordered
  steps are checkout → (tag re-check) → `verified-bundle` → stage → login/upload. Nothing touches a
  registry or an index before revalidation.
- **Secret isolation is real, not nominal.** forge index job holds `FORGE_PACKAGE_TOKEN` only;
  TestPyPI holds an OIDC identity and no secret; the image job holds `GITHUB_TOKEN` only. Docker Hub
  secrets are declared optional and never passed from `dev.yaml`, and its login step is `if:`-gated,
  so no credential reaches the disabled destination.
- **Shell hygiene.** The `[[ -z "$tag" ]] && continue` at `publish-image.yaml:186` is *safe* under
  `set -e` (the failing test is not the command following the final `&&`, and the list is not the
  last command in the body). Every heredoc terminator dedents to column 0 correctly under the YAML
  block scalars. The `GITHUB_ENV`-visibility trap is correctly avoided at
  `publish-image.yaml:141-148` by hashing in the same step that writes the variable. No multi-line
  `GITHUB_OUTPUT` value is produced anywhere.
- **Dimension 6.** `urllib.parse` and `git rev-parse` / `merge-base --is-ancestor` are genuinely
  used as the story's answer claims — `stable_tags.py` shells out to git for peeling and
  reachability and pattern-matches only the tag *name*, which is a naming convention rather than a
  git fact. No hand-rolled parser was introduced.

## HIGH-1 — The F16 hardening is enforced by nothing; deleting it leaves the suite green

**Where:** `.github/workflows/dev.yaml:231-249` and `:323-341` (the two "Re-check the stable tag set
before the first credentialed step" steps); `tests/ci/test_workflow_contracts.py:1135-1500` (the 11
new guards).

**What is wrong.** F16's accepted-race mitigation is the *only* thing standing between a
late-arriving release tag and an immutable, unretractable `X.Y.(Z+1).devN` published for a release
commit. The story's own test anchor is explicit: *"plant a tag arriving between the guard job and the
upload; suppression must still fire."* No guard in the diff asserts that these steps exist.
`test_every_development_publisher_is_gated_on_stable_tag_suppression` asserts only the job-level
`needs:` + `if:` pair, which is the *guard job's* conclusion, not the re-read. Delete either re-check
step and all 198 tests still pass, the runbook still claims the behaviour, and the window silently
widens back to "guard job start → upload".

This is the failure mode the repository's own global rule 3 names: a rule that lives only in prose
and in a step somebody can delete. The story's verification section lists thirteen planted
violations; a removed re-check is not among them.

**Fix.** Add a guard whose scope is derived, not named. For every job in `dev.yaml` that
`_publishers()` returns *and* has `steps` (the two package publishers — the image publisher reaches
its destination through `uses:` and legitimately cannot), assert that some step whose index is
strictly less than the first `_is_publishing_step` index runs `scripts/stable_tags.py` and acts on
its result. Prove it by deleting one re-check step and confirming the guard fails. Deriving the set
from `_publishers()` rather than naming the two jobs means a third step-based publisher is covered
without editing the guard.

## HIGH-2 — `git fetch` after `persist-credentials: false` is unauthenticated, and it is on the
publication path

**Where:** `.github/workflows/dev.yaml:192`, `:241`, `:333` (`git fetch --tags --force origin`, and
at `:194` the branch refspec fetch), against the `persist-credentials: false` on the checkouts at
`:171-176`, `:236-241` and `:328-333`.

**What is wrong.** `actions/checkout` with `persist-credentials: false` deliberately removes the
`http.extraheader` credential after cloning. Every later `git fetch origin` in the same job is
therefore anonymous. That works today only because this repository is public on github.com. On the
Gitea deployment CI-AR6 exists to support — the forge where `publish-package-forge` is the only
destination that actually runs — a private or auth-required repository makes all three fetches fail.
The failure is fail-closed (the run stops rather than publishing), so it is not a correctness hazard,
but it is a first-real-run failure on the host this whole coordinate-derivation surface was built
for, and it disables the F16 hardening exactly where it matters.

Note this is not a pre-existing pattern being extended: `verify-build.yaml`'s checkouts also set
`persist-credentials: false`, but none of its jobs issues a follow-up `git fetch`.

**Fix.** Either (a) drop the extra `git fetch --tags --force origin` in the two re-check steps and
rely on a fresh `actions/checkout` with `fetch-depth: 0, fetch-tags: true` immediately before the
re-check — the checkout is authenticated and gives the same freshness — or (b) keep the fetch and
supply a credential explicitly, e.g. `git -c http.extraheader="AUTHORIZATION: basic $(printf '%s' \
"x-access-token:${{ secrets.GITHUB_TOKEN }}" | base64 -w0)" fetch --tags --force origin`, which
keeps the token scoped to the one command. Option (a) is preferable: it adds no credential to a job
whose credential set is currently minimal and is what the guard job (`:171-194`) could also use.

## MEDIUM-1 — The descriptor-count prohibition does not match the spelling it will actually meet

**Where:** `tests/ci/test_workflow_contracts.py:1380-1384`.

```python
assert not re.search(r"len\(\s*manifests\s*\)\s*(?:==|!=|<|>)", command)
```

**What is wrong.** The rule is right and the positive half (must filter on
`vnd.docker.reference.type`) is well made. The negative half only fires when the count is written
against a bare local named exactly `manifests`. The most natural violation —
`if len(index["manifests"]) != 2:` — is not matched, nor is `len(index.get("manifests", []))`, nor
`assert 2 == len(manifests)` (operator precedes), nor a shell spelling
(`test "$(jq '.manifests | length' published-index.json)" -eq 2`). Scope is also the single
hand-named `PUBLISH_IMAGE_WORKFLOW`, so the same count assertion moved into a `scripts/` helper —
which is where F9 pushes non-trivial logic — escapes entirely.

The guard proves the rule; it does not prove the rule's reach. The planted violation that "proved"
it must have used the one spelling the regex catches.

**Fix.** Assert against the *parsed* Python, not the text: for each step whose `run` contains
`vnd.docker.reference.type`, extract the heredoc body and `ast.parse` it, then reject any `Compare`
node whose left or comparator is a `Call` to `len` on anything named or subscripted `manifests`.
Failing that, at minimum broaden the regex to
`r"len\(\s*[A-Za-z_][\w\[\]\"'\.\s]*manifests[\w\[\]\"'\.\s]*\)"` and add the `jq ... length`
spelling, and widen the file scope to every governed definition plus `scripts/*.py`. Re-prove it
with `len(index["manifests"]) != 2` as the planted violation.

## MEDIUM-2 — `_publishers()` is a second hand-kept copy of the publisher derivation

**Where:** `tests/ci/test_workflow_contracts.py:1167-1183`, duplicating the inline block at
`:473-482` inside `test_any_push_triggered_workflow_verifies_before_it_ships`.

**What is wrong.** The two blocks are byte-for-byte the same logic (called-workflow that is not the
verifier, OR `_is_credential_bearing`). The new helper's docstring even asserts they are the same
derivation — "The same derivation `test_any_push_triggered_workflow_verifies_before_it_ships` uses"
— but nothing makes that true. This is precisely the drift the same diff correctly avoided when it
hoisted `REGISTRY_READ_COMMANDS` to module scope, with the same reasoning written two hundred lines
above: *"two hand-kept copies of the same pattern list would drift, and the copy nobody updated would
be the one still reporting success."* If gate finding F15's capability derivation is ever refined
(say, to recognise a job that uses a credential-bearing composite action), one copy gets it.

**Fix.** Delete the inline set comprehension at `:473-482` and call `_publishers(document)` there.
One definition, both callers.

## MEDIUM-3 — `test_push_fixture_targets_the_protected_default_branch` is tautological

**Where:** `tests/ci/test_workflow_contracts.py:1490-1500`; fixture
`tests/ci/fixtures/workflows/push-main.json`.

**What is wrong.** Every assertion in this test restates a literal that appears in the fixture file
it just read, including `assert event["sha"][:12] == "0123456789ab"` against a fixture `sha` of
`0123456789abcdef...`. No production code is exercised. The comment claims the assertion covers the
short-SHA rule — *"The immutable development image tag is the first 12 characters of the event SHA"*
— but `short_sha="${SOURCE_SHA:0:12}"` at `dev.yaml:108` and the tag composition at `dev.yaml:113`
are never fed this fixture and are not verified by anything. The fixture is used by exactly one
test, and that test is a checksum of the fixture.

This matters beyond tidiness: the whole reason F9 moved logic out of `run:` blocks is that a test
which grep-confirms a literal "asserts nothing about behaviour". This test is the same shape as the
thing F9 rejects.

**Fix.** Either delete the fixture and the test (nothing consumes the fixture, so it costs nothing
to remove), or make it drive something real: assert that `dev.yaml`'s identity step, run with the
fixture's `sha` in `SOURCE_SHA` and the plan job's `IMAGE_REPOSITORY`, produces
`image-tags=<repo>:dev-0123456789ab` — i.e. extract the `run:` body and execute it in `bash` with a
temporary `GITHUB_OUTPUT`. That test would fail if the `:0:12` slice were changed; the current one
would not.

## MEDIUM-4 — "One Buildx invocation" is scoped to one hand-named file

**Where:** `tests/ci/test_workflow_contracts.py:1328-1355` (`document = _load_workflow(PUBLISH_IMAGE_WORKFLOW)`).

**What is wrong.** CI-AR39's rule is "one image build per channel run, every destination tagged
inside it". The guard checks "exactly one `buildx bake|build` step in `publish-image.yaml`". A
per-registry second build planted in `dev.yaml` — a `run: docker buildx build --push ...` step in
the image job or a new one — passes every guard in the file, and that is exactly where the cheapest
"just push it to Docker Hub too" patch would go when E009 or story 003 adds a second registry.
`release.yaml`, when it lands, is likewise outside the scope.

Secondary, same guard: `:1355` asserts the two-platform requirement against the *workflow_call
default*. A caller passing `platforms: linux/amd64` satisfies every guard while shipping a
single-platform development image.

**Fix.** Derive the scope: build the set of channel workflows the way
`test_channel_workflows_consume_image_inspection_rather_than_performing_it:1414-1421` already does
(any workflow with a job whose `uses` is `PUBLISH_IMAGE_REFERENCE`), and assert those files contain
*zero* `buildx bake|build` steps while `publish-image.yaml` contains exactly one. For the platform
half, additionally assert that no caller job passes a `platforms:` input narrower than
`REQUIRED_IMAGE_PLATFORMS` — read from the caller's `with:`, not from the callee's default.

## MEDIUM-5 — `publish-image.yaml` never checks its tag list against the destinations it logged into

**Where:** `.github/workflows/publish-image.yaml:174-197` (tag composition) and `:216-227` (the two
logins).

**What is wrong.** The workflow logs in to `inputs.registry`, and to Docker Hub only when
`inputs.dockerhub` is true, then pushes whatever is in `inputs.tags`. Nothing relates the two. A
caller that passes a `docker.io/...` tag with `dockerhub: false` causes buildx to issue an
unauthenticated push request to Docker Hub — a request to a destination the run declared disabled,
which is the second half of the story's AC ("disabled destinations receive no credentials **or
requests**"). It fails, so nothing ships wrong, but the AC is about the request, and this is the
shared surface `release.yaml` will consume, where the tag list *is* conditional on
`PUBLISH_IMAGE_DOCKERHUB`.

`dev.yaml` is correct today only because `plan` emits a single forge tag.

**Fix.** In the "Compose the single Buildx tag list" step, derive the authority of each tag (first
path segment when it contains a `.` or `:`, else Docker Hub) and reject any tag whose authority is
neither `inputs.registry` nor — when `inputs.dockerhub` is true — `docker.io`/`index.docker.io`.
Fail closed with the offending tag named. Add a contract guard asserting that step exists, scoped to
`publish-image.yaml`'s single build path.

## MEDIUM-6 — The runbook overstates the tag re-check's coverage

**Where:** `docs/operational.md:148-152`.

> `dev.yaml` suppresses development publication when the pushed commit carries an exact annotated
> `vX.Y.Z` tag, and re-reads the tag set immediately before each credentialed step

**What is wrong.** The image publisher — the destination that *always* runs in the development
channel, unlike both package destinations — does not re-read anything. The story records why
(`dev.yaml` reaches it through `uses:` and a called workflow takes no caller steps) and that is a
sound decision, but the runbook states the opposite of the truth for the one destination that is
never optional. A reader sizing the accepted race for the image tag gets the narrow window and the
real one is "guard job start → push".

Same section, `:154`: `X.Y.(Z+1).dev0` is unreachable. The distance is
`git rev-list --count --first-parent HEAD` (`dev.yaml:96`), which is ≥ 1 for any commit, so `.dev0`
never occurs. Minor, but it is the concrete example the reader will look for in a registry.

**Fix.** Replace with: "…and the two package publishers re-read the tag set immediately before their
upload. The image publisher is reached through `uses:` and cannot re-read inline; it is protected at
job granularity by the guard job's conclusion, so its window remains 'guard job start → push'." Drop
the `.dev0` literal or write `.devN`.

## LOW-1 — The bundle's exact-wheel check is the third hash of the same file, and its comment
misdescribes the validator

**Where:** `.github/actions/verified-bundle/action.yml:106-118`.

The comment says *"The contract validator already proves the manifest is internally consistent; this
proves the file on this runner's disk is that wheel."* The validator proves more than that:
`src/publication_contract/contract.py:278-296` resolves `artifact_root`, hashes the wheel and the
sdist on disk, and fails if either differs from `distributions.<kind>.sha256`; `:270-276` then binds
`image_plan.build_args.WHEEL_SHA256` to that same value through the fingerprint. The preceding
`verify-checksums` step hashes them a second time. So the `sha256sum` at `:114` is the third hash of
the same bytes against the same authority.

Not harmful, and the *identity* match in the same step (source SHA / package version, `:96-105`) is
the genuinely new check that CI-AR36 needs. Keep the step; fix the comment to say what it actually
adds, or drop the hash and keep the identity match, so the next reader does not conclude the
validator is weaker than it is.

## LOW-2 — Two outputs are emitted and never consumed, and one authority is bypassed

`verify-build.yaml:33-35` emits `dist-artifact-name` as the canonical artifact-name authority.
`dev.yaml` never consumes it; both publishers rely on `verified-bundle`'s `artifact-name` default
(`verified-bundle/action.yml:20-23`) and `publish-image.yaml`'s own default (`:70-72`). Three
independent spellings of `verified-dist-v1`, one of which calls itself the authority. It fails loudly
if they diverge (download-artifact 404s), which is why this is LOW, but the fix is one line:
`artifact-name: ${{ needs.verify.outputs.dist-artifact-name }}` on both publishers and on the
`publish-image` call.

`publish-image.yaml:83-85` emits `image-reference` (the immutable digest reference); no caller reads
it, and `dev.yaml`'s evidence table prints tags and digest separately. Story 003's alias finalizer
will want it — either consume it now in the evidence row or note it as deliberately provided ahead
of use.

## LOW-3 — The review-date guard accepts any date, including the commit date

`tests/ci/test_workflow_contracts.py:1465-1489` requires a `20\d\d-\d\d-\d\d` anywhere in the twelve
lines before a SHA-pinned `uses:`. Both comment blocks in `dev.yaml` (`:266-269`, `:352-353`) contain
two dates: "committed 2026-07-28" and "reviewed 2026-09-02". Deleting the review date leaves the
commit date, and the guard passes — so the story's claim that the guard "fails if that record is
removed" holds only for removing *both*. Anchor the pattern to the word: `r"reviewed\s+20\d\d-..."`.

## LOW-4 — Two prose claims that are not true as written

- `publish-image.yaml:4` — "It is the fifth workflow file on disk". There are four
  (`ci`, `dev`, `publish-image`, `verify-build`); it becomes the fifth when `release.yaml` lands.
  Write "it will be the fifth once `release.yaml` lands (P2)".
- `tests/ci/test_workflow_contracts.py:1437` — the positive half of the P1 guard
  (`assert any(re.search(probe, published) ...)`) matches raw file text, so a *commented-out*
  `imagetools inspect` satisfies "the reads really are somewhere". Same at `:1287`
  (`assert "scripts/forge_coordinates.py" in action.read_text()`), which a comment satisfies. Both
  should search the parsed `run:`/`uses:` values, which the file already has helpers for.

## LOW-5 — Forge-coordinate edge cases

- **IPv6 server host.** `forge_coordinates.py:_server_host` returns `parts.hostname` unbracketed, so
  `https://[::1]:3000` yields `::1:3000`, and `derive` then builds `image_repository` as
  `::1:3000/owner/name`. `validate_registry_override` re-brackets (`:1291`) but `_server_host` does
  not, and `permitted` is computed with `partition(":")[0]`, which is `""` for an IPv6 host — so an
  IPv6 override can never match. Bracket in `_server_host` and split the authority with `urlsplit`
  rather than `partition(":")`.
- **`user: ${{ github.actor }}`** at `dev.yaml:278` pairs the *pusher's* username with a repository
  token that belongs to whoever minted it. Gitea's basic auth resolves a token supplied as the
  password regardless of the username, so this works in practice, but the coupling is accidental
  rather than chosen and it varies per push. Prefer `__token__`, or a documented
  `vars.FORGE_PACKAGE_USER` alongside `FORGE_PACKAGE_TOKEN`.
- **`enabled-destinations["image-forge"]`** (`dev.yaml:164`) is emitted and gates nothing — the
  image job's `if:` reads only `suppressed`. Correct today (it is always enabled) but it means the
  key is evidence, not a gate; say so in the comment so story 003's finalizer does not assume the
  gate exists.
- **`primary=${first%:*}`** (`publish-image.yaml:191`) strips everything after the last `:`. A tag
  list entry without a `:tag` suffix on a ported registry (`git.example.com:3000/owner/name`) yields
  `git.example.com`, and the digest reference is then wrong. Callers always supply `:tag` today;
  reject a tag with no `:` after the last `/` in the same loop that rejects commas.

## LOW-6 — TestPyPI trusted publishing is gated only by the toggle, not by forge kind

`dev.yaml:194-229` requests `id-token: write` and relies on the GitHub OIDC endpoint. On a Gitea
runner there is no such identity, so with `PUBLISH_PACKAGE_TESTPYPI=true` the job fails rather than
being absent. `plan` already emits `forge`; adding `&& needs.plan.outputs.forge == 'github'` to the
`if:` (or recording TestPyPI as host-capability-gated in the enabled set, alongside
`package-forge`'s `unsupported`) makes the absence a stated capability rather than a runtime error —
which is the exact distinction ADR-0011 §2 exists to preserve.

## Not findings — checked and cleared

Recorded so they are not re-litigated.

- `set -e` and `[[ -z "$tag" ]] && continue` (`publish-image.yaml:186`) — safe; the failing test is
  not the command after the final `&&`, and the list is not the loop body's last command.
- `--output ""` on the re-check invocations (`dev.yaml:243`, `:335`) — argparse honours the explicit
  empty string over the `GITHUB_OUTPUT` default, so the conclusion reaches stdout. If it did not,
  `conclusion` would be empty and `grep -qx` would fail the step: fail-closed either way.
- `docker buildx bake --push` overriding the HCL's `output = ["type=docker"]` — `--push` is
  shorthand for `--set *.output=type=registry`, and `verify-build.yaml:543` already relies on the
  same override semantics with `--load`.
- `poetry run python` in the staging step (`publish-image.yaml:127`) — `verified-bundle` runs
  `setup-poetry-python` with `dependencies: build-only` and the default `poetry: true`, so the venv
  exists. Stdlib-only script, so plain `python3` would also do; not worth changing.
- `linux/arm64` variant handling — the index assertion reads `os`/`architecture` only and ignores
  `variant`, so a `v8`-annotated descriptor still compares equal to `linux/arm64`.
- `SHA_PINNED_ACTIONS` being hand-kept — ADR-0009 makes that deliberate ("adding an entry here **is**
  the grant"), and `test_credential_handling_publishers_are_registered_as_sha_pinned` supplies the
  reach. The new guard's derived-scope claim is accurate given that pair.
- `development-evidence` not failing on "enabled but skipped" — that is the finalizer's job under
  ADR-0011 §3, and story 003 owns the finalizer. This job is evidence only.
- Test tautology sweep over `tests/test_forge_coordinates.py` and `tests/test_stable_tags.py` — both
  exercise real behaviour (the stable-tag cases build actual temporary git repositories rather than
  mocking `subprocess`, which is the right call and the one the module docstring justifies). The
  only tautological test in the diff is MEDIUM-3.
