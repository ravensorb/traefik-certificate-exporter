# Adversarial review — E008-S01-003 (Create the Forge Release and Finalize All Aliases Last)

Reviewed: `/tmp/E008-S01-003.diff` (2232 lines), the story, and the three named ADR sections.
Every finding below that claims a guard is blind was **executed**: the violation was planted in
the working tree, `pytest tests/ci/test_workflow_contracts.py` was run, and the pass/fail result
is quoted. The tree was restored afterwards and re-verified green (196 passed).

**Verdict: no CRITICAL. Four HIGH, six MEDIUM, six LOW.** The runtime logic is largely sound —
the ordering decision, the gate module, the split of ref authority from registry authority, and
the digest-copy alias mechanism all hold up under attack. The weaknesses cluster in two places:
**guard scope** (several new guards prove their rule but not that the rule is reached, and one
inherited blind spot lets the whole ADR-0006 grant registry be bypassed), and **failure
handling in the alias fan-out** (partial success with no evidence, and a non-re-runnable
finalization).

Counts: CRITICAL 0 · HIGH 4 · MEDIUM 6 · LOW 6.

## HIGH

### H1. Nothing enforces that the finalization gate runs *before* anything is written

**Where:** `tests/ci/test_workflow_contracts.py:2879` (`_gate_step`), `:3002`
(`test_every_finalizer_waits_for_every_publisher_and_reads_every_result`);
`.github/workflows/release.yaml:611`; `.github/workflows/dev.yaml:514`.

**What is wrong.** Every guard about the gate is *set*-shaped: does the finalizer `needs:` each
publisher, and does the gate step's `env:` name each `needs.<job>.result`. Nothing asserts step
*order*. The gate step's own comment says "Before anything is written" — that is prose only.

Planted and executed:

* Moved `Refuse to finalize unless every enabled destination delivered` from the top of
  `release.yaml`'s `finalize` to the **end** of the job, after the Release is created and after
  `git-action-tag-floating-version` has moved `vMAJOR`/`vMAJOR.MINOR`. Result: **126 passed.**
* Moved `Halt unless the candidate is still that head` in `dev.yaml`'s `finalize-dev-alias` to
  after `Point the development alias at the published digest`. Result: **126 passed.**

(Deleting the dev head re-check *is* caught, but only incidentally, by a `StopIteration` inside
`_step_with_id` — see L5.)

**Why it matters.** This is the story's central invariant. With the gate last, an enabled
destination that skipped or failed would still get a Release, a moved `vMAJOR`, a moved `latest`
and a moved `dev` — and the job would then go red *after* the damage, which is strictly worse
than not gating at all, because the run is now half-finalized. The same reordering defeats the
F16 tag re-check in `finalize-image-aliases` and the JIT head proof the `dev` AC names
explicitly. A reordering is exactly the edit a future refactor makes without thinking.

**Fix.** In the finalizer guards, compute step indices from the parsed `steps` list and assert
the decision steps precede the writing steps. Derive both sets, never enumerate them:

```python
writes = [
    i
    for i, s in enumerate(steps)
    if str(s.get("uses", "")).startswith(
        (APPROVED_RELEASE_ACTION, APPROVED_ALIAS_ACTION)
    )
    or any(
        re.search(p, _uncommented(str(s.get("run", "")))) for p in ALIAS_MOVE_COMMANDS
    )
]
guards = [
    i
    for i, s in enumerate(steps)
    if "scripts/finalizer_gate.py" in _uncommented(str(s.get("run", "")))
    or "--expect-tag" in _uncommented(str(s.get("run", "")))
    or s.get("id") == "recheck-head"
]  # better: derive by the module/flag it runs
assert not writes or (guards and max(guards) < min(writes))
```

Plant the reordering as the proving violation, as the story's other anchors do.

### H2. A mid-loop alias failure leaves a partially aliased registry and writes **no** run summary

**Where:** `.github/workflows/release.yaml:790-848`, the `Point every permitted image alias at
the published digest` step; specifically the `for repository … for alias …` loop at `:831` and
the summary block that follows it.

**What is wrong.** `set -euo pipefail` aborts the step on the first failing
`docker buildx imagetools create`. The `moved=()` accumulator is only rendered into
`$GITHUB_STEP_SUMMARY` **after both loops complete**, so a failure part-way through emits
nothing at all.

Executed with a stub `docker` that fails on its second invocation
(`ADVANCE_MAJOR=true ADVANCE_MINOR=true`, both repositories set):

```
rc 1
invocations: ghcr.io/owner/name:1.3   (moved)
             ghcr.io/owner/name:1     (failed)
summary:     ''            <-- empty
```

`ghcr.io/…:1.3` now points at the new digest; `:1`, `:latest` and every Docker Hub alias still
point at the previous release. The step's own comment asserts the opposite — "`latest` follows
`vMAJOR` … both move together or neither does" — and that invariant is broken by any transient
registry error. `release-evidence` then reports only `| Image aliases | failure |`.

**Why it matters.** This is the exact state the story exists to prevent ("convenient names never
advertise incomplete or stale delivery"), reached through the ordinary failure mode of a
registry write, and it violates the DoD clause "run summaries record … alias outcomes as
workflow-native evidence (CI-AR41)" precisely in the case where an operator needs that evidence
to reconcile by hand. No test covers a failing `docker`: `_stub_docker` always exits 0.

**Fix.** Three changes, all local to the step:

1. Emit evidence as it happens, or install `trap` so it is emitted on any exit:
   ```bash
   moved=(); trap 'printf "%s\n" "### Stable image aliases" "" "- Digest: \`${IMAGE_DIGEST}\`" \
       "${moved[@]/#/- Moved: }" >> "$GITHUB_STEP_SUMMARY"' EXIT
   ```
2. Move `MAJOR` and `latest` in **one** `imagetools create` invocation
   (`--tag "${repository}:${MAJOR_ALIAS#v}" --tag "${repository}:latest"`), so the pair the
   comment claims is atomic actually is one registry operation.
3. Add a test that stubs a failing `docker` and asserts both the non-zero exit **and** that the
   summary names every alias that did move.

### H3. `permissions: write-all` bypasses the entire ADR-0006 grant registry

**Where:** `tests/ci/test_workflow_contracts.py:712`
(`test_no_workflow_holds_github_token_write_access_to_contents`), inherited by the amended
`:1827` (`if addressed == {"package"} and isinstance(permissions, dict):`) and by `:224`
(`_is_credential_bearing`).

**What is wrong.** Every permissions inspection is written as `if not isinstance(permissions,
dict): continue` or `and isinstance(permissions, dict)`. GitHub and Gitea both accept the scalar
forms `permissions: write-all` / `read-all`, which grant *all* scopes. A job written that way is
silently skipped by every check.

Planted and executed: replaced `publish-package-forge`'s `permissions: {contents: read}` with
`permissions: write-all`. Result: **126 passed.** That job now holds `contents: write` and
`packages: write` while being registered nowhere in `RELEASE_FINALIZER_JOBS`.

**Why it matters.** `RELEASE_FINALIZER_JOBS` is described in ADR-0006 and in this story's DoD as
*the* grant — "adding a name to it is the grant". The registry is enforced by exactly this
check, and a one-word edit walks past it. The pre-existing hole was harmless while the repo had
no `contents: write` anywhere; this story is the change that makes it exploitable, so it belongs
in this review. It also makes H4's credential leak reachable from an unregistered job.

**Fix.** Wherever `permissions` is read, treat a non-dict as a hard failure rather than a skip:

```python
assert permissions is None or isinstance(permissions, dict), (
    f"{path.name}: job {job_name!r} uses the scalar `permissions:` form, which grants "
    f"every scope and is invisible to the ADR-0006 grant registry; spell the scopes out"
)
```

Apply it at `:224`, `:712` and `:1827`, and plant `permissions: write-all` on a publisher as the
proving violation.

### H4. The push credential written into `.git/config` is never revoked

**Where:** `.github/workflows/release.yaml:678-692`, `Grant this job the push credential the
alias action needs`.

**What is wrong.** The step writes `https://${FORGE_ACTOR}:${FORGE_TOKEN}@<authority>` into the
workspace's `.git/config` as `remote.origin.pushurl` and nothing ever removes it. There is no
`if: always()` teardown, and `actions/checkout`'s post step cleans up only the credential *it*
persisted — which, under `persist-credentials: false`, is none.

Consequences, in increasing order of concern:

* The token stays live in the workspace for every subsequent step of `finalize` (the alias
  action and the summary step), and any `git remote -v`, `git config --list` or git error
  message in those steps prints it. Log masking usually saves this, and masking is not a control
  you get to rely on for a secret you chose to write to disk.
* **It survives the job.** ADR-0006's amendment and this story both target self-hosted Gitea
  (`act_runner`) for E009, where the workspace directory is reused across runs and jobs by
  default. The token is left on disk for whatever runs next on that runner. `persist-credentials:
  false` is a repository-wide invariant precisely to prevent this, and this step defeats it
  without a matching teardown — while the surrounding comment claims the grant is scoped "for the
  push URL only", which is a statement about *which URL*, not about *how long*.

**Why it matters.** A finalizer token is the highest-value credential in the repository: it can
create Releases and force-move tags. Leaving it in a reused workspace converts a job-scoped grant
into a runner-scoped one, which is the thing ADR-0006's whole split exists to avoid.

**Fix.** Add a teardown step immediately after the alias action, unconditional:

```yaml
- name: Revoke the push credential
  if: ${{ always() }}
  run: |
    set -euo pipefail
    git remote set-url --delete-push origin '.*' 2>/dev/null || true
    git remote set-url --push origin "$REMOTE_URL"
```

(`always()` is correct here and is not the ADR-0011 prohibition, which is about *job* gating on
other jobs' results — but the repo has a blanket step-level `always()` ban at
`test_workflow_contracts.py:590`, so use `!cancelled()` plus an explicit note, or exempt
teardown steps in that guard and say why.) Better still, replace the persisted remote URL with a
single-invocation credential the action can inherit without a config write, if
`git-action-tag-floating-version` ever accepts a token input; record the check either way.

## MEDIUM

### M1. Docker Hub gating in `finalize-image-aliases` is asserted nowhere

**Where:** `.github/workflows/release.yaml:782` (the Docker Hub login `if:`) and `:795`
(`DOCKERHUB_REPOSITORY` expression); `tests/ci/test_workflow_contracts.py:3355`
(`test_a_disabled_docker_hub_receives_no_alias_request`).

**What is wrong.** The test that claims to cover this passes `DOCKERHUB_REPOSITORY=""` **from
the test**, so it proves the bash handles an empty value — never that the workflow computes an
empty value when the destination is off. Planted and executed:

* Deleted `if: ${{ fromJSON(needs.plan.outputs.enabled-destinations)['image-dockerhub'] ==
  'enabled' }}` from the Docker Hub login step. Result: **126 passed.**
* Replaced the `DOCKERHUB_REPOSITORY` expression with an unconditional
  `${{ format('docker.io/{0}', needs.plan.outputs.dockerhub-repository) }}`. Result:
  **126 passed.**

**Why it matters.** "A disabled destination receives no credentials and no requests" is the rule
`publish-image`'s `secrets:` block is guarded on (release.yaml:551-554, story 002). The alias job
is the second place that rule now has to hold and the only place it is unguarded. Today the
runtime is safe only because `plan` emits an empty `dockerhub-repository` when the toggle is off
— a coincidence of two independently-edited derivations, which is the F7 drift ADR-0011 names.

**Fix.** Assert from the parsed job that both the login step's `if:` and the
`DOCKERHUB_REPOSITORY` env expression reference `needs.plan.outputs.enabled-destinations`, and
derive the set of "Docker Hub-addressing steps" (any step whose `uses`/`env`/`with` mentions
`docker.io` or `DOCKERHUB`) rather than naming the two steps.

### M2. The amended credential guard passes vacuously for an unclassified publisher

**Where:** `tests/ci/test_workflow_contracts.py:1740-1770` (`DESTINATION_CLASSES`,
`_destination_classes`), `:1822` (`assert len(addressed) <= 1`), `:1817`
(`assert any(classes.values())`).

**Assessment of the amendment itself: it is a genuine correction, not a weakening.** The
`unclassified:{name}` fallback puts an unrecognised job in a bucket of its own, which reproduces
the old pairwise behaviour, so it is the *strictest* outcome; the original planted violation (a
registry credential on the package job) still fires, and I could not construct a cross-destination
leak that the new form accepts and the old form rejected.

**But** the *compensations* the amendment was paid for can go vacuous:

* `assert len(addressed) <= 1` is satisfied by a publisher with **zero** classes.
* `assert any(classes.values())` is satisfied by any *one* classified job in the file.

So a publisher that falls out of the class vocabulary silently escapes the new
`packages: write` obligation while the guard stays green. `DESTINATION_CLASSES` is a hand-kept
regex list: `twine upload`, `uv publish`, `poetry publish`, `crane`/`skopeo`/`regctl` writes and
a direct `curl` to a package index are all absent from it. Today both package publishers do
classify (`pypa/gh-action-pypi-publish` at release.yaml:417 and `"id-token": "write"` at :456),
so the guard is not vacuous *yet* — the hole opens on the first publisher written any other way.

**Fix.** `assert len(addressed) == 1, f"...extend DESTINATION_CLASSES"`. An unclassifiable
publisher should be a loud failure telling the author to extend the vocabulary, not a quiet
fallback — this is exactly the "scope narrower than the rule it claims" pattern.

### M3. Finalization is not re-runnable: a failure after the Release strands the run

**Where:** `.github/workflows/release.yaml:659-676` (`allow-updates: "false"`), ordered *before*
`:678` (credential grant) and `:697` (alias move), and before the whole
`finalize-image-aliases` job.

**What is wrong.** The Release is created first; every alias move happens after it. Any failure
in the credential grant, the alias action, the tag re-check in `finalize-image-aliases`, or the
alias loop (see H2) leaves the Release created and some or all aliases unmoved. Re-running the
failed jobs then fails at the Release step, because `allow-updates: "false"` refuses an existing
Release. Recovery requires manually deleting the Release from the forge UI.

**Why it matters.** ADR-0006 frames this as a transaction; in practice the first write is the
one that cannot be retried, which is the inverse of what you want. The transient-registry-error
case (H2) is not exotic.

**Fix.** Either (a) order the writes so the retryable ones come first and the Release last, or
(b) make the Release step idempotent for the same `(tag, commit)` — a pre-step that queries for
an existing Release at the exact tag and skips creation when it already points at
`source-sha`, keeping `allow-updates: false` for the mismatched case. Whichever is chosen, add
the manual-recovery procedure to ADR-0006's "transaction as a state machine" section, because
"the operator deletes the Release and re-runs" is currently undocumented tribal knowledge.

### M4. `stable_tag_order()` counts unreachable tags, so one stray tag freezes every alias forever

**Where:** `scripts/stable_tags.py:122-149` (`stable_tag_order`), consumed at `:188`/`:190`.

**What is wrong.** The order is every annotated `vX.Y.Z` in `refs/tags`, with no reachability
filter — while the plan job (release.yaml:130-140) requires the released commit to be reachable
from `origin/main` before it will release at all. The two disagree about which tags count.

One annotated `v9.9.9` pushed on a side branch, or left behind by an abandoned release attempt,
makes `advance-major` permanently `false`. Every subsequent release then finishes **green**,
creates its Release, moves no `vMAJOR`, no `latest`, no image `MAJOR` and no image `latest`, and
reports only `| v1 may advance | false |`. Nothing is red, nothing alerts, and the symptom
("`latest` stopped updating months ago") is discovered by a user.

The direction is fail-safe — I could not make a stray tag cause a *wrong* alias to move — so
this is availability and silent degradation, not a correctness hole.

**Fix.** Scope the order to the same authority the plan job uses:

```python
[
    "for-each-ref",
    "--merged",
    "origin/main",
    "--sort=v:refname",
    "--format=...",
    "refs/tags",
]
```

or filter with the module's existing `is_ancestor()`. Both keep git as the reachability
authority, which is the module's stated delegation. Add a test with an annotated stable tag on
an unmerged branch asserting it does not enter the order.

### M5. The finalize summary says `v1.2 may advance: true` on a back-port that moves no Git alias

**Where:** `.github/workflows/release.yaml:711-731` (the summary step's
`| \`${MINOR_ALIAS}\` may advance | \`${ADVANCE_MINOR}\` |` row);
`docs/adr/0006-release-version-transaction.md`, "Alias tags move…" as amended.

**On the question I was asked to settle:** the accepted limitation *is* compatible with the ACs
as written. Both alias clauses are stated as "only if" — necessary conditions — so declining to
move `vMAJOR.MINOR` on a back-port does not violate them, and the DoD clauses are all met. It is
a recorded limitation, not a silently unmet requirement.

**What is wrong is the reporting.** `alias_plan` computes `advance-minor=true` for a back-port,
the summary prints that row verbatim, and the actual Git outcome is *no move at all* (the whole
invocation is gated on `advance-major`). The only correction is the `Git aliases moved: none
none` row two lines below. Meanwhile the **image** `1.2` alias *does* move. So after a back-port,
`git rev-parse v1.2` and `docker pull …:1.2` resolve to different releases, and the run summary
states, on its own terms, that `v1.2` may advance when nothing advanced it.

**Fix.** Split the row so it cannot be misread — `| v1.2 eligible (image) | true |` and
`| v1.2 moved (Git) | no — superseded major, see ADR-0006 |` — and state the Git/image
divergence for back-ports explicitly in the same table. This is cheap and it is the difference
between a documented limitation and a surprise.

### M6. Only one gate step per workflow file is ever located, and only the release one is checked
for coverage

**Where:** `tests/ci/test_workflow_contracts.py:2879` (`_gate_step` uses `next(...)` over a
`set` of finalizers), `:3002`.

**What is wrong.** `_gate_step(path)` returns the *first* step calling `finalizer_gate.py` across
all finalizers in a file, iterating a `set` (non-deterministic order). It happens to be
unambiguous today because only one finalizer per file has a gate. If a second finalizer in the
same file grows its own gate — the natural next step, since `finalize-image-aliases` currently
inherits its gating entirely from `needs.finalize.result == 'success'` — the coverage assertion
at `:3018-3027` would check a set-ordering-dependent one of them and pass while the other reads
nothing.

**Fix.** Collect *all* gate steps per file and assert the publisher-result coverage over each,
and assert that every registered finalizer that performs a write either has its own gate or
transitively `needs:` a job that does.

## LOW

### L1. `github.actor` is interpolated into URI userinfo without encoding
`.github/workflows/release.yaml:689-692`. Bot actors (`github-actions[bot]`, `dependabot[bot]`)
contain `[`/`]`, which are not legal in URI userinfo; Gitea usernames admit further reserved
characters. The push then fails *after* the Release is created (M3 makes that unrecoverable).
The username is not used for authentication with a forge token anyway. Fix: use a fixed
placeholder (`x-access-token`) or percent-encode `FORGE_ACTOR`.

### L2. `REMOTE_URL` scheme parse has no validation
Same step, `scheme="${REMOTE_URL%%://*}"` returns the whole string if `github.server_url` ever
lacks a scheme, producing a silently malformed remote. Fix: `[[ "$REMOTE_URL" == *://* ]] ||
{ echo "…" >&2; exit 2; }`.

### L3. The alias action's *output* names are asserted nowhere
`.github/workflows/release.yaml:704-705` reads `steps.floating.outputs.majorTag` / `minorTag`.
The developer correctly hardened the *input* spellings (`updateMinor`, `ignorePrerelease`) with a
guard and a planted violation, but the outputs got no equivalent. A wrong output name renders
`none` in the summary on a fully successful move, and no test would notice — the same silent
class of defect the input correction was about. Fix: assert both output names alongside the input
assertions in `test_the_git_alias_action_runs_only_behind_the_ordering_gate`, and record them in
ADR-0006 beside the input correction.

### L4. The gate is one-sided, and does not say so
`scripts/finalizer_gate.py`, module docstring and `evaluate()`. `success` for a `disabled` or
`unsupported` destination is always `ok`. That is *necessary* for the image publisher, which
serves two destinations from one job — the docstring's justification. It is not necessary for the
package publishers, which have one job each and whose `if:` is the only thing keeping them off; a
job whose `if:` was widened would publish to a destination the plan declared disabled and the
gate would return `ok`. Answering the question directly: **`success` for a non-enabled destination
is safe today**, because no over-publication path exists that would produce it. But the module
presents a one-sided check as a decision table. Fix: state in the docstring that the gate detects
under-publication only, or restrict the allowance to destinations that share a publisher job
(passed in as a small map, derived from the same `PUBLISHER_RESULTS` shape).

### L5. Guard failures surface as `StopIteration`, not as diagnoses
`tests/ci/test_workflow_contracts.py:2167` (`_step_with_id`), `:2879` (`_gate_step`), `:3200`ish
(the `bundle` and `decider` lookups inside
`test_the_release_carries_the_whole_verified_bundle_and_is_traceable`). Deleting the dev head
re-check produces `E StopIteration` with no message. It fires — which is what matters — but a
guard whose failure is an opaque traceback reads as a broken test rather than a caught violation,
and gets "fixed" accordingly. Fix: `next(..., None)` plus an `assert` carrying the rule.

### L6. The destination-key vocabulary is hand-written in three places
`release.yaml:267` (plan `printf`), `:615-620` (gate `PUBLISHER_RESULTS`), and the test fixtures
(`_stable_bindings`, `tests/test_finalizer_gate.py:ENABLED`). Verified fail-closed: renaming the
key on the gate side only makes four contract tests fail, and `evaluate()`'s set-equality would
fail the release at runtime. A *consistent* rename across plan and gate is caught only by story
002's hard-coded key assertions. Not a defect today; note that no guard derives one vocabulary
from the other, and the cheapest close is to have the contract test execute the plan job's
`destinations` step (it already does, at `:2650`ff) and use its emitted keys as the fixture.

### L7. Two prose/scope notes
* `scripts/stable_tags.py:182-184` and the matching ADR-0006 line attribute the safety of
  `startswith(f"v{major}.{minor}.")` to the ban on leading zeros. The trailing separator is what
  prevents `v1.2.` from prefixing `v1.20.3`; the leading-zero ban is needed for a *different*
  reason (`v1.02.3` and `v1.2.3` would otherwise be one minor under two alias names). The code is
  correct and `test_a_neighbouring_minor_is_not_mistaken_for_this_one` asserts the behaviour —
  only the stated justification conflates two arguments.
* `.github/workflows/dev.yaml:508` hard-codes `ref: main` for the protected default branch rather
  than deriving it (`github.event.repository.default_branch`), restating a fact the workflow's own
  `on: push: branches:` also states.

## Checked and found sound (recorded so the next reviewer does not redo it)

* **Reused-before-written.** No hand-rolled anything. Version ordering is genuinely delegated —
  `git for-each-ref --sort=v:refname`, verified: there is no tuple parse, no `sorted()`, and the
  only string manipulation is the within-minor prefix membership. JSON is stdlib. Release and tag
  writes are the two approved maintained actions. `finalizer_gate.py` is a decision table, not a
  reimplementation of a library concern. The escape-hatch ADR is not owed here.
* **`order[-1]` / `within_minor[-1]`.** Both are provably non-empty: `alias_plan` raises unless
  the tag is in `order`, and the tag always matches its own minor prefix. Prefix collision is
  impossible in both directions (`v1.2.` vs `v1.20.3` and `v1.` vs `v10.0.0`).
* **`set -euo pipefail` with the empty array.** `aliases=()` is length-checked before any
  `"${aliases[@]}"` expansion; `moved` is provably non-empty where it is expanded. No `set -u`
  hazard.
* **Quoting** in both alias steps: every expansion that reaches `docker` is quoted; no word
  splitting or glob path exists.
* **Digest validation** (`^sha256:[0-9a-f]{64}$`) is correct and is applied before any name moves
  in both channels; the empty/`latest`/short/non-hex cases are all covered and all halt with zero
  `docker` invocations (executed).
* **`_render` / `EXPRESSION`.** It does prove wiring for the failure modes that matter: degrading
  a publisher result, the enabled set, or the required-results map to a literal each makes at
  least one test fail (a literal drops the binding the negative test relies on, and the coverage
  guard independently requires each `needs.<job>.result` to appear). The `KeyError`-on-unbound
  behaviour is the right default. Its blind spot is H1 (order), not substitution.
* **`!cancelled()` never `always()`** holds in all three new jobs, at job and step level, and the
  pre-existing guard at `:590` enforces it.
* **The privilege split** is real: `finalize` holds `contents: write` and no registry credential
  or `docker/login-action`; `finalize-image-aliases` and `finalize-dev-alias` hold
  `packages: write` and no `contents: write`; `test_ref_writing_and_registry_alias_privileges_
  never_meet` checks both directions and is not vacuous (both counters are non-zero).
* **Alias mechanism.** `buildx imagetools create` from a digest reference is a content-addressed
  index copy: no rebuild, no registry *read* that could decide ordering (P1 respected), and the
  index digest is identical in the forge registry and Docker Hub because one Buildx invocation
  pushed both.
* **Empty enabled set, malformed JSON, unknown state, unknown result, missing result, unplanned
  result** all block in `finalizer_gate.evaluate`, and all are executed in
  `tests/test_finalizer_gate.py`. I could not construct an input combination that passes when it
  should block, other than the one-sidedness noted in L4.

**Suite status:** 196 passed before and after every planted violation was reverted.
