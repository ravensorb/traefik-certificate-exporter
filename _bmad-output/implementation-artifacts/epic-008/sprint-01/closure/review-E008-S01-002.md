## HIGH-1 — `github.sha` is compared to `git rev-parse HEAD` without being peeled, and the channel accepts only annotated tags

**File:** `.github/workflows/release.yaml`, plan job, step `id: tag` (the `head_commit` comparison,
`~line 858`); the same equality is restated in step `id: identity` (`TAG_COMMIT` vs `SOURCE_SHA`).

**What is wrong.** `refs/tags/vX.Y.Z` for an annotated tag points at a *tag object*, not at a
commit. A forge's push event reports the ref's new object id, so `github.sha` on an annotated-tag
push is, on at least some forges, the tag object SHA — Gitea in particular derives the context
`sha` from the push payload's `after`, which is the ref's new value. The step then does:

```
head_commit="$(git rev-parse HEAD)"
if [[ "$head_commit" != "$SOURCE_SHA" ]]; then ... exit 2
```

Checking out a tag object SHA leaves `HEAD` at the *commit*, so the two differ and the step exits 2.
Verified mechanically in a scratch repository: `git rev-parse v1.2.3` = `16990ca…`,
`git rev-parse v1.2.3^{commit}` = `git rev-parse HEAD` = `557d09d…`, and checking out the tag
object leaves `HEAD` at `557d09d…`.

**Why it matters.** This channel deliberately accepts *only* annotated tags, so the failing path is
the only path. If the forge reports the tag object, every stable release refuses to publish — the
residual on BL-E008-001 that this story exists to close stays open, and it stays open in a way the
suite cannot see, because `_run_step()` injects `SOURCE_SHA` = the commit and the `push-tag.json`
fixture's `sha` is a synthetic literal bound to no object at all. It fails closed, which is why this
is HIGH and not CRITICAL — nothing wrong is published — but the DoD ("`release.yaml` owns exact
stable-tag events") is unmet on first use, and the diagnosis on the day of a release is expensive.

**Smallest correct fix.** Peel once, with git, and use the peeled value everywhere downstream —
peeling is a no-op for a commit SHA, so this is correct on both forges without a conditional:

```
source_commit="$(git rev-parse --verify "${SOURCE_SHA}^{commit}")"
if [[ "$head_commit" != "$source_commit" ]]; then ... fi
...
echo "tag-commit=$source_commit"
```

and emit `source-sha=$source_commit` from the identity step. Add the case to the ref table:
drive the step with `SOURCE_SHA="$(_git(repo, 'rev-parse', 'v1.2.3'))"` — the tag object — and
assert acceptance. That test fails today.

## HIGH-2 — the `destinations` step is this story's ADR-0011 contract and no test executes it

**File:** `.github/workflows/release.yaml`, plan job, step `id: destinations` (`~lines 897–960`);
`tests/ci/test_workflow_contracts.py` (absence).

**What is wrong.** Every decision ADR-0011 assigns to this story lives in that step — the
`""|true|false` toggle validation, the `enabled`/`disabled`/`unsupported` trichotomy, the
GitHub-only PyPI capability rule, and the `DOCKERHUB_REPOSITORY` well-formedness gate — and not one
line of it is executed by a test. `_step_with_id(RELEASE_WORKFLOW, …)` is called with `"tag"` and
`"identity"` only; `_release_identity_environment()` supplies `DOCKERHUB_REPOSITORY` directly and so
*bypasses* the step that produces it. The behaviour is asserted only in prose, in
`docs/operational.md`: "any other value fails the plan job rather than being coerced" and "Enabling
`PUBLISH_IMAGE_DOCKERHUB` without a well-formed value **fails the plan job**". Delete the `case`
arm, delete the `=~` repository check, or flip `unsupported` to `disabled`, and all 74 contract
tests stay green.

**Why it matters.** The repository-namespace check is the thing standing between an enabled toggle
with a typo'd `DOCKERHUB_REPOSITORY` and an *immutable* tag pushed to a namespace nobody chose —
the failure `FORGE_REGISTRY` fails closed on, per the step's own comment. And the
`unsupported`/`disabled` distinction is recorded specifically so "the forge silently stopped
publishing packages" cannot be read as "someone turned it off"; a regression there is invisible.
This is exactly rule 3 — the rule was written, the check was not — and the harness to write it
(`_run_step`) already exists in this diff.

**Smallest correct fix.** One parametrised test over `_step_with_id(RELEASE_WORKFLOW,
"destinations")["run"]`, asserting the emitted `enabled-destinations` JSON and the exit status:

- `DOCKERHUB_TOGGLE="yes"` and `PYPI_TOGGLE="1"` → non-zero;
- `DOCKERHUB_TOGGLE="true"` with `DOCKERHUB_REPOSITORY` in `""`, `"Foo/Bar"`, `"nonamespace"`,
  `"a/b/c"` → non-zero, and `"acme/exporter"` → `image-dockerhub:enabled` plus
  `dockerhub-repository=acme/exporter`;
- `FORGE=gitea, PYPI_TOGGLE=true` → `package-pypi:unsupported` (the toggle cannot conjure it);
- `FORGE=github, PYPI_TOGGLE` absent → `disabled`; `PACKAGE_INDEX_SUPPORTED=false` →
  `package-forge:unsupported`, never `disabled`.

## MEDIUM-1 — the publishers' "still names this commit" refusal is a third hand-written copy of a decision the tested module owns, and no test runs it

**File:** `.github/workflows/release.yaml`, `publish-package-forge` step "Re-check the tag still
names this commit…" (`~lines 1052–1077`) and the identical block in `publish-package-pypi`
(`~lines 1150–1176`); guard at `tests/ci/test_workflow_contracts.py:1654`.

**What is wrong.** `stable_tags.py` is asked "which annotated exact `vX.Y.Z` tags peel to this
commit"; the workflow then re-implements "is mine one of them" in nine lines of shell — three
times, once in the plan job and once per package publisher.
`test_step_based_publishers_re_read_the_tag_set_before_they_upload` only greps those bodies for
`scripts/stable_tags.py` and for the emitted key. Set `still_named=true` unconditionally, invert the
`!=`, or drop the `exit 2`, and the guard stays green while the CI-AR36/ADR-0006 refusal it
documents no longer exists. Only the plan job's copy is ever executed by a test.

**Why it matters.** This is the guard-that-cannot-fail shape the repository keeps finding, sitting
directly in front of an upload to PyPI — the one destination from which a version can never be
withdrawn, as the step's own comment says. It is also the half-honoured reading of F9: the module
owns the peel and the spelling, the workflow re-derives the membership relation.

**Smallest correct fix.** Add `--expect-tag NAME` to `scripts/stable_tags.py` (it already owns the
peel, the spelling and the commit resolution): non-zero unless `NAME` is in `stable_tags_at(commit)`.
Replace all three shell loops with one call, and cover it in the module's own tests — one
implementation, tested once, used three times.

## MEDIUM-2 — Docker Hub credentials are passed to the image job even when Docker Hub is a disabled destination

**File:** `.github/workflows/release.yaml`, `publish-image` job, `secrets:` block (`~lines
1240–1244`).

**What is wrong.** `dockerhub_username` and `dockerhub_password` are handed to
`publish-image.yaml` unconditionally. `publish-image.yaml` skips the *login* on
`if: ${{ inputs.dockerhub }}`, so no request is issued — but the secrets are still materialised into
the called workflow's context on every stable run, including runs where the plan job reported
`image-dockerhub: disabled`.

**Why it matters.** The AC quoted inside this repository's own guard is "Disabled destinations
receive no credentials **or requests**". The *requests* half is enforced (`publish-image.yaml`'s
permitted-authority check, exercised by `test_every_published_tag_addresses_a_destination_the_run_logged_into`);
the *credentials* half is enforced nowhere and is violated here. CI-AR24/CI-AR40 disjointness passes
only because `_publishers()` treats the whole image job as one publisher.

**Smallest correct fix.** Gate the secrets on the same single enabled set every other consumer
reads:

```
dockerhub_username: ${{ fromJSON(needs.plan.outputs.enabled-destinations)['image-dockerhub'] == 'enabled' && secrets.DOCKERHUB_USERNAME || '' }}
dockerhub_password: ${{ fromJSON(needs.plan.outputs.enabled-destinations)['image-dockerhub'] == 'enabled' && secrets.DOCKERHUB_TOKEN    || '' }}
```

and extend `test_publisher_credentials_stay_disjoint_between_destinations` with the other half of
the AC: a secret named for a destination must appear only under a condition that reads that
destination's key out of `enabled-destinations`.

## MEDIUM-3 — the widened credential-disjointness guard turned a per-file vacuity check into a global one

**File:** `tests/ci/test_workflow_contracts.py:1541–1560` (`vacuous = vacuous and not
any(used.values())`, `assert not vacuous` after the loop).

**What is wrong.** Before the diff the guard asserted, for `dev.yaml`, `assert any(used.values()),
"no publisher references a secret; the guard is vacuous"`. The rewrite hoisted that assertion out of
the per-file loop and made it an `and`-fold, so it now passes if *any* channel workflow has a
publisher referencing a secret. A channel workflow whose publishers reference no secret at all —
precisely the state in which pairwise disjointness proves nothing about that file — passes on
`dev.yaml`'s behalf.

**Why it matters.** The vacuity check exists to stop the disjointness assertion reporting success
over an empty set. Making it global reintroduces exactly the failure it was written to prevent, one
file along, and it does so silently: the assertion message still says "the guard is vacuous", which
will now never name the file that is.

**Smallest correct fix.** Put it back inside the loop:
`assert any(used.values()), f"{path.name}: no publisher references a secret; the guard is vacuous"`,
and drop the `vacuous` accumulator.

## MEDIUM-4 — `test_every_stable_consumer_reads_the_planned_identity_rather_than_its_own` claims a reach it does not have

**File:** `tests/ci/test_workflow_contracts.py:2142–2178` (docstring and the `blocks` construction).

**What is wrong.** The docstring says "a publisher added later that re-derives a version, or
restates one, fails here. That is the scope attack: the rule is trivial, the reach is the whole
point." The implementation examines `job["with"]` and each `step["with"]` only. Every `env:` block
is invisible — and `env:` is where `release.yaml` actually carries identity today (`RELEASE_TAG`,
`SOURCE_SHA`, `PACKAGE_VERSION`, `TAG_COMMIT` in the plan and publisher steps, and the whole
evidence table). A publisher added later with `env: { PACKAGE_VERSION: ${{ github.ref_name }} }`
re-derives the version in the most natural spelling available and passes this guard.

**Why it matters.** Prose that overstates its own coverage is worse than no prose: it stops the next
reader looking. The rule here is CI-AR11's single planned identity, which is the story's central
interface contract.

**Smallest correct fix.** Add the `env:` blocks to `blocks` (job-level and per-step) and keep the
same key regex. `release.yaml` already satisfies the widened rule, so the change is free today —
which is the cheapest moment to widen it.

## LOW-1 — the protected default branch is hand-written rather than derived

**File:** `.github/workflows/release.yaml`, step `id: tag`, `DEFAULT_BRANCH_REF: origin/main`
(`~line 839`).

The forge reports the default branch on the event (`github.event.repository.default_branch`), so
this is an enumerated copy of a value the source of truth already carries. It fails closed on a
rename (git errors, `stable_tags.py` raises), but it fails closed on *every* release, which is its
own outage. Fix: `DEFAULT_BRANCH_REF: origin/${{ github.event.repository.default_branch }}`.
(`dev.yaml` hardcodes `main` in its trigger for the same reason; that one is a filter, not a
correctness gate, so it is not the same risk.)

## LOW-4 — the tag-acceptance loop has a branch that accepts when it should refuse

**File:** `.github/workflows/release.yaml`, step `id: tag` (`~lines 853, 871–882`).

With `EVENT_REF="refs/tags/"` the prefix strip yields `tag=""`; if the commit carries no stable tag
then `stable_tags=""` and `tr ',' '\n' <<<""` still yields one empty line, so `candidate == tag`
holds and `accepted=true`. Not reachable from a real forge event, and the identity step's emptiness
check catches it one step later — but it is the shape of defect this repository keeps finding, in
the step whose whole job is to refuse. Fix: `[[ -n "$tag" ]] || { echo "empty tag name" >&2; exit 2; }`
after the strip, or `[[ -n "$candidate" ]] &&` in the loop body.

## LOW-5 — the concurrency prose describes queueing the group key does not produce

**Files:** `.github/workflows/release.yaml` (`~lines 787–793`) and `docs/operational.md`
(`~lines 13–15` of the new section), both saying two tag pushes mean "the second queues behind the
first".

`group: ${{ github.workflow }}-${{ github.ref }}` gives every tag its own group, so two *different*
tag pushes never queue — they run concurrently, which is correct and harmless (distinct immutable
identities). Only a re-push of the same ref queues. The behaviour is right; the stated mechanism is
not, and `test_the_stable_channel_owns_exact_tag_pushes` asserts only `cancel-in-progress == "false"`,
so the prose is the only place the claim lives. Fix: say "a stable run is never cancelled by a later
one; runs for the same ref queue rather than superseding" in both places.
