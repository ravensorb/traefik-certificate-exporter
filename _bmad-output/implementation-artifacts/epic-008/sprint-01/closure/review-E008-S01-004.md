## HIGH-1 — "each event has exactly one owner" is only enforced against an identical literal filter string

**File:** `tests/ci/test_workflow_contracts.py:4359-4416` (`TRIGGER_FILTER_KEYS`,
`_trigger_surface`, `_surface_overlap`), proven at `:4495` by a plant that uses
`push: branches: [main]` — the exact literal `dev.yaml` already carries.

`_trigger_surface` flattens every filter key into one untyped set of `"<key>:<value>"` strings, and
`_surface_overlap` calls two claims on the same event disjoint whenever those string sets do not
intersect. Two consequences, both false negatives on the story's central AC:

1. **Glob patterns are compared as literals.** `branches: ["ma*"]` does not equal
   `branches: ["main"]` as a string, so it is judged disjoint.
2. **Different filter categories are treated as separating ref space.** `paths:` and `types:`
   narrow an event but never partition the ref namespace, yet a surface that carries only
   `paths:` shares no string with one that carries only `branches:` and is therefore judged
   disjoint.

I ran four plausible second owners through `_topology_findings` against the real on-disk set:

| planted second owner | result |
|---|---|
| `push: {branches: ["ma*"]}` | **passes** (races `dev.yaml` on every push to `main`) |
| `push: {paths: ["src/**"]}` | **passes** (fires on every push to `main`) |
| `push: {tags: ["v1.*"]}` | **passes** (races `release.yaml` on every `v1.x` tag — two publishers for one release tag) |
| `pull_request: {types: ["labeled"]}` | **passes** |
| `push: {tags: ["v*"]}` | fails, as intended |

Only the fifth — a byte-identical filter — is caught, which is exactly the plant the test uses. So
`test_the_topology_rejects_a_second_owner_of_an_event_and_a_triggered_reusable` passes for a
reason far narrower than the rule it claims: it proves string equality is detected, not that the
event has one owner. The `push: tags: ["v1.*"]` case is the delivery race the whole cutover exists
to prevent.

**Change I would make.** Replace the flat string set with a per-category comparison and make
overlap the *default*, disjointness the thing that must be proven:

- Keep the surface as `{event: {category: tuple[patterns]}}` for the ref-space categories only
  (`branches`, `branches-ignore`, `tags`, `tags-ignore`). `paths`, `paths-ignore` and `types` must
  not participate in the disjointness decision at all — record them, but never let them separate
  two claims.
- Two claims on the same event are **disjoint only if** one filters `branches` and the other
  filters `tags` (genuinely different ref namespaces), **or** both filter the same category and
  every pattern pair is provably non-overlapping. For that pair test, use a conservative rule:
  if either pattern contains `*`, `?`, `[` or `+`, treat the pair as overlapping unless
  `fnmatch.fnmatchcase` proves one side's literal is excluded by the other — i.e. wildcard vs
  wildcard is always an overlap. False positives here are safe; false negatives are the defect.
- Anything else — an unfiltered event, an `-ignore` form, an unrecognised key — is an overlap.
- Then add the four rows above to `test_the_topology_rejects_...` as plants, so the rule is proven
  at its claimed width and not at literal equality.

## HIGH-2 — the runbook prohibition regexes miss the plausible rewordings of all four prohibited actions

**File:** `tests/ci/test_workflow_contracts.py:4548-4564` (`PROHIBITED_RECOVERY_ACTIONS`), plants at
`:4654`.

The four patterns match a narrow vocabulary. I ran good-faith instruction rewordings through
`_runbook_findings`; every one of these is accepted as lawful runbook prose:

| planted instruction | verdict |
|---|---|
| `Re-run the workflow from the start.` | **evades** (`the start` is not in `all\|every\|the whole\|the entire`) |
| `Re-run the run.` | **evades** |
| `Trigger the workflow again from the tag.` | **evades** |
| `Push the tag again with -f so the release points at the new build.` | **evades** (`-f` is not `--force`; `force[- ]` needs a following word) |
| `git push -f origin v1.2.3` | **evades** |
| `When the package index rejects the upload, remove the published version and try again.` | **evades** (`remove` is not `delet…`) |
| `Yank the version from PyPI and publish the same wheel again.` | **evades** — and `yank` is PyPI's own verb for this |
| `Replace the published image tag with the corrected image.` | **evades** (`replace` is not `overwrit…`) |
| `Re-run all jobs.` | caught |

The comment above the tuple asserts the actions are "matched as behaviours rather than as literal
sentences, so a rewording that reintroduces one is still caught". That claim is false as written,
and per global rule 3 prose that overstates its own coverage is the part that stops the next reader
from looking.

**Change I would make.**

- Whole-workflow rerun: `re-?run(?:ning)?\s+(?:all|every|the (?:whole|entire|full|complete)\s+\w+|the (?:run|workflow|pipeline|job list))|whole[- ](?:workflow|run)\s+re-?run|(?:re-?trigger|re-?dispatch|trigger .{0,20}again)`.
- Force: add `\bforce\b(?!\s*(?:update|push|overwrit|mov)\w*\s+is)` is too loose — instead add the
  short flags and the bare verb: `--force|(?<![\w-])-f(?![\w-])|force[- ](?:push|updat|overwrit|mov|re-?creat)|\bforce-?(?:push|updat)\w*`.
- Deletion: `\b(?:delet|remov|purg|yank|drop)(?:e|es|ed|ing|ion|al)?\b`.
- Overwrite: `\b(?:overwrit(?:e|es|ing|ten)|re-?upload|re-?push|re-?publish(?:es|ed|ing)?|replac(?:e|es|ing|ed))\b`.
- Then extend `test_the_runbook_guard_rejects_a_rerun_all_jobs_instruction` with every row of the
  table above as a plant, and re-check the real section (widening `delet` to `remov|replac` will
  need the "the conflicting tag, release and package are never moved, deleted or republished"
  sentence and the prohibited-actions table rows to keep their markers — they already do).

## MEDIUM-1 — `PROHIBITION_MARKER` is satisfied by an unrelated negation anywhere in the same statement

**File:** `tests/ci/test_workflow_contracts.py:4566-4571`, used at `:4616`.

The marker set includes `is not`, `are not`, `do not`, `does not`, `cannot`. Those are ordinary
conditional English, so a negation that has nothing to do with the prohibited verb excuses it:

```
If the release is not yet consumed, delete it and republish.
```

`_runbook_findings` returns nothing for that statement — `is not` satisfies the marker and the
instruction ships. This is a plausible good-faith edit and it is precisely the instruction the AC
forbids.

**Change I would make.** Require the marker to *govern* the matched verb rather than merely
co-occur. Two cheap options, either sufficient:

1. Restrict the marker set to the unambiguous prohibitive forms — `never`, `prohibited`,
   `forbidden`, `must not`, `may not`, `is refused`, `unsupported`, `instead of`, `rather than`,
   `not a recovery` — and drop the generic `is not` / `are not` / `do not` / `does not` /
   `cannot`; or
2. keep them but require the marker to appear **before** the matched verb in the statement
   (`marker.start() < action_match.start()`), which is how a prohibition is actually written.

Add `If the release is not yet consumed, delete it and republish.` as a plant so the hole cannot
reopen.

## MEDIUM-2 — the runbook guard examines one section, but the AC governs the runbook

**File:** `tests/ci/test_workflow_contracts.py:4573-4583` (`_recovery_section`), used at `:4651`.

The AC reads "The runbook never presents whole-workflow rerun, force update, deletion, or
overwrite as normal recovery." The guard scopes itself to the text between `## Publication
recovery` and the next `## `. The very next heading in the same file is `## Rollback`
(`docs/operational.md:356`) — another recovery procedure, entirely unexamined. Any of the four
prohibited actions written there passes. This is the "guard proves the rule but not its reach"
shape global rule 4 names, and the docstring's justification ("a guard that read the whole file
would fail on somebody else's prose") is not true today: I ran `_runbook_findings` over the entire
`docs/operational.md` and it returns **zero** findings, so widening the scope is free right now
and only gets more expensive later.

**Change I would make.** Run `_runbook_findings` over the whole of `docs/operational.md` (and,
better, over every `docs/**/*.md` that GitHub renders as operator guidance), and keep the section
locator only for the *positive* assertions that are genuinely section-local (the failed-jobs-only
prescription, the three halt conditions, the two named strings). Add a non-vacuity assertion that
the scanned text is non-empty and that at least one file was scanned.

## MEDIUM-3 — `_statements` hand-rolls a Markdown block parser and a sentence segmenter

**File:** `tests/ci/test_workflow_contracts.py:4585-4614`.

Global rule 1 lists "parsers and serialisers of any format" as the domain where a hand-rolled
implementation is almost always wrong, and this is a small Markdown block parser (headings, table
rows, list items, fences, block quotes, blank-line paragraph boundaries) plus a sentence
segmenter, written by hand and carrying the usual defects: a line inside a fenced code block that
does not start with a fence character is treated as prose; `re.split(r"(?<=[.!?])\s+", …)` splits
on `e.g. ` and on any abbreviation; a wrapped list item's continuation line becomes a separate
statement from its own bullet. No ADR records the decision.

`markdown-it-py` 3.0.0 is **already installed in this environment** (transitively, via `rich`), so
block tokenisation is a few lines and one declared dev dependency, not a new build-vs-buy fight.

**Change I would make.** Replace `_statements` with `markdown_it.MarkdownIt().parse(section)`,
take the `inline`/`text` content of `paragraph`, `list_item`, `heading` and table-cell tokens as
the statement units, and skip `fence`/`code_block` tokens outright. Declare `markdown-it-py` in
the dev dependency group so the transitive availability is not load-bearing. If the team would
rather keep the hand-rolled splitter, that needs the ADR global rule 1 requires — naming
`markdown-it-py` and `mistune`, and stating who owns the splitter's defects.

## MEDIUM-4 — `RETIRED_INVOCATION` misses the bare-relative-path invocation, and its `act-build.sh` escape hatch is unreachable

**File:** `tests/ci/test_workflow_contracts.py:4721-4724` and `:4753-4757`; the same pattern shape
is duplicated at `tests/test_release_version.py:642-644`.

The pattern requires `./` or a `sh`/`bash` prefix. Running it over realistic invocation forms:

| text | matched? |
|---|---|
| `./build.sh` | yes |
| `bash docker/build.sh` | yes |
| `docker/build.sh --push` | **no** — a bare relative path is a perfectly normal command in a justfile recipe or a workflow `run:` |
| `$GITHUB_WORKSPACE/build.sh` | **no** |
| `source build.sh` | **no** |
| `'docker/build.sh'` (quoted) | **no** |
| `./docker/act-build.sh` | **no** |

Two problems. First, the reach is narrower than "nothing invokes them" — a resurrected
`docker/build.sh` called as `docker/build.sh --push` is invisible (the existence assertion only
covers the two exact paths; a *new* path resurrecting the same shell pipeline is not covered
either way). Second, because `./docker/act-build.sh` never matches the pattern at all, the
`assert "act-build.sh" in match.group(0)` allowance at `:4754` is dead code — it can never
execute, so the comment explaining why `act-build.sh` is exempt describes a branch that does not
run.

**Change I would make.** Broaden to a command-position match rather than a prefix match —
`(?<![\w./-])(?:[\w.${}/-]*/)?build\.sh(?![\w.-])` with the `act-build.sh` exclusion expressed as a
negative lookbehind (`(?<!act-)`) so the exemption is in the pattern and provable, then delete the
now-redundant in-loop assert. Add plants for `docker/build.sh --push` and `source build.sh`, and
one plant proving `./docker/act-build.sh` is still accepted (which today's test does not
demonstrate).

## MEDIUM-5 — the CI-AR41 aggregator guard does not assert the fields its own docstring says are covered elsewhere

**File:** `tests/ci/test_workflow_contracts.py:4766-4805`.

The docstring says it covers "the two fields nothing else asserts", implying digest, platforms and
the Release URL are asserted by other guards. They are — but not *at the aggregator*:

- `tests/ci/test_workflow_contracts.py:2848-2866` asserts `needs.<image job>.outputs.digest` and
  `…outputs.platforms` appear in `json.dumps(document)` — anywhere in the **whole workflow file**.
  Moving those rows out of `release-evidence` into any other job keeps that guard green while
  CI-AR41's evidence table loses the digest and platform rows.
- the Release URL is asserted (around `:3730`) on the `finalize` job's own outputs and step `env`,
  not on the aggregator that writes the run summary.

So the story's DoD sentence — "Run summaries expose source/tag, version, artifact hashes, image
digest/platforms, destination conclusions, Release URL, and alias outcomes" — is guarded for
exactly two of its eight items at the job that actually writes the summary. The new test already
computes `body = json.dumps(jobs[name])` for the aggregator; adding the rest is three lines.

**Change I would make.** In the aggregator loop, additionally assert the aggregator body contains
`needs.plan.outputs.source-sha`, `needs.plan.outputs.package-version`, and — derived, not
enumerated — for each image-publisher job name, `needs.<job>.outputs.digest` and
`needs.<job>.outputs.platforms`; and for each job that calls `APPROVED_RELEASE_ACTION`,
`needs.<job>.outputs.release-url`. Derive each set from the parsed document exactly as
`_publishers` does, so a destination added later is covered without an edit. Then correct the
docstring: it currently overstates what the surrounding guards reach.

## MEDIUM-6 — the docs dangling-reference check only sees full-path citations, so the rename attack it claims to cover is half-covered

**File:** `tests/ci/test_workflow_contracts.py:4696-4703`.

`re.findall(r"\.github/workflows/([\w.-]+\.ya?ml)", text)` finds exactly **two** citations in
`docs/operational.md` today (lines 115 and 179). Every other workflow reference on the page —
including the ones this diff adds, `` `verify-build.yaml` `` at line 304 and the finalizer
workflow names — is a bare backticked filename and is never checked for existence. So the
docstring's "renaming it and leaving the old reference behind fails the second" holds only for
references written with the full path; the more common form on the page silently dangles.

The reverse half (`assert name in text` for each channel) *does* match bare names, which makes the
asymmetry easy to miss: a rename is caught going one way and not the other.

**Change I would make.** Widen the citation regex to also collect backticked workflow filenames —
e.g. `` `([\w.-]+\.ya?ml)` `` — and check existence for any collected name whose stem matches a
file that ever lived in `.github/workflows/`, or more simply: for every backticked `*.ya?ml` token
on the page, assert `(WORKFLOWS / name).exists()` unless it resolves elsewhere in the repository
(`docker-compose.yml` and friends). Keep `assert cited` and raise it to a count that reflects the
real page so the check cannot quietly go vacuous.

## LOW-2 — `dev.yaml`'s summary echoes `IMAGE_TAGS` unnormalised while `release.yaml` normalises it

## LOW-4 — the digest→run lookup command needs one more step for a multi-platform index

**File:** `docs/operational.md:335-341`.

`docker buildx imagetools inspect --format '{{json .Image}}' <ref>@sha256:…` against a
multi-platform **index** — which is what this repository publishes, per CI-AR39 — returns a map
keyed by platform (`{"linux/amd64": {...}, "linux/arm64": {...}}`), not a single image config. The
instruction "Read `org.opencontainers.image.revision` from the labels" therefore needs a
drill-down the operator has to invent at 3am.

**Change I would make.** Show the working one-liner, e.g.

```bash
docker buildx imagetools inspect --format '{{json .Image}}' <ref>@sha256:... \
  | jq -r 'to_entries[0].value.config.Labels."org.opencontainers.image.revision"'
```

and say in one clause that the output is keyed by platform because the artifact is an index.
(The underlying claim is correct — `docker-bake.hcl:65` sets `org.opencontainers.image.revision`
from `REVISION`, and `.github/workflows/publish-image.yaml:153` sets `REVISION` from the build
manifest's `source_sha`. The 30-day retention claim also checks out against
`verify-build.yaml:663`.)

## LOW-5 — a legitimately dispatch-only workflow would be reported as an unreachable orphan

**File:** `tests/ci/test_workflow_contracts.py:4354` and `:4455-4460`.

`workflow_dispatch` is excluded from the trigger surface, and the orphan branch fires on
`elif not surface`. A maintenance workflow triggered only by a person (`on: workflow_dispatch:`,
no `workflow_call`, called by nobody) therefore produces "owns no automatic event and no workflow
calls it, so nothing can reach it" — which is untrue, and Epic 9 adding one such workflow would
hit a false failure with a misleading message.

**Change I would make.** Make the orphan condition `not surface and not _declared_events(document)
& NON_AUTOMATIC_EVENTS`, i.e. only a workflow reachable by neither an automatic event, nor a
caller, nor a person is an orphan. Add it as a lawful case in
`test_the_topology_rejects_a_second_owner_of_an_event_and_a_triggered_reusable` alongside
`nightly.yaml`.

(`assert examined == len(list(tracked_files))`) rather than the magic `100`, so the scope
assertion is derived from the source of truth rather than a number someone chose once.

## What is done well (recorded so it is not lost in a re-review)

- The topology assertion genuinely derives its scope from `WORKFLOWS.glob("*.yaml")` and from the
  parsed `on:` block; the `.yml` blind spot in that glob is separately closed by
  `test_governance_scope_is_derived_from_disk`'s `iterdir()` set-equality (`:258-264`).
- Every new guard carries a non-vacuity assertion (`assert documents`, `assert cited`,
  `assert channels`, `assert examined`, `assert owners and reusable`) — the "examines nothing"
  failure mode is covered throughout.
- The planted violations run through the *same* pure function the real assertion uses
  (`_topology_findings`, `_runbook_findings`), not a second implementation. That is the right
  shape; HIGH-1 and HIGH-2 are about the function's rule, not its plumbing.
- Both diffs to the workflows are runtime-safe: `release-evidence` and `development-evidence` both
  already list `verify` in `needs`, and `verify-build.yaml` declares the `build-manifest-sha256`
  `workflow_call` output, so `needs.verify.outputs.build-manifest-sha256` resolves at run time.
- No pre-upload existence probe was introduced anywhere in the diff, and no bespoke test harness
  was added — everything is pytest functions and module-level pure helpers.
