# Certify End-to-End Gitea Delivery and Migration

As an operator,
I want a repeatable Gitea conformance suite and migration runbook,
So that ownership moves only after pull-request, development, and stable delivery are proven.

Depends on: `E008-S01-006`, `E009-S01-002`.

## Acceptance Criteria

**Given** the pinned Gitea staging tuple
**When** the conformance suite executes
**Then** it proves secret-free pull-request verification, default-branch development planning,
optional TestPyPI, stable PyPI, Docker Hub plus Gitea registry fan-out, active-forge Release, and
one `linux/amd64`/`linux/arm64` index (CI-AR35)

**Given** failures are injected before preflight, during an immutable publisher, before alias
finalization, and after forge Release creation
**When** recovery reruns
**Then** exact remote identities are reconciled, mismatches fail, and aliases never expose an
incomplete transaction

**Given** untrusted fork code attempts privilege escalation
**When** negative conformance scenarios run
**Then** it cannot select a publisher runner, obtain protected secrets, publish a package/image,
create a Release, or poison an artifact/cache consumed by protected publication

**Given** certification is green and approved
**When** the migration runbook executes
**Then** GitHub publication is disabled before Gitea publication is enabled
**And** one active forge owns every run
**And** a tested rollback point exists until production validation completes (CI-AR1)

## Technical Acceptance Criteria

### Conformance interface and evidence

- A versioned checklist/harness identifies the pinned tuple, workflow commit, run IDs, source or
  exact tag, channel, enabled targets, and expected failure/success state.
- Evidence records package filenames/hashes, image index digest/platform descriptors, forge
  release URL/identity, alias values before/after, receipt hash, and cleanup result without
  credentials.
- Certification artifacts are retained with the project-defined evidence period and linked from
  the migration decision record.
- Any change to Gitea server, runner, execution image, CA path, action major, or shared workflow
  invalidates the certification or triggers the documented risk-based subset plus final full run.

### Scenario matrix

- PR scenarios include internal and forked contributions, cancellation, failed test, malicious
  secret reference, and artifact/cache poisoning attempts.
- Development scenarios include all destinations disabled, TestPyPI only, each image target
  alone, both image targets, all enabled, exact-tag suppression, one-target outage, and rerun.
- Stable scenarios include PyPI only, each image target, combined fan-out, forge Release,
  forward-only aliases, existing identical objects, mismatched objects, and partial recovery.
- Platform scenarios inspect both required OCI descriptors and smoke-test the installed version/
  wheel provenance.
- Private-CA scenarios include valid, missing, wrong, and rotated chains.

### Migration transaction

- The runbook defines owners, go/no-go approval, maintenance window, backups, repository mirror
  validation, action availability, variables/secrets/environments, registry namespaces, package
  publisher configuration, CA rollout, and runner capacity.
- GitHub publisher toggles/credentials are disabled or revoked before Gitea protected publication
  is enabled; a shadow verification run occurs before the first Gitea publication.
- First production development and stable runs are observed against explicit expected plans and
  receipts.
- Rollback criteria identify how to stop mutation, restore GitHub ownership/publication, and
  reconcile immutable objects without moving aliases backward or deleting packages.

### Error handling, observability, and security

- A conformance failure blocks certification and names the scenario/evidence gap; manual claims
  cannot mark a red scenario green without a recorded exception and expiry.
- Runner, workflow, Gitea, registry, and package-index logs are correlated by non-secret run and
  source identities.
- Secret scanning validates all captured logs/artifacts before retention.
- Migration credentials are short-lived or rotated immediately afterward; temporary dual-access
  is time-bound and documented.

### Test anchors

- The suite runs every externally hosted action used by the production workflow and records its
  resolution source/version under Gitea.
- Workflow contract tests prove there is no `ACT`/forge-mode branch and the four-file topology
  remains intact (CI-AR2, CI-AR5).
- Failure injection verifies aggregate preflight, immutable-first ordering, aliases-last, and
  receipt-based idempotency (CI-AR23, CI-AR26–CI-AR30).
- A tabletop rollback exercise demonstrates the runbook can return to a single active owner
  without overwriting immutable identities.
- Final sign-off identifies any accepted limitation and its owner/expiry.

## Deliverables

- Automated/assisted Gitea conformance suite and evidence template.
- Migration, rollback, and re-certification runbooks.
- Completed staging certification record for the pinned tuple.

## Out of Scope

- Running the production ownership migration without explicit operator approval.
