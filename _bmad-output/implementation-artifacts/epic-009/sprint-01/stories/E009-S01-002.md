# Configure Private-CA Trust and Gitea Destinations

As a Gitea operator,
I want private-CA trust and host-derived registry/release coordinates configured before network
operations,
So that the shared workflows authenticate safely without GitHub-specific assumptions.

Depends on: `E009-S01-001`.

## Acceptance Criteria

**Given** Gitea uses a private certificate authority
**When** a workflow begins
**Then** the approved CA action installs trust before checkout where possible, registry login,
artifact access, or API requests
**And** certificate material is never retained as a workflow artifact

**Given** the repository owner is Gitea
**When** publication planning derives forge coordinates
**Then** `PUBLISH_IMAGE_FORGE=true` selects the local Gitea registry and release API, never GHCR
**And** `FORGE_REGISTRY` is used only when host derivation is unsafe/impossible (CI-AR1,
CI-AR6, CI-AR20)

**Given** PyPI or TestPyPI is enabled from Gitea
**When** the applicable package publisher starts
**Then** it uses a scoped protected token rather than GitHub OIDC and maps it only to that job
(CI-AR24, CI-AR25)

**Given** any required CA, endpoint, capability, or token is invalid
**When** aggregate preflight runs
**Then** it blocks the entire enabled fan-out before authentication or mutation (CI-AR23)

## Technical Acceptance Criteria

### CA interface and lifecycle

- The CA action input accepts PEM certificate chains only, validates parsing and trust purpose,
  masks inputs, and writes to an ephemeral runner-owned path with restrictive permissions.
- Trust installation precedes every TLS client used by checkout/action resolution where the
  platform allows, Docker login/push, Gitea API, and artifact operations.
- CA content, fingerprints derived from private configuration, and temporary paths are excluded
  from plans, manifests, receipts, caches, and uploaded artifacts.

### Forge-coordinate contract

- Forge derivation normalizes `server_url`, API base, registry host, owner, and repository from
  runtime context and records only non-secret values in `publication-plan-v1.json`.
- The override accepts a host[:port] under documented rules and rejects scheme confusion,
  embedded userinfo, path/query/fragment, whitespace/control characters, and cross-forge hosts.
- GitHub context maps to GHCR; non-GitHub supported context maps to the configured Gitea registry;
  there is no operator-maintained GitHub/Gitea boolean.

### Credentials and permissions

- Gitea token scopes are documented and minimized for image push and forge Release operations;
  separate tokens are used when Gitea cannot scope one token safely.
- PyPI/TestPyPI protected tokens are channel-specific and never exposed to image or release jobs.
- Disabled destinations map no secret, install no destination-specific CA, and contact no
  endpoint (CI-AR19, CI-AR24).

### Error handling and observability

- Probes distinguish DNS/connectivity, TLS trust, authentication, authorization, missing
  namespace/repository, and unsupported API capability without logging credential values.
- Preflight output names the destination and configuration key and exposes only aggregate
  `publication-ready=true` on success.
- Logs record normalized host, credential mode (not value), CA enabled/disabled, and probe
  outcome.

### Test anchors

- Tests cover public CA, valid private CA chain, malformed PEM, wrong CA, expired CA, and missing
  required CA.
- Coordinate tests cover GitHub, derived Gitea, safe override, credential-in-URL, path traversal,
  alternate host, and disabled forge target.
- Credential-mode tests cover GitHub OIDC vs Gitea token and prove job-scoped secret isolation.
- A local TLS fixture proves the installed CA affects the intended clients and cleanup removes
  temporary trust material.
- Token rotation/revocation and CA rollover procedures are documented and rehearsable.

## Deliverables

- Private-CA integration, forge-coordinate derivation, preflight checks, and tests.
- Gitea secret/scope and CA operation documentation.

## Out of Scope

- End-to-end certification and owner migration (E009-S01-003).
