# Certify the Gitea Evidence/Recovery Contract Design (Statically)

As a maintainer, I want the certification-report schema, recovery/fault-injection contract, and
action-closure-drift check this project would need for a future live Gitea certification to
already exist as tested, fixture-driven code, so that if live certification is ever pursued, the
hard part — correctly validating the evidence — is not written under time pressure against a
production forge.

Depends on: `E009-S01-001`.

**Rescope note (2026-10-06):** This story originally required acquiring a real evidence export
from a pinned, live Gitea instance and resolving a real certification report against it before
gating production-owner migration. That live-acquisition/live-execution requirement is dropped
(no production-owner migration is currently planned or blocked on this). What remains in scope —
and what this story actually delivers — is the *validator*: a tested, static implementation of
the evidence-export schema (ADR-0017), the certification-case registry (F20), the recovery
fault-injection/cleanup contract (ADR-0020), and the action-closure-drift check (ADR-0016),
proven against synthetic fixtures. See the referenced ADRs' scope notes and `issues.yaml`
(`BL-E009-014` through `BL-E009-021`, resolved `wontfix`) for the specific live-Gitea items
dropped.

## Business acceptance criteria

### Outcome

Maintainers get a tested, reusable validator — not yet exercised against real evidence — that
would reject a certification report with a missing required case, an extra undeclared case, a
duplicate, a stale or cross-tuple/cross-source/cross-workflow row, a credential-shaped leak, or an
unexplained action-closure drift, the moment real Gitea evidence is ever produced to run it
against. No production migration is currently gated on this story.

Spec: _bmad-output/planning-artifacts/architecture/architecture-ci-cd-pipeline-2026-08-31/ARCHITECTURE-SPINE.md#trust-boundaries-and-gitea-certification

### Non-goals

- Does not acquire a real evidence export from a live Gitea API, or run a real certification
  pass; that scope is dropped (see rescope note above).
- Does not gate any production migration decision — none is currently planned.
- Does not build a new evidence-storage platform; the schema this story validates matches
  ADR-0017's retained-export shape, should live acquisition ever be pursued.

## Technical acceptance criteria

### Interface contracts

- The evidence-export record shape the validator checks: source-native run/job records,
  immutable run/attempt/job IDs, timestamps and conclusions, source SHA, workflow path and
  revision SHA, the canonical pinned-tuple record and fingerprint, referenced artifact hashes and
  published digests, and a `SHA256SUMS` covering the whole export (ADR-0017) — all constructed as
  synthetic fixtures for this story, never acquired live.
- `tests/ci/test_certification.py`'s `REQUIRED_GITEA_CASES` registry is the single source of
  required case IDs, independent of `docs/ci/gitea-certification.md`'s prose; the validator
  resolves each synthetic report row against both the registry and a synthetic evidence export
  (F20).
- Sibling convention: fixtures and helpers follow `tests/ci/support.py`'s existing pattern
  (`PROJECT_ROOT`, YAML loaders), with certification-specific fixtures living in
  `tests/ci/test_certification.py` itself.
Spec: _bmad-output/planning-artifacts/architecture/architecture-ci-cd-pipeline-2026-08-31/ARCHITECTURE-SPINE.md#lean-publication-requirements

### Error and edge case handling

- The validator rejects, against synthetic fixtures: a missing required case, an extra
  undeclared case, a duplicate, a stale run, a cross-tuple/cross-source/cross-workflow row, an
  unhashed or locally-synthesized record presented as authoritative, and a credential-shaped
  value anywhere in export or report.
- The recovery contract's pre-state/expected-partial-state/rerun-identity/preservation/cleanup-
  postcondition schema is validated against synthetic fixtures representing both a clean recovery
  and a planted violation (orphaned upload, stale credential, lost output) (ADR-0020).
- Live negative cases (wrong CA, missing credential/scope against a running forge, restricted-
  permission write refusal, endpoint-scope omission observed at runtime, absent default-branch
  context observed at runtime, failed-jobs-only-unsupported probed against a real rerun API) are
  out of scope; they require an actual Gitea instance (`BL-E009-015`, `BL-E009-016`,
  `BL-E009-018`, resolved `wontfix`).
Spec: none — the validator's rejection taxonomy and the recovery-contract schema are this story's
Definition of Done and ADR-0017/ADR-0020 content; neither is yet reflected in the indexed
architecture spec.

### Observability requirements

- `resolve_certification_report` projects a synthetic report row from a synthetic evidence
  export and asserts the projection is exact (case ID, run ID/attempt, job IDs, source/workflow
  identities, tuple fingerprint, artifact hashes/digests, conclusion, evidence-export digest);
  this is a pure-function contract check, not a live observability pipeline (ADR-0017, CI-AR41).
- A step-summary-is-an-observation predicate (`case_passed`/`CaseOutcome`) encodes that rendered
  step-summary text is never itself a pass/fail signal — job outputs are — and is unit-tested
  against synthetic job-output fixtures.

### Security considerations

- The validator fails closed on synthetic fixtures simulating wrong API authority, incomplete
  pagination, missing identity, or credential-shaped content in the response (ADR-0017); it has
  never been exercised against a real API response, which is explicitly documented in
  `docs/ci/gitea-certification.md`.
- A planted credential-shaped string (e.g. a token-looking value) in either a synthetic export or
  report fixture must fail the redaction-scanning check.
Spec: none — ADR-0017's fail-closed collection rules and the credential-shaped-content scan are
`docs/adr/` content, outside the indexed spec.

### Testability approach

- `tests/ci/test_certification.py` owns the `REQUIRED_GITEA_CASES` registry, the evidence/report
  validator, the recovery-contract validator, and the action-closure-drift comparison, each
  proven against synthetic fixtures explicitly marked as fixtures (never presented as real
  evidence).
- Each Test anchor below is a guard-then-violation pair, consistent with `tests/ci/test_gates.py`'s
  precedent of testing "the checks that examine the pipeline" rather than the pipeline itself.
- All fixtures are synthetic and constructed in-test; no live Gitea instance, credential, or
  network call is used anywhere in this story's test suite.
Spec: none — read directly from `tests/ci/`'s existing siblings (`test_gates.py` precedent); no
spec section prescribes the registry/test layout.

### Existing-library check

- No marketplace action performs Gitea-API evidence export or certification-gate resolution;
  this remains bespoke analysis code, justified because the alternative (an unverifiable Markdown
  narrative) is worse, even though it is not yet exercised against real data (F20).
- The recovery contract assumes Gitea's native per-job rerun capability exists; this story does
  not implement or probe a custom retry orchestrator, and does not verify the real rerun API
  (CI-AR38; `BL-E009-018` resolved `wontfix`).

## Acceptance Criteria

**Given** a synthetic evidence export built as a test fixture, **when** the evidence/report
validator runs, **then** it accepts a report whose rows are an exact projection of that export
(case ID, run ID/attempt, job IDs, source/workflow identities, tuple fingerprint, artifact
hashes/digests, conclusion, evidence-export digest) and rejects a missing row, an extra
undeclared row, a duplicate, a stale row, and a row referencing a different tuple, source, or
workflow (ADR-0017, F20). Acquiring a *real* export from a live Gitea API, and proving every
positive certification case (PR verification, protected delivery, artifact round-trip, private-CA
boundaries, multi-arch image, forge package channel, forge Release, both reusable workflows,
aliases-last) against it, is out of scope (`BL-E009-014`, `BL-E009-020`, resolved `wontfix`).

**Given** the Story 9.1 vetted action closure and a synthetic Story 9.2-scenario closure fixture,
**when** the drift comparison runs, **then** it detects an unexplained addition, omission, or
resolution-digest difference between the two closures. Deriving the *real* full-scenario closure
from actually-executed Gitea runs is out of scope (`BL-E009-019`, resolved `wontfix`) (ADR-0016).

**Given** a synthetic recovery fixture representing one destination failing after another's
successful immutable publication, **when** `assert_recovery_contract` runs, **then** it accepts a
fixture that preserves the successful destination's original conclusion/start time/outputs, shows
no second upload request, and documents a clean cleanup postcondition for every touched resource
class, and rejects a fixture planting an orphaned partial upload, a stale credential, a stale
workspace, or a lost output. Rehearsing this against a *real* Gitea fault injection and rerun is
out of scope (`BL-E009-017`, resolved `wontfix`) (ADR-0020).

**Given** step-summary text and job outputs as two different signals, **when**
`case_passed`/`CaseOutcome` evaluate a synthetic job-output fixture, **then** the predicate
treats step-summary rendering as an observation only and job outputs as the authoritative
pass/fail signal.

**Given** the `git-action-release@v2` Gitea-path release-fallback decision from Story 9.1
(ADR-0022), **when** this story's scope is defined, **then** it does not select or exercise a
release-fallback action itself; any such decision is a Story 9.1 predecessor concern.

## The certification gate needs a home, or it is prose (F20)

This story declares mechanical anchors — "the gate derives its required cases from the declared
negative-case set and demands a run URL and conclusion for each; plant a removed case" — while
originally having nowhere for that check to live. Resolved by implementing it as real test code:
`tests/ci/test_certification.py` owns a `REQUIRED_GITEA_CASES` requirements registry independent
of `docs/ci/gitea-certification.md`'s prose, and a validator proven against synthetic fixtures.
The registry enumerates requirements, not repository contents; this story does not yet have real
evidence to resolve it against.

- `docs/ci/gitea-certification.md` (new) — case registry, the validator's contract, and an

## Definition of Done

- `REQUIRED_GITEA_CASES` enumerates every case this project would need to certify if live
  certification were pursued, independent of the narrative document.
- The evidence/report validator (`resolve_certification_report`) accepts/rejects correctly
  against synthetic fixtures covering: exact projection, missing case, extra case, duplicate,
  stale row, and cross-tuple/source/workflow row (ADR-0017).
- The recovery contract validator (`assert_recovery_contract`) accepts/rejects correctly against
  synthetic fixtures covering: clean recovery, orphaned upload, stale credential, stale
  workspace, and lost output (ADR-0020).
- The action-closure-drift comparison detects an unexplained addition, omission, or
  resolution-digest difference between two synthetic closures (ADR-0016).
- The step-summary-is-an-observation predicate is unit-tested.
- `docs/ci/gitea-certification.md` documents, per required case, its current status (validated
  statically / requires live Gitea — not executed) and the manual runbook steps a future live
  certification pass would need.
- No production-owner migration decision is gated on this story; that scope does not currently
  exist for this project.
- All live-acquisition/live-execution items originally in this story's scope are explicitly out
  of scope and tracked as resolved (`wontfix`) backlog issues `BL-E009-014` through
  `BL-E009-021`.

## Test anchors

Guard, then the violation planted to prove it fires — all against synthetic fixtures, no live
Gitea instance:

- Case-set completeness: the registry demands an export-backed report row for each required case;
  plant a new required case without export evidence, and separately remove a report row.
- Evidence authenticity: plant a plausible report row with no matching export record, a stale run
  from another source SHA, a cross-tuple row, a changed export after checksumming, and a locally
  synthesized record; each must fail.
- Closure-drift: plant an action used only by a synthetic failure/rerun-path fixture and require
  unexplained drift to fail.
- Recovery contract: plant an orphaned partial upload, a stale credential, a stale workspace, and
  a lost output in synthetic recovery fixtures; each must fail the cleanup-postcondition check.
- Evidence and secrecy: plant a credential-shaped value anywhere in a synthetic export or report
  fixture, and a missing evidence-export digest field; both must fail.
- Step-summary rendering is an observation, not a pass/fail criterion, verified against synthetic
  job-output fixtures.

## Out of Scope

- Acquiring a real evidence export from a live Gitea API, or resolving a real certification
  report against it (`BL-E009-020`, resolved `wontfix`).
- Certifying any positive case (PR verification, protected delivery, artifact round-trip,
  private-CA boundaries, multi-arch image, forge package channel, forge Release, both reusable
  workflows, aliases-last) against a running Gitea forge (`BL-E009-014`, resolved `wontfix`).
- Proving live forge denials (wrong-CA, missing-credential/scope, endpoint-scope omission,
  restricted-permission write refusal) (`BL-E009-015`, resolved `wontfix`).
- Observing absent default-branch context or `environment:pypi` parse-acceptance behavior on a
  real Gitea runner (`BL-E009-016`, resolved `wontfix`).
- Rehearsing real failed-jobs-only recovery (fault injection, native per-job rerun, pre/post
  state capture) against a live Gitea instance (`BL-E009-017`, resolved `wontfix`).
- Probing failed-jobs-only-unsupported against a real Gitea rerun API (`BL-E009-018`, resolved
  `wontfix`).
- Deriving the real action closures from actually-executed runs (`BL-E009-019`, resolved
  `wontfix`).
- Any production-owner migration decision — none is currently planned or blocked on this epic.
- Claiming compatibility with unpinned Gitea/runner/action versions.
