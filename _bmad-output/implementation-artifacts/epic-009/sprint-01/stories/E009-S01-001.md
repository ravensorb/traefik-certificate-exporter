# Establish a Pinned and Isolated Gitea Runner Baseline

As a Gitea operator,
I want a documented and pinned Gitea Actions runner baseline with separate trust pools,
So that portable workflow syntax does not hide runner or security differences.

Depends on: `E007-S01-005`.

## Acceptance Criteria

**Given** the project declares Gitea support
**When** its support matrix is inspected
**Then** it records the tested Gitea server, act-runner, runner image/digest, action major aliases,
and known compatibility exceptions (CI-AR34)

**Given** an untrusted pull request and a protected publisher job
**When** runner labels and policies are evaluated
**Then** they cannot execute on the same persistent trust pool or share credentials, workspace,
or writable caches

**Given** an untrusted verification job executes
**When** its host/container configuration is inspected
**Then** it has no publisher secrets, protected environment, broad host filesystem mount,
privileged container, or unrestricted Docker socket

**Given** the pinned tuple changes
**When** an operator proposes production use
**Then** the conformance certification expires and must be rerun before publication resumes

## Technical Acceptance Criteria

### Runner contract

- A checked-in support matrix pins Gitea server, act-runner, runner execution image by digest,
  Docker/Buildx/QEMU expectations, and every externally hosted action major used by workflows.
- Runner labels distinguish at least untrusted verifier and protected publisher pools; workflow
  jobs cannot accept a caller-provided arbitrary label.
- Publisher registration tokens and job tokens are isolated from verifier pool configuration.

### Isolation and lifecycle

- Each job receives an ephemeral workspace/container that is destroyed after success, failure,
  cancellation, or timeout.
- Dependency/build caches are read-only or namespace-separated across trust levels; verified
  artifacts cross the boundary only through the forge artifact service and same-run identity
  validation.
- Untrusted runners have the minimum network required for checkout/dependencies and cannot reach
  protected registries, release APIs, or metadata/management networks.
- Docker builds use an isolated rootless/remote builder or a documented equivalently constrained
  mechanism; mounting the unrestricted host Docker socket into fork code is prohibited.

### Error handling and observability

- Registration, job pickup, action download, artifact transfer, Buildx, cleanup, and timeout
  failures are distinguishable in runner logs.
- Logs include runner pool/label, pinned tuple, job/run ID, and cleanup outcome without
  registration tokens or job credentials.
- An orphan-cleanup procedure detects and removes stale job containers/workspaces safely.

### Test anchors

- A smoke workflow proves checkout, Python/Poetry setup, action resolution, artifact round trip,
  QEMU/Buildx, and workspace cleanup without publisher credentials.
- A negative job attempts to access publisher secret names/endpoints and must fail.
- A cache-poisoning test proves untrusted cache content cannot become authoritative protected
  publication input.
- A cancellation test proves workspace and ephemeral credentials are removed.
- Documentation defines upgrade, drain, rollback, incident response, and re-certification.

## Deliverables

- Pinned Gitea support matrix and runner configurations/templates.
- Runner smoke/negative tests and operator runbook.

## Out of Scope

- Private-CA and destination credentials (E009-S01-002).
- Production migration approval (E009-S01-003).
