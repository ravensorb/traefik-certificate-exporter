# Pin Gitea Runners, Bootstrap Trust, and Isolate Credentials

As an operator, I want a pinned Gitea runner environment with explicit trust boundaries, so the
shared workflows start reliably without exposing publication credentials.

Depends on: `E008-S01-004`.

## Acceptance Criteria

**Given** a private-CA Gitea installation, **when** a runner is provisioned, **then** runner-host
bootstrap trust is installed before runner registration, forge resolution, or action download. A
job step is never claimed to establish trust required for that same job to start.

**Given** a running job must contact a separate private-CA endpoint, **when** downstream trust is
needed, **then** the approved job-level CA import action installs only that downstream trust before
the endpoint call. Bootstrap and job trust are documented as separate controls.

**Given** forge and registry coordinates, **when** the runner selects them, **then** unknown forges
fail closed and `FORGE_REGISTRY` accepts only same-forge `host[:port]` with no userinfo, path,
query, or fragment.

**Given** untrusted verification and protected publication, **when** jobs are scheduled, **then**
they use separate pinned runner pools, ephemeral workspaces, minimal mounts/network access, and
job-local credentials (CI-AR32, CI-AR34).

## Carried from the E008 architecture gate (F18, F19)

Recorded here because the gate found them unaddressed and nothing documented a deferral —
these are E009's to close, not oversights.

**F18 — the smoke set omits the two capabilities the whole topology rests on.** Nested reusable
workflows (`uses: ./.github/workflows/verify-build.yaml` at job level, i.e. `workflow_call`), and
downloading in a *caller* job an artifact uploaded inside the *called* workflow. Everything else
in the list is secondary. Both must be in the pinned tuple and **run first** — if the pinned
`act_runner` cannot do them, E008's topology is not portable and that must be known before
E009-S01-002 starts.

**F19 — the verifier is structurally unable to receive a job-level CA bundle.** `secrets:` is a
literal prohibition in its text (ADR-0007 invariant 2), so on a private-CA Gitea *every* endpoint
it touches — forge clone, action download, PyPI for `poetry install`, and ghcr.io for the base
image — must be covered by runner-host bootstrap trust. That constraint decides how the runner
image is built. Enumerate every endpoint and assert each is covered; add a negative case where
bootstrap trust covers the forge but not the package index, which must fail at the verifier
rather than mid-publication.

**Also for the pinned tuple:** both `LiquidLogicLabs/git-action-release@v2` and
`git-action-tag-floating-version@v1` are `using: node24`, so the runner must accept node24 —
already load-bearing here, since `actions/checkout@v7` and `actions/setup-python@v7` are node24
too. And whether `git-action-release`'s platform auto-detection makes a network probe is
**unverified** (its detector ships from a private npm registry); behind a private CA that decides
whether TLS trust matters at that step.

## Definition of Done

- The supported Gitea server, act-runner, runner image, and action tuple are recorded.
- Bootstrap CA installation and rotation are operational prerequisites outside workflow jobs.
- Job-level CA action scope is limited to downstream endpoints after job startup.
- Image jobs receive only enabled registry credentials; package jobs receive only their own
  credentials; verifier/PR/local paths receive none.
- Smoke tests prove checkout/action resolution, artifacts, Poetry, QEMU/Buildx, downstream CA,
  cleanup, wrong-CA failure, and missing-scope failure without leaking values.

## Test anchors

Guard, then the violation planted to prove it fires:

- Bootstrap versus job trust: no job installs the trust its own startup required; plant a
  job-level CA step in a job whose checkout already needed that CA.
- Wrong CA: run against a bundle lacking the private CA; resolution must fail rather than fall
  back to system trust.
- Missing scope: revoke one scope from a job-local token; only that job fails, actionably.
- Credential isolation: per-job secret references derived from the parsed workflows; plant a
  registry secret in the verifier job (scope attack on the secret-free set).
- Coordinate validation: plant an unknown forge, and a validator missing the same-host check.
- No leaked values: smoke output is scanned for the literal secret values; plant an echoed token.
