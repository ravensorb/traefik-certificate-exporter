# Certify the Gitea Forge Classifier, Credential Matrix, and Runner-Trust Design (Statically)

As a maintainer, I want this repository's own forge-classification and per-job credential-
selection logic proven correct against static, fixture-driven tests, so the shared workflows
behave correctly on Gitea without this project re-certifying runtime behavior that the
independently-maintained `LiquidLogicLabs/git-action-*` reusable actions it already consumes are
responsible for.

Depends on: `E008-S01-004`.

**Rescope note (2026-10-06):** This story originally required provisioning a pinned, live Gitea
runner tuple and proving bootstrap-trust/scheduling/credential-denial behavior against it. That
requirement is dropped: cross-forge runtime mechanics (CA-trust import, Docker metadata, action
execution) are the responsibility of the vendor actions this project consumes, not this
project's to re-certify. What remains in scope — and what this story actually certifies — is
the correctness of this repo's *own* glue code: the forge classifier/coordinate-projection
function and the per-job credential-selection matrix, both fully verifiable with parsed-YAML and
fixture-driven unit tests. See `docs/adr/0015`, `0016`, `0017`, `0020`, `0022` scope notes for the
ADR-level detail, and `issues.yaml` (`BL-E009-007` through `BL-E009-021`, resolved `wontfix`) for
the specific live-Gitea items dropped.

## Business acceptance criteria

### Outcome

Maintainers get a statically-verified guarantee that this repo's forge classifier always derives
Gitea package/image coordinates from `github.server_url`/`github.repository` alone and fails
closed on an unknown forge, and that its per-job credential matrix never lets one destination's
job touch another destination's credential. Both are proven by table-driven guard-then-violation
tests, not by runtime observation of a live Gitea instance.

Spec: _bmad-output/planning-artifacts/architecture/architecture-ci-cd-pipeline-2026-08-31/ARCHITECTURE-SPINE.md#trust-boundaries-and-gitea-certification

### Non-goals

- Does not provision, register, or prove behavior against a live Gitea runner; that scope is
  dropped (see rescope note above).
- Does not introduce label divergence or forge-specific workflow files; either requires a later
  ADR under ADR-0015.
- Does not widen `AUTHORITY_SCOPES` past the recorded four-scope boundary (`contents`,
  `packages`, `id-token`, `attestations`); this story records the residual risk instead of
  expanding the grant.

## Technical acceptance criteria

### Interface contracts

- The forge classifier/coordinate-projection function accepts only `github.server_url` and
  `github.repository`, returns canonical Gitea package/image coordinates, and exposes a typed
  failure taxonomy (unknown forge, malformed registry, normalization failure, same-host/path
  mismatch) (ADR-0021).
- The per-job credential matrix record shape is: principal/login identity, secret/context name,
  minimum scopes, protected owner/environment, permitted mutations, forbidden mutations
  (ADR-0019).
- The trust-class eligibility matrix maps each runner registration (untrusted-verification pool
  vs. protected-publication pool) to a boolean eligibility per triggering scope (fork, PR, push,
  tag).
- Sibling convention: every existing `tests/ci/test_*.py` module imports shared fixtures and
  parsing helpers from `tests/ci/support.py` (`PROJECT_ROOT`, `_jobs`, `_steps`, loader
  functions) rather than re-implementing YAML parsing per module; new test modules for this
  story follow the same import. `docs/adr/` entries follow the existing `00NN-kebab-title.md`
  numbering, currently at `0022`; any new ADR this story produces continues that sequence.
(The classifier's full failure taxonomy and the credential-matrix record shape are ADR-0021 and
ADR-0019 content recorded in `docs/adr/`, which is outside the indexed planning-artifacts spec.)
Spec: _bmad-output/planning-artifacts/architecture/architecture-ci-cd-pipeline-2026-08-31/ARCHITECTURE-SPINE.md#configuration-contract

### Error and edge case handling

- Wrong CA bundle: TLS validation fails outright; there is no fallback to system trust.
- Unknown forge: fails closed before any destination or credential is selected (Trigger and
  Coordinate Guards).
- Missing scope: revoking one scope from a job-local token fails only that job, actionably.
- Overlapping or planted registration scope: rejected by the trust-class eligibility matrix even
  when the untrusted runner wins a scheduling race against the protected pool.
- Denied destination independent of trust: a valid-certificate request to a disallowed
  destination is refused by the named enforcement boundary, and that failure is distinguishable
  in evidence from a TLS/wrong-CA failure (ADR-0018).
(The trust-vs-egress separation and the overlapping-registration denial rule are ADR-0018 and
ADR-0015 content recorded in `docs/adr/`, outside the indexed spec.)
Spec: _bmad-output/planning-artifacts/architecture/architecture-ci-cd-pipeline-2026-08-31/ARCHITECTURE-SPINE.md#trigger-and-coordinate-guards

### Security considerations

- The four-scope boundary (`contents`, `packages`, `id-token`, `attestations`) is the ceiling;
  widening it is a separate, later architecture change, not an in-story fallback. This is a
  structural/documentation check (the workflows request no broader scope), not a live denial
  test (`TokenPermissionMode=restricted` live proof is out of scope; `BL-E009-012` resolved
  `wontfix`).
- Publication-capable credentials use distinct principals per destination unless an ADR-level
  trade-off accepts a named combined blast radius; verifier/PR jobs and disabled destinations
  receive no publication-capable secret.
- Cross-destination credential use is negative-tested against the parsed credential-matrix
  structure (which secret name each job references), not against a running Gitea forge
  (`BL-E009-008` resolved `wontfix`).
(The per-job credential matrix's full field set is ADR-0019 content recorded in `docs/adr/`,
outside the indexed spec.)

### Testability approach

- Guard tests live in `tests/ci/`, one module per concern, following the existing naming
  (`test_action_policy.py`, `test_gates.py`, `test_topology.py`) and importing shared

- Each Test anchor below is a guard-then-violation pair: the guard proves the control holds, and

## Acceptance Criteria

**Given** a job must contact a separate private-CA endpoint, **when** downstream trust is
needed, **then** the already-approved job-level CA import action (`LiquidLogicLabs/git-action-ca-certificate-import@v3`)
is placed after that job's checkout/setup steps and before the first call to the endpoint
requiring it, in both `dev.yaml` and `release.yaml`. This is a step-ordering check against the
parsed workflow YAML, not a live trust-chain validation.

**Given** TLS issuer trust and network-egress authorization are distinct controls, **when** the
endpoint model is documented, **then** `docs/ci/gitea-runners.md` states, for each public endpoint
derived from the workflows/local composite actions/`docker/Dockerfile` (GHCR, Alpine CDN, Docker
Hub/BuildKit/QEMU sources, forge, action source, PyPI), whether it relies on system trust or the
private interception root, and states explicitly that a CA bundle proves issuer trust only — it
is not a network-egress allowlist. Enforcing a named network boundary (firewall/proxy/DNS-level
denial) against that documented model requires live infrastructure and is out of scope
(ADR-0018; `BL-E009-010`'s endpoint-coverage portion resolved `wontfix` where it required a real
runner to exercise).

**Given** forge and registry coordinates, **when** the runner selects them, **then** unknown
forges fail closed and every coordinate is derived from `github.server_url` and
`github.repository` alone — no operator-supplied registry value participates (`FORGE_REGISTRY`
is retired; see ARCHITECTURE-SPINE.md, Configuration Contract). Table-driven tests cover the
failure taxonomy (unknown forge, malformed registry, normalization failure, same-host/path
mismatch) against synthetic context fixtures.

**Given** publication-capable jobs need isolated credentials, **when** credentials are
provisioned, **then** a per-job credential matrix records, for every job holding a
publication-capable credential: principal/login identity, secret/context name, minimum scopes,
protected owner/environment, permitted mutations, and forbidden mutations. Image publication,
forge Release creation, and Git-alias mutation use distinct principals unless an ADR-level
trade-off accepts a named combined blast radius. Verifier/PR jobs and any job with no publication
need receive no publication-capable secret. Negative tests attempt each destination's mutation
with another destination's credential (against the parsed matrix structure) and require denial; a
disabled destination's job receives no secret for that destination (ADR-0019).

**Given** the deliberate four-scope boundary (`contents`, `packages`, `id-token`, `attestations`),
**when** the workflows are inspected, **then** no job requests a broader scope than this boundary,
and the residual risk of not widening it is recorded in `docs/ci/gitea-runners.md`; widening the
boundary is a separate architecture change, not an in-story fallback. (Live proof that
`TokenPermissionMode=restricted` is enforced requires a real Gitea instance and is out of scope —
`BL-E009-012` resolved `wontfix`.)

**Given** forge and registry coordinates must be unambiguous across independent implementations,
**when** the classifier is defined, **then** one authoritative forge classifier and
coordinate-projection function accepts only `github.server_url` and `github.repository`, states
its forge-recognition rule, normalization (case, trailing slash, scheme), same-host/path rules,
canonical Gitea package and image coordinate outputs, and a named failure taxonomy distinguishing
unknown forge, malformed registry, normalization failure, and same-host/path mismatch. Every job
and the plan consume this classifier's output as the single coordinate value; none recomputes
coordinates independently. Table-driven cases cover each rejection reason and at least one
normalization edge case (ADR-0021).

**Given** the observed-at-runtime action closure cannot be produced without a live Gitea tuple,
**when** the closure is instead vetted statically, **then** the record extends beyond reference
and resolved commit to include, per action currently referenced in the workflows: publisher and
trust class, maintenance status, license compatibility, GA status, and supported major version,
checked against GitHub-published action metadata. Credential-bearing actions and any unapproved
third-party action require a full-SHA pin. Any non-GA/preview action in the closure requires its
own ADR recording the accepted risk and exit plan; absent that ADR, the check fails (ADR-0022).
Whether `git-action-release@v2`'s Gitea-path platform detection makes a network request behind a
private CA is explicitly **unverified** without a live probe and is documented as such, not
assumed either way (`BL-E009-009`/`BL-E009-021` resolved `wontfix`).

## Carried from the E008 architecture gate (F18, F19) — status under rescope

Recorded here because the gate found them unaddressed and nothing documented a deferral at the
time. Under the 2026-10-06 rescope, both are reframed as documentation/static-check items rather
than live-runner smoke tests:

**F18 — the smoke set previously omitted the capabilities the whole topology rests on.** Nested
reusable workflows (`uses: ./.github/workflows/verify-build.yaml` at job level) and
cross-workflow artifact download are documented as required topology features in
`docs/ci/gitea-runners.md`; proving they execute correctly on a real Gitea runner requires a live
instance and is out of scope (`BL-E009-010` resolved `wontfix`).

**F19 — the verifier is structurally unable to receive a job-level CA bundle.** `secrets:` is a
literal prohibition in its text (ADR-0007 invariant 2), so on a private-CA Gitea *every* endpoint
it touches must be covered by runner-host bootstrap trust instead. The endpoint set (forge, action
source, PyPI, GHCR, Alpine CDN, Docker Hub/BuildKit/QEMU sources) is derived and documented in
`docs/ci/gitea-runners.md`; a negative case proving a missing endpoint fails verification
requires a live runner and is out of scope.

**Also recorded for the (documented, not live) pinned tuple:** both
`LiquidLogicLabs/git-action-release@v2` and `git-action-tag-floating-version@v2` are
`using: node24`, so any eventual runner must accept node24 and only node24 — one JavaScript
runtime, not two.

## Definition of Done

- The forge classifier and coordinate-projection contract (accepted inputs, normalization,
  canonical outputs, failure taxonomy) is defined once, consumed by every job, and proven by
  table-driven tests (ADR-0021).
- The per-job credential matrix (principal, secret, scopes, protected owner/environment, permitted
  and forbidden mutations) is recorded and proven by cross-destination denial tests against the
  parsed matrix structure (ADR-0019).
- The statically-vetted action closure records publisher/trust class, maintenance/license/GA
  status, and supported major per action currently referenced in the workflows, with full-SHA
  pinning for credential-bearing or unapproved third-party actions and an ADR for any non-GA
  exception (ADR-0022).
- Job-level CA-import step ordering (download trust only after checkout/setup, before the
  endpoint call needing it) is correct in `dev.yaml` and `release.yaml`.
- TLS trust-store roots and network-egress enforcement are documented as separate, named
  mechanisms in `docs/ci/gitea-runners.md` (ADR-0018); live enforcement proof is out of scope.
- The deliberate four-scope boundary (`contents`, `packages`, `id-token`, `attestations`) is
  recorded with its residual risk; no job requests a broader scope.
- `docs/ci/gitea-runners.md` contains a Mermaid trust-ordering sequence diagram (as a design
  statement) and `docs/README.md` links the CI runbooks.
- All live-runner-dependent items originally in this story's scope (bootstrap-trust
  installation, scheduling-race/sentinel-job proof, `TokenPermissionMode` live denial,
  structural probes "on a real Gitea runner", observed transitive action closure, the
  release-action network probe) are explicitly out of scope and tracked as resolved (`wontfix`)
  backlog issues `BL-E009-007` through `BL-E009-013`.

## Test anchors

Guard, then the violation planted to prove it fires — all against parsed YAML/synthetic
fixtures, no live Gitea instance:

- CA-import step ordering: parse `dev.yaml`/`release.yaml`; plant a downstream-endpoint call
  before the CA-import step in a job that needs it, and require the guard to fail.
- Trust vs egress separation (documentation check): `docs/ci/gitea-runners.md` states, per
  endpoint, system-trust vs. private-interception-root reliance, and states the CA-bundle/egress
  distinction explicitly; a missing endpoint in the documented set fails the check (ADR-0018).
- Credential matrix: attempt each destination's mutation using another destination's credential
  (against the parsed matrix) and require denial; verify a disabled destination's job receives no
  secret for it (ADR-0019).
- Forge/coordinate contract: exercise the classifier's table-driven cases for each rejection
  reason (unknown forge, malformed registry, normalization failure, same-host/path mismatch) and
  at least one normalization edge case (ADR-0021).
- Action governance: plant a non-GA/preview action in the closure with no accepting ADR and
  require rejection; plant a credential-bearing action pinned to a floating tag rather than a
  full SHA and require rejection (ADR-0022).
- Credential isolation: per-job secret references derived from the parsed workflows; plant a
  registry secret in the verifier job (scope attack on the secret-free set).
- Coordinate validation: plant an unknown forge, and a validator missing the same-host check.
- No leaked values: smoke output is scanned for the literal secret values; plant an echoed token.
