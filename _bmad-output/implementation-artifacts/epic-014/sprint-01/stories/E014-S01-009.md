**What E014-S01-004 leaves in place, and this story builds on.**

- `tests/test_settings_surface.py` holds `_scan_pathspecs()`, the dotted extraction regex, the confuse mapping restatement, the valid-name set derived from `config_default.yaml` plus the `src` env-name literals, and the placeholder rule (a match ending in `_` is a placeholder prefix, valid when it prefixes a valid name).

**What is still missing.** An operator who copied a 0.2.x sample still has the old name in their compose file or config file. Nothing tells them: the setting is silently off. And the history of the docs shows which names operators may have copied, but nothing ties that history to a table in the package.

**Recorded decisions (moved from E014-S01-004).**

- **The legacy-name policy gets no ADR (explicit decision, C-16b).** The policy is: warn at start-up, ignore the legacy name, no aliases. It is local to settings loading and reversible, and it changes no stored data and no interface contract. It is recorded in product-spine AD-6 (the 2026-10-11 consolidated AD-6 already states it; S02-003 verifies it and routes only deltas from this story's notes file), and stated to operators in `docs/upgrading.md` (E014-S02-005). Revisit if aliases are ever wanted, because aliases would be a compatibility contract and would need an ADR.
- **Shared difflib helper (C-04).** This story creates `libs/suggest.py` with `nearest_name(candidate, options) -> str | None`, a thin wrapper over `difflib.get_close_matches(candidate, options, n=1, cutoff=0.6)`, the same parameters E014-S01-008 specifies for flag typos. S01-008 lands after this story and must call `nearest_name` for its `Did you mean` line instead of calling `difflib` directly, so env-name and flag-name suggestions behave identically.

**Maintainer decisions 2026-10-11**

- "If possible we should detect any 'old' settings and warn with recommendations." Decision: at start-up the exporter detects legacy or misspelled setting names in the environment and the config file, and emits one actionable WARNING per name (old name → new name, and where it was found), never echoing the value.
- The legacy → replacement map is one data table in the package, derived from the names the docs and samples historically used (table above), and a test fails if a documented legacy name is missing from it.
- Unknown `TRAEFIK_CERTIFICATE_EXPORTER_*` env vars that match no setting and no legacy entry get one WARNING suggesting the nearest valid name (`difflib`), consistent with S01-008's flag suggestions.

## Acceptance Criteria

- **The single legacy table.** `src/traefik_certificate_exporter/libs/legacy_settings.py` holds `LEGACY_SETTING_NAMES`, the single legacy → replacement table (the Context table). No other module contains a legacy name as a literal; detection code reads only this table. The module carries the marker comment `tce-settings-scan: legacy-names-listed`.
- **Legacy and misspelled setting names are detected at start-up (maintainer decision 2026-10-11).**
  - Detection runs once per process, after logging is configured and after the config file is located, before the first export pass. It inspects:
    - **env:** every `os.environ` name starting with `TRAEFIK_CERTIFICATE_EXPORTER_`;
    - **config:** the dotted key paths of the loaded config file's raw YAML (`yaml.safe_load`), when a config file is in use;
    - CLI flags are not inspected: no flag has ever been renamed, so the table has no CLI rows and its `source` field takes only `env` and `config` (FR-16, product AD-6); unknown flags are already rejected by the strict parse (ADR-0025) with S01-008's suggestion.
  - Each legacy name present gives exactly one WARNING naming the old name, the source (`environment` or `config file <path>`) and the replacement, and stating that the old name is ignored. Entries with no replacement (`…_CONFIG_FILE`, `…_CONFIGFILE`) state the fix in words. The value is never logged.
  - A `TRAEFIK_CERTIFICATE_EXPORTER_*` env name that is not a valid name (confuse-mapped `config_default.yaml` path, or a `src` env-name literal) and not a legacy entry gives exactly one WARNING: `Unknown setting <name> in environment; did you mean <nearest>?`, with `<nearest>` from `suggest.nearest_name` over the valid env names. With no close match it says the name matches no setting and points to the README `## Usage` section.
  - Tests in `tests/libs/test_legacy_settings.py`:
    - `test_each_legacy_env_name_warns_once_with_replacement`, parametrized from `LEGACY_SETTING_NAMES` itself;
    - `test_legacy_config_key_warns_once_with_replacement` (`settings.restartcontainer`);
    - `test_unknown_env_name_suggests_nearest` (`…_SETTINGS_OUTPUTPAHT` → `…_SETTINGS_OUTPUTPATH`);
    - `test_unknown_env_name_without_close_match_points_to_usage` (`…_FOO`);
    - `test_settings_load_warns_about_legacy_env_name_and_config_key`, through `SettingsManager` loading, which FAILS on the current code (no warning is emitted).
- **Values are never logged.** `tests/libs/test_legacy_settings.py::test_legacy_and_unknown_values_are_never_logged` plants a secret-looking value under a legacy name and under an unknown name and asserts it appears in no log record.
- **Map-coverage test (global rule 4):** `tests/test_settings_surface.py::test_legacy_map_covers_documented_names` runs `git log -p HEAD -- <_scan_pathspecs()>`: the history reachable from the commit under test, so local branches, stashes and other refs cannot make `just check` and `build.yaml` disagree. Because it uses pathspecs rather than today's file list, files deleted since are covered too. It extracts every name with the dotted regex, removes valid names and valid placeholder prefixes (E014-S01-004's rule), and asserts each remainder is matched by a `LEGACY_SETTING_NAMES` entry (exact or prefix). It fails, not skips, on a shallow clone (`git rev-parse --is-shallow-repository`), because CI already checks out with `fetch-depth: 0` (`build.yaml:36`) and a skip would be a false green. Probes, recorded in the notes file:
  - deleting any one env row from the table makes it fail;
  - deleting the dotted `…_SETTINGS.RESTARTCONTAINER` row makes it fail, which proves the dotted extraction works;
  - running it in a `--depth 1` clone fails with the shallow-clone message.
  - **Coverage limit, stated in the test docstring (global rule 3):** history is immutable, so a committed invalid name that is neither valid nor in the table makes `main` red until a table row is added. That is the intended pressure: the remedy is a table row (the name was documented, so operators may use it), never a scope exclusion.
- **No legacy name is valid.** `tests/test_settings_surface.py::test_no_legacy_name_is_valid` asserts that no `LEGACY_SETTING_NAMES` name is in the valid set E014-S01-004's check derives.
- **Files that list legacy names by design are found by a derived rule, not a path list (maintainer decision 2).** E014-S01-004's `test_documented_env_names_map_to_settings` is extended:
  - a file opts in by containing the marker token `tce-settings-scan: legacy-names-listed` in a comment (`<!-- … -->` in Markdown, `#` in YAML and Python);
  - in a marked file, a name matching a `LEGACY_SETTING_NAMES` entry is permitted; every other name must still be valid or a valid placeholder, so a typo in a marked file still fails (`tests/test_settings_surface.py::test_marked_file_permits_only_legacy_names`);
  - the `src` literal scan skips marked `.py` files, which is how `libs/legacy_settings.py` (marked) stays out of the valid set without being named in the test;
  - the intended marked files are `libs/legacy_settings.py` (this story) and `docs/upgrading.md` (E014-S02-005), plus any later file that must quote legacy names.
- **The marker cannot become a silent opt-out.** `tests/test_settings_surface.py::test_stale_marker_fails` asserts that every marked file contains at least one `LEGACY_SETTING_NAMES` name, so a stale marker fails `just check`.
  - **Rule attacks, recorded in the notes file and then removed:**
    - a legacy name planted in an unmarked new file fails;
    - the same legacy name in a new file carrying the marker passes;
    - a new file carrying the marker but no legacy name fails.
- **The env-name mapping is checked against confuse itself (A-11).** `tests/test_settings_surface.py::test_valid_env_names_match_confuse_envsource` feeds each name from `valid_env_names()` through `confuse.EnvSource(prefix, sep="_")` (via a temporary environment) and asserts that it lands on the same key path the derived rule computed. If confuse's mapping rule ever changes, this test fails rather than the two diverging silently.
- `just check` passes.
- **Spine/ADR routing (maintainer decision 7).** The dev writes `_bmad-output/implementation-artifacts/epic-014/sprint-01/closure/notes-E014-S01-009.md` with a section `## Spine/ADR amendments for S02-003`. It gives the exact text for:
  - product spine AD-6 (verify, route only deltas): legacy and unknown names are warned about at start-up and ignored, with no aliases; `LEGACY_SETTING_NAMES` is the single table; the `tce-settings-scan: legacy-names-listed` marker rule; the history-derived coverage test; the explicit no-ADR decision (C-16b).

  The same section carries a **"Contract for writers"** paragraph for E014-S01-005, E014-S02-003 and E014-S02-005: placeholders end in `_` (`…_SETTINGS_<KEY>`, E014-S01-004's rule); a file that lists legacy names must carry the marker (`docs/upgrading.md` does) and must contain at least one; a grep pattern that is a bare prefix passes as a placeholder; any name ever committed in scope that is neither valid nor a placeholder needs a `LEGACY_SETTING_NAMES` row.

## Business acceptance criteria

### Outcome

- An operator still using an old or misspelled name (for example `TRAEFIK_CERTIFICATE_EXPORTER_RESTART_CONTAINERS` from the old compose sample) sees a start-up WARNING telling them the exact name to use instead, rather than a setting that is silently off.
- An operator with a typo in a `TRAEFIK_CERTIFICATE_EXPORTER_*` variable is told the nearest valid name.
- A name that was ever documented cannot be dropped from the legacy table without `just check` failing.

#### 0.3.0 release notes

E014-S02-005 generates `docs/upgrading.md` from this list. Every bullet is a user-visible change.

- "The exporter warns at start-up about legacy or misspelled setting names (environment and config file), names the replacement, and ignores the old name. Values are never logged."
- "Unknown `TRAEFIK_CERTIFICATE_EXPORTER_*` environment variables get one WARNING with the nearest valid name."

Spec: none — l3io-plan run, no spec index bound

### Non-goals

- No support for the dead names as deprecated aliases. They never worked, so no one depends on them. Detection only warns; a legacy name still has no effect.
- No nearest-name suggestion for unknown config-file keys that are not in the legacy table. The maintainer asked for suggestions on unknown env vars; config files get the legacy-table check only. Recorded as an assumption; revisit if operators report silent config-key typos.
- No CLI-flag legacy rows (no flag was ever renamed); flag typos are E014-S01-008's.
- Does not change the documented names, the dest fix, the key registry or `LOGGING_LEVEL` (E014-S01-004).
- Does not change precedence (CLI > env > file > default).

## Technical acceptance criteria

### Interface contracts

- `libs/legacy_settings.py` (new):
  - `LegacyName`, a frozen dataclass: `source: Literal["env", "config"]`, `name: str` (a trailing `*` means prefix match), `replacement: str | None`, `hint: str` (the fix in words, used when `replacement` is `None`).
  - `LEGACY_SETTING_NAMES: tuple[LegacyName, ...]`, the single table. The module carries the `tce-settings-scan: legacy-names-listed` marker comment.
  - `valid_env_names() -> frozenset[str]`: derived from `config_default.yaml` leaves and lists via the confuse rule, plus the `src` env-name literals (`LOGGING_*`, `EXPORTED_DOMAINS`, `CORRELATION_ID`). At runtime the literal set is the module constants that hold those names, not a source scan. The test-side source scan skips marked files (see the marker AC), so `legacy_settings.py` never contributes.
  - `find_legacy_settings(environ: Mapping[str, str], config_tree: Mapping | None) -> list[Finding]`, pure, returning one finding per name (legacy or unknown), with no values in it.
  - `warn_legacy_settings(findings, logger) -> None`, which formats and emits the WARNINGs.
- `libs/suggest.py` (new): `nearest_name(candidate: str, options: Iterable[str]) -> str | None`, wrapping `difflib.get_close_matches(..., n=1, cutoff=0.6)`. Shared with E014-S01-008.
- `settings.py`: calls `find_legacy_settings` / `warn_legacy_settings` once when settings are loaded.
- `tests/test_settings_surface.py`: reuses E014-S01-004's `_scan_pathspecs()`, extraction regex, mapping and valid-set helpers, and placeholder rule; adds the marker handling and the history test. No second pathspec list.
- **Sibling conventions:** tests for `libs/x.py` live in `tests/libs/test_x.py`; cross-cutting repository checks stay in `tests/test_settings_surface.py` with its `PROJECT_ROOT` idiom.
- **Scan contract extension** (also copied into the notes file): the marker token `tce-settings-scan: legacy-names-listed` permits `LEGACY_SETTING_NAMES` names in that file only, and a marked file must contain at least one.

Spec: none — l3io-plan run, no spec index bound

### Error and edge case handling

- **Legacy and new name both set** (`…_RESTART_CONTAINERS` and `…_SETTINGS_RESTARTCONTAINERS`): one WARNING for the legacy name, which is ignored; the new name takes effect as usual. Test `test_legacy_and_new_name_both_set_warns_only_for_legacy`.
- **Prefix legacy entry** (`…_NOTIFY_*`): several matching vars (`…_NOTIFY_0`, `…_NOTIFY_1`) give one WARNING per variable name, each pointing to `…_SETTINGS_APPRISEURLS_<n>`. Test `test_prefix_legacy_entry_warns_once_per_variable`.
- **Indexed valid name** (`…_SETTINGS_APPRISEURLS_3`): valid after dropping the index; no warning. Test `test_indexed_valid_name_is_not_warned`.
- **Unknown name with no close match** (`…_FOO`): one WARNING saying it matches no setting, with the README `## Usage` pointer, and no suggestion.
- **Config file absent or unreadable:** config detection is skipped; the existing config-load error handling is unchanged.
- **Same name in env and config** (not possible today; names differ per source): each source is reported separately.
- Detection never raises: a failure inside it is logged once at WARNING and start-up continues, because it is advisory. Test `test_detection_failure_is_logged_once_and_startup_continues`.

Spec: none — l3io-plan run, no spec index bound

### Observability requirements

- Legacy-name WARNINGs: one per legacy name found, e.g. `Legacy setting TRAEFIK_CERTIFICATE_EXPORTER_RESTART_CONTAINERS in environment is ignored; use TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_RESTARTCONTAINERS` and `Legacy key settings.restartcontainer in config file /config/config.yaml is ignored; use settings.restartcontainers`.
- Unknown-env WARNINGs: one per unknown name, with the nearest valid name when there is one.
- All of these run under the start-up `correlation_id`, before the first pass. Nothing is logged when no legacy or unknown name is present (test `test_no_findings_logs_nothing`).

### Security considerations

- Legacy and unknown-name WARNINGs carry the name only, never the value: legacy names such as `…_NOTIFY_*` held Apprise URLs with embedded tokens. The never-echo test plants a secret-looking value under a legacy name and an unknown name and asserts it appears in no log record.
- Names are passed through `_sanitize_for_log` (an env name is attacker-influenced in shared environments).
- The raw config tree is read with `yaml.safe_load` only; no object construction from YAML tags.
