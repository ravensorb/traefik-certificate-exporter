# CA-agnostic, null-safe ACME store parsing with per-resolver isolation

## Context

Promoted from deferred finding(s):
- BL-E011-018 (Low, redteam (RT-014)) — See _bmad-output/implementation-artifacts/epic-011/sprint-01/closure/redteam-report.md

**Review findings:** `review-product.md`, findings M3 and M4 (the per-resolver and per-file half). Also the FR-1 row ("Partial") and the "Convention: ACME v1 + v2" row ("Partially conforms").
**Research:** `research-2026-10-10-release-0.3.0.md` §3 "Traefik ACME store format (M3, M4)", covering Facts, "Defects confirmed against the parser", "Recommended parsing" and "Minimal tests".
**Red team:** RT-014 (`epic-011/sprint-01/closure/redteam-report.md:189-190`). The recommendation is an `st_size` guard, `b64decode(..., validate=True)`, and an explicit "no resolver node" branch. Per the maintainer decision below, this story takes the strict base64 and the "no resolver node" branch and does **not** take the `st_size` guard.

**The store format, verified upstream (research §3)**

- The file is `map[resolverName]*StoredData{Account *Account; Certificates []*CertAndStore}`, with no JSON tags.
- Any nil slice or pointer encodes as `null`. So `"Certificates": null`, `"Account": null` and `"Registration": null` are all valid stores (Go encoding probe).
- `Registration.uri` is the account URL **at the CA**. It identifies the CA, not the protocol version; every current CA speaks RFC 8555.
- The v1.7 form is one unkeyed `StoredData`. Legacy ACME-v1 carries `DomainsCertificate.Certs`.

**Defects in `src/traefik_certificate_exporter/libs/certificate_exporter.py`**

- **`:335`** `"acme-v02" in data["Account"]["Registration"]["uri"]`:
  - a ZeroSSL, Google or step-ca store is treated as v1, giving `KeyError 'DomainsCertificate'`, and nothing is exported;
  - `Account: null` or `Registration: null` gives `TypeError`.
- **`:352-358`** `for c in data["Certificates"]` runs outside the per-certificate `try`. With `null`, it raises into `exportCertificatesForFile`'s `except` (`:584-586`), which returns `None`. Domains already written by earlier resolvers then go unreported (M4).
- **`:560-564`** Auto-detect inspects only `elementNames[0]`:
  - `{}` gives `IndexError`;
  - a first key that is not a resolver misclassifies the whole file;
  - the lower/upper key choice is tied to whether a resolver id was configured (`:545-566`), not to the keys actually present.
- **`:420-421`** `b64decode` runs without `validate=True`, so a corrupt value silently decodes to garbage or to empty bytes (RT-014). The uncapped `json.loads(Path(sourceFile).read_text())` at `:542` stays uncapped by decision (see Non-goals).

## Acceptance Criteria

- The deferred finding BL-E011-018 (ACME file ingestion is unbounded and unvalidated: no size cap, b64decode without validate) is resolved by strict base64 decoding plus the recorded no-cap rationale:
  - No size cap is added. The reason (trusted Traefik output; a `/data` writer can already do worse; `/data:ro` is unenforced defence in depth) is written in this story's Non-goals and in the ADR amendment, and BL-E011-018 is closed with a pointer to it.
  - Every base64 field is decoded with `b64decode(value, validate=True)`. An invalid value is a per-certificate error: one ERROR naming the domain and the field, no files written for it, and the other certificates still exported.
  - The test uses `"key": "!!!not-base64"`. On the current code it FAILS, because an empty `privkey.pem` is written.
- **CA-agnostic detection.** The store shape is detected by the keys present, never by `Registration.uri`:
  - a resolver node is a `dict` with a `Certificates` or `Account` key, in either case;
  - a v1.7 single store is a top-level dict that is itself a resolver node;
  - legacy certificates come from `DomainsCertificate.Certs`, at node level or under `Account`.
  - Fixture (a), a v3 store with `uri: "https://acme.zerossl.com/v2/DV90/account/x"`, exports its domain. It FAILS on the current code.
- **Null-safety.** Each of these exports what is present and raises nothing:
  - `"Certificates": null` → `[]` for that resolver;
  - `"Account": null`;
  - `"Registration": null`;
  - a missing `uri`.

  Fixture (c), with `"Account": null`, exports. It FAILS on the current code.
- **Per-resolver isolation.**
  - Each resolver is processed inside its own `try`. A failure logs one ERROR with the sanitized resolver name and moves on.
  - Fixture (b) has two resolvers, the first valid and the second with `"Certificates": null` or a structurally broken entry. It returns the first resolver's domains, and the returned list is not `None`. It FAILS on the current code.
- **Empty and non-resolver input.**
  - `{}` returns `[]` with one WARNING "no resolver node found". Fixture (d) FAILS on the current code (`None`).
  - A top-level key whose value is not a resolver node (`"foo": 1`) is skipped with a WARNING, and the other resolvers are processed.
- **Key case per entry.** Each certificate entry reads `domain.main`/`Domain.Main`, `key`/`Key` and `certificate`/`Certificate` according to which keys that entry has. A store mixing both cases exports both.
- **Return type.** `exportCertificatesForFile` returns `list[str]`, never `None`:
  - file-level failures (missing, empty, invalid JSON, `RecursionError`) return `[]` with an ERROR;
  - after the resolvers, one WARNING `N of M resolvers failed in <file>` is emitted when N > 0.
- `traefikresolverid` scoping is unchanged: a named resolver that is absent gives a WARNING and `[]`. When a resolver id is set, only that node is processed, with the same shape detection.
- **The changed signal passes through per resolver (maintainer decision 2026-10-11).** `exportCertificatesForFile` returns the de-duplicated union of each resolver's changed domains, as E014-S01-002's `__exportCertificate` reports them. Tests:
  - a two-resolver store exported twice: the second call returns `[]`;
  - one certificate changed in the second resolver only: the call returns only that resolver's changed domain;
  - the first resolver changed and the second broken: the call returns the first resolver's changed domains (isolation and signal together).
- The ADR amendment is written (see Context), including the no-size-cap rationale. `just check` passes.
- **Spine/ADR routing (maintainer decision 7).** The dev writes `_bmad-output/implementation-artifacts/epic-014/sprint-01/closure/notes-E014-S01-003.md` with a section `## Spine/ADR amendments for S02-003`. It gives the exact replacement text for:
  - product spine AD-7 (verify, route only deltas): shape-based, CA-agnostic detection; null-safe; per-resolver isolation; strict base64; no size cap;
  - product spine AD-7: cite ADR-NNNN (as extended);
  - the SANs decision (PRD #22): SANs are logged, not exported, as decided by deletion in E006. The consolidated product spine already records it (Conventions "Data & formats — artifacts" and Deferred "SANs export"); verify only;
  - the no-size-cap rationale: already in AD-7 and PRD §5; verify only, and route a delta only if the merged code differs.

## Business acceptance criteria

### Outcome

- An operator whose Traefik uses ZeroSSL, Google Trust Services, step-ca or any RFC 8555 CA gets certificates exported. Before this, nothing was exported and the log showed a `KeyError`.
- An operator with several resolvers, one of them empty or broken, still gets restarts, hooks and notifications for the healthy resolvers' domains.
- A corrupt store file is reported clearly: invalid JSON fails the file, invalid base64 fails only the affected certificate.

#### 0.3.0 release notes

E014-S02-005 generates `docs/upgrading.md` from this list. Every bullet is a user-visible change.

- "Non-Let's-Encrypt ACME CAs (ZeroSSL, Google Trust Services, step-ca, any RFC 8555 CA) are supported. The store shape is detected from its keys, not from the CA URL."
- "Stores with empty resolvers (`\"Certificates\": null`, `\"Account\": null`) no longer abort the file."
- "Invalid base64 in the store is reported per certificate instead of producing empty files."
- "One resolver's failure no longer drops the other resolvers' domains from the restart, the post-export hook (`TRAEFIK_CERTIFICATE_EXPORTER_EXPORTED_DOMAINS`) and notifications."
- "There is no size limit on `acme.json`. It is trusted Traefik output."

Spec: none — l3io-plan run, no spec index bound

### Non-goals

- Does not model `CertAndStore.Store` values other than `"default"`; they are ignored, as today (research §3 Risks).
- Does not add an ACME store size cap, configurable or fixed (maintainer decision 2026-10-11). `acme.json` is trusted Traefik output, and anyone able to write `/data` can already do worse than supply an oversized file (for example, replace the certificates being exported). A cap would guard a boundary the deployment already controls. RT-014's `st_size` recommendation is declined on that basis. Mounting `/data` `:ro` is defence in depth only: it is documented, not enforced, and the stock deployment runs as root under ADR-0030 as amended, where `:ro` is not required.
- Does not change PKCS12/PEM production (E014-S01-002).
- Does not change the watch/debounce pipeline or the pass sequence (export → hook → notify → restart).
- Does not extract the parser into its own module. That is the M7 layering work, which is not in this sprint.
- Does not use `sans` beyond the existing log line. PRD #22 (SANs export) was decided by deletion in E006 without a record (review-coherence §2): SANs are logged, not exported. This story keeps that and routes the record to S02-003 through the notes file.
- Does not change the change test (E014-S01-002), the restart policy (E014-S01-006) or the hook and notification policy (E014-S01-010).

## Technical acceptance criteria

### Interface contracts

- `AcmeCertificateExporter.exportCertificatesForFile(self, sourceFile: str) -> list[str]`. The annotation changes from `list[str] | None`. Callers (`exportCertificates`, `AcmeCertificateFileHandler.__processPath` at `:1045`, `app.py:141`) keep their `or []`. `exportCertificates` keeps its de-duplication.
- New module-level helpers in `certificate_exporter.py`. They are pure, take no settings, and follow the `_snake_case` sibling style:
  - `_iter_resolver_nodes(data: dict) -> Iterator[tuple[str | None, dict]]`. The yielded name is the resolver key for a resolver-wrapped store and `None` for an unwrapped one (v1.7 single `StoredData`, unwrapped uppercase v2), after `traefikresolverid` scoping; E014-S01-006 passes it unchanged to `_artifact_paths` (ADR-0040), so it is never replaced by a synthetic or empty name;
  - `_is_resolver_node(node: object) -> bool`;
  - `_ci_get(node: dict, key: str) -> object` (case-insensitive key lookup);
  - `_certificate_entries(node: dict) -> list[dict]`;
  - `_read_store(path: str) -> dict`, which reads and parses the whole file (no size limit) and raises `ValueError` on empty or invalid JSON.
- `__exportCertificate` drops its `keys` parameter. The case is chosen per entry.

Spec: none — l3io-plan run, no spec index bound

### Error and edge case handling

| Input | Result |
|---|---|
| Missing file, or 0 bytes | `[]` + ERROR (as today) |
| Invalid JSON, or nesting deep enough to raise `RecursionError` | `[]` + ERROR |
| Top level not a dict (e.g. a JSON list) | `[]` + WARNING "no resolver node found" |
| Resolver name fails `_is_safe_path_component` with `resolverinpathname` on | that resolver is skipped with an ERROR (as today); the others continue |
| Certificate entry missing domain/key/cert | WARNING per entry (as today) |
| Entry not a dict | WARNING; skipped |
| `Certificate` nested object (legacy v1: `Certificate.Certificate`/`PrivateKey`/`Domain`) | supported, as today |
| Non-UTF-8 bytes after base64 decode | per-certificate ERROR |

Spec: none — l3io-plan run, no spec index bound

### Observability requirements

- **Per resolver:** INFO `Resolver <name>: <n> certificate entries`. DEBUG gives the CA account URI, read null-safe and passed through `_sanitize_for_log`. It is informational only.
- **Per resolver failure:** one ERROR with the sanitized resolver name and the exception class and message.
- **Per file:** one WARNING `N of M resolvers failed in <file>` when N > 0. ERROR for file-level rejects.
- Every line runs inside the caller's `correlation_id` context: the drain or start-up pass id, as today.

Spec: none — l3io-plan run, no spec index bound

### Security considerations

- The store's contents are validated defensively (`certificate_exporter.py:267-271`): shape checks, strict base64, path-component checks. Its size is not limited: the file is Traefik's own output, and RT-014's memory-exhaustion path requires write access to `/data`, which already grants worse outcomes (see Non-goals). A `:ro` mount is defence in depth, documented but not enforced.
- `validate=True` rejects smuggled non-alphabet bytes.
- Accepting more shapes widens what is parsed (research §3 Risks). The `_is_safe_path_component` checks on resolver and domain names must remain before any path join. A test plants `"../escape"` as a resolver key in an otherwise CA-agnostic store and asserts nothing is written outside `outputPath`.
- CA URIs and resolver names are sanitized before logging (log injection).

Spec: none — l3io-plan run, no spec index bound

### Existing-library check

- `json` (stdlib) and `base64.b64decode(validate=True)` (stdlib) cover parsing and decoding.
- No maintained Python library models Traefik's `acme.json` (`StoredData` is internal to Traefik's Go code; research §3 sources). A JSON-Schema validator (`jsonschema`) was considered. It would add a dependency to validate a shape that is defined by Go struct encoding rather than published as a schema, and the shape logic needed is small: about 30 lines of key lookups. Per-field `dict.get` navigation is warranted here, and no parser is being written.
