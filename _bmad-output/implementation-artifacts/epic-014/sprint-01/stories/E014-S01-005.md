# Container lifecycle: run-once vs watch under s6

## Context

**Review finding:** M5 (MAJOR) in `review-product.md`, plus the FR-6 row ("Yes for PyPI; not in container") and the ADR-0030 row ("One inconsistency with the ADR's own principle, M5"). The same review lists, under Recommended ADRs, #4: "Container run-once / `watchforchanges` source of truth in the s6 service".
**Research:** `research-2026-10-10-release-0.3.0.md` §4, "s6-overlay and the container service (M5)". The parts used are Facts (the s6-overlay 3.2.1.0 probe), "Current behaviour", "Recommended fix" and "Minimal test".

### Current behaviour

`docker/root/etc/s6-overlay/s6-rc.d/svc-traefik-certificate-exporter/run:14` tests the **raw env var** `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_WATCHFORCHANGES` against `true`/`1`. Anything else prints "Skipping start of application..." and exits 0. This breaks ADR-0030's principle, "ask the installed package, never a second parser", and the init script states that principle at `init-traefik-certificate-exporter-config/run:12-16`.

Facts from the local probe on the pinned base image (research §4):

- The image carries s6-overlay 3.2.1.0.
- A longrun whose `run` exits, with no `finish`, is respawned **every second** (20 times in 20 s).
- A `finish` that exits 125 is not restarted.
- A `finish` can end the container by writing `/run/s6-linux-init-container-results/exitcode` and running `/run/s6/basedir/bin/halt` (s6-overlay README@v3.2.1.0).

What that does to each configuration:

- Env `false`, or `yes`/`True` (which confuse accepts but the shell test does not), gives a 1 Hz "Skipping" loop.
- If the test did pass in run-once mode, the exporter would run one pass, exit, and be re-run every second. Exports, hooks and notifications would all repeat.
- `docker/README.md:43-47` documents a `WATCHFORCHANGES=false` smoke path that in fact produces this loop.

### App-level gap found while elaborating

`app._run` (`app.py:134,165`) does nothing at all when both `runAtStart` and `watchForChanges` are false: there is no pass and no message. In the image, `RUNATSTART=true` (`docker/Dockerfile:129`), so run-once works there by default. An operator who also sets `RUNATSTART=false` would get a silent no-op.

### Decision (research §4 "Recommended fix", recommended choice)

- **Run-once ends the container with the pass's exit code.** The alternative, `exit 125` (stay up idle), was rejected as the default because it hides the run-once result.
- **The resolved mode is written to its own state file**, `/run/traefik-certificate-exporter/watch-for-changes`. It is not appended to `resolved-settings`, because that file has a positional layout: `privilege-decision.sh` and `tests/test_s6_privilege_drop.py` read lines 1–4 followed by a variable-length list of matches (`test_resolver_writes_exactly_four_lines_when_nothing_matches`).

### Recorded decisions this story changes

- **New ADR-NNNN (reserved at dev time):** "Container run-once contract and run-mode source of truth". It covers the init-resolved mode, the `finish`/`halt` behaviour, the `restart: "no"` guidance and the missing-state default.
- **ADR-0030** (`docs/adr/0030-conditional-privilege-drop.md`) gets an "Amended by ADR-NNNN" marker: the init resolver now emits a second answer, which the service script consumes the same way it consumes the privilege state.

### Exit code: the "usable from cron" claim (decided here, F-07)

- **Decision:** the claim is qualified, not delivered. The run-once container exits with the pass's exit code, and that code reflects **start-up failures only** (0, or 1 for a missing data path). Export failures are logged at ERROR and do not change the exit code. Making them non-zero needs a failure contract across E014-S01-002/003 (which failures count, and whether a partial export is a failure). That contract is PRD §6 #23, and it is not in E014.
- So the image *can* be scheduled from cron, a systemd timer or a Kubernetes Job, but a scheduler cannot detect a failed export from the exit code. The docs and the release note say exactly that.
- The dev files PRD #23 as a backlog item with `pm-status append-issue` (Low, "run-once exit code does not reflect export failures (PRD §6 #23)") and records the key in the notes file.

## Acceptance Criteria

1. **The init resolver emits the mode.** The Python heredoc in `init-traefik-certificate-exporter-config/run` writes `true` or `false` to `${STATE_DIR}/watch-for-changes`. It does so atomically (temp file + `os.replace`, as `resolved-settings` already is), using `settings.watchForChanges` from the same `SettingsManager`.
   - Init removes any stale copy before resolving, as it already does for `resolved-settings` at `:43`.
   - Test: for env `false`, `no` or `False`, or for config-file `watchforchanges: false` with the env unset, the file reads `false`. For `yes` or `1` it reads `true`.
2. **The service always execs the exporter.** `svc-traefik-certificate-exporter/run`:
   - reads the mode file and has no reference to `TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_`;
   - always `exec`s `traefik-certificate-exporter -c /config/config.yaml` through the existing privilege branch (the `s6-setuidgid abc` vs `root` selection, unchanged);
   - echoes `Starting application (watch mode)` or `Starting application (run-once mode)`.

   Test: with mode `false` and the env var unset, a stub exporter on `PATH` is invoked exactly once. This FAILS on the current script, which prints "Skipping".
3. **A new `svc-traefik-certificate-exporter/finish`** (mode 100755, bash, as its siblings are) uses `set -uo pipefail` and deliberately **not** `set -e`: it must never abort before writing the exit code, so each write and the `halt` lookup is checked explicitly. It behaves as follows:
   - Mode `true`, or the mode file missing or unreadable: exit 0. s6 respawns the service, which is today's watch behaviour after a crash.
   - Mode `false`: compute the exit code (`$1`, or `128 + $2` when `$1` is 256), write it to `/run/s6-linux-init-container-results/exitcode`, and `exec /run/s6/basedir/bin/halt`.
   - Tests run the script with substituted paths and a stub `halt`, checking each case: `false` + exit 3 writes `3` and calls halt; `false` + 256/15 writes `143`; `true` does not call halt; a missing file does not call halt.
   - These tests FAIL on the current tree, where no `finish` exists.
4. **Missing mode state means watch.** If `watch-for-changes` is absent (the init resolver failed), `run` uses watch mode and echoes `WARNING: run mode unresolved; defaulting to watch mode`. This matches the long-standing image default (`WATCHFORCHANGES=true`).
5. **The app warns when there is nothing to do.** When both `runAtStart` and `watchForChanges` are false, `app._run` logs one WARNING, `neither runatstart nor watchforchanges is set; nothing to do`, and returns normally (exit 0). Test in `tests/test_app.py`; it FAILS on the current code, which logs nothing.
6. **A guard against a second parser.** A `pygrep` hook, `s6-no-raw-settings-env`, in `.pre-commit-config.yaml`'s `repo: local` block, with:
   - `entry: 'TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_'`
   - `files: ^docker/root/`

   The scope is everything the image ships under `docker/root/`, not only `etc/s6-overlay/`, so it also covers the sourced privilege helper `docker/root/usr/local/lib/traefik-certificate-exporter/privilege-decision.sh`. It fails on any shipped script that reads a settings env var directly.
   - Scope attacks, recorded in the notes file and then removed. Each must fail the hook:
     - the string planted in a **new** service directory, `s6-rc.d/svc-probe/run`;
     - the string planted **outside** `etc/s6-overlay/`, in `docker/root/usr/local/lib/traefik-certificate-exporter/probe.sh`.
   - Run against the current tree, the hook FAILS on `svc-…/run:14`.
   - The `entry:` string passes E014-S01-004's env-name scan and E014-S01-009's history scan as a placeholder prefix (see Sequencing). The notes file records that `just check` is green with the hook present.

## Business acceptance criteria

### Outcome

- An operator can run the image as a one-shot job (`-e TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_WATCHFORCHANGES=false`, or `watchforchanges: false` in `/config/config.yaml`). The image runs one export pass and then exits with that pass's exit code. It can be scheduled from cron, a systemd timer or a Kubernetes Job. The exit code reflects start-up failures only: export failures are logged, not signalled (see "Exit code" in Context).
- No container configuration produces a 1 Hz restart loop, or repeated hooks and notifications.

#### 0.3.0 release notes

E014-S02-005 generates `docs/upgrading.md` from this list. Every bullet is a user-visible change.

- "The container honours `watchforchanges: false` from any source: config file, env, or any YAML truthy spelling. It runs one pass and then **the container exits**."
- "Run-once containers must use `restart: \"no\"` (or be started by cron, a systemd timer or a Kubernetes Job). With `restart: always` or `unless-stopped`, Docker restarts the exited container, which turns run-once into a loop."
- "The run-once exit code is 0 on success and 1 when the data path is missing. Export failures are logged at ERROR and do **not** change the exit code, so a scheduler cannot detect them from the exit code."
- "The 0.2.x 'Skipping start of application' respawn loop is gone."
- "When both `runatstart` and `watchforchanges` are false, the exporter logs one WARNING that it has nothing to do, instead of doing nothing silently."

### Non-goals

- No change to the privilege decision or its state file (ADR-0030 rows 1–7 unchanged).
- No `HEALTHCHECK` or liveness signal (review m10).
- Does not make export failures produce a non-zero exit code. The pass's existing exit semantics are kept (0, or 1 for a missing data path). The outcome and the release note state this limit, and PRD #23 is filed as a backlog item (see "Exit code" in Context).
- Does not use the `exit 125` stay-up-idle mode.
- Does not change PyPI CLI semantics. Watch false plus run-at-start false is still a no-op there, but now one that warns.
- Does not bump s6-overlay or the base image (E014-S01-007 accepts the digest bump and re-verifies these semantics).

## Technical acceptance criteria

### Interface contracts

- **State file contract:** `/run/traefik-certificate-exporter/watch-for-changes` holds exactly one line, `true` or `false`. Init writes it and the service's `run`/`finish` read it. No other value is valid. Anything else is treated as missing, which means watch mode.
- **`finish` contract:** the s6-supervise arguments are `$1` (exit code, or 256 if the process was killed by a signal) and `$2` (the signal number). The exit-code file is `/run/s6-linux-init-container-results/exitcode`. Halt is `/run/s6/basedir/bin/halt` (s6-overlay 3.2.1.0).
- **`app._run`:** the signature is unchanged; it adds one WARNING branch.
- **Sibling conventions:**
  - The s6 service dirs hold `run` (100755), `type` and `dependencies.d/`. The new `finish` is 100755 and bash, starts with `# shellcheck shell=bash`, and has a header comment giving its rationale, as `run` does.
  - The init script's state-file constants (`STATE_DIR`, `PRIV_STATE`, `RESOLVED`) gain a `RUN_MODE` constant in the same block.
  - The heredoc receives its output path through an env var, as `TCE_RESOLVED_OUT` does today; the new one is `TCE_RUN_MODE_OUT`.
- **Script-level test conventions:** these follow `tests/test_s6_privilege_drop.py` (copied scripts with substituted paths, stub binaries first on `PATH`, `_embedded_python()` extraction). The new module is `tests/test_s6_run_mode.py`. It reuses that module's idioms; shared helpers may be moved into `tests/s6_helpers.py` if both modules need them.

Spec: none — l3io-plan run, no spec index bound

### Error and edge case handling

- **Init resolver fails** (malformed config): no mode file is written. The service uses watch mode with one WARNING, and `finish` respawns. These are today's semantics for a failing watch service.
- **The exporter is killed by `docker stop`:**
  - In watch mode, `finish` exits 0 and s6 is already shutting down.
  - In run-once mode, `finish` computes 143 and halts. That is harmless during a shutdown already in progress.
- **The exit-code file cannot be written** (path absent outside s6-overlay): still `exec halt`. Halt absent: exit 125, so the service is not respawned and the container stays up idle. That is better than a loop. Log one line saying so.
- **`finish` time limit:** s6's default 5 s finish timeout. The script does only constant work.
- **`restart: always` with run-once:** a container-level loop, documented as an operator error (research §4 Risks).

Spec: none — l3io-plan run, no spec index bound

### Observability requirements

- `run` echoes the mode at every start, and the WARNING when the mode is unresolved.
- `finish` echoes, in run-once mode, `run-once pass finished with exit code <n>; stopping container`.
- The app's WARNING for the both-false case.
- All of these go to `docker logs` through s6's stdout, the same channel as the existing privilege WARNING. Correlation ids are app-level and unchanged.

### Security considerations

- Removing the shell's env parse removes a second, divergent interpretation of operator config. This is the same class of risk ADR-0030 closed for privilege.
- The mode file lives in root-owned `/run/traefik-certificate-exporter`, which init creates as root. The unprivileged service only reads it.
- `finish` runs as root under s6-supervise, and writes only to the fixed s6-overlay results path. It takes no operator-controlled input beyond the mode file's exact `true`/`false` match.
- The privilege branch in `run` is unchanged and still tested by `test_service_script_runs_as_root_unless_the_state_file_says_false`.
