## F1 — HIGH — kind: claim — config-file `watchforchanges: false` cannot select run-once in the image

- **Location:** `docker/README.md` "### Run once" (first paragraph); `docs/adr/0044-container-run-once-contract.md`
  Consequences bullet 1; the story's Business outcome and the 0.3.0 release-note bullet. The cause
  is `docker/Dockerfile:128`, which bakes `ENV TRAEFIK_CERTIFICATE_EXPORTER_SETTINGS_WATCHFORCHANGES=true`
  (and `RUNATSTART=true` on `:129`).
- **Claims contradicted:**
  - README: "With `watchforchanges` false — `-e …WATCHFORCHANGES=false`, `watchforchanges: false`
    in `/config/config.yaml`, or any YAML false spelling — the container runs one export pass
    and then **exits**", and "so the config file and the environment cannot disagree about it".
  - Story outcome: "An operator can run the image as a one-shot job (… or `watchforchanges: false`
    in `/config/config.yaml`)".
  - Release note: "The container honours `watchforchanges: false` from any source: config file, env…".
- **Issue:** confuse gives env a higher priority than the file, and the image always sets the env
  to `true`. The init resolver therefore writes `true` for an operator whose only change is
  `watchforchanges: false` in `/config/config.yaml`, and the container stays in watch mode. The
  unit test `test_resolver_writes_watch_mode_false_for_falsy_spellings[config-file-false]` passes
  only because it runs with the env unset, which the shipped image never does. No test covers
  the configuration the image actually ships. The opt-in container test sets the env and not the
  file, so it does not cover this either.
- **Suggested fix:** choose one of these.
  - (a) Drop `WATCHFORCHANGES` and `RUNATSTART` from the Dockerfile `ENV` block and let the
    packaged default or the seeded `config.yaml.sample` (both `true`) supply the default, so the
    file can override it. Then add a container-test case that mounts a config with
    `watchforchanges: false` and no env. Check that the 0.2.x env-only operators still get the
    same default.
  - (b) Keep the ENV, correct the README, the ADR and the release note to say that in the image
    only the env var selects run-once, and drop the "cannot disagree" sentence.

  Either way, add a resolver test that sets the image's env (`WATCHFORCHANGES=true`) together
  with a file saying `false`, so the documented contract is pinned.

## F2 — MEDIUM — kind: claim — a start-up config error in run-once intent becomes an endless 1 Hz respawn loop with a repeated WARNING

- **Location:** `svc-traefik-certificate-exporter/run` (`*)` branch of the mode `case`);
  `svc-traefik-certificate-exporter/finish` (the `!= "false"` → `exit 0` guard); `docker/README.md`
  "### Run once".
- **Claims contradicted:**
  - Story outcome: "No container configuration produces a 1 Hz restart loop".
  - Technical AC edge case: "The service uses watch mode with **one** WARNING".
  - README / operational.md: "exit code reflects start-up failures only: 0, or 1 when the data
    path is missing".
- **Issue:** a malformed `/config/config.yaml`, or a value confuse rejects (for example
  `WATCHFORCHANGES=1`, as the story's own deviation 1 shows), makes the resolver write no mode.
  Then:
  - `run` takes watch mode and the exporter dies on the same config error.
  - `finish` sees no mode and exits 0, so s6 respawns the service after 1 s, indefinitely.
  - `run` prints `WARNING: run mode unresolved…` on every respawn (once per second), not once.
    The header comment's "a longrun restart here does not repeat it" holds only for the
    privilege WARNING.

  For an operator running the image as a cron or systemd-timer job, the container never exits.
  Each scheduled invocation adds another looping container, and the exit code never reports this
  start-up failure. No exports or hooks repeat (the exporter dies before loading), which keeps
  this below HIGH. The technical AC accepted the watch fallback "as today's semantics", but the
  business outcome and the exit-code documentation state the opposite.
- **Suggested fix:**
  - Minimum: in README "### Run once", operational.md and the release note, state that a
    configuration error which prevents the mode from resolving leaves the container running and
    respawning. Recommend a scheduler-side deadline (`timeout`, `activeDeadlineSeconds`,
    systemd `RuntimeMaxSec`).
  - Better: have init write an explicit third state (`unresolved`) when the resolver fails, and
    have `finish` halt with the exporter's non-zero exit code in that state. A start-up config
    error is not transient, so respawning it is useless in either mode. Have init emit the
    unresolved WARNING once rather than `run` on every respawn.
  - Either way, make the outcome sentence match the shipped behaviour.

## F3 — MEDIUM — testability — the required 0.3.0 release-evidence command reports success when it tested nothing

- **Location:** `tests/test_container_run_once.py` `_skip_reason()` / `pytestmark` skipif, and
  `_run_once` (`pytest.skip` on `ImageNotFound`).
- **Issue:** AC 12 makes `just image && TCE_DOCKER_INTEGRATION=1 poetry run pytest -m integration
  tests/test_container_run_once.py` *required* release evidence. With the opt-in set, a missing
  socket (for example a non-default Docker context, which the client deliberately ignores) or a
  mistyped or unpulled `TCE_IMAGE` turns both tests into skips. pytest then exits 0 ("2 skipped"),
  which is green. E014-S02-005 can record a pass that checked nothing, which is the false-green
  failure mode.
- **Suggested fix:** when `TCE_DOCKER_INTEGRATION=1`, make a missing daemon or image a
  `pytest.fail` (the operator has already opted in). Keep `skip` only when the opt-in is unset.
  Alternatively, add `-p no:cacheprovider -rs` together with `--strict` or an explicit check in
  the release recipe that zero tests were skipped. The first option is the one-line fix.

## F4 — LOW — kind: deletion (confidence: low) — the "watch false = idle container" behaviour is gone

- **Location:** removed `else` branch of `svc-traefik-certificate-exporter/run` ("Skipping start
  of application...").
- **Issue:** the removed branch never ran the exporter when the env said false. An operator who
  used `WATCHFORCHANGES=false` as a kill switch, under a Compose policy of `restart:
  unless-stopped`, had a container that exported nothing. After the upgrade, every Docker restart
  runs a full export pass with its hooks and notifications. That is Docker's backoff loop, not
  1 Hz. The release note and README cover `restart: always` as an operator error, so no contract
  is silently lost. Recorded for completeness; no code change needed.
- **Suggested fix:** none required. Optionally name this specific upgrade path ("if you used
  `WATCHFORCHANGES=false` to disable the exporter…") in the 0.3.0 upgrading notes.

## F5 — LOW — error handling — `finish` can write 256 as the container exit code

- **Location:** `svc-traefik-certificate-exporter/finish`, `exit_code_for`.
- **Issue:** if `$1` is `256` and `$2` is missing or non-numeric, the first branch is skipped and
  the second (`^[0-9]+$`) echoes `256`. That value is written to the exitcode file, and the
  container exit status (mod 256) becomes **0**, so a signal kill reads as success. s6-supervise
  always sends `$2` with 256, so this cannot happen in practice. The script's own comment says
  that anything s6 would not send should "report a failure rather than a success", and this
  branch contradicts it.
- **Suggested fix:** in the numeric branch, map values outside `0..255` to `1`, for example
  `elif [[ "$1" =~ ^[0-9]+$ ]] && (( 10#$1 <= 255 ))`.

## F6 — LOW — docs — the README smoke path can hang indefinitely

- **Location:** `docker/README.md` smoke block (`docker run --rm --name traefik-certificate-exporter-smoke …; echo "exit code: $?"`).
- **Issue:** the corrected smoke path now runs in the foreground with no deadline. On a
  regression (mode unresolved, or F1-style precedence), the container stays in watch mode and
  the documented command never returns. It also leaves a named container that blocks the next
  attempt. The automated test has a 60 s limit; the manual path does not.
- **Suggested fix:** prefix with `timeout 60` (and `docker rm -f traefik-certificate-exporter-smoke`
  on timeout), or add `--stop-timeout` guidance, so a hang reports as a failure.

## Deliberate deviations — assessed

1. **Env `1` → no mode (watch fallback).** Sound as a resolver contract: it reaches the
   application's own answer (confuse rejects int 1), and the test pins it. Its downstream
   consequence is the respawn loop in F2, which needs documenting.
2. **Unresolved-mode WARNING on stderr.** Sound. s6-overlay passes longrun stderr to the
   container's stderr and `docker logs` shows both streams, and the unchanged privilege test
   requires it. The per-respawn repetition is covered in F2.
3. **`set -- "${1:-x}" "${2:-}"` plus `exit_code_for`.** Sound. It avoids a `-u` abort, maps
   missing args to failure code 1, and gives the ShellCheck plant a quoted `"$1"` to attack.
   Edge case in F5.
4. **`types: [file]` with `types_or: [shell, executable]` on the shellcheck hook.** Sound. The
   shipped tree under `docker/root/` holds exactly three executables (init `run`, svc `run`,
   `finish`), all bash with `# shellcheck shell=bash`, plus `privilege-decision.sh` (shell).
   No non-shell executable is swept in. The hook passes.

## Dimensions with no findings

- **Interface contracts:** the state file is exactly `true`/`false`, consistent across init,
  `run` and `finish`, and pinned by `test_the_three_scripts_agree_on_the_mode_path`. `app._run`
  keeps its signature. Sibling conventions are followed (`RUN_MODE` constant, `TCE_RUN_MODE_OUT`
  optional, `finish` 0755 with header).
- **Security:** the mode file is created by root in the root-owned state dir via `mkstemp`
  (0600) + `os.replace` and read only by root (`run` before `s6-setuidgid`, and `finish`).
  `finish` writes only the fixed results path. The privilege branch is unchanged, and the
  53 `test_s6_privilege_drop.py` tests pass unchanged.
- **Reused before written:** s6-overlay's `finish`/exitcode/`halt`/125, the confuse resolver,
  pre-commit `pygrep` and `shellcheck-py` are all used as intended. No hand-rolled supervisor,
  parser or linter.
- **Guard reach:** the pygrep scope `^docker/root/` matches the image's single
  `COPY docker/root /` (`docker/Dockerfile:133`), so the scope comes from what the image ships.
  The guard is a literal-string check: an indirect read such as `${!name}` or `env | grep` built
  from fragments would evade it. The hook's name, "read no settings env var", is slightly broader
  than what it checks. This is acceptable for its purpose and not raised as a finding.
