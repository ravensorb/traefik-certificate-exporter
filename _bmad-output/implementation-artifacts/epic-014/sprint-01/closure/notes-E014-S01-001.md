Evidence file for the story's `## Verification` table. Host: Python 3.11.11, Poetry 2.4.2,

## Decision recorded now (A-15): `use_context=False`

The Docker client is built only by `DockerManager._create_client()` as
`docker.from_env(use_context=False)`. docker-py 7.2 changed `from_env()` so that, when
`DOCKER_HOST` is unset, it falls back to the active Docker CLI context (`~/.docker/config.json`,
`DOCKER_CONTEXT`). Ignoring the context keeps the 0.2.x target: `DOCKER_HOST` if it is set,
otherwise `unix:///var/run/docker.sock`. The reason is security. The socket is
host-root-equivalent, so a `~/.docker` planted in the service's `HOME` must not be able to
redirect restarts to a different daemon. This decision was appended as a `- (decision)` line
to the product spine's `.memlog.md`. E014-S01-006's restart ADR records it formally; its text
is in the amendments section below.

## Implementation notes

- **Error classification (AC 8).** `EXPECTED_ENGINE_ERRORS = (docker.errors.DockerException, OSError)`.
  - Expected errors log one ERROR naming the endpoint and the error, with no traceback.
  - `docker.errors.NotFound` on `restart()` logs INFO `container gone`, releases the
    reservation, and continues the loop.
  - Anything else keeps `logger.exception`.
- **Verified fact (review F-03 follow-up).** On 7.2, a client built with a *fixed* `version`
  raises `requests.exceptions.ConnectionError` from `ping()` on a missing socket. Its MRO is
  `ConnectionError → RequestException → OSError`; it is not a `DockerException`. Only the
  version negotiation at construction wraps it in `DockerException`. This is why `OSError`
  must be in the expected set, and why the AC 3 test keeps construction inside the
  `pytest.raises` block.
- **`DEFAULT_DOCKER_ENDPOINT`.** It is derived from `docker.constants.DEFAULT_UNIX_SOCKET`
  with the internal `http+` prefix removed, not hard-coded.
  `test_logged_endpoint_is_the_endpoint_the_client_targets` pins `_endpoint()` to the socket
  the real client resolves.
- **Lock.** `poetry lock` moved `docker` 6.1.3 → 7.2.0 and dropped `websocket-client`, which
  is an optional extra in docker 7 and is not imported by `src/`. No other package changed.
  `docker-pycreds` and the direct `requests` are left for E014-S01-007.
- **Process deviation.** The development and fix passes ran inline in the story agent. They
  were not spawned through the `bmad-dev-story` skill. Dispatch open/close brackets were still
  written for `l3io-dev-implement`, and the code review was a separate scoped subagent.

4. **Decision text for E014-S01-006's restart ADR** (the `use_context=False` choice):

   > The Docker client is constructed in exactly one place, `DockerManager._create_client()`,
   > as `docker.from_env(use_context=False)`. Since docker-py 7.2, `from_env()` falls back to
   > the active Docker CLI context when `DOCKER_HOST` is unset. We switch that off: the target
   > is `DOCKER_HOST` if set, otherwise `unix:///var/run/docker.sock`, exactly as in 0.2.x.
   > The Docker socket is host-root-equivalent; honouring the CLI context would let a
   > `~/.docker/config.json` planted in the service's `HOME` redirect container restarts to a
   > different daemon. The cost is that a PyPI install on a workstation with a non-default
   > context must set `DOCKER_HOST` explicitly; this is documented in `docs/operational.md`
   > and the 0.3.0 upgrade notes. Revisit if Docker CLI context support is requested as a
   > feature (currently a non-goal). Evidence: `tests/libs/test_docker.py::test_client_ignores_docker_cli_context`.
