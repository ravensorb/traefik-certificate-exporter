## R-01 — MEDIUM — kind: design (BL-E014-012 decision)

**Location:** `src/traefik_certificate_exporter/libs/certificate_exporter.py:786-801` (claim block in
`__exportDomain`). ADR-0043 decision 6 "One owner per target" and the first Consequences bullet.

**Trigger:** `resolverinpathname` is off and two resolvers hold the same domain, with the stale one
first in sorted key order. One case: the operator moved from resolver `le` to `le-dns`. Traefik
keeps the old resolver's section in `acme.json` and does not prune its entries, so `le` (sorted
first) still holds the old certificate after `le-dns` has issued and renewed a new one.

**Why it matters:** the first resolver in store order always wins, whatever the certificate's
validity. The exporter keeps writing `le`'s certificate, past its `notAfter`, while a valid
certificate for the same domain sits in `le-dns`. Consumers are handed an expired certificate. The
only signal is a WARNING every pass, which does not say that the winning certificate is older.

The ADR's mitigation ("takes effect once the old resolver's entry leaves the store") assumes that
Traefik removes the entry. Traefik does not remove the entries of a resolver that is no longer
configured. Store order is stable, but it is alphabetical by resolver name, which has nothing to do
with which certificate should be served.

**Suggested fix:** keep the claim mechanism, but choose the owner by certificate validity. Prefer
the entry whose leaf has the latest `not_valid_after_utc`, and break ties by store order so the
result stays stable and quiet. The parsed `certs` are already in hand at the claim point. This
needs a pre-pass over all resolvers, or deferring the writes until every candidate for a target is
known. Then update decision 6 and the Consequences bullet to match. At minimum, put both
certificates' expiry dates in the WARNING and correct the ADR's "leaves the store" premise.

## R-02 — MEDIUM — kind: deletion (confidence: high)

**Location:** `certificate_exporter.py:786-801` (claim block) together with `:660`
(`name.removeprefix("*.")`).

**Trigger:** one resolver holds both `example.test` and `*.example.test`. This is common, because
the wildcard is often issued as a separate certificate. Both names strip to `example.test` and map
to the same target directory. The probe confirmed it:

```
WARNING Not exporting 'example.test' from resolver 'le': resolver 'le' already exports it to '.../certs/example.test' in this pass (set resolverinpathname to export both)
```

The files keep the first entry (here the apex certificate). Before this story, the last entry won:
both were written, and the later one stayed on disk. For an unwrapped (v1.7) store, the message
reads `from resolver '': resolver '' already exports it`.

**Why it matters:**
- The claim block was written for the cross-resolver case (BL-E014-012). It also changes which
  certificate a single resolver exports for wildcard+apex pairs. That change is not recorded:
  ADR decision 6 speaks only of "two resolvers".
- The WARNING's advice is wrong for this case. Setting `resolverinpathname` cannot separate two
  entries of the same resolver.
- Operators whose files held the wildcard (listed after the apex) silently get the apex-only
  certificate after the upgrade. Subdomain consumers then fail TLS name checks.

**Suggested fix:**
- Decide the intra-resolver policy explicitly and record it in ADR-0043 decision 6. One option is
  the R-01 validity rule. Another is preferring the entry whose SANs cover both names.
- Word the WARNING for the same-resolver case: name the two colliding entries (`*.example.test` and
  `example.test`), not the resolver twice, and drop the `resolverinpathname` hint. Render a `None`
  resolver as `(unnamed)`, as `__exportCertificate` already does.
- Add a test for the wildcard+apex pair.

## R-04 — LOW — kind: design (BL-E014-012 reach)

**Location:** `certificate_exporter.py:920` (`claimedTargets` is created per call of
`exportCertificatesForFile`) and `exportCertificates` at `:944-952`.

**Trigger:** each resolver has its own `storage` file, for example `acme-dns.json` and
`acme-http.json` matched by `fileSpec`. The two files hold the same domain, with
`resolverinpathname` off. Each file has its own empty claim map, so on every full pass the
glob-later file overwrites the glob-earlier one. In watch mode, whichever file last changed wins.

**Why it matters:** ADR-0043 says "the first resolver in store order keeps them … an unchanged store
stays quiet". That holds within one file only. A per-resolver storage file is a documented Traefik
pattern, and in that setup the flip that BL-E014-012 describes remains, across files.

**Suggested fix:** either share one claim map across files in `exportCertificates` (watch-mode
single-file passes would still need a policy), or narrow the ADR wording to "within one store
file", and either keep BL-E014-012 open for the cross-file case or file a follow-up.

## R-05 — LOW — kind: deletion (confidence: medium)

**Location:** `certificate_exporter.py:890-900` and `:902-941`, compared with the old
`exportCertificatesForFile`, which wrapped everything in `except Exception` and returned `None`.

**Trigger:** an exception that is not an `OSError` or `ValueError` is raised outside the
per-resolver `try`. The realistic case is `MemoryError` from `_read_store` reading a very large
store whole, which this story deliberately allows ("no size limit").

**Why it matters:** the old catch-all turned any such failure into an ERROR plus `None`, which
callers coerced to `[]`. Now it propagates into `exportCertificates` and `__processPath`, and the
remaining files of the pass (and the hook, notify and restart steps) are skipped.

The interface contract ("returns `list[str]`, never `None`… file-level failures return `[]` with an
ERROR") is narrower than the old safety net, and nothing records the narrowing. Impact is low,
because the input is trusted.

**Suggested fix:** add `MemoryError` to the file-level `except` (ERROR, `[]`), or record in ADR-0043
decision 6 that only `OSError` and `ValueError` are file-level rejects and anything else propagates.
