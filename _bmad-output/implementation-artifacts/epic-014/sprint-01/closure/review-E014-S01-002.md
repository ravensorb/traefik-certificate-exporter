## R-02: an unchanged certificate with no subject CN logs an ERROR on every pass

- **Severity:** MEDIUM
- **Kind:** claim
- **Location:** `src/traefik_certificate_exporter/libs/certificate_exporter.py:812`, inside
  `build_pkcs12`, called unconditionally from `__exportDomain` (`:600`).
- **Claims contradicted:** Observability: "Unchanged domain: one DEBUG line `Certificate for <name>
  unchanged; nothing written`. There is no INFO line, so a quiet pass stays quiet." Also: "Per-domain build
  failure: one ERROR naming the domain ...".
- **Trigger:** a stored leaf with no CN in its subject. Let's Encrypt's `tlsserver` and `shortlived`
  profiles issue such certificates, and any CA that puts names only in the SAN does too. Build-first now
  runs `build_pkcs12` for every domain on every pass, including unchanged ones. The `except` around the
  CN lookup therefore emits `globalLogger.error("Failed to get common name from certificate")` on every
  pass for that domain. The export then succeeds with the "LetsEncrypt Certificate" fallback.
- **Why it matters:**
  - A pass over an unchanged store is supposed to be quiet. Here it logs an ERROR per CN-less domain.
  - The ERROR does not name the domain, which also breaks the "one ERROR naming the domain" rule.
  - It describes a condition that is not a failure. Operators who alert on ERROR get paged on every
    store write.
  - The friendly-name fallback is a non-goal, but the log level of a successful build falls under this
    story's observability contract.
- **Suggested fix:** keep the fallback value but log at DEBUG, for example "no subject CN; using fallback
  friendly name". Add a unit test: a CN-less leaf over unchanged output produces no ERROR record.

## R-03: on a filesystem that ignores `chmod`, every pass rewrites and reports every domain

- **Severity:** LOW
- **Kind:** claim
- **Confidence:** medium. This is reasoned from the code; no such mount was available to test on.
- **Location:** `src/traefik_certificate_exporter/libs/certificate_exporter.py:298`
  (`_breaks_write_policy`), as used by `_file_differs` and `_pfx_differs`.
- **Claim contradicted:** Business outcome: "A pass over an unchanged store rewrites nothing and reports
  nothing, so nothing downstream (restart, hook, notification) is triggered by it."
- **Trigger:** `outputpath` is on a mount whose reported mode is fixed and above the floor, and where
  `os.chmod` succeeds without effect. Examples: CIFS/SMB with `file_mode=0755` or `noperm`, WSL drvfs
  without `metadata`, some FUSE filesystems. Then `privkey.pem` and `cert.pfx` always report a mode above
  0600, so `_breaks_write_policy` returns True on every pass. The domain is rewritten and reported every
  pass. Once S01-006 and S01-010 consume the signal, that means a restart, hook and notification every
  time. Nothing is logged that explains why.
- **Why it matters:** this is not a regression, because 0.2.x rewrote everything anyway. But the new
  change signal is silently always true on these mounts. The `_inheritable_metadata` "refusing to inherit
  permissive mode" WARNING fires on every pass, which is the only clue.
- **Suggested fix:** keep the deliberate rule. Additionally:
  - after the write, re-`lstat` the target;
  - if the mode still breaks the policy, log one WARNING per path naming the mount limitation (the
    once-per-path `_SYMLINK_WARNED` pattern can be reused);
  - document in ADR-0043 Decision 2 that such mounts get a permanent "changed".

  Optionally, compare only the content for a file the process has just failed to tighten.

## R-04: one domain held by two resolvers keeps flipping its files when `resolverinpathname` is off

- **Severity:** LOW
- **Kind:** claim
- **Confidence:** high
- **Location:** `src/traefik_certificate_exporter/libs/certificate_exporter.py:621` (directory
  derivation) together with the compare-then-write in `__exportDomain`.
- **Claim contradicted:** ADR-0043 Consequences and Business outcome: "A pass over an unchanged store
  writes nothing and reports nothing."
- **Trigger:** `resolverinpathname: false` (or flat mode without it), with the same domain present under
  two resolvers. This happens, for example, during an HTTP-01 to DNS-01 migration or when a staging
  resolver is left in place. Each pass goes like this:
  - resolver A writes A's artifacts;
  - resolver B compares against A's files, finds them different, and overwrites them;
  - the next pass repeats the cycle.

  The domain is reported twice per pass, forever, and the files end up holding whichever resolver comes
  last.
- **Why it matters:** this is not a regression, because 0.2.x also last-writer-won and reported everything
  every pass. But ADR-0043 now states that an unchanged store is quiet, and that statement is false for
  this layout. The two-resolver case is covered for `artifactMtime` (S01-006), not for the writer.
- **Suggested fix:** either name this layout as an exception in ADR-0043's Consequences, or detect a
  duplicate target directory within one pass (`sweptDirectories` is already per pass) and log one WARNING.
  Leave the behaviour change to S01-003 or S01-006 if preferred, but record it.

## R-05: the image test leaks its named volume if removing the container fails

- **Severity:** LOW
- **Kind:** testability
- **Location:** `tests/test_container_pkcs12.py:151-153`
- **Trigger:** `container.remove(force=True)` raises, for example because of a daemon hiccup or because the
  container is already being removed. The exception propagates out of the `finally`, so
  `volume.remove(force=True)` never runs. The run leaves a `tce-pkcs12-it-*` volume behind. The exception
  also masks the test's original assertion failure.
- **Why it matters:** AC 11 says "force-removes the container and the volume in a `finally`". This test is
  the release evidence that S02-005 will run repeatedly on CI or release hosts, and partial cleanup there
  leaves debris and hides the real failure.
- **Suggested fix:** wrap each removal separately, for example
  `with contextlib.suppress(docker.errors.APIError): container.remove(force=True)`, then remove the volume
  the same way. Alternatively, use nested `try/finally` so the volume removal always runs.
