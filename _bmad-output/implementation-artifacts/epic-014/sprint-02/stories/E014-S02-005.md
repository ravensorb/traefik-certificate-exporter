**One release run per tag** (CI `.memlog.md` maintainer decision 2026-10-11 (2), refined by the 2026-10-11 option-2 decision; plan review A-07/A-08; recorded in AD-9 and the E014 pipeline ADR by E014-S02-003; this story cites it and does not originate it). All destinations of a release publish from ONE forge's run, all-GitHub or all-Gitea, never split. Every `PUBLISH_*` secret lives on that forge only; the other forge holds none, so a mirrored tag's run there is silent and publishes nothing. This keeps AD-10's one digest across all registries and one writer per tag (AD-8). The rule is not mechanically enforced; the checklist verifies it by comparing secret names on both forges.

For 0.3.0 the publishing forge is **GitHub**. An all-Gitea run is an equally valid topology and can publish every destination (maintainer decision 2026-10-11, option 2; CI spine AD-9, AD-13): Gitea, which ignores `environment:`, then holds the PyPI, TestPyPI, GHCR and Docker Hub tokens as repository-level secrets alongside its own. That topology requires the mitigations in the checklist's "Gitea topology" item: protected `main` and `v*` tags with pushes and tag creation limited to trusted accounts, project-scoped tokens, and rotation of every token after any untrusted push. The residual risk (a trusted account's branch workflow on Gitea can read the tokens) is accepted. Either way each destination's secrets live on exactly one forge. ADR-0039's earlier "Gitea never holds non-Gitea tokens" is amended by E014-S02-003.

**Versioning.** The project stays on 0.x until the maintainer declares it stable, then releases v1.0.0. Existing `:0` image tags (written by the retired pipeline) stay frozen; 0.x releases do not write `X` (E014-S02-001 gates `type=semver,pattern={{major}}` with `enable=${{ !startsWith(<version>, '0.') }}`). From 1.0.0 that `enable` is true, so the major tag `1` is produced automatically with no workflow change.

**Restart behaviour change** (maintainer decision 2026-10-11, implemented in E014-S01-002/S01-006; PRD review F-02). In 0.2.x, `restartcontainers` silently failed (B1). In 0.3.0 restarts take effect: a labeled container is restarted when its domains' newest exported file is more than 2 s newer than the container's start (FR-15, product AD-10); the 5-minute per-container floor with a deferred trailing restart applies on top. The upgrade notes must say so, because operators who set labels long ago will now see restarts.

## Business acceptance criteria

### Outcome

Users can install 0.3.0 from PyPI or the Gitea index, and pull one identical multi-arch image as `0.3.0`, `0.3` or `latest` from GHCR, Docker Hub or Gitea. The forge release carries the generated notes and the exact wheel and sdist. The maintainer can cut a release from either forge, with all destinations published by that one forge's run. The maintainer has recorded proof, against the release-commit image, that restart, run-once and passphrase PKCS12 work, and that every destination of the pipeline works live.

### Error and edge case handling

- **An integration test is missing or skipped** at the release commit (for example the passphrase `.pfx` import test is not defined). Do not tag. Stop with `BLOCKED: <story> integration test missing`, or file the gap with `append-issue` and get the maintainer's recorded decision before going on.
- **An integration test fails.** Do not tag. File the defect; fix it in a code story or a patch commit on `main`; re-run AC 3.
- **A "0.3.0 release notes" bullet contradicts the code** at the release commit. The code wins; the note is written from the code and the discrepancy is recorded in the cross-read table.
- **The dry run fails.** Do not tag. File the defect, fix it in a code story or a patch commit on `main`, then re-run the dry run.
- **A publish job fails mid-run**, for example because a token is wrong:
  - fix the secret, then re-run the failed jobs;
  - uploads skip existing files (PyPI `--skip-existing`, the Gitea files check, AD-11);
  - image tags are re-pointed to the re-run's digest (ADR-0036 §5);
  - the release is updated in place (`allow-updates: true`);
  - never re-push the tag.
- **A destination warning appears for a target destination.** It is partially configured; the warning names the missing item and where to set it (GitHub `release` environment). Set it, then re-run the run's jobs. The flags are evaluated per run. Do not announce until the run shows zero warnings.
- **A target destination is silent (no enabled line, no warning).** None of its inputs is set on GitHub. Set them in the `release` environment and re-run.
- **The release run is cancelled while pending** (AD-14 as corrected by E014-S02-001). Re-run it.
- **A 429 from ghcr.io in `build` or `publish-image`.** Re-run (E014-S02-001).
- **The digests differ across registries.** That breaks AD-10. Stop: do not announce. Re-run `publish-image`, which re-points all three registries to one digest, then re-verify.
- **The PyPI project name is not yet registered, or the token is project-scoped to a missing project.** The first upload needs an account-scoped token. Afterwards, replace it with a project-scoped token and record the rotation.
- **A GHCR package is created private on first push.** The maintainer sets it public and links it to the repository, then the anonymous pull is re-run.
- **The mirror runs `release.yaml` on Gitea.** With no `PUBLISH_*` secrets there, it is silent and publishes nothing. If Gitea is found to hold a `PUBLISH_*` secret, the run would re-point the same image tags to a different digest or race on the same upload: stop, do not announce, delete the secret from Gitea, re-run `publish-image` on GitHub so all tags point to one digest, and re-verify AC 9.
