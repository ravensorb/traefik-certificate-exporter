# Destination gating: publish only when token and all variables are set

## Context

Today a publish destination switches on when its token secret alone is set (the pre-consolidation spine AD-9 said: "Each destination is enabled exactly when its token secret is set"; the consolidated AD-9 now requires the token and every variable). E013-S01-005 (BL-E013-008) then added a fail-fast "Registry configuration guard" to `publish-image`. That guard fails the whole job when a registry's token is set but its image or registry variable is empty (`.github/workflows/dev.yaml:163-182`, `.github/workflows/release.yaml:207-226`). Two consequences follow:

- **A half-configured registry fails the release.** It fails the image job, and therefore the `release` job, which `needs` it (`docs/ci/pipeline-walkthrough.md` §"Releasing", the "registry configuration guard" bullet).
- **The two Gitea destinations cannot be enabled separately.** The Gitea package index and the Gitea registry share `PUBLISH_GITEA_TOKEN` (spine AD-9 table; `docs/operational.md:325-330`).
- **Package indexes and the forge release are never checked at all.** An empty `vars.PUBLISH_GITEA_PYPI_URL` is passed straight to twine (`dev.yaml:84`).

Maintainer decision, 2026-10-10, verbatim from the dispatch: "a destination is enabled only when its token AND every variable it requires are set and non-empty; otherwise it is skipped with a visible `::warning::` (GitHub/Gitea annotation) naming what is missing. This replaces the E013-S01-005 fail-fast "Registry configuration guard" and amends spine AD-9/AD-10 (and AD-11 for package indexes, AD-12/13 for the release token). Must keep the conditional forms simple (AD-9: flags computed in job env, single-flag `if:`), keep zizmor/actionlint green, and preserve the one-multi-arch-build rule."

The same decision as recorded in `.memlog.md`: "(3) A destination is enabled only when its token AND every variable it needs are set and non-empty; otherwise it is skipped with a visible ::warning:: (replaces the E013-S01-005 fail-fast registry guard; amends AD-9/AD-10) — E014-S02-002."

Required inputs per destination. **Where the fix goes**, named in every partial warning: on GitHub, secrets and variables of the job's environment (`dev` for `dev.yaml`, `release` for `release.yaml`; Settings → Environments → `<env>`); on Gitea, repository Actions secrets and variables (Gitea ignores `environment:`, AD-6 / ADR-0039). The step prints both, because the same workflow file runs on both forges.

**Shared Gitea inputs.** `PUBLISH_GITEA_TOKEN` and `PUBLISH_GITEA_USERNAME` serve both Gitea destinations, so they cannot by themselves show which destination was intended. Each Gitea destination's intent is judged by its own variables (`PYPI_URL`; `REGISTRY`/`IMAGE`). A shared input set with no Gitea destination's own variable set is reported once, by `publish-package` only (the "Gitea shared inputs" row), so a maintainer using only the Gitea registry gets no index warning, and an orphan Gitea token still gets one warning per run, not two.

Assumptions made by the enricher (recorded; overturn at review):

1. **Only a partially configured destination warns** (maintainer decision 2026-10-11, superseding this story's earlier "every skipped destination warns" assumption). A destination with nothing configured is silent; one with some but not all inputs gets exactly one `::warning::` per run; a fully configured one publishes. The private CA is excluded, because it is not a destination.
2. **"Non-empty" means `!= ''` in the expression language.** On GitHub an unset variable is null, and null compares equal to `''`, so unset counts as missing; act and Gitea must be shown to agree (Testability). Whitespace is not trimmed: a value of `" "` counts as set, and the consuming action fails loudly.
3. **The flag name `PUBLISH_GITEA` changes meaning in `publish-package`.** There it is renamed `PUBLISH_GITEA_PYPI`, so that one name never means two different conditions. In `publish-image`, `PUBLISH_GITEA` remains the registry flag.
4. **The flags stay in job-level `env`.** This is the decision's wording and AD-9's current form. A job-level `env` entry cannot reference another, so `PUBLISH_IMAGE` repeats the three registry conjunctions; that stays the only flag combining destinations (AD-10). Step-written `$GITHUB_ENV` flags were considered and rejected, because they would move the rule out of job `env`.
5. **The rule lives only in job `env`** (plan review A-04). Next to each `PUBLISH_<DEST>` flag, job `env` computes `ANY_<DEST>` ("any intent input set") the same way. The "Destination configuration" step does not re-derive or cross-check any rule: `enabled` = `PUBLISH_<DEST>` is `'true'`; `partial` = `ANY_<DEST>` is `'true'` and `PUBLISH_<DEST>` is `'false'`; otherwise unconfigured. It lists missing names from per-input presence booleans, a mechanical loop with no conjunction in it.

**Maintainer decisions 2026-10-11**

- Warnings must be "useful and actionable and not overly noisy".
- A destination with nothing configured (no token and no variables) is silent.
- A partially configured destination (token without one or more required variables, or any required variable set without its token) emits exactly one `::warning::` per destination per run, naming the missing item(s) and the fix (which environment, secret or variable to set).
- A fully configured destination publishes.

## Acceptance Criteria

1. **Each flag is the full conjunction.** In every publish job of `dev.yaml` and `release.yaml`, each destination flag in job `env` is exactly the conjunction in the Context table, for example:
   `PUBLISH_GHCR: ${{ secrets.PUBLISH_GHCR_TOKEN != '' && vars.PUBLISH_GHCR_USERNAME != '' && vars.PUBLISH_GHCR_IMAGE != '' }}`
2. **Each multi-input destination has an intent flag.** Beside it, job `env` carries `ANY_<DEST>`, the disjunction of the Context table's intent inputs, for example:
   `ANY_GHCR: ${{ secrets.PUBLISH_GHCR_TOKEN != '' || vars.PUBLISH_GHCR_USERNAME != '' || vars.PUBLISH_GHCR_IMAGE != '' }}`
   `publish-package` also carries `ANY_GITEA_SHARED`. Single-input destinations have no `ANY_*` flag.
3. **`PUBLISH_IMAGE` combines the three registry conjunctions.** It is true iff at least one registry conjunction is true. `GHCR_IMAGE`, `GITEA_IMAGE` and `DOCKERHUB_IMAGE` are non-empty only when their own registry's conjunction is true.
4. **The fail-fast guard is gone.** The "Registry configuration guard" step is removed from both workflows.
5. **Each publish job begins with a "Destination configuration" step**, in the step order of the AD-17/AD-18 amendment: Destination configuration → AD-15 version guard (dev only) → hash verify → CA import → login / publish.
   - It has no `if:`.
   - It reads the job's `PUBLISH_*` and `ANY_*` flags and classifies each destination the job owns: `enabled` iff `PUBLISH_<DEST>` is `'true'`; `partial` iff `ANY_<DEST>` is `'true'` and `PUBLISH_<DEST>` is `'false'`; otherwise `unconfigured`. It contains no conjunction or disjunction of inputs of its own.
   - For each `partial` destination it prints exactly one `::warning title=<job>::<Destination> partially configured, skipped: missing <comma-separated list of secrets.NAME / vars.NAME>. Set them as <env> environment secrets/variables (GitHub) or repository Actions secrets/variables (Gitea), or unset <the set items> to disable it.` The missing list is every required input whose presence boolean is false.
   - For each `unconfigured` destination it prints nothing: no warning and no log line.
   - For each `enabled` destination it prints one plain log line `<Destination> enabled` (not an annotation).
   - The "Gitea shared inputs" orphan case (`ANY_GITEA_SHARED` true) is reported only by `publish-package`, once, in the same format.
   - It never prints a secret's value. For naming missing items it receives only per-secret presence booleans in step `env`, for example `HAS_PUBLISH_GHCR_TOKEN: ${{ secrets.PUBLISH_GHCR_TOKEN != '' }}`, plus per-variable presence booleans.
   - The `release` job reports `Forge release` only.
6. **Steps keep single-flag gating.** Every publishing step still tests exactly one flag (`if: env.PUBLISH_X == 'true'`). No `if:` contains `secrets.` or `vars.`. The `release` job keeps its per-step `PUBLISH_RELEASE` gating (AD-12).
7. **The Gitea destinations are independent.** With `PUBLISH_GITEA_TOKEN` set:
   - an empty `PUBLISH_GITEA_PYPI_URL` skips the index silently and still publishes the image;
   - empty `PUBLISH_GITEA_REGISTRY` and `PUBLISH_GITEA_IMAGE` skip the image silently and still upload the package;
   - `PUBLISH_GITEA_REGISTRY` set with `PUBLISH_GITEA_IMAGE` empty skips the image with one warning naming `vars.PUBLISH_GITEA_IMAGE`, and still uploads the package.
8. **The build and the no-op path are unchanged.**
   - There is still exactly one `docker/build-push-action` push step per `publish-image` job, building `linux/amd64,linux/arm64` once and pushing to every enabled registry (AD-10).
   - With nothing configured, every job succeeds, publishes nothing and emits no destination warning.
9. **Docs match the new behaviour.** These describe the new rule and match the Context table:
   - `docs/ci/pipeline-walkthrough.md` §"Where things are published" (table column "switched on by" → "enabled when all set"), §"How 'publish if the token is set' is written", and the guard bullet in §"Releasing";
   - `docs/operational.md` §"Publishing" (guard paragraph, shared-token paragraph);
   - the `README.md` "Releases and images" bullet;
   - the `dev.yaml`/`release.yaml` header comments.

   The walkthrough states the three states (silent / one warning / publishes) and where each fix goes on GitHub and on Gitea. Its per-release checklist gains the item "the release run shows **zero** destination warnings and each target destination `enabled` exactly once; otherwise fix and re-run before announcing", with the sentence "not mechanically enforced: a partially configured destination does not fail the run (NFR-4 trade-off, E014 pipeline ADR)".
10. **`just check` is green, with no new zizmor suppression.** actionlint, zizmor (auditor persona: `secrets-outside-env`, `anonymous-definition`) and all hooks pass. The act evidence matrix (Testability) is recorded. This story closes on act evidence; the GitHub unset-variable check runs in E014-S02-005.

## Business acceptance criteria

### Outcome

A maintainer, or a fork, can configure any subset of destinations:
- a missing or partial configuration never fails a dev or release run;
- a destination nobody configured adds no noise to the run summary;
- a partly configured destination produces exactly one warning per run, naming exactly which secret or variable it lacks and where to set it;
- the two Gitea destinations can be switched on independently.

From any run, the maintainer can read which destinations published (the `enabled` lines) and which were left half-configured (the warnings). A no-secret run shows neither.

- **0.3.0 release notes:**
  - "A publish destination is enabled only when its token and every variable it needs are set. A partly configured destination is skipped with one warning naming what is missing; an unconfigured one is silent. The Gitea package index and the Gitea registry can be enabled separately." (Maintainer- and fork-facing.)
  - Internal-only (no upgrade note): the removal of the fail-fast registry guard; flag renames inside workflow files.

Spec: none — l3io-plan run, no spec index bound

### Non-goals

- Does not add, rename or remove any `PUBLISH_*` secret or variable name.
- Does not move variables into environments, and changes no environment or forge setting.
- Does not make a skipped destination fail the run. The maintainer chose warn-and-skip; a "required destinations" mode is not built.
- Does not deduplicate `dev.yaml`/`release.yaml`. E014-S02-003 records that duplication in an ADR (F-05).
- Does not edit the CI spine, ADR-0035, ADR-0039 or `docs/architecture.md`. E014-S02-003 does.
- Does not validate the shape of variable values (URL form, lower-case image names).
- Does not produce live-forge evidence; E014-S02-005 records it.

## Technical acceptance criteria

### Interface contracts

Inputs: the secret and variable names in the Context table, with no new names.

Job `env` per publish job:

| Job | `env` keys |
| --- | --- |
| `publish-package` (dev) | `PUBLISH_CA`, `PUBLISH_GITEA_PYPI`, `ANY_GITEA_PYPI`, `ANY_GITEA_SHARED`, `PUBLISH_TESTPYPI` |
| `publish-package` (release) | `PUBLISH_CA`, `PUBLISH_GITEA_PYPI`, `ANY_GITEA_PYPI`, `ANY_GITEA_SHARED`, `PUBLISH_PYPI` |
| `publish-image` (both) | `PUBLISH_CA`, `PUBLISH_GHCR`, `ANY_GHCR`, `PUBLISH_GITEA`, `ANY_GITEA`, `PUBLISH_DOCKERHUB`, `ANY_DOCKERHUB`, `PUBLISH_IMAGE`, `GHCR_IMAGE`, `GITEA_IMAGE`, `DOCKERHUB_IMAGE` |
| `release` | `PUBLISH_CA`, `PUBLISH_RELEASE` |

All values are `'true'`/`'false'` strings, except the image names, which are the variable value or `''`.

"Destination configuration" step contract:
- **Inputs** are the job's `PUBLISH_*`/`ANY_*` flags, plus step `env` presence booleans (`HAS_<SECRET>`, `HAS_<VAR>`) used only to name missing items.
- **Output** is `enabled` log lines and, for partial destinations only, `::warning::` workflow commands (at most one per destination per run). It has no `$GITHUB_OUTPUT` and no `$GITHUB_ENV` writes; flags stay in job `env`.
- **Classification** reads the flags only (Acceptance Criterion 5). The rule exists once, in job `env`.
- **Body shape.** A loop over a per-job list of `<Destination>|<PUBLISH flag>|<ANY flag>|<required input names>` entries. The list is the only per-job difference between copies.
- **Exit 0 always.** The step never fails, which is the point of warn-and-skip.

Publish-job step order: Destination configuration → AD-15 version guard (dev only) → hash verify (E014-S02-001) → CA import (AD-18) → login / publish.

Sibling conventions to keep:
- every job's `name:` equals its id;
- `environment:` stays on every publish job (ADR-0039);
- each step has a one-line comment citing its AD;
- `shell: bash` comes from `defaults.run`;
- secrets are passed only to the step that consumes them (AD-9).

Downstream consumers:
- E014-S02-005 reads the warnings as release evidence.
- E014-S02-003 copies the Context table into the AD-9 table, and applies the `## Spine/ADR amendments for S02-003` section of this story's notes.

### Error and edge case handling

- **Nothing set for a destination** → skipped silently: no warning, no log line.
- **Variable set, token absent** → partial: skipped, with one warning naming `secrets.PUBLISH_X_TOKEN` and where to set it.
- **Token set, one variable empty** → partial: skipped, with one warning naming that variable and where to set it. This replaces the old hard failure, so a release can now ship without a registry the maintainer intended. The mitigation is the walkthrough's per-release checklist item (zero destination warnings), recorded in the E014 pipeline ADR as not mechanically enforced, and E014-S02-005's verification.
- **No registry enabled** → `PUBLISH_IMAGE` is false and every image step skips. The job succeeds, as before.
- **Gitea index enabled, registry not (or the reverse)** → each runs or skips on its own flag. The shared token is consumed only by the enabled side's step. The unused side is silent unless one of its own variables is set.
- **Gitea token (or username) set, no Gitea destination's own variable set** → one warning per run from `publish-package` ("Gitea shared inputs"), naming `vars.PUBLISH_GITEA_PYPI_URL` and `vars.PUBLISH_GITEA_REGISTRY` + `vars.PUBLISH_GITEA_IMAGE` as the options. `publish-image` stays silent for it, so the run has one warning, not two.
- **Single-input destinations** (TestPyPI, PyPI, Forge release) are either enabled or silent; they never warn.
- **Noise bound.** A run emits at most one destination warning per destination plus one for Gitea shared inputs; a fully configured or fully unconfigured setup emits none.
- **A flag edit makes `PUBLISH_*` and `ANY_*` disagree** (for example `PUBLISH_X` true while `ANY_X` false). This cannot arise from inputs, only from a workflow edit; the act matrix rows prove each pair, and review of any later edit covers it. No runtime cross-check is written (A-04).
- **Gitea and act** ignore `environment:` (AD-6) and read repository/organisation secrets and variables. The conjunction is identical there. Whether the runner renders `::warning::` as an annotation or as a plain log line, the line is present in the log, and that is the requirement.
- **Unset variable on act.** If act evaluates an undefined `vars.X` differently from `''` (for example as the literal string `null`), the conjunction would wrongly be true. This is caught by the act matrix. If it happens, the conjunction must use the form that evaluates false on all three runners, chosen by evidence, and the form is recorded in the notes.
- **Re-run.** Gating is evaluated per run, so changing a variable between attempts changes what the re-run publishes. This is documented in the walkthrough re-run bullet. A re-run attempt repeats its own warnings; "one per run" means per workflow run attempt.

### Observability requirements

- Every publish job's log begins with the "Destination configuration" step: one plain `<Destination> enabled` line per enabled destination; nothing for unconfigured ones.

### Security considerations

- The flag expressions read secrets only as `!= ''` presence tests inside an `environment:` job, the same pattern ADR-0039 accepted, so zizmor `secrets-outside-env` stays clean.
- The warning step gets booleans, never secret values. Variables are not secret, and printing their names is safe; their values are not printed either, beyond what later steps already log.
- Gating on variables does not reduce the variable-redirect risk documented in `docs/operational.md` §"Publishing": whoever can edit variables controls where a token is sent. That paragraph stays.
- A partly configured destination no longer logs in. Before this change, a token with no image variable failed before login; now it never logs in at all. Credential exposure is the same or lower.

### Existing-library check

| Need | Mechanism |
| --- | --- |
| Gating | The workflow expression language in job `env` (AD-9). No action exists for "skip unless configured", and a composite action would hide the rule from zizmor's per-step view. |
