**This story is HITL (human in the loop).** Every step that creates a token, writes a secret or variable, changes or confirms a forge setting, pushes the tag or approves the release is the maintainer's. An agent may run the read-only verification commands (rows marked "agent may run" in `## Verification`) and record their output, but never stores a secret, never runs `just release` and never edits a forge setting. **One release run per tag** (CI `.memlog.md` maintainer decision 2026-10-11 (2), refined by the 2026-10-11 option-2 decision; plan review A-07/A-08; recorded in AD-9 and the E014 pipeline ADR by E014-S02-003; this story cites it and does not originate it). All destinations of a release publish from ONE forge's run, all-GitHub or all-Gitea, never split. Every `PUBLISH_*` secret lives on that forge only; the other forge holds none, so a mirrored tag's run there is silent and publishes nothing. This keeps AD-10's one digest across all registries and one writer per tag (AD-8). The rule is not mechanically enforced; the checklist verifies it by comparing secret names on both forges.

For 0.3.0 the publishing forge is **GitHub**. An all-Gitea run is an equally valid topology and can publish every destination (maintainer decision 2026-10-11, option 2; CI spine AD-9, AD-13): Gitea, which ignores `environment:`, then holds the PyPI, TestPyPI, GHCR and Docker Hub tokens as repository-level secrets alongside its own. That topology requires the mitigations in the checklist's "Gitea topology" item: protected `main` and `v*` tags with pushes and tag creation limited to trusted accounts, project-scoped tokens, and rotation of every token after any untrusted push. The residual risk (a trusted account's branch workflow on Gitea can read the tokens) is accepted. Either way each destination's secrets live on exactly one forge. ADR-0039's earlier "Gitea never holds non-Gitea tokens" is amended by E014-S02-003.

## Business acceptance criteria

### Outcome

Users can install 0.3.0 from PyPI or the Gitea index, and pull one identical multi-arch image as `0.3.0`, `0.3` or `latest` from GHCR, Docker Hub or Gitea. The forge release carries the generated notes and the exact wheel and sdist. The maintainer cut the release from one forge, with all destinations published by that one forge's run, after verifying forge hygiene and that no other forge holds a publishing secret, and has recorded proof that every destination of the pipeline works live.

### Error and edge case handling

- **A publish job fails mid-run**, for example because a token is wrong:
  - fix the secret, then re-run the failed jobs;
  - uploads skip existing files (PyPI `--skip-existing`, the Gitea files check, AD-11);
  - image tags are re-pointed to the re-run's digest (ADR-0036 §5);
  - the release is updated in place (`allow-updates: true`);
  - never re-push the tag.
- **A destination warning appears for a target destination.** It is partially configured; the warning names the missing item and where to set it (GitHub `release` environment). Set it, then re-run the run's jobs. The flags are evaluated per run. Do not announce until the run shows zero warnings.
- **A target destination is silent (no enabled line, no warning).** None of its inputs is set on GitHub. Set them in the `release` environment and re-run.
- **The release run is cancelled while pending** (AD-14 as corrected by E014-S02-006). Re-run it.
- **A 429 from ghcr.io in `build` or `publish-image`.** Re-run (E014-S02-006).
- **The digests differ across registries.** That breaks AD-10. Stop: do not announce. Re-run `publish-image`, which re-points all three registries to one digest, then re-verify.
- **The PyPI project name is not yet registered, or the token is project-scoped to a missing project.** The first upload needs an account-scoped token. Afterwards, replace it with a project-scoped token and record the rotation.
- **A GHCR package is created private on first push.** The maintainer sets it public and links it to the repository, then the anonymous pull is re-run.
- **The mirror runs `release.yaml` on Gitea.** With no `PUBLISH_*` secrets there, it is silent and publishes nothing. If Gitea is found to hold a `PUBLISH_*` secret, the run would re-point the same image tags to a different digest or race on the same upload: stop, do not announce, delete the secret from Gitea, re-run `publish-image` on GitHub so all tags point to one digest, and re-verify AC 8.
- **The release commit differs from the one E014-S02-005 verified.** Re-run E014-S02-005's integration rows at the new commit before tagging.

### Security considerations

Before any secret is added:
- **F-01.** The legacy repository-level `DOCKERHUB_TOKEN`/`DOCKERHUB_USERNAME` are deleted and the old Docker Hub token is revoked.
- **F-02 (already applied, verify only).** Repository Actions settings are `default_workflow_permissions: read` and `can_approve_pull_request_reviews: false`, so a branch workflow cannot approve its own PR.
- **PRD #19 (PRD review F-06).** Secret scanning and push protection are enabled on the GitHub repository, verified with `gh api repos/{owner}/{repo} --jq .security_and_analysis`; if not enabled and the maintainer chooses not to enable them now, that is filed with `append-issue`.

Token scopes are least privilege:
- **PyPI:** project-scoped after the first upload.
- **GHCR:** a token with `write:packages` only. The maintainer confirms the minimal token type GHCR accepts at creation time.
- **Docker Hub:** an access token with Read & Write, not Delete.
- **Gitea:** `write:package` only, issued from a bot user or organisation that owns only this project's packages (ADR-0039 §6). Stored in the GitHub `release` environment for 0.3.0.
- **`PUBLISH_RELEASE_TOKEN`:** a fine-grained GitHub token on this repository only, with Contents: read/write and whatever read scopes the changelog builder needs (confirm against `LiquidLogicLabs/git-action-release-changelog-builder@v3`'s README at creation time).

Other controls:
- On GitHub, secrets live only in the `release` environment (Tag `v*` policy), never at repository level (ADR-0039, AD-13). With GitHub as the publishing forge, Gitea holds no `PUBLISH_*` secret for this release. If the maintainer chooses Gitea instead, the Gitea-topology checklist item applies and GitHub holds none.
- One release run per tag: every destination's secret is on the publishing forge only, verified by name comparison before tagging (AD-9 as amended; not mechanically enforced).
- The `release-tags` and `main` rulesets are active before tagging (ADR-0038/0039 checklist).
- Read-only Gitea API calls use a read token from the environment, sent on stdin (`curl -H @-`), never on argv.
