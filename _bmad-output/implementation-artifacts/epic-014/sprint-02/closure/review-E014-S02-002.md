# E014-S02-002 code review: destination gating (token AND every variable), warn-and-skip

Reviewer role: bmad-code-review (read-only). Scope: this story's hunks only (job-level
`PUBLISH_*`/`ANY_*` flags and image names, the five "Destination configuration" steps, the
"Registry configuration guard" removal, the `PUBLISH_GITEA_PYPI` rename, the header comments,
the `workflows-if-no-secrets-vars` hook, and the doc edits listed in the dispatch). The
hunks from E014-S02-001 and E014-S02-006 were not reviewed.

## What was checked and found correct (no finding)

- **The flag pairs match the Context table.** Every `PUBLISH_*` flag, `ANY_*` flag,
  `PUBLISH_IMAGE` and the three `*_IMAGE` names in `dev.yaml` (lines 38-42 and 242-252) and
  `release.yaml` (lines 90-94, 292-302 and 499-500) is exactly the Context-table conjunction
  or disjunction. `ANY_GITEA_SHARED` is disjoint from `ANY_GITEA_PYPI` and from `ANY_GITEA`,
  so one Gitea input set can never produce two warnings. The job `env` keys match the
  Interface-contracts table.
- **`if:` conditions.** Every publishing step tests one flag. `grep` found no `if:` that
  tests `secrets.` or `vars.`. The only other `if:` is `validate-tag` at `release.yaml:43`,
  which is not a publishing step.
- **The bash under `-e -o pipefail` behaves as intended.**
  - `has` and `(( ${#found[@]} ))` are called only as `if` conditions, so their non-zero
    returns do not trip `-e`.
  - Empty `|` fields split correctly with `IFS='|'`. The trailing `|` and the extra newline
    from `<<<` are absorbed by `[ -n "$dest" ] || continue`.
  - The script's last command is an `if` whose result is 0, so the step exits 0 in every
    configuration state.
  - The act logs for rows (c), (d), (e) and 12 show well-formed lines with no stray `|`.
- **No injection or secret leak.** Every printed token comes from literal step `env`:
  destination names, input names, `JOB`, `ENVIRONMENT` and the hint text. No variable value
  and no secret value is interpolated; only `HAS_*` booleans and flag strings are read. The
  messages contain no `%`, CR/LF or `::`.
- **Noise bound.** A dev run can produce at most: Gitea index + Gitea shared + legacy from
  `publish-package`, and GHCR, Gitea and Docker Hub from `publish-image`. A release run adds
  `Forge release`, which is single-input and never warns. The legacy warning is produced
  once, by `publish-package` only.
- **AC 7 and the Docker Hub default.** `PUBLISH_GITEA` requires `PUBLISH_GITEA_REGISTRY`.
  The guard used to prevent the Gitea login from defaulting to Docker Hub; the conjunction
  now gives that same protection.
- **Existing-library check.** The step is the single reporting loop the story justified,
  plus the maintainer-requested legacy loop. No action or platform feature does
  presence-based reporting, so nothing here duplicates a maintained capability.
- **Deletion check: the guard step and the guard paragraphs.** The guard had two jobs.
  - Fail-fast on a half-configured registry: dropped on purpose (maintainer decision
    2026-10-10). The walkthrough checklist now covers it (`docs/ci/pipeline-walkthrough.md:258`).
  - Never log in to Gitea with an empty registry: re-established by the conjunction.

  The deleted "release halts loudly" and "neither can be enabled without the other" text
  describes behaviour this story intentionally replaces. No unintended loss was found.

## Findings

### F-01 — MEDIUM — kind: edge — Following the documented setup makes a one-workflow destination warn on every run of the other workflow, and the warning's own fixes are wrong

- **Location:**
  - `.github/workflows/dev.yaml:244-248` (`ANY_GHCR`, `ANY_GITEA`, `ANY_DOCKERHUB`) and
    `dev.yaml:40` (`ANY_GITEA_PYPI`); the same lines in `release.yaml:292-298` and `:92`
  - Warning text: `dev.yaml:87,97`
  - The convention it conflicts with: `docs/ci/pipeline-walkthrough.md:131-135`
- **Trigger:**
  - On GitHub, the walkthrough says `PUBLISH_*` secrets go in the `dev`/`release`
    environment and `PUBLISH_*` variables "stay at repository level".
  - A maintainer or fork wants images on Docker Hub for releases only. They set
    `PUBLISH_DOCKERHUB_TOKEN` in the `release` environment and the two Docker Hub variables
    at repository level. Before this change, that was a silent, valid setup.
- **Evidence:**
  - In every `dev.yaml` run, `ANY_DOCKERHUB` is true (the repository variables are visible
    to the `dev` environment job) and `PUBLISH_DOCKERHUB` is false (no token in `dev`).
  - So every push to `main` emits `Docker Hub partially configured, skipped: missing
    secrets.PUBLISH_DOCKERHUB_TOKEN`. The same happens for GHCR, the Gitea registry and the
    Gitea index, and the other way round for a dev-only destination: that one warns on every
    release run and breaks the "zero destination warnings" release checklist.
  - Both remedies the warning offers are wrong for this case:
    - "Set them as dev environment secrets/variables" would turn on dev publishing that was
      never wanted.
    - "or unset vars.PUBLISH_DOCKERHUB_USERNAME, vars.PUBLISH_DOCKERHUB_IMAGE" would break
      the release.
  - The only silencing fix is to move the variables into the `release` environment, which
    contradicts the walkthrough.
  - Notes deviation 4 noticed the wording mismatch but not this effect. The maintainer
    requirement asks for warnings that are "useful and actionable and not overly noisy".
- **Recommended fix:** pick one and make the docs match it.
  - (a) Document that a destination used by only one of the two workflows must have its
    variables in that workflow's environment, not at repository level. Change the
    walkthrough line and the warning's GitHub hint to say so: "Set secrets in the `<env>`
    environment; set variables in the `<env>` environment if the destination is
    `<env>`-only, otherwise at repository level".
  - (b) Judge GitHub intent by the token alone for env-scoped destinations. This changes
    the Context table and would need a maintainer decision.

  At minimum, record the trade-off in the E014 pipeline ADR that S02-003 writes.

### F-02 — MEDIUM — kind: claim — The amendment text says the hook enforces a rule it does not check, and the hook's stated coverage limit omits real bypasses

- **Location:**
  - `.pre-commit-config.yaml:85-92` (hook and comment)
  - `notes-E014-S02-002.md:203-208` (Conventions amendment, copied verbatim into the spine
    by S02-003)
  - `docs/ci/pipeline-walkthrough.md` §"How 'publish if the token is set' is written"
    (last sentence)
- **Trigger:** an edit adds either of these:
  - `if: env.PUBLISH_GHCR == 'true' && env.PUBLISH_DOCKERHUB == 'true'` (two flags), or
  - `if: ${{ vars['PUBLISH_GHCR_IMAGE'] != '' }}` (index syntax).
- **Evidence:**
  - The amendment says: "Every step `if:` tests exactly one job-env flag and never
    `secrets.`/`vars.` directly (enforced by the `workflows-if-no-secrets-vars` pre-commit
    hook; a multi-line `if: >-` is checked on its first line only)".
  - The hook regex `^\s*(?:-\s+)?if:.*\b(secrets|vars)\.` checks only the second half. A
    probe of the regex (python `re`) returned **False** for:
    - `if: ${{ format('{0}', vars['X']) }}`
    - `"if": vars.X`
    - `if: env.A == 'true' && env.B == 'true'`
  - The hook comment names only the multi-line limit. Global rule 3 forbids prose that
    overstates a check's coverage.
- **Recommended fix:**
  - Reword the amendment so the hook is said to enforce only "never `secrets.`/`vars.`
    (dot form)". State that "exactly one flag" is held by review, or add a second pygrep,
    e.g. `^\s*(?:-\s+)?if:.*env\.\w+.*env\.\w+` as a heuristic with its own stated limits.
  - Extend the regex to `\b(secrets|vars)\s*[.\[]`, and list the quoted-key and folded-value
    limits in the hook comment.
  - Plant a violation against the hook itself, not only against the row-3 grep wrapper
    (notes deviation 3 tested only the wrapper).

### F-03 — MEDIUM — kind: testability — A wrong name in `DESTINATIONS`/`LEGACY` silently drops a report or mislabels an input, and nothing checks the names against the flags

- **Location:**
  - `dev.yaml:85,90,92,103` (`has`, `${!publish}`, `${!any}`, legacy `has`)
  - The same body in all five copies (`dev.yaml:47-107`, `:257-301`; `release.yaml:99-159`,
    `:307-351`, `:505-538`)
- **Trigger:** an edit to the list, for example:
  - renaming a flag in job `env`, or a typo in a `DESTINATIONS` flag field
    (`PUBLISH_GHCR` → `PUBLISH_GHRC`);
  - adding a `LEGACY` or `DESTINATIONS` input without its `HAS_*` boolean;
  - editing one of the two `LEGACY` lists and not the other.
- **Evidence:**
  - An undefined flag expands `${!publish}`/`${!any}` to `""`. The destination then
    classifies as unconfigured and prints nothing, even when it is publishing or partially
    configured. That is a false quiet in the very step the S02-005/S02-007 release evidence
    reads.
  - A missing `HAS_*` makes `has` (`${!v:-}`) return false. A set input is then listed as
    "missing", or a set legacy secret is never reported.
  - No hook, test or runtime assertion ties the list names to the job-env keys or to the
    `HAS_*` keys. The story's own answer ("the act matrix rows prove each pair") covers only
    the inputs at the time of the run (see F-04).
- **Recommended fix:** make the step fail loudly on a programming error, as distinct from a
  configuration state.
  - Before classifying, check that each named flag and each derived `HAS_*` variable is
    defined, e.g. `[ -n "${!publish+x}" ] || { echo "::error title=$JOB::unknown flag
    $publish"; exit 1; }`, and the same for `HAS_*` in `has`.
  - This keeps "exit 0 for every configuration" and turns list drift into a red run.
  - Note it in the S02-003 duplication ADR, because it affects all five copies.

### F-04 — LOW — kind: claim — "The act matrix rows prove each pair" is contradicted by the recorded matrix

- **Location:** story `E014-S02-002.md:189` (Error and edge handling); notes Verification

- **Trigger:** later reliance on the claim, for example by S02-003's ADR text, or by a
  reviewer accepting a flag edit as covered.
- **Evidence:**
  - The recorded rows exercise:
    - GHCR partial (d) and Docker Hub partial (c);
    - Gitea registry enabled (b) and partial (12);
    - Gitea shared (e);
    - the all-unset case (a).
  - Never exercised:
    - Gitea package index: not partial, not enabled;
    - GHCR and Docker Hub: never enabled;
    - TestPyPI, PyPI and Forge release: never enabled.
  - So `PUBLISH_GITEA_PYPI`/`ANY_GITEA_PYPI`, and the `enabled` lines of six of the eight
    reported rows, rest on reading alone. They read correct today: this review checked every
    pair against the Context table.
- **Recommended fix:** reword the claim to "the act matrix exercises the GHCR, Docker Hub,
  Gitea registry and Gitea shared pairs; the others are verified by reading". Or add one act
  row with `PUBLISH_GITEA_PYPI_URL` set and no token, which also gives the Gitea-index
  partial case some evidence.

### F-05 — LOW — kind: edge — For a Gitea destination, the "unset … to disable it" advice includes the shared token and username, which also disables the other Gitea destination

- **Location:**
  - `dev.yaml:97` / `release.yaml:149` (the `present` list), for the `Gitea container
    registry` and `Gitea package index` rows
  - Notes deviation 5
- **Trigger:**
  - The Gitea index is enabled (token, username and `PYPI_URL` set).
  - `PUBLISH_GITEA_REGISTRY` is set without `PUBLISH_GITEA_IMAGE`.
- **Evidence:**
  - The recorded row-12 warning ends: "or unset secrets.PUBLISH_GITEA_TOKEN,
    vars.PUBLISH_GITEA_USERNAME, vars.PUBLISH_GITEA_REGISTRY to disable it."
  - Following that advice turns off the working Gitea package index, which defeats AC 7
    (independent Gitea destinations).
  - AC 5 says "unset <the set items>" literally, so the implementation is per spec. The
    defect is in the guidance it produces, against the maintainer's "actionable" requirement.
- **Recommended fix:** add a sixth field to the `DESTINATIONS` row, or reuse the intent
  inputs, listing the "disable by unsetting" items. For Gitea rows these are the
  destination's own variables only (`vars.PUBLISH_GITEA_REGISTRY`/`IMAGE`;
  `vars.PUBLISH_GITEA_PYPI_URL`). Take the AC 5 wording change to S02-003.

### F-06 — LOW — kind: edge — The "Gitea shared inputs" warning tells the maintainer to set all of the index and registry variables, then says they are alternatives

- **Location:** the `dev.yaml:55` / `release.yaml:107` row (`required inputs` lists all
  five), and the warning at `dev.yaml:97`.
- **Trigger:** `PUBLISH_GITEA_TOKEN` set alone (row e).
- **Evidence:**
  - The recorded line reads "missing vars.PUBLISH_GITEA_USERNAME, vars.PUBLISH_GITEA_PYPI_URL,
    vars.PUBLISH_GITEA_REGISTRY, vars.PUBLISH_GITEA_IMAGE. Set them as …".
  - The hint then says PYPI_URL **or** REGISTRY + IMAGE. The first sentence asks for all
    four, which would turn on both Gitea destinations.
  - "partially configured, skipped" is also not quite true of "Gitea shared inputs", which
    is not a destination.
- **Recommended fix:** for this row, list only the shared inputs as required
  (`secrets.PUBLISH_GITEA_TOKEN vars.PUBLISH_GITEA_USERNAME`) and let the hint name the
  per-destination options. Wording such as "Gitea token/username set but no Gitea
  destination chosen" would be clearer.

### F-07 — LOW — kind: claim — The walkthrough's state table says Gitea partials occur in cases where the code is silent

- **Location:** `docs/ci/pipeline-walkthrough.md:86-87`.
- **Trigger:** a reader sets `PUBLISH_GITEA_TOKEN` and `PUBLISH_GITEA_USERNAME` with
  `PUBLISH_GITEA_REGISTRY`/`IMAGE`, expecting an index warning.
- **Evidence:**
  - The table says "partial | some, not all, of its inputs are set", and unconfigured is
    "none of its own inputs is set".
  - For the Gitea index, token and username are among its inputs, yet with `PYPI_URL`
    unset it is silent by design: `ANY_GITEA_PYPI` tests only `PYPI_URL`. The next
    paragraph explains this, but the table contradicts it.
- **Recommended fix:** say "partial: any of its *intent* inputs is set but not all of its
  required inputs (for Gitea, the destination's own variables; see below)". Or add an
  "Intent inputs" column, matching the AD-9 table change routed to S02-003.

### F-08 — LOW — kind: edge — The legacy detection covers secrets only; legacy variables are not reported

- **Location:** the `LEGACY` lists at `dev.yaml:57-67` / `release.yaml:109-119`; notes
  deviation 1.
- **Trigger:** a fork or mirror still has a pre-0.3.0 variable such as `DOCKER_IMAGENAME`
  or `PACKAGE_REPO` set and has not set the `PUBLISH_*` replacement.
- **Evidence:**
  - The maintainer requirement is "detect legacy settings (e.g. legacy DOCKERHUB_* secret
    names) and warn with a recommendation".
  - Variables were excluded because their mapping is "ambiguous". The step already supports
    an entry with no replacement (`secrets.PYPI_USERNAME|`), so ambiguity does not block a
    "no longer read" report.
  - The walkthrough says that unlisted names are not detected, but does not say that
    variables are excluded as a class.
- **Recommended fix:** add the historical variable names as `vars.NAME|` entries (or
  `vars.NAME|<best replacement>`) with `HAS_*` booleans. Or state "legacy variables are not
  detected" in the walkthrough paragraph and the AD-9 amendment.
