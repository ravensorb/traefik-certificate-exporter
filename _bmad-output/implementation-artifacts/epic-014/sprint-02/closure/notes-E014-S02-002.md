## Deviations and decisions (each recorded once here)

1. **Legacy-settings warning (maintainer requirement in the dispatch, not in the story
   text).** `publish-package` (both workflows) also reports, in **one** warning per run, any
   legacy secret the pre-0.3.0 workflows read and nothing reads now, with its `PUBLISH_*`
   replacement:
   `::warning title=publish-package::Legacy settings found, no longer read: secrets.DOCKERHUB_TOKEN (now secrets.PUBLISH_DOCKERHUB_TOKEN), … Move each value to its replacement (docs/ci/pipeline-walkthrough.md, "Where things are published"), then delete the legacy name.`
   The list (10 secrets) is hand-kept: it was derived from
   `git log --all -p -- '.github/workflows/*' | grep -oE 'secrets\.[A-Z_]+'`, and the
   replacement for each from the step that consumed it in history: `DOCKERHUB_TOKEN`,
   `DOCKERHUB_USERNAME`, `PYPI_TOKEN`, `PYPI_USERNAME` (no replacement: PyPI uses
   `__token__`), `FORGE_PACKAGE_TOKEN`, `REGISTRY_USERNAME`, `REGISTRY_PASSWORD`,
   `CI_CA_CERTIFICATE`, `GITEA_PACKAGE_INDEX_CA_CERTIFICATE`,
   `GITEA_FORGE_API_CA_CERTIFICATE`. Not included: legacy *variables*
   (`DOCKER_IMAGENAME`, `PACKAGE_REPO`, …) whose mapping to one `PUBLISH_*` name is
   ambiguous, and `GITHUB_USERNAME` (GitHub and Gitea refuse `GITHUB_`-prefixed secret
   names, so it cannot exist). Coverage limit (global rule 4): a legacy name not on the list
   is not detected; the walkthrough says so. It is reported by `publish-package` only, so a
   run carries at most one legacy warning. Presence only (`HAS_<NAME>` booleans), no value.
   The text does not contain "partially configured", so the story's `warns` filter is not
   affected. Proven by the legacy probe below.
2. **Row 7's event payload lacks `repository.default_branch`.** As written
   (`{"ref":"refs/tags/v9.9.9"}`) `validate-tag` refuses:
   `refusing to release tag v9.9.9: the event payload names no default branch` (exit 1,
   act log `/tmp/e014-s02-002-rowa-rel.log` first attempt). That is the AD-12 guard working,
   not this story's change, so that probe was **not** recorded with `add-test-run` (it cannot
   exit 0 on correct code). The recorded row 7 uses
   `{"ref":"refs/tags/v9.9.9","repository":{"default_branch":"main"}}`. E014-S02-005's act
   dry run needs the same payload.
3. **Grep rows recorded in exit-0-on-correct form.** Rows 1 and 3 are "no output" greps
   (grep exits 1 on correct code); row 4 is a count. They were recorded as
   `! grep -q …`, `! grep -nE …` and `test "$(grep -c …)" = N`. Each wrapper was tested
   against a planted copy (a guard step name, an `if: ${{ vars.X != '' }}`, a third
   Destination configuration step in `dev.yaml`): all three exited 1 on the plant. Row 13
   was recorded as the conjunction of its four greps (`… && ! grep -qi 'configuration guard' …`).
4. **"Set them as `<env>` environment secrets/variables (GitHub)"** is the AC 5 wording,
   kept verbatim. Review F-01 showed the consequence of the old walkthrough rule "variables
   stay at repository level": a destination meant for one workflow only (e.g. Docker Hub
   for releases) would warn on every run of the other workflow. Resolved by documentation
   (review option a): the walkthrough (§Where things are published, §Environments) and
   `docs/operational.md` now say a one-workflow destination keeps its variables in that
   workflow's environment. The gating rule is unchanged. **Trade-off for the E014 pipeline
   ADR (S02-003):** on GitHub, intent is judged by variables as well as tokens, so
   variable placement is part of the configuration; option (b) (token-only intent on
   GitHub) was not taken because it changes the Context table.
5. **"or unset <the set items>"** lists the set items among the destination's **own**
   (intent) inputs, a fifth list field `<own inputs>` = the Context table's intent-inputs
   column (single-input destinations: the token; Gitea shared inputs: token and username).
   So the Gitea-registry warning advises unsetting `vars.PUBLISH_GITEA_REGISTRY`, never the
   shared token that also feeds the index (review F-05). AC 5's wording is read as "the set
   items that make it partial"; S02-003 should carry that reading into AD-9.
6. **Out of scope, routed to S02-003:** `docs/architecture.md:180` still says "Each
   destination is enabled only by its own `PUBLISH_*` secret (AD-9)"; the story's non-goals
   forbid editing it here. `docs/ci/gitea-certification.md:303` ("every destination whose
   Gitea secret is set still publishes") is similarly stale; not in this story's file list.

## Spine/ADR amendments for S02-003

Exact text for the CI/CD spine
(`architecture-ci-cd-pipeline-2026-10-08/ARCHITECTURE-SPINE.md`) and the E014 pipeline ADR.

- **AD-9 (rule).** "A destination is enabled exactly when its token secret **and** every
  variable it requires are set and non-empty (`!= ''`; an unset variable counts as missing,
  whitespace is not trimmed). Each publish job computes, in job `env`, one `PUBLISH_<DEST>`
  flag per destination it owns as the conjunction of those presence tests, and beside each
  multi-input destination an `ANY_<DEST>` intent flag, the disjunction of its intent inputs.
  The first step of every publish job, `Destination configuration`, has no `if:` and reads
  only these flags: `enabled` (`PUBLISH_<DEST>` true) prints one plain `<Destination>
  enabled` line; `partial` (`ANY_<DEST>` true, `PUBLISH_<DEST>` false) prints exactly one
  `::warning title=<job>::` naming each missing `secrets.NAME` / `vars.NAME`, where to set
  it (GitHub environment `<env>`; Gitea repository Actions secrets/variables) and how to
  disable the destination; `unconfigured` prints nothing. The private CA is not a
  destination and never warns. The step receives presence booleans only, never a secret
  value. The `unset … to disable it` advice names only the destination's own (intent)
  inputs that are set. On GitHub a destination published by one workflow only keeps its
  variables in that workflow's environment (repository-level variables are visible to both
  environments). `publish-package` also reports, in one warning per run, legacy secrets the
  pre-0.3.0 workflows read (a hand-kept list; legacy variables are not detected) with their
  `PUBLISH_*` replacements."
  AD-9 table gains two columns — **Required to enable** and **Intent inputs** — with the
  values of the story's Context table (Gitea index: token, `GITEA_USERNAME`,
  `GITEA_PYPI_URL` / intent `GITEA_PYPI_URL`; TestPyPI, PyPI, forge release: token / none;
  GHCR: token, `GHCR_USERNAME`, `GHCR_IMAGE` / all three; Gitea registry: token,
  `GITEA_USERNAME`, `GITEA_REGISTRY`, `GITEA_IMAGE` / `GITEA_REGISTRY`, `GITEA_IMAGE`;
  Docker Hub: token, `DOCKERHUB_USERNAME`, `DOCKERHUB_IMAGE` / all three; Gitea shared
  inputs: report-only row, `ANY_GITEA_SHARED` = (token or username set) and none of
  `GITEA_PYPI_URL`, `GITEA_REGISTRY`, `GITEA_IMAGE` set, reported by `publish-package`
  only). F-08 rewording: "no step is handed the ambient token for publishing".
- **AD-10.** "`PUBLISH_IMAGE` is the disjunction of the three registry conjunctions, and
  `GHCR_IMAGE` / `GITEA_IMAGE` / `DOCKERHUB_IMAGE` are `<conjunction> && vars.<IMAGE> || ''`.
  The fail-fast Registry configuration guard (E013-S01-005, BL-E013-008) is retired: a
  half-configured registry is skipped with one warning, not failed; the other registries
  still receive the one multi-arch build. Because `PUBLISH_GITEA` requires
  `PUBLISH_GITEA_REGISTRY`, the Gitea login never runs with an empty registry (which would
  default `docker/login-action` to Docker Hub)."
- **AD-11.** "The Gitea package index is enabled by `PUBLISH_GITEA_PYPI` =
  `PUBLISH_GITEA_TOKEN` and `PUBLISH_GITEA_USERNAME` and `PUBLISH_GITEA_PYPI_URL` non-empty;
  it is independent of the Gitea registry, whose intent is judged by
  `PUBLISH_GITEA_REGISTRY` / `PUBLISH_GITEA_IMAGE`."
- **AD-12 / AD-13.** "The forge release is enabled by `PUBLISH_RELEASE` =
  `secrets.PUBLISH_RELEASE_TOKEN != ''` (single input: enabled or silent, never partial).
  The `release` job's `Destination configuration` step reports `Forge release` only; its
  other steps keep per-step `PUBLISH_RELEASE` gating (CA import on `PUBLISH_CA`)."
- **AD-17 / AD-18 (step order).** "Publish-job step order: Destination configuration →
  AD-15 version guard (dev; release has the AD-12 tag/version guard) → hash verify →
  CA import → login / publish. Destination configuration is first so it reports even when
  a later step fails. Presence-only evaluation of secrets (`!= ''` in job `env` and the
  step's `HAS_*` booleans) is not a credential touch; the CA import remains the first step
  that touches a credential."
- **Conventions, "Conditionals".** "Flags are conjunctions of presence tests computed in
  job `env`; `ANY_*` intent flags are disjunctions beside them. Every step `if:` tests
  exactly one job-env flag (held by review) and never reads `secrets` or `vars` (enforced
  by the `workflows-if-no-secrets-vars` pre-commit hook, dot and index form; a multi-line
  `if: >-` is checked on its first line only). The one unconditional `Destination
  configuration` step per publish job is allowed; it holds no gating rule, and a list entry
  naming an undefined flag or input fails it with an `::error::`."
- **NFR-4 trade-off (E014 pipeline ADR).** "A partially configured destination is skipped
  with a warning and the run stays green. A release is acceptable only with zero
  partial-configuration warnings and each target destination `enabled` exactly once; this
  is a per-release checklist item in `docs/ci/pipeline-walkthrough.md` §Releasing, not
  mechanically enforced (PRD review F-05)."
- **Duplication count (duplication ADR).** "The `Destination configuration` step exists in
  5 copies (`dev.yaml` 2, `release.yaml` 3). The `run:` body is identical in all five; the
