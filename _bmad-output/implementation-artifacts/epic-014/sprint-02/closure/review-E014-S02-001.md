## Findings

### R1. HIGH. kind: security / claim. The hash verify passes a dist with an extra `.zip` sdist, and twine uploads it

- **Location:** `.github/workflows/dev.yaml` and `.github/workflows/release.yaml`, `publish-package`: the "Verify dist hashes" step, then "Upload to Gitea" (`for file in dist/*`) and "Upload to PyPI" (`twine upload ... dist/*`).
- **Problem:** The verify step counts and hashes only `dist/*.whl` and `dist/*.tar.gz`. Both upload steps take all of `dist/*`. twine treats `.zip` as an sdist: the locked twine's `twine/package.py` has `DIST_EXTENSIONS = {".whl", ".tar.gz", ".zip"}`. Suppose the `dist` artifact gains `traefik_certificate_exporter-<ver>.zip` between `build` and `publish-package`. Verify still sees one wheel and one tar.gz, both match, and the step exits 0. The Gitea step then uploads the unverified `.zip`, and so does the PyPI step if the index accepts zip sdists (not checked here).
- **Story claims this contradicts:**
  - Security: "a `dist` artifact altered between the build job and a publish job is refused."
  - Business AC: "a `dist` file altered between the build job and a publish job is refused before any credential is touched."
- **Not affected:** `publish-image` (it uses the verified `wheel-path`) and the `release` job (`artifacts: dist/*.whl,dist/*.tar.gz` with counts fixed at 1).
- **Fix (either one):**
  - In the verify step, also assert that `dist/` holds exactly two entries: `all=(dist/*); (( ${#all[@]} == 2 ))`, with dotglob for hidden files if wanted.
  - Or have both upload steps upload only the verified paths, exposed as `wheel-path` and `sdist-path` outputs of `verify`, instead of `dist/*`.

  Add a negative act run that plants an extra `.zip` in `dist/`.

### R2. MEDIUM. kind: claim. The generated `poetry.txt` header does not carry the exact regeneration command

- **Location:** `.github/requirements/poetry.txt`, lines 1-6.
- **Problem:** The header is pip-compile's default: `pip-compile --generate-hashes --output-file=.github/requirements/poetry.txt .github/requirements/poetry.in`. It has no `pipx run --python 3.14 --spec 'pip-tools==7.6.2'`. The exact command is only in `poetry.in` and `docs/developer.md`.
- **Consequence:** A maintainer who copies the command from the file pip-compile tells them to regenerate (the `.txt`) runs it under their own interpreter. Under 3.11 that reintroduces the backports-tarfile, backports-zstd, importlib-metadata and zipp entries that the recorded deviation removed, and the pip-tools version is uncontrolled.
- **Claim:** AC 4: "with this exact regeneration command recorded in the file header and in `docs/developer.md`". "The file" is the generated `poetry.txt`. The technical AC also says "Its header names the exact regeneration command".
- **Fix:** pip-tools supports this directly (existing-library check). Regenerate with `CUSTOM_COMPILE_COMMAND="pipx run --python 3.14 --spec 'pip-tools==7.6.2' pip-compile --generate-hashes --output-file .github/requirements/poetry.txt .github/requirements/poetry.in"` set in the environment. Record that env var in `poetry.in` and `docs/developer.md` as part of the command. The "autogenerated by pip-compile with Python 3.14" line, which Dependabot reads, is unaffected.

### R3. LOW. kind: claim (guard reach). `precommit-revs-frozen` misses a `rev:` written as the first key of a list item

- **Location:** `.pre-commit-config.yaml`, hook `precommit-revs-frozen`. Regex `^\s+rev:\s+(?![0-9a-f]{40}\b)`.
- **Problem:** The repo entry
  ```yaml
  - rev: v6.0.0
    repo: https://github.com/pre-commit/pre-commit-hooks
  ```
  is valid block-style YAML, and pre-commit accepts it. The line `  - rev: v6.0.0` does not match (tested with Python `re`: False), so an unfrozen tag passes. The hook comment says its coverage limit is "block-style `rev:` lines in this file only; a flow-style ... mapping is not matched". This form is block-style, so the comment overstates the coverage (global rule 3).
- **Checked:** these are correctly flagged: indented `rev: v6.0.0`, quoted `'v6.0.0'`, a value on the next line (`\s+` consumes the newline), and a 41-hex value. A frozen SHA line passes. Comment lines and the hook's own `entry:` line do not self-match.
- **Fix:** Change the regex to `^\s*(?:-\s+)?rev:\s+(?![0-9a-f]{40}\b)`, and add a `- rev: v6.0.0` plant to the hook-plant evidence.

### R4. LOW. kind: claim (guard reach). `workflows-pip-install-from-requirements` accepts a compliant prefix followed by another `-r`

- **Location:** `.pre-commit-config.yaml`, hook `workflows-pip-install-from-requirements`. The regex is verbatim from ADR-0042 item 3, so it is not a deviation from the ADR.
- **Problem:** The lookahead only requires the text after `pip install` to start with the allowed form. `python -m pip install --require-hashes -r .github/requirements/poetry.txt -r tools/other.txt` passes (tested: no match). `--require-hashes` forces hashes onto `other.txt`, but that file sits outside the `pip-audit-bootstrap` glob `^\.github/requirements/[^/]+\.txt$`. So the hook's stated purpose ("so the pip-audit-bootstrap glob above sees every package set CI bootstraps") is not fully enforced. The hook's coverage-limit comment lists `pip3 install` and `uv pip` but not this case.
- **Fix:** Pick one:
  - Tighten the regex so nothing but whitespace, end of line, `&&`, `;` or `|` may follow the `.txt`, for example `pip install(?! --require-hashes -r \.github/requirements/[^/\s]+\.txt\s*(?:$|&&|;|\|))`. Route the changed regex to ADR-0042 through E014-S02-003.
  - Or add this case to the hook's coverage-limit comment.

### R5. LOW. kind: maintainability (rule 3/4). The verify script is copied verbatim into five steps, and nothing keeps the copies identical

- **Location:** "Verify dist hashes" in `dev.yaml` (publish-package, publish-image) and `release.yaml` (publish-package, publish-image, release).
- **Problem:** There are five identical 22-line copies. A later fix to one copy (R1 is an example) can miss the others, and no check would notice. The `wheel-path` output is written in the three copies that never read it.
- **Fix:** Pick one:
  - Move the script into a local composite action, for example `.github/actions/verify-dist/action.yml`. It runs after checkout, which every job already does first, so it is ref-free (AD-6).
  - Or accept the duplication and record it, with a plant that diffs the five step bodies.

## Checks that found nothing (recorded so the scope is visible)

**Verify-step bash** (all five copies identical):
- `${output%%-*}` then `${var^^}_SHA256` gives `WHEEL_SHA256` / `SDIST_SHA256`, and `${!var}` reads the env. An unset or empty output fails the `^[0-9a-f]{64}$` test and is named.
- `printf '%s  %s\n'` with four arguments emits two correctly formatted `sha256sum -c` lines (two spaces, text mode).
- `nullglob` makes the empty case count 0 instead of a literal pattern.
- `defaults.run.shell: bash` applies `-eo pipefail`, and `sha256sum -c` is the last command in the pipeline, so a mismatch fails the step.
- The GitHub-output write happens only after the check.
