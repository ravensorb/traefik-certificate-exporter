## Findings

### MEDIUM-1 — SBOM/provenance Deferred bullet keeps a deferral reason the recorded inspection contradicts (claim; PLAUSIBLE)

- **Location:** `_bmad-output/planning-artifacts/architecture/architecture-ci-cd-pipeline-2026-10-08/ARCHITECTURE-SPINE.md` Deferred, first bullet (diff line "Inspected 2026-10-11 …"); the same content is in the CI `.memlog.md` BL-E013-035 line.
- **Issue:** The bullet still says explicit `provenance: mode=max` is deferred "because Gitea registry acceptance and `act` behaviour are unverified". The inspection it records shows something else. The Gitea registry already stores a provenance attestation per platform, and that attestation carries `internalParameters.buildConfig` and `buildkit_metadata.layers`. BuildKit documents both as fields that only max mode emits. No workflow sets a `provenance` input (`grep provenance .github/workflows/*.yaml` is empty), so build-push-action's default produced it. That default is max mode when the repository payload is not marked private.

  So the "Gitea acceptance unverified" reason no longer holds for provenance. A reader can conclude that max-mode provenance is absent when the evidence says it is present. The attestation also embeds the full `github_event_payload` in a published artifact, and nothing records that. Separately, "built by an E013-S02-001 `act` run" is not shown by the inspection output in the notes, which shows only VERSION, REVISION and the key names.
- **Fix:** Reword the bullet to say what was observed. The default attestation already includes the max-mode fields (`buildConfig`, layer metadata, event payload), and the Gitea registry accepted it. What stays deferred is `sbom: true` and making the provenance mode explicit. Keep "unverified" only for the SBOM and `act` behaviour. Either cite where the E013-S02-001 attribution comes from (run id or log), or drop it. Add a note to BL-E014-073 that the event payload is published inside the attestation, so its disclosure is weighed when the item is evaluated.

### LOW-1 — "a mirrored tag run there is silent" is true only if the other forge also holds no `PUBLISH_*` variables

- **Location:** `docs/adr/0039-publish-credentials-in-forge-environments.md`, amendment "### Consequences", first bullet (repeats CI spine AD-9 line 188).
- **Issue:** The `ANY_*` intent flags are computed from variables alone (`dev.yaml:40-41`: `ANY_GITEA_PYPI: vars.PUBLISH_GITEA_PYPI_URL != ''`; `ANY_GITEA_SHARED` also fires on `vars.PUBLISH_GITEA_USERNAME`). A non-publishing forge that keeps any `PUBLISH_*` variable, with no secret, gets a "partially configured, skipped" warning on every mirrored run. That run is not silent. The rule as written ("holds no `PUBLISH_*` secret") allows those variables.
- **Fix:** Say "holds no `PUBLISH_*` secret or variable" in the ADR-0039 amendment. Apply the same correction to CI spine AD-9, and add one memlog line.

### LOW-2 — "Clear one of the required variables" omits the per-run warning, so a release then fails the zero-warning rule

- **Location:** `docs/operational.md` "## If a publication credential is compromised", step 2 (the new "or clear one of the destination's required `PUBLISH_*` variables" sentence).
- **Issue:** If a variable is cleared while the token secret stays, the destination is partially configured. Every run then emits a `::warning::`, and ADR-0046 item 3 makes any such warning a release blocker. The text says only "the destination switches off and runs keep succeeding".
- **Fix:** Add: "clearing a variable while the secret remains reports the destination as partially configured on every run; delete the secret too, or clear every variable it needs, before the next release."

### LOW-4 — ADR-0046 item 6 says the hook enforces the `# frozen:` comment; it enforces only the 40-hex SHA

- **Location:** `docs/adr/0046-e014-pipeline-amendments.md:65-67`
- **Issue:** "pinned to a commit SHA with a `# frozen: vX.Y.Z` comment. The `precommit-revs-frozen` pygrep hook enforces it". The hook's entry is `^\s*(?:-\s+)?rev:\s+(?![0-9a-f]{40}\b)` (`.pre-commit-config.yaml:119`). A SHA with no `# frozen:` comment passes.
- **Fix:** "The `precommit-revs-frozen` hook enforces the 40-hex SHA (block-style `rev:` lines only; a flow-style mapping is not matched); the `# frozen:` comment is written by `autoupdate --freeze` and not checked."
