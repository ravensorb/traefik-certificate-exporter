### R1. MEDIUM. kind: correctness / claim. The documented recovery for a cancelled pending release moves `latest` (and `X.Y`) backwards

- **Location:** `.github/workflows/release.yaml` lines 12-15 (concurrency comment) and `docs/ci/pipeline-walkthrough.md` §"Releasing", the new "At most one release runs and one waits" bullet.
- **Problem:** Take tags v0.3.1 (running), v0.3.2 (waiting) and v0.3.3 (pushed, which cancels v0.3.2). v0.3.3 starts when v0.3.1 finishes. The note says to re-run v0.3.2 "once the running one finishes". That re-run queues behind v0.3.3, or runs after it. Either way it finishes last and re-points `latest` and `0.3` to the 0.3.2 digest. That is exactly what the walkthrough means by "image tags are re-pointed to the digest this run built" (ADR-0036 §5). Nothing in `publish-image` or `release` checks that the version is the newest. The note's claim that "the re-run is safe for the reasons in the bullet above" therefore does not hold for the case the note itself describes. AD-14 exists to prevent "two releases racing on `latest`". The documented action produces the same end state, only in sequence instead of in parallel.
- **Claim:** AC 3 asks only that the comment and the walkthrough say "must be re-run". The wording satisfies the AC, but it guides the operator into an AD-14 violation.
- **Fix:** Make the note conditional. Re-run the cancelled release only if no newer tag has released since. If one has, either leave the cancelled version unpublished (cut the next patch) or re-run with image publishing disabled. Put the same caveat in the `release.yaml` comment. Hand the AD-14 wording ("which must then be re-run") to E014-S02-003 for the same qualification.

### R3. MEDIUM. kind: claim (guard reach). `workflows-no-auth-header-argv` misses common literal forms its coverage comment does not exclude

- **Location:** `.pre-commit-config.yaml`, hook `workflows-no-auth-header-argv`, regex `(?i)(-H|--header)[=\s]*["']?authorization:`.
- **Problem:** pygrep matches one line at a time. I tested these with Python `re`. Each is a literal header flag, each puts the token on argv, and none is flagged:
  - A flag whose value is on the next line after a `\` continuation: `curl -H \` followed by `"Authorization: token $T"`. Continuations are common in long `run: |` curls. A continuation that keeps `-H "Authorization: …"` together on one line is still caught.
  - ANSI-C quoting: `-H $'Authorization: …'`.
  - Leading space inside the quotes: `-H " Authorization: …"`.

  The comment states the limit as "literal header flags only -- a header assembled in a variable, or passed through curl's `--config`/`-K` file, is not matched". The forms above are literal header flags, so the comment overstates the coverage (global rule 3). F-09 and AC 2 are titled "No credential on argv", but argv credentials that are not an Authorization header are also unmatched and unstated: `curl -u user:$T`, `--user`, `--oauth2-bearer "$T"`. None of these exists in the tree today; I grepped `.github/`.
- **Fix:** Widen the scope, or state the limit honestly. Two options:
  - Extend the comment's coverage-limit sentence (and the AD-5/AD-11 amendment text for S02-003) to "a flag whose value starts on the next line, `$'…'` quoting, and other credential flags (`-u`/`--user`/`--oauth2-bearer`) are not matched".
  - Or add those flags as alternatives, e.g. `(?i)(?:(?:-H|--header)[=\s]*\$?["']?\s*authorization:|\s(?:-u|--user|--oauth2-bearer)[=\s])`, and add plants for each.

### R4. LOW. kind: claim. `workflows-lll-major-tag` accepts `@V6` because `(?i)` also applies to the `v`

- **Location:** `.pre-commit-config.yaml`, hook `workflows-lll-major-tag`.
- **Problem:** AC 1 asks for a ref that is "exactly `v<digits>`", and for the owner match to be case-insensitive. The leading `(?i)` also makes `@v\d+` match `@V6`. `@v06` passes too. Tested: both pass, while `@main`, `@v6.2.1`, a quoted lower-case owner, `@v6#c`, a mismatched quote, a SHA and a missing ref are all correctly flagged. A `@V6` ref does not resolve on GitHub, so the consequence is a confusing run failure rather than a silent mutable pin. That is why this is LOW.
- **Fix:** Scope the case-insensitivity: `…@(?-i:v)[1-9]\d*\1…`, or move `(?i)` to cover only the owner: `uses:\s*(["']?)(?i:liquidlogiclabs)/…`. Add a `@V6` plant.
- **Also not matched, but stated in the comment:** flow-style `{uses: …}`. Not stated: a quoted key (`"uses": …`) and a folded or next-line value (`uses: >-`). Add these to the coverage-limit sentence.

### R5. LOW. kind: claim (guard reach). `workflows-major-tag-gated` misses a prefixed bare-major pattern

- **Location:** `.pre-commit-config.yaml`, hook `workflows-major-tag-gated`, regex `^(?!.*\benable=).*pattern=\{\{\s*major\s*\}\}(?![.\w])`.
- **Problem:** `type=semver,pattern=v{{major}}` writes a bare-major tag (`:v0`) and is not flagged (tested). The metadata action supports such prefixes. The hook's stated purpose is "no bare `:0` tag is written while major is 0", and its coverage comment states only the presence-not-value limit. Correctly handled (tested): `{{major}}.{{minor}}` is not flagged, `{{ major }}`, `pattern=` after `value=`, and `{{major}}-…` are flagged, and the real `release.yaml:345` passes.
- **Fix:** Allow a literal prefix: `pattern=[^,{]*\{\{\s*major\s*\}\}(?![.\w])`. Or add "a prefixed pattern such as `v{{major}}` is not matched" to the coverage limit.
