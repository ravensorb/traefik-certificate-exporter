# Redact Secrets Held as Configuration Values

As a maintainer,
I want credentials that live as configuration *values* redacted wherever settings are logged,
So that turning on debug logging cannot leak them — before a feature is added whose whole
configuration is credentials.

Ships independently of 10.2 and is worth landing on its own: the defect it closes exists today.

**Acceptance Criteria:**

**Given** `_SECRET_FIELD_PATTERN` matches on key *name*, so a credential held as a value inside a
list is unreachable by it whatever the key is called
**When** redaction is implemented
**Then** it uses `confuse`'s own path-based facility — marking a config path
`.redact = True` and dumping with `redact=True`, verified to emit `REDACTED` — rather than a
second redactor written beside a library one that already works (global rule 1)

**Given** secret-bearing configuration paths
**When** the guard for this is written
**Then** the paths are declared in **one registry** and both the redaction and its guard derive
from it. A guard that names sinks or fields by hand is this repository's signature defect: the
rule is right and the set is hand-written

**Given** a planted credential in a config value, a config file, an environment variable and a
command-line flag
**When** a full `loadFromFile` runs at DEBUG
**Then** it appears in **no** log record — asserted over everything captured, not over two named
functions. `_dump_config()` has no test at all today

**Given** the plant must attack the scope and not only the rule
**When** the guard is proven
**Then** a **newly added** secret-bearing setting is covered without editing the guard

**Given** `BL-E001-005` currently tells an implementer to "consider expanding the pattern list"
**When** this story lands
**Then** the tracked record is re-scoped in the same change — prose and machine-readable record
disagreeing is how the superseded fix gets implemented anyway

## Decision record
