## 1. The bounded shutdown join does not bound shutdown — non-daemon Timer threads still hold the process at interpreter exit

**Severity:** Medium
**Kind:** claim
**File:** `src/traefik_certificate_exporter/libs/certificate_exporter.py:561-566`
(`AcmeCertificateFileHandler.cancel`), `docs/operational.md` (Shutdown section),
`src/traefik_certificate_exporter/libs/certificate_exporter.py:446` (comment)

**Claim contradicted.** `docs/operational.md` states: *"If a drain is already running,
shutdown waits a bounded 5s for it and then exits regardless rather than holding the
process open past the container runtime's grace period."* The module comment at line 446
makes the same claim: *"an unbounded join would hand the container runtime's grace period
… the job of killing us."*

**Problem.** `cancel()`'s `timer.join(SHUTDOWN_JOIN_TIMEOUT_SECONDS)` bounds only
`cancel()`'s own wait. `threading.Timer` threads are non-daemon, and CPython's
`threading._shutdown()` joins every non-daemon thread before the interpreter exits. After
`cancel()` logs "still running after 5s; exiting without waiting further", `main()` returns
and the process then blocks for however long the drain actually takes.

**Evidence.** Reproduced directly:

```
$ python3 -c '<timer firing a 3s target; cancel(); join(0.2)>'
after bounded join, alive: True elapsed 0.7
main returning now
atexit at 3.0      # process still held for the full 3s
```

A worst-case drain is not short: per path it runs the export, then
`run_post_export_command` (`POST_EXPORT_COMMAND_TIMEOUT_SECONDS = 30`), then Apprise
network delivery. That comfortably exceeds `docker stop`'s 10s grace, so the container
runtime still SIGKILLs the process — the exact exposure BL-E010-002 asked this code to
close itself.

**Why it matters.** The story's error-handling AC requires the shutdown path to "not block
indefinitely if the in-flight drain is slow"; the operational doc now tells operators a
guarantee the code does not provide, so a SIGKILL during shutdown will be read as a
deployment fault rather than expected behaviour.

**Suggested fix.** Set `timer.daemon = True` on both `Timer` constructions (lines 523 and
648) so the interpreter does not join them — the atomic writes added by this same story are
what make abandoning a mid-flight drain safe — or have `cancel()` escalate (e.g. `os._exit`
after the warning). Either way, align `docs/operational.md` with whichever is chosen.

## 2. `cancel()` reports "cancelled the pending export drain" when nothing was pending

**Severity:** Medium
**Kind:** claim
**File:** `src/traefik_certificate_exporter/libs/certificate_exporter.py:546-559`

**Claim contradicted.** Observability AC: *"Shutdown (timer cancellation) is itself logged
at INFO with the correlation ID of any in-flight or cancelled pass, so a truncated run is
distinguishable in logs from a clean exit."*

**Problem.** `cancel()` branches on `timer is None` only. After any drain has completed
normally, `self.timer` still references the fired `Timer` and `self.correlationId` still
holds that completed pass's id. `Timer.cancel()` on a fired timer is a documented no-op, so
the code falls through and emits
`"Shutdown requested; cancelled the pending export drain"` at INFO, stamped with the
correlation id of a pass that ran to completion.

**Evidence.** Reproduced against the real handler (mocked exporter):

```
INFO Certificates changed found in file: /data/acme.json
--- drain complete, isWaiting= False pending= set()
INFO Shutdown requested; cancelled the pending export drain
```

The existing test `test_cancel_does_not_raise_when_the_timer_has_already_fired`
(`tests/libs/test_certificate_exporter_watch.py`) drives exactly this path but asserts only
that it does not raise.

**Why it matters.** This is the inverse of the property the AC asks for: the clean exit —
the common case, since most shutdowns happen when no window is open — is logged as a
truncated one, and an operator grepping the correlation id of a fully successful pass finds
a "cancelled" line attached to it.

**Suggested fix.** Distinguish the three states under the lock: no timer ever armed; a timer
armed and not yet fired (`self.isWaiting` true and `not timer.finished.is_set()`) → log
"cancelled"; a timer that already fired → log "waiting for an in-flight drain" or, if the
drain has finished, "no export drain was pending". Clearing `self.timer`/`self.correlationId`
at the end of a clean `doTheWork` would also work, provided it is done under the lock.

## 3. Nothing prevents a new Timer being armed after `cancel()` has returned

**Severity:** Medium
**File:** `src/traefik_certificate_exporter/libs/certificate_exporter.py:537-567`
(`cancel`), `:505-526` (`handleEvent`), `:636-651` (`__rearm`),
`src/traefik_certificate_exporter/app.py:127-133`

**Problem.** `cancel()` cancels the timer it observed and sets no shutdown latch. Two paths
can arm a fresh, non-daemon `Timer` after it returns:

1. `app.py` calls `observer.stop()`, then `cancel()`, then `observer.join()`. An event the
   watchdog dispatcher is already handling (or has queued) can reach `handleEvent` after
   `cancel()` has released the lock. With `isWaiting` false — the state left behind by any
   completed drain — `handleEvent` arms a brand-new timer that fires
   `WATCH_DEBOUNCE_SECONDS` later. Combined with finding 1, that timer runs a full export
   pass (files, post-export hook, notifications) *after* the "Traefik Certificate Exporter
   stopping…" line, and the process stays alive for it.
2. `doTheWork`'s `except BaseException` handler calls `__rearm()` (line 630/636), which
   unconditionally starts a new `Timer`. A drain that dies on any un-caught `BaseException`
   while `cancel()` is in its `join()` re-arms work that nothing will ever cancel.

**Why it matters.** The story's shutdown half is specifically about not leaving an orphaned,
non-daemon `Timer` thread behind; both paths reinstate one, and neither is covered by the
new tests (which only exercise cancel-before-fire, cancel-with-no-timer, and
cancel-after-fire).

**Suggested fix.** Add a `self.shuttingDown` flag set under `self.lock` at the top of
`cancel()`, and return early from `handleEvent`'s arming branch and from `__rearm()` when it
is set. The flag also makes the state machine in finding 2 easy to express.

## 4. Atomic write silently changes file ownership that `Path.open("w")` preserved

**Severity:** Medium
**Kind:** deletion
**File:** `src/traefik_certificate_exporter/libs/certificate_exporter.py:62-104`
(`_atomic_write`), replacing the ten `Path.open("w")` / `write_bytes` sites

**Problem.** The replaced `Path.open("w")` opened the *existing inode*: mode, owner and
group all survived a re-export untouched. `_atomic_write` creates a new inode and
`os.replace`s it in. It explicitly restores mode (`target.stat().st_mode & 0o7777`, line
79/97) but not `st_uid`/`st_gid`. The new file is owned by the exporter's euid, with the
directory's gid only when the directory is setgid.

**Why it matters.** The story's security AC asks explicitly to "preserve whatever file
permissions the existing `Path.open('w')` calls produced … verify explicitly rather than
assume parity, since a regression here would loosen private-key file permissions." Mode is
verified (`test_an_atomic_write_preserves_an_existing_files_permissions`); ownership is not,
and it is the half that matters in the container profile this story targets: the image uses
LinuxServer's PUID/PGID model and `/certs` is a bind mount. A `privkey.pem` that an operator
chowned to `root:traefik` with mode `0640` keeps mode `0640` after the first re-export but
becomes owned by `abc:abc` — the consuming service loses read access entirely, and the file
is now readable by the exporter's own group instead. Hardened deployments break on the next
renewal, with no log line explaining why.

**Suggested fix.** When `target.stat()` succeeded, best-effort `os.chown(tmpPath, st.st_uid,
st.st_gid)` before `os.chmod`/`os.replace`, swallowing `PermissionError` (an unprivileged
process that already owns the file is a no-op). Add a test asserting `st_gid` parity, or —
if ownership preservation is deliberately out of scope — record that in ADR-0024 and in
`docs/operational.md`, because it is a behaviour the removed code carried.

## 5. A symlinked certificate path is replaced by a regular file instead of written through

**Severity:** Low
**Kind:** deletion
**File:** `src/traefik_certificate_exporter/libs/certificate_exporter.py:99-100`
(`os.replace(tmpPath, target)`)

**Problem.** `Path.open("w")` follows symlinks and writes through to the link's target.
`os.replace` does not: it unlinks the symlink and puts the new regular file in its place.

**Evidence.** Reproduced:

```
fullchain.pem -> real.pem  ;  _atomic_write_text(fullchain.pem, "new")
link is symlink: False | real content: old
```

**Why it matters.** Where an operator has symlinked an output filename into a service's own
directory (a documented-nowhere but common pattern for feeding nginx/haproxy), the first
export after this change breaks the link: the service keeps reading the now-frozen original
file and silently serves an expiring certificate. No error is logged.

**Suggested fix.** Either resolve the target with `Path.resolve()` (or `os.path.realpath`)
before choosing the temp directory and replace path, or note the changed semantics in
`docs/operational.md` alongside the existing "keep `outputpath` on a single filesystem"
caveat.

## 6. The end-to-end atomic-write assertion covers only the flat branch (5 of the 10 sites)

**Severity:** Low
**Kind:** claim
**File:** `tests/libs/test_certificate_exporter.py` —
`test_a_real_export_writes_every_artifact_atomically`

**Claim contradicted.** Testability AC: *"Covers all 10 sites the helper now serves: the 8
PEM text sites (`.key`, `.crt`, `.chain.pem`, `.fullchain.pem`, `privkey.pem`, `cert.pem`,
`chain.pem`, `fullchain.pem`) and the 2 PKCS12 `.pfx`/`cert.pfx` sites."*

**Problem.** The test constructs settings with `flat=True` and asserts the five flat
artifacts. Nothing exercises the non-flat branch (`privkey.pem`, `cert.pem`, `chain.pem`,
`fullchain.pem`, per-domain `cert.pfx`), and nothing asserts that those five call sites route
through the helper at all. The planted-failure tests all target `_atomic_write_*` directly,
so a future edit that reintroduces `Path.open("w")` in the non-flat branch would leave the
whole suite green while reopening the exact window BL-E010-002 names.

**Why it matters.** The guarantee is per-call-site, not per-helper; half the call sites have
no regression guard.

**Suggested fix.** Parametrise the existing end-to-end test over `flat=True`/`flat=False`,
or add a case that patches `certificate_exporter._atomic_write` and asserts the set of
targets it was called with for the non-flat branch.

## Passes with nothing to report

- **Backward compatibility.** `run_post_export_command` / `send_export_notifications` gained
  `correlationId` as a trailing keyword with a `None` default; every existing call site and
  test still binds positionally in the same order. Default console output is unchanged
  (`CONSOLEJSON` defaults off, asserted by
  `test_console_output_is_coloured_text_by_default`), and `CONSOLEONLY` is untouched.
- **Record-factory approach.** `install_correlation_id_record_factory` is idempotent
  (`isinstance` guard) and non-reentrant, runs at module import as well as from
  `setup_logging`, and sets the attribute at record creation — so no handler/formatter
  referencing `%(correlation_id)s` (including the root handler, which sees third-party
  records) can hit a missing attribute. `reset_correlation_id` swallowing the cross-context
  `ValueError` is correct for the `Timer`-thread rebind.
- **Atomic-write temp placement and cleanup.** Temp file is created in `target.parent`
  (asserted by `test_the_temp_file_is_created_next_to_its_target`), `delete=False` plus
  `except BaseException: os.unlink` covers `KeyboardInterrupt`/`SystemExit`, and the temp
  file lives at `tempfile`'s 0o600 until the final `chmod`, so key material is never exposed
  at a wider mode than the destination.
- **Debounce invariants.** The `isWaiting`-cleared-inside-the-critical-section invariant and
  the `paths[index:]` requeue are preserved unchanged; the correlation-id additions take no
  new locks and `cancel()` releases `self.lock` before joining, so no new deadlock or lost
  wakeup is introduced (the live re-arm gap is finding 3, not a lock-discipline defect).
- **Secret safety.** Nothing new is logged that can carry a PKCS12 passphrase or an Apprise
  URL; `TRAEFIK_CERTIFICATE_EXPORTER_CORRELATION_ID` carries a bare UUID4 (or `-`), asserted
  by `test_the_correlation_id_is_a_plain_uuid_carrying_no_domain_or_path`.
- **Existing-library check.** `contextvars`, `uuid4`, `tempfile` + `os.replace` and
  `Timer.cancel` are all stdlib as the AC requires; no new dependency was added.
