## Finding 1 — Re-import test leaves two live copies of `app` and `cli_args` reachable by different import idioms

**File:** `/home/ravenwolf.org/sanderson/source/git/ravensorb/traefik/traefik-certificate-exporter/tests/libs/test_cli_args.py:108-115`
**Severity:** Low
**Kind:** bug (test isolation)
**Confidence:** high that the divergence exists; impact is latent, not currently failing

**Problem:** `monkeypatch.delitem(sys.modules, ...)` restores the `sys.modules` entries at
teardown, but `importlib.import_module("traefik_certificate_exporter.app")` also rebinds
the *attributes* `traefik_certificate_exporter.app` and
`traefik_certificate_exporter.libs.cli_args` on their parent packages, and monkeypatch
does not restore those. After this test runs, the two lookup paths disagree.

**Evidence:** reproduced directly against the installed package (sequence identical to the
test, then restoring `sys.modules` only):

```
pkg attr app is old:            False   # traefik_certificate_exporter.app -> NEW module
libs attr cli_args is old:      False   # NEW module (a second globalArgParser instance)
from ...app import main is old: True    # resolves via sys.modules -> OLD module
import ...app as a2 is old:     False   # resolves via package attr -> NEW module
```

So a later test that patches `traefik_certificate_exporter.app` attributes via
`import traefik_certificate_exporter.app` would be patching a different module object than
the `main` obtained by `from traefik_certificate_exporter.app import main` executes in.
The suite is green today only because no other test does both; this is the kind of leak
that produces an unexplainable failure in an unrelated file later.

**Remediation:** make the re-import self-contained — either run it in a subprocess
(`sys.executable -c "import traefik_certificate_exporter.app"` with hostile argv, asserting
returncode 0, mirroring `test_main_hard_fails_on_a_typo_end_to_end`), or explicitly restore
the parent-package attributes as well, e.g. capture
`traefik_certificate_exporter.app` / `traefik_certificate_exporter.libs.cli_args` before the
re-import and `monkeypatch.setattr` them back on their parent packages.

## Finding 2 — New redaction tests assert on a shape no sink produces, so they add helper-level, not sink-level, assurance

**File:** `/home/ravenwolf.org/sanderson/source/git/ravensorb/traefik/traefik-certificate-exporter/tests/libs/test_settings.py:198-236`
**Severity:** Low
**Kind:** claim
**Confidence:** high

**Triggering claim (story, Testability approach):** "extend `tests/libs/test_settings.py` …
with the nested-list edge case noted above, following its existing `_capture_all_records`
helper pattern rather than writing a new capture mechanism." And (Security considerations)
"the verification task for this story is to prove no gap remains across all three sinks."

**Contradicting location:** both new tests call `_redact_secrets` directly with a
hand-built `{"destinations": [...]}` / `[[{"api_key": ...}]]` literal. No `caplog`, no
`_capture_all_records`, no `loadFromFile` — neither `_dump_settings`
(`settings.py:333-339`) nor `_dump_config` (`settings.py:341-349`) is executed, and the
`destinations` list-of-objects shape is not produced by the `Settings` dataclass or the
confuse schema (the real `appriseUrls` is a flat list of strings at `settings.appriseUrls`).
They therefore prove that `_redact_secrets` recurses through lists — they do not prove any
sink is safe for that shape. The sink-level guarantee behind the ADR-0014 status flip rests
entirely on the pre-existing tests, not on anything this change adds.

Secondary, same block: `redacted["destinations"][0]["pkcs12Passphrase"]` is masked by the
`_SECRET_FIELD_PATTERN` backstop, not by the registry — verified:
`_SECRET_FIELD_PATTERN.search("pkcs12Passphrase")` is truthy, so the `or` short-circuits
before `_is_declared_secret` is consulted. That assertion would still pass with
`SECRET_CONFIG_KEYS` emptied, contrary to the docstring's "the declared-key check has to
fire". Only the `appriseUrls` assertion (pattern does not match; `_is_declared_secret` does)
is actually registry-driven, which is why the test as a whole is not vacuous.

**Remediation:** drive at least one of the two new cases through a real sink — load a
config with a planted secret at DEBUG and assert over captured records with the existing
`_capture_all_records` helper, as the AC specifies — and either drop the
`pkcs12Passphrase` assertion from the nested-list test or re-key it to a name the regex
cannot match (e.g. `appriseUrls` only) so that the registry is what the assertion depends on.
