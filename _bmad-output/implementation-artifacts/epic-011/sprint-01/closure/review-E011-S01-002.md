## Issue: The vendored-integrity claim in CODEOWNERS overstates what the manifests verify by ~16x

**File:** `.github/CODEOWNERS:33-34` (and `tests/ci/test_gates.py:505-507`, 519-536)
**Severity:** High
**Problem:** The header states "Each skill that ships a `payload-manifest.json` declares the
release it came from and a SHA-256 per file", and the guard's docstring repeats "a SHA-256 for
every file the installer wrote". Neither is true. `payload-manifest.json` carries
`"generated_from": "skills/_shared/"` — it is a manifest of *shared assets copied into* the
skill, not an inventory of the skill. Measured across both trees: 164 skill directories, 16 with
a manifest, 2,364 files on disk, **142 files covered** (6%). Even inside a manifested skill the
coverage is partial — `.agents/skills/l3io-arch-review/` has 21 files and the manifest declares
5; the undeclared ones include `SKILL.md`, `customize.toml` and all of `assets/`. `SKILL.md` is
precisely the file the same CODEOWNERS paragraph calls executable surface ("READ its entire
contents and follow its directions exactly"), and it is verified against nothing upstream in
every skill, manifested or not.

The guard also only iterates `manifest["files"]`, so a file *added* inside a manifested skill
directory is not detected at all — the manifest is treated as a whitelist of things to check
rather than as the directory's declared contents.

This defeats the story's AC that the vendored check "fail closed (loudly state the gap) rather
than silently passing": the gap is stated, but stated as far smaller than it is, which is the
same "unchecked claim stated as a checked one" defect BL-E008-009 exists for.
**Evidence:** `json.load` over every `payload-manifest.json` in `.agents/` and `.claude/`
compared against `rglob('*')` of each skill directory — 142 of 2,364 files covered; manifest key
`generated_from` = `skills/_shared/`.
**Suggested fix:** Restate the CODEOWNERS caveat in terms of files, not skills (e.g. "the
manifests cover the shared payload copied into 16 skills — 142 of 2,364 files; everything else,
including every `SKILL.md`, is pinned only by the two trees matching each other"), and have
`test_the_vendored_integrity_guard_records_what_it_cannot_verify` compute the gap over files so
the stated number cannot drift from the real one.

## Issue: Gap accounting at skill granularity can force the caveat to be deleted while most files stay unverified

**File:** `tests/ci/test_gates.py:583-610`
**Severity:** Medium
**Problem:** `unverified` counts *skills whose directory lacks a `payload-manifest.json`*. If a
future BMad release ships a manifest in every skill — plausible, since 16 already do and the
manifest is installer-generated — `unverified` becomes empty and the `else` branch asserts
`"no upstream reference" not in owners`, i.e. the test then **fails until the caveat is removed
from CODEOWNERS**. At that point the repository would state that the vendored trees are fully
verified while, on the current manifest semantics (`generated_from: skills/_shared/`), only the
shared-payload subset of each skill is actually hashed. The guard would actively drive the
standing claim from understated to false, which inverts its stated purpose ("fail closed on the
gap rather than let the prose imply there is none").
**Evidence:** `else` branch at `test_gates.py:607-610`; manifest-coverage measurement above
showing a manifest's presence does not imply full-directory coverage.
**Suggested fix:** Make the condition file-based — gap closes only when every file under each
vendored tree is named by some manifest — rather than directory-presence-based.

## Issue: Code deliberately contradicts the story's literal edge-case AC on staged files (kind: claim)

**File:** `tests/ci/test_gates.py:260-266` (planted-repo test, staged-file assertion)
**Severity:** Low
**Problem:** The story's Error-and-edge-case AC says the coverage check "must fail when a new
file is `git add`-ed but not yet linted in the same run". The implementation asserts the
opposite: a staged-but-uncommitted file must **not** be reported ("a staged file is in
`git ls-files` and is linted; reporting it would make the guard cry wolf"). The implementation is
the technically correct reading — `pre-commit run --all-files` enumerates `git ls-files`, which
includes staged files — and the AC's own parenthetical ("replicating BL-E000-001's third
recurrence — `tests/ci/test_gates.py` itself was untracked") describes the untracked case the
code does implement. Flagged only because the divergence from the written AC is not recorded
anywhere in the story's Dev Agent Record, so a closer reading the ACs literally will score this
as unmet.
**Evidence:** AC text vs. `test_gates.py:260-266`; confirmed behaviour by running the test.
**Suggested fix:** Note the corrected reading in the Dev Agent Record (or amend the AC) so the
divergence is deliberate on the record rather than apparent.
