# CLI and settings hardening: unrecognized-arg failure, settings-dump redaction

## Context

Promoted from deferred finding(s):
- BL-E001-006 (Low, sprint-closure adversarial review (E001-S01)) — The fix for the import-time argv-parsing crash (parse_args -> parse_known_args) is necessary for testability but as a side effect means a genuine CLI typo (e.g. --dtaa-path) is now silently ignored in the real console-script entry point too, rather than erroring. A more complete fix would move argument parsing out of module-import time and into main() specifically, so production invocations can still hard-fail on unrecognized flags while imports (tests, embedding) remain safe -- but that is a larger architectural change than this story's scope (a testability blocker fix) warranted.
- BL-E010-003 (Low, epic-010 architecture gates) — ADR-0014 Decision 4 adopts confuse's .redact/dump(redact=True), which redacts by CONFIG PATH. _dump_settings dumps the Settings dataclass through jsonpickle, not the confuse Configuration, so the registry of secret paths does not map onto that sink without an explicit translation. E010-S01-001's AC forces the right outcome empirically -- a planted credential must appear in no record during a DEBUG loadFromFile -- so this is a design note for the implementer rather than a gap in the obligation.

## Business acceptance criteria

### Outcome

- A genuine CLI typo in the production console-script entry point (e.g. `--dtaa-path`)
  causes the process to exit non-zero with a clear "unrecognized argument" message,
  instead of being silently ignored (BL-E001-006) — while `import
  traefik_certificate_exporter...` from pytest, a REPL, or an embedding host continues to
  succeed even with foreign argv present.
  Spec: none — l3io-plan does not pass a spec index
- A planted credential in any `Settings`-dumping sink is provably absent from every DEBUG
  log record (BL-E010-003). Reading the current code, this outcome is **already achieved**
  by the `SECRET_CONFIG_KEYS` registry and `tests/libs/test_settings.py`'s
  `test_every_declared_secret_key_is_redacted_in_every_sink`; this story's outcome is
  confirming and recording that closure rather than re-implementing it (see Interface
  contracts).
  Spec: none — l3io-plan does not pass a spec index

### Non-goals

- Does not restructure argument parsing into a full subcommand/argparse-actions
  redesign — the fix is moving *when* `parse_args()` (vs. `parse_known_args()`) runs, not
  changing the flag surface itself.
- Does not change any existing flag name, `dest=`, default, or help text in
  `cli_args.py`.
- Does not introduce a new redaction mechanism for settings — confuse's `redact`/`dump`
  and the existing `SECRET_CONFIG_KEYS` registry already cover every sink; per
  ADR-0014 Decision 4 and global rule 1, a second redactor is explicitly the wrong move.
- Does not change `ADR-0014`'s Decision 4 substance — if its `Status:` field is stale
  (`Proposed` despite a matching, tested implementation), this story may correct the
  status field but does not reopen or re-litigate the decision.

## Technical acceptance criteria

### Interface contracts

- Files touched/added, and conventions their siblings set:
  - `src/traefik_certificate_exporter/libs/cli_args.py` — keep `globalArgParser`
    module-level (unchanged import-time side effect of *building* the parser), but move
    the `globalArgs, _ = globalArgParser.parse_known_args()` call site so production
    entry (`app.py:main()`) calls a strict `globalArgParser.parse_args()` while
    import-only consumers (tests) keep using `parse_known_args()` — e.g. export a
    `parse_args_strict()` / `parse_known_args_safe()` pair, or a `parse(strict: bool)`
    helper, called explicitly from `app.py`'s `main()` rather than at import time.
  - `src/traefik_certificate_exporter/app.py` — `main()` is the one place
    `sys.argv` reflects only this process's real invocation; this is where the strict
    parse call belongs, matching the existing comment in `cli_args.py` that already
    states production "only ever sees its own argv."
  - `tests/libs/` — a new `test_cli_args.py` (no existing file for this module; every
    other `libs/` module already has a `test_<module>.py` twin — `test_settings.py`,
    `test_docker.py`, `test_domains.py` — so this fills a gap in that pattern) covering
    both the strict-production and lenient-import paths.
  - `src/traefik_certificate_exporter/libs/settings.py` — no code change expected for
    BL-E010-003; if a gap is found during verification, it is fixed in `_dump_settings`/
    `_dump_config`/`_redact_secrets` in place, following the existing registry-derived
    pattern (`SECRET_CONFIG_KEYS`, `_is_declared_secret`), not a new redactor.
  - `docs/adr/0014-post-export-notifications-via-apprise.md` — correct `Status:` from
    `Proposed` to `Accepted` if verification confirms Decision 4 is fully implemented and
    tested (it appears to be, per `_secret_leaf_names`/`_is_declared_secret` and the
    existing test suite).
- `parse_args_strict()`'s contract: raises `SystemExit(2)` (argparse's existing behavior
  on unrecognized args) with a message naming the offending flag(s); no new exception
  type is introduced.
  Spec: none — l3io-plan does not pass a spec index

### Error and edge case handling

- An unrecognized flag in production argv must fail with a non-zero exit and a
  human-readable message — covered by `argparse.parse_args()`'s existing default
  behavior; no custom error formatting needed beyond letting it propagate from `main()`.
  Spec: none — l3io-plan does not pass a spec index
- Importing the module under pytest with foreign CLI args present (e.g. pytest's own
  `-x`, `-v`) must continue to succeed with no `SystemExit` — this is the regression this
  story must not reintroduce, and is exactly what motivated the original
  `parse_known_args()` change.
  Spec: none — l3io-plan does not pass a spec index
- A `--help`/`-h` invocation in production must still print help and exit 0 (argparse's
  built-in behavior) — confirm the relocation to `main()` doesn't change this, since
  `-h` is itself technically an "unrecognized positional" path through argparse's
  internals if mishandled.
  Spec: none — l3io-plan does not pass a spec index
- For BL-E010-003: a secret-shaped value nested inside a list-of-dataclasses (not just a
  top-level dict key) must still redact correctly through `_redact_secrets`'s existing
  recursive list/dict handling — add a test case for this nesting shape if none exists,
  since `appriseurls` (a list of strings) is covered by path-level redaction in
  `_dump_config` but `_dump_settings`'s dataclass-walk redacts by *value position*, not
  config path, and a list of secret-bearing objects (not raw strings) is the edge this
  verification should explicitly check.
  Spec: none — l3io-plan does not pass a spec index

### Observability requirements

- N/A for BL-E001-006 beyond argparse's own stderr usage message — no structured
  logging is warranted for a CLI parse failure that exits before logging is configured
  (`setup_logging()` runs after arg parsing in `main()` today).
- For BL-E010-003: no change to observability surface — `_dump_settings`/`_dump_config`
  remain DEBUG-level log statements; this story only verifies their existing redaction,
  it does not add new log fields.
  Spec: none — l3io-plan does not pass a spec index

### Security considerations

- BL-E010-003 is itself a security requirement (credential non-exposure in logs); the
  verification task for this story is to prove no gap remains across all three sinks
  named in ADR-0014 Decision 4 (`_dump_settings`, `_dump_config`, raw argparse
  namespace) — all three already have passing tests
  (`test_every_declared_secret_key_is_redacted_in_every_sink`,
  `test_command_line_args_are_redacted_before_they_reach_the_log`); this story's AC is
  that this coverage is confirmed current, not re-derived.
  Spec: none — l3io-plan does not pass a spec index
- Making unrecognized-arg failure strict in production must not regress the import-time
  safety that was the entire reason `parse_known_args()` was adopted — a regression here
  reopens BL-E001-006's parent crash (an import-time `SystemExit` under pytest), so the
  dual-path test (strict in `main()`, lenient on bare import) is the security-relevant
  regression guard, not a nicety.
  Spec: none — l3io-plan does not pass a spec index

### Testability approach

- New `tests/libs/test_cli_args.py`: invoke `globalArgParser.parse_known_args(["--dtaa-path", "x"])`
  directly (no subprocess needed — argparse objects are first-class and testable without
  spawning the console script) to assert silent-ignore under the lenient path, and
  `globalArgParser.parse_args([...])` wrapped in `pytest.raises(SystemExit)` to assert
  strict failure — matching the direct-object-testing style already used across
  `tests/libs/`.
  Spec: none — l3io-plan does not pass a spec index
- For BL-E010-003, extend `tests/libs/test_settings.py` (not a new file — this is the
  existing, actively-maintained home for every redaction test) with the nested-list edge
  case noted above, following its existing `_capture_all_records` helper pattern rather
  than writing a new capture mechanism.
  Spec: none — l3io-plan does not pass a spec index

### Existing-library check

- `argparse`'s own `parse_args()` vs. `parse_known_args()` split is the existing stdlib
  facility that solves BL-E001-006 entirely — no custom argv pre-scanning or a second
  parser instance is warranted.
  Spec: none — l3io-plan does not pass a spec index
- `confuse`'s `Configuration.dump(redact=True)` and per-view `.redact = True` (already
  adopted per ADR-0014 Decision 4) is the existing facility for BL-E010-003; the
  `SECRET_CONFIG_KEYS` registry plus `_is_declared_secret`'s leaf-name matching is the
  already-written bridge from that mechanism to the non-confuse sinks
  (`_dump_settings`, raw argparse namespace) — no further library is needed, only
  verification that the bridge has no remaining gap.
  Spec: none — l3io-plan does not pass a spec index
