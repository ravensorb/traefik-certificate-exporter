## Findings

### F-01: Requiring a PR with no approval does not stop a write-holder from putting a workflow on `main`, so the `dev` tokens are still exposed

- **Severity:** HIGH
- **Kind:** security (overstated coverage)
- **Location:**
  - `docs/ci/pipeline-walkthrough.md:399`, `:412`, `:421-425`
  - `docs/adr/0039-publish-credentials-in-forge-environments.md:93-100`, `:105-107`
  - `docs/ci/gitea-runners.md:66-70`
- **Description:**
  - The `main` ruleset requires "Require a pull request before merging". It sets no
    `required_approving_review_count`, so the count defaults to 0.
  - The verification checks only that a rule of type `pull_request` exists. It never reads
    the rule's `parameters`.
  - With 0 required approvals, any write-holder can open a PR that edits `dev.yaml` and
    merge it themselves, from the UI or with `gh pr merge`. That includes a collaborator, a
    stolen write token, or a write-capable agent, which are the actors RT-E013-01 names.
  - The merged workflow then runs on `refs/heads/main`. The `dev` policy admits it, and it
    can print every `dev` secret. Those include the GHCR, Docker Hub and Gitea registry
    tokens, which `release` also uses. With them, an attacker can overwrite release image
    tags.
  - The story's business outcome says "A collaborator, a stolen write token or a
    write-capable agent cannot read any publish token by pushing a branch or a workflow
    file". ADR-0039 and the walkthrough present the threat as closed. Neither records this
    self-merge residual.
  - Gitea has the same gap. Required approvals and a merge allowlist are marked
    "Optionally". Without them, any write-holder can merge an unreviewed PR. So the
    statement "the `main` and `v*` protections stop unreviewed code from being
    **published**" (gitea-runners.md and ADR-0039 Decision 6) is not true as configured.
  - This conflicts with global rule 3: the prose overstates its own coverage.
- **Suggested fix (either):**
  - **(a) Close the gap.**
    - GitHub: set the `pull_request` rule's `required_approving_review_count` to 1 and
      `require_last_push_approval` to true. Keep the Repository admin role on the bypass
      list, so the sole maintainer still merges their own PRs as a bypass. Extend the
      verification with
      `--jq '.rules[] | select(.type=="pull_request") | .parameters'` and expect a count of 1
      or more.
    - Gitea: make a merge allowlist (maintainer only) or required approvals mandatory
      rather than optional, and add the corresponding fields to the expected
      `branch_protections` output.
  - **(b) Record the residual.** If the maintainer declines (a), state explicitly in
    ADR-0039 Consequences, in the walkthrough's "Branch protection on main", and in
    gitea-runners.md: "any write-holder can self-merge a PR into `main` and read the `dev`
    secrets, including the registry tokens shared with `release`". Then soften the
    "cannot read any publish token" and "stop unreviewed code from being published"
    statements to match.

### F-02: The removed Deferred "Branch protection" bullet carried the required-check contract, and the new required `main` ruleset drops it

- **Severity:** MEDIUM
- **Kind:** deletion (confidence: high)
- **Location:**
  - `ARCHITECTURE-SPINE.md`, Deferred (removed bullet "Branch protection. This is a forge
    setting outside the repository; the required check is named in the Conventions table.")
  - `docs/ci/pipeline-walkthrough.md:399`, `:410-413`
  - `docs/adr/0039-publish-credentials-in-forge-environments.md:95-97`
- **Description:**
  - The deleted bullet tied branch protection to the Conventions row "Job ids … Required
    check on pull requests: `build / build`". ADR-0039 also keeps `name:` equal to the job
    id "so check names (`build / build`) are unchanged". That only matters if something
    requires the check.
  - The new required `main` ruleset lists only `deletion`, `non_fast_forward` and
    `pull_request`. It has no `required_status_checks` rule for `build / build`, and the
    verification does not expect one.
  - Two things follow:
    - The required check named in Conventions is now configured nowhere.
    - The zizmor `secrets-outside-env` rule, which ADR-0039 says "fails `just check`",
      gates merges only if the CI check is required. A PR that fails `build / build` can
      still be merged into `main`.
  - Nothing in the change re-establishes this contract, and nothing records dropping it.
- **Suggested fix:**
  - Add "Require status checks to pass", with the check `build / build`, to the `main`
    ruleset steps in the walkthrough and in ADR-0039 Decision 4.
  - Add `required_status_checks` to the expected rule types, and show
    `.rules[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context`
    in the verification.
  - On Gitea, enable status checks with the matching context in the protected-`main` steps.
  - Alternatively, if dropping the requirement is intended, record that in ADR-0039 and
    remove "Required check on pull requests" from Conventions.

### F-03: The "delete the secret to stop publishing" instruction ignores that shared tokens live in both environments

- **Severity:** LOW
- **Kind:** correctness (docs)
- **Location:** `docs/operational.md:385-386`
- **Description:**
  - The new text tells the operator to update a shared token in both `dev` and `release`.
    The next sentence, unchanged, still says "To stop publishing to that destination
    instead, delete the secret".
  - On GitHub, deleting a shared token (GHCR, Docker Hub, Gitea, CA) from one environment
    leaves the other workflow publishing to that destination.
- **Suggested fix:** Say "delete the secret from every environment that holds it (both
  `dev` and `release` for a shared token) and from the Gitea store".

### F-04: The bypass note implies a collaborator on a user-owned repository can hold the admin role

- **Severity:** LOW
- **Kind:** correctness (GitHub fact)
- **Location:** `docs/ci/pipeline-walkthrough.md:275-277`. The same idea appears more
  briefly in ADR-0039 line 46 and ADR-0038 line 42.
- **Description:**
  - The walkthrough says "the owner … is the only admin unless a collaborator is given the
    admin role, so keep it that way."
  - On a personal-account repository, collaborators have a single fixed collaborator
    permission. Owner or admin permission cannot be granted to another account, and
    repository roles exist only for organisations.
  - The sentence is harmless, but it describes a configuration that GitHub does not offer
    for this repository.
  - Confidence: medium. This rests on GitHub's "Permission levels for a personal account
    repository"; it was not re-fetched in this review.
- **Suggested fix:** Replace it with "on this user-owned repository only the owner holds
  admin; collaborators cannot be granted it".
