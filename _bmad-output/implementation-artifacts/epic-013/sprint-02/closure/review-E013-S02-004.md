## F2 — MEDIUM — kind: testability — `tests/test_s6_privilege_drop.py` (`_decide` ~L727, `_run_init` ~L973; tests `test_a_writable_store_is_appended_to_the_root_warning`, `test_the_last_path_is_probed_without_a_trailing_newline`, `test_a_file_name_with_a_space_is_probed_once_and_reported_whole`, `test_init_keeps_root_when_the_output_path_stays_unwritable`)

**Description:** The stub signals a malformed probe (wrong user, `-x` on a file, `-r` on the
output path, unknown operator) by logging `VIOLATION` and exiting 99. The helper treats any
non-zero `s6-setuidgid` exit as "not readable / not writable", i.e. **root** — the same result
these tests expect. Only some tests call `_assert_no_violation`; the four listed above do not,
so in them a probe violation is indistinguishable from the intended root outcome. The story
requires the stub to fail the test "via a recorded `$TCE_TEST_STUB_LOG`", which only happens
where the log is checked.

**Failure scenario:** a regression makes init call `tce_output_writable` with a probe the
stub rejects (e.g. `test -r` on the output path, or the user variable swapped so the probe runs
as `root`): stub logs `VIOLATION`, exits 99, init writes `true` and prints the `cannot write`
WARNING — `test_init_keeps_root_when_the_output_path_stays_unwritable` stays green. Same for a
wrong-operator probe of `b.json` in `test_a_writable_store_is_appended_to_the_root_warning`
(b becomes "unreadable" too; the test only checks the anchor). A false green, precisely the
mode the stub's policing was specified to prevent.

**Suggested fix:** make the violation check unconditional: call `_assert_no_violation` inside
`_decide` and `_run_init` after the subprocess returns (opt-out only for the `unknown user`
case), or an autouse fixture that asserts `VIOLATION` is absent from `stub.log` at teardown.

## F3 — LOW — kind: testability — `tests/test_s6_privilege_drop.py` stub `-O)` branch (~diff L681-684); `docker/root/usr/local/lib/traefik-certificate-exporter/privilege-decision.sh:32-35`

**Description:** `_tce_user_controls` has two ways to flag the store as controlled by `abc`:
`abc test -w`, or root-`[ -w ]` (writable filesystem) **and** `abc test -O` (owned). The stub
answers `-O` with exit 1 unconditionally, so the owned-but-not-writable branch is never
exercised; the real-image scenario 4 used a `1000:1000 0600` file, which `abc` can write, so it
too took the `-w` branch.

**Failure scenario:** a regression in the `-O` branch (e.g. operator typo, or dropping the
`[ -w ]` guard so an `abc`-owned store on a `:ro` mount produces the `:ro` advice the Dev
Agent Record says it must not) passes the whole suite. Concretely: `abc`-owned `0400`
`acme.json` on a read-write `/data` — the case the AG-27 note exists for — is untested.

**Suggested fix:** add a `TCE_TEST_OWNED` list to the stub (`-O` → 0 when listed) and two
cases: owned + root-writable path → `INFO:` `:ro` line; owned + path not writable by the
runner (skip under root, or a stub for `[ -w ]` is not possible — use a `chmod 0500` parent
or mark skipif euid==0) → no line.

## F4 — LOW — kind: correctness (confidence: plausible) — `privilege-decision.sh:75`; init `run` lines 120-137

**Description:** The helper rejects a relative `settings.datapath` as row 1 because "the
service runs from s6's service directory, so a relative path cannot be probed reliably here"
(Dev Agent Record interface choice). The same reasoning applies to `settings.outputpath`, but
a relative output path is not rejected: init chowns and probes it (`find "${outputPath}"`,
`s6-setuidgid abc test -w "${outputPath}"`) relative to **init's** cwd, while the service
resolves it against its own service directory.

**Failure scenario:** `settings.outputpath: certs`; init oneshot cwd `/` (the story's own
assumption) → `/certs` exists in the image, gets chowned, `abc test -w certs` passes → row 7,
drop to `abc`. The service (cwd = its service directory) then writes `./certs` under the
read-only/root-owned s6 service tree and every export fails with per-domain errors — the
"drops to an account that exports nothing" failure class BL-E013-041 exists to remove. If
init's cwd has no `certs`, the probe fails and root is kept (safe), so the bad outcome depends
on s6-rc's oneshot cwd.

**Suggested fix:** in `tce_privilege_decision`, treat a non-absolute line 2 (outputPath) as
row 1 alongside dataPath, with a test case `["false", "certs", "/abs/data", "*.json"]` →
`true`/`could not resolve`.

## F5 — LOW — kind: claim — `privilege-decision.sh:73-92`; `docs/operational.md` table row 1

**Claim:** AC "Each container start emits exactly one privilege WARNING when root is retained,
**naming the reason**"; operational.md row 1: "a relative `settings.datapath` … WARNING `could
not resolve settings` — **the exporter then reports the configuration error itself**".

**Description:** The relative-datapath check is evaluated inside row 1, before row 2. A
relative datapath is a valid configuration the exporter loads without error, so (a) the
WARNING text "Check /config/config.yaml … the exporter reports the configuration error itself"
and the operational.md row-1 text are false for that case — the exporter runs as root and
reports nothing; and (b) with `settings.restartcontainers: true` and a relative datapath the
single WARNING names "could not resolve settings" instead of `restartcontainers`, so the
operator is pointed at the wrong cause.

**Failure scenario:** operator sets `datapath: data` and `restartcontainers: true`; log shows
only `WARNING: running as root because the container could not resolve settings
(settings.datapath 'data' is not an absolute path) … the exporter reports the configuration
error itself`; no configuration error ever appears, and the actual root driver
(restartcontainers) is never mentioned.

**Suggested fix:** keep rows 1 strictly "resolved file missing/short/line-1 invalid"; move the
absolute-path checks after row 2 as their own reason (e.g. "settings.datapath 'data' is
relative, so it cannot be probed as the service will resolve it; use an absolute path"), and
adjust the operational.md row-1 wording to match.
