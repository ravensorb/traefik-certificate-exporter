# Release only from main: validate tag ancestry and protect v* tags

## Context

Promoted from deferred finding(s):
- BL-E013-019 (High, redteam (RT-E013-02)) — Needs maintainer decision (changes a recorded design decision); not implemented in closure. Proposed: validate-tag ancestor check against origin/main plus forge tag protection for v*; amend AD-12. See _bmad-output/implementation-artifacts/epic-013/sprint-01/closure/redteam-report.md and _bmad-output/implementation-artifacts/epic-013/sprint-01/closure/adversarial-review.md

### Research findings (verified 2026-10-09)

1. **The checkout provides `refs/remotes/origin/<default>` on GitHub and Gitea.**
   - Source: `actions/checkout` at the pinned SHA `3d3c42e…` (v7.0.1), `src/ref-helper.ts`
     `getRefSpecForAllHistory`. With `fetch-depth: 0` it fetches
     `+refs/heads/*:refs/remotes/origin/*` plus tags (`src/git-source-provider.ts`, "Fetch all
     branches and tags").
   - Gitea's `act_runner` runs the same action against the Gitea server. I inferred from the
     same code path that it gets the same refs; this is not run live on Gitea (see
     Testability approach).
   - No extra `git fetch` is needed. That matters because `persist-credentials: false` leaves
     no credential for one.
2. **Under nektos/act 0.2.89 the local `.git` is used as is.** Verified by running a
   throwaway repository with a bare `origin`, using the job shape below:
   - Tag `v9.9.9` on a commit only on a side branch, with `refs/remotes/origin/main` present:
     `git merge-base --is-ancestor` reported **not an ancestor**.
   - Tag `v1.0.0` on `main`: **ancestor**.
   - No event file: act synthesises `github.event.repository.default_branch = master` (its
     `--defaultbranch` flag defaults to `master`), so the check fails closed.
   - `origin` removed: `fatal: Not a valid object name refs/remotes/origin/main`, so the check
     fails closed.
   - The ref was `refs/tags/<tag>`, taken from the tag at HEAD.
3. **The default-branch name comes from the event payload.**
   `github.event.repository.default_branch` is in GitHub's push payload. Gitea v1.27.3's
   `structs.Repository` has `DefaultBranch json:"default_branch"`
   (`modules/structs/repo.go:89`), and its push payload carries `repository`. The Gitea value
   is not run live; see Testability approach.
4. **No LiquidLogicLabs action reports ancestry.** I read `action.yml` on each default
   branch:
   - `git-action-tag-info` outputs `exists`, `item-sha` and `commit-sha`, and can query forge
     releases with a token.
   - `git-action-commit-info` outputs SHA, message, author and date, by HEAD offset only.
   - `git-action-tag-validate-version` outputs version parsing results and `tag-exists`.

   None reports "is ancestor of" or branch containment. So AD-5 allows a `run:` step, and
   `git merge-base --is-ancestor` is git's own primitive for this.
5. **GitHub tag protection.** Rulesets target tags by `fnmatch` pattern.
   - "Restrict creations", "Restrict updates" and "Restrict deletions" each limit the action
     on matching tags to bypass actors.
   - Rulesets are available on public repositories, and this repository is public. None
     exists today (`gh api …/rulesets` → `[]`).
   - Sources (github/docs): `…/managing-rulesets/available-rules-for-rulesets.md` and
     `about-rulesets.md`.
6. **Gitea protected tags.** Configured at Settings → Tags with a glob or `/regex/` pattern
   and allowed users or teams. "If you leave these fields empty no one is allowed to create
   or modify this tag" (gitea/docs `docs/usage/access-control/protected-tags.md`).
   - Verified in v1.27.3 source (`routers/private/hook_pre_receive.go`): every tag ref update
     in a push goes through `preReceiveTag`. It rejects users who are not allowed ("Tag %s is
     protected"). That covers creation, force-move and deletion.
   - The glob `v*` matches every tag beginning with `v` (docs example table).
   - The API endpoint is `/repos/{owner}/{repo}/tag_protections` (v1.27.3 swagger).
7. **Why the workflow check alone is not a control.** This is load-bearing.
   - `release.yaml` runs from the **tagged commit**. A write-holder who tags their own
     unreviewed commit can also delete the step in that commit.
   - The step therefore stops honest mistakes:
     - tagging the wrong commit;
     - tagging before `main` is pushed;
     - a plain `git push` that bypasses `just release`.
   - The boundary is forge tag protection, which restricts who can create a `v*` tag. Behind
     it sits the required `main` protection from E013-S02-002, which decides what "on main"
     means.
   - The ADR says this plainly (global rule 3).
8. **AR-07: a re-pushed tag splits one version.**
   - Decision: rely on tag protection plus registry immutability, with no "already released"
     guard.
   - With creation, update and deletion of `v*` restricted, a tag cannot be moved without an
     explicit bypass. Every re-run (ADR-0036 §5) therefore rebuilds the same commit.
   - PyPI never accepts a re-upload of an existing filename, and Gitea's package index
     returns a conflict. `--skip-existing` keeps re-runs green.
   - I rejected a "release exists" guard for three reasons:
     - (a) It would break ADR-0036 §5 re-runs.
     - (b) `git-action-tag-info` in release mode needs a token and forge-derived
       `platform`/`base-url`, which AD-9 forbids.
     - (c) It would need a conditional form that the Conventions table does not allow.
   - What remains is an admin bypass. The operator rule is: never delete or re-push a
     released tag; cut the next patch.

**Decisions recorded here:**
- **`validate-tag`:** gets a ref-free, full-history checkout and one `run:` step with no
  `if:`. The default branch comes through `env` from the payload, and the step fails closed
  if it is empty.
- **`justfile`:** derives the default branch **once**, in one shared definition used by both
  `act` and `release`. `just act` passes it as `--defaultbranch`. A local copy without
  `origin` fails closed; this is documented.
- **Same YAML on all three runners.** No `env.ACT`.
- **Gitea protected-tag pattern:** the glob `v*`, which matches GitHub's ruleset target.
- **Sequencing:** this story lands **before** E013-S02-002. It creates
  `## Forge settings the maintainer applies` in `docs/ci/pipeline-walkthrough.md`, with
  `### Tag protection`. S02-002 adds its subsections and the six-step order under that
  heading afterwards. S02-002's `release` environment relies on this story's tag protection.

## Business acceptance criteria

### Outcome

Once this story's settings and S02-002's required `main` protection are applied:
- A release can only come from a commit already on `main`, and only from a `v*` tag the
  maintainer created. A release here means PyPI, every image tag including `latest`, and the
  forge release.
- `README.md`'s "A release is a `vX.Y.Z` tag on `main`" holds on the server, not only inside
  `just release`.
- A released version cannot be silently moved to different code by deleting and re-pushing
  its tag. Downstream users can trust that the wheel and the image for `X.Y.Z` come from the
  same commit.
- These hold on both GitHub and Gitea.

## Technical acceptance criteria

### Interface contracts

`release.yaml` `validate-tag` (AD-12 step 1, amended) runs these steps in order:
1. The existing `git-action-tag-validate-version@v2` step and its `Reject tag` step, unchanged.
2. `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1` with `fetch-depth: 0` and `persist-credentials: false`.
   - No `ref:` or `repository:` (AD-6 / ADR-0028, enforced by the `workflows-ref-free-checkout` hook).
   - No `fetch-tags`, because only branches are needed.
3. A step named `Tag is on the default branch`, with no `if:` and with `env: { DEFAULT_BRANCH: ${{ github.event.repository.default_branch }}, TAG: ${{ github.ref_name }} }`. No expression goes inside `run:`.
   - It fails if `DEFAULT_BRANCH` is empty.
   - It echoes the tag, `git rev-parse HEAD` and the default branch.
   - It runs `git merge-base --is-ancestor HEAD "refs/remotes/origin/$DEFAULT_BRANCH"`. `HEAD` is the checked-out commit, so annotated tags need no peeling.
   - On failure it writes `refusing to release tag $TAG: commit <sha> is not on origin/$DEFAULT_BRANCH` to stderr and exits 1.
   - Its comment cites AD-12 and ADR-NNNN, and says that the step guards against mistakes while tag protection is the control.

Job-level constraints:
- Keep `runs-on: ubuntu-latest` and `permissions: contents: read`.
- No `environment:`; this job reads no secret.
- No new conditional.
- `build` still `needs: validate-tag`.
- S02-002 later adds `name: validate-tag`. Do not add it here, to avoid rebase conflicts. If S02-002's rule is already in force when this story is implemented, adding it is harmless.

`justfile`:
- Define one shared default-branch value, for example a top-level backtick variable `default_branch` or a private `_default-branch` recipe.
- Derivation: `git symbolic-ref --quiet --short refs/remotes/origin/HEAD` with `origin/` stripped, falling back to `main`. It must never make just fail, because just evaluates top-level backticks at load time.
- `release` reads it instead of its inline derivation; its behaviour is otherwise unchanged.
- `act` adds `--defaultbranch <value>`, with its AD-16 comment extended to give the reason.

Spine:
- AD-12:
  - Rule step 1 gains the checkout and the ancestry step.
  - **Prevents** adds "a release from a commit not on the default branch".
- AD-16:
  - The `just act` line gains `--defaultbranch`.
  - Note that the default branch is derived once.
- Deferred gains "Tag protection for `v*` (GitHub ruleset / Gitea protected tag `v*`) is a forge setting; checklist in pipeline-walkthrough.md; documentation unless configured". The "Branch protection" bullet is S02-002's to remove.
- The Conventions "Conditionals" row is unchanged.
- Bump `updated:` and add a `(decision)` entry to `.memlog.md`.

Docs, all in `docs/ci/pipeline-walkthrough.md`:
- "Releasing":
  - The diagram shows `validate-tag (exactly vX.Y.Z, on main)`.

### Error and edge case handling

- **Tag on a commit not on `main`.** `validate-tag` fails, and nothing builds or publishes. Deleting the bad tag needs bypass rights once protection is on, which is intended.
- **Tag pushed before `main`.** The check fails. Push `main` (through a PR, under S02-002's ruleset), then re-run the workflow. The re-run checks out fresh and passes. This is documented in "Releasing".
- **`main` rewritten.** Force-pushing `main` is blocked by S02-002's required ruleset. If it happened through a bypass, a re-run of an old tag fails closed.
- **Empty or absent `default_branch`.** The step fails explicitly with a message.
- **act without `origin`, or with a stale `origin/main`.** The check fails closed with `Not a valid object name` (verified). This is documented.
- **Default branch renamed.** The payload carries the new name, and the justfile derivation follows `origin/HEAD`.
- **Re-run of a successful release.** It runs on the same, protected commit, so the check passes. ADR-0036 §5 holds.
- **Admin bypass moves a tag (AR-07).** The workflow does not prevent this. It is recorded as a residual in the ADR, together with the operator rule.
Spec: none — l3io-plan run, no spec index bound

### Observability requirements

- Every release log shows the tag, the commit SHA and the default branch that were checked, plus the refusal message on failure.
- Rejected tag pushes are reported to the pusher by the forge: the ruleset violation on GitHub, and "Tag … is protected" on Gitea.
- The checklist names the audit trail for bypasses: GitHub Settings → Rules → Insights.
Spec: none — l3io-plan run, no spec index bound

### Security considerations

- **The control is forge tag protection with the pattern `v*` on both forges.** Only the maintainer can create, move or delete `v*` tags: the bypass list on GitHub, the allowed users on Gitea. This closes RT-E013-02 and AR-01 against write-holders, stolen write tokens and agents. It is what makes S02-002's `release` environment a real gate.
- **The ancestry step is not a boundary** (finding 7). The ADR and the step comment say so, and the walkthrough does not describe it as protection.
- **"On main" equals "reviewed" only together with S02-002's required `main` protection:** a PR is required, force-push and deletion are blocked, and the maintainer may bypass. Until that is applied, the check proves only that the commit is reachable from `main`.
- **Pattern:** `v*` also covers floating `v1`/`v1.2` tags, which `release.yaml` rejects by name. The maintainer pushes those under bypass or as an allowed user.
- **Template injection:** forge values reach `run:` only through `env:`, which zizmor checks.
- **Residuals recorded in the ADR:**
  - admin bypass (AR-07);
  - forge settings are not mechanically checked from the repository, because that needs forge-specific API calls, which AD-9 forbids. The docs say so, and the `gh api` / Gitea API verifications are the evidence.
Spec: none — l3io-plan run, no spec index bound

## Dev Agent Record

### act verification (act 0.2.89, 2026-10-09)

Setup, in a throwaway directory (`/tmp/e013s02003.iEbu`); nothing was pushed to a real
remote and no tag or branch was created in the real repository:

```bash
git clone --bare <repo> origin.git && git clone origin.git work
rsync -a --exclude .git <worktree>/ work/        # the uncommitted story change
cd work && git add -A && git commit -m "S02-003 under test" && git push origin HEAD:main
# HOME=<tmp>/home with .actrc: -P ubuntu-latest=ghcr.io/catthehacker/ubuntu:act-latest / --pull=false
```

(a) Side-branch tag, detached, through the recipe:

```text
$ git switch -c side && <commit> && git tag v99.0.0 && git checkout v99.0.0
$ just act release.yaml                         # exit=1
[release/validate-tag] ⭐ Run Main Tag is on the default branch
[release/validate-tag]   | tag=v99.0.0 commit=b5ec9cd0ddf5e273afcafde15955dfc2116d9361 default-branch=main
[release/validate-tag]   | refusing to release tag v99.0.0: commit b5ec9cd0ddf5e273afcafde15955dfc2116d9361 is not on origin/main
[release/validate-tag]   ❌  Failure - Main Tag is on the default branch
[release/validate-tag] 🏁  Job failed
$ grep -c '\[release/build' a.log               # 0 — build never ran
```

(b) Tag on the default branch. The recipe's exact command plus `-j validate-tag`, because
later jobs run the whole build; only `validate-tag`'s result is asserted:

```text
$ git checkout main && git tag v98.0.0 && git checkout v98.0.0
$ act --detect-event -W .github/workflows/release.yaml --defaultbranch "$(just --evaluate default_branch)" \
    --artifact-server-path "$(mktemp -d)" -j validate-tag      # exit=0
[release/validate-tag]   | tag=v98.0.0 commit=86a1631f8face9e5727e7a156564700e87ee685a default-branch=main
[release/validate-tag]   ✅  Success - Main Tag is on the default branch
[release/validate-tag] 🏁  Job succeeded
```

(c) No `origin`, then (b) again — fails closed:

```text
$ git remote remove origin && git update-ref -d refs/remotes/origin/main
$ just --evaluate default_branch                # main (fallback; never fails)
$ act ... -j validate-tag                       # exit=1
[release/validate-tag]   | tag=v98.0.0 commit=86a1631f8face9e5727e7a156564700e87ee685a default-branch=main
[release/validate-tag]   | fatal: Not a valid object name refs/remotes/origin/main
[release/validate-tag]   | refusing to release tag v98.0.0: commit 86a1631f8face9e5727e7a156564700e87ee685a is not on origin/main
[release/validate-tag] 🏁  Job failed
```

Quoting check (review R-03): with `refs/remotes/origin/HEAD` pointing at `origin/a$(id)` and
an `act` shim that prints its arguments, `just act release.yaml` passed the literal
argument `a$(id)`; nothing was executed.
