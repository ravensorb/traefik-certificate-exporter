# Gate publish credentials behind forge environments

## Context

Promoted from deferred finding(s):
- BL-E013-018 (High, redteam (RT-E013-01)) — Needs maintainer decision (changes a recorded design decision); not implemented in closure. Proposed: GitHub environments (release=v* tags, dev=main) holding PUBLISH_* secrets; Gitea equivalent via ADR; gate zizmor secrets-outside-env. See _bmad-output/implementation-artifacts/epic-013/sprint-01/closure/redteam-report.md

### Research findings (verified 2026-10-09)

Sources are listed for each finding. "Verified" means I read the official source or ran the
tool myself.

1. **GitHub `jobs.<id>.environment`.**
   - A job receives environment secrets only if it references that environment.
   - All deployment protection rules must pass before the job is sent to a runner. A job on a
     ref the policy does not allow never gets the secrets.
   - "Selected branches and tags" matches `GITHUB_REF` using `File.fnmatch`. Branch rules and
     tag rules are set up separately, through a Ref type of **Branch** or **Tag**. So
     `release` uses Tag `v*` and `dev` uses Branch `main`.
   - Required reviewers are optional.
   - The repository is public (`gh api repos/ravensorb/traefik-certificate-exporter` →
     `visibility: public`), so policies and environment secrets are available.
   - Sources (github/docs): `content/actions/reference/workflows-and-actions/deployments-and-environments.md`
     §§"Deployment branches and tags", "Environment secrets";
     `data/reusables/actions/jobs/section-using-environments-for-jobs.md`;
     `content/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments.md`.
2. **GitHub creates missing environments.** Quoting `manage-environments.md`: "Running a
   workflow that references an environment that does not exist will create an environment
   with the referenced name … the newly created environment will not have any protection
   rules or secrets."
   - The gate therefore needs two things:
     - No publish secret at repository level.
     - Both environments created with their policies before the workflow change merges.
       Otherwise the first run auto-creates them unprotected.
3. **AD-9 presence flags still work.** An environment secret takes precedence over a
   repository secret with the same name. In a job that references the environment,
   `PUBLISH_X: ${{ secrets.PUBLISH_X_TOKEN != '' }}` reads the environment value. Source:
   `content/actions/how-tos/reuse-automations/reuse-workflows.md`.
4. **Reusable workflows.** A job that calls a reusable workflow cannot set `environment:`
   (`reuse-workflows.md`). `build.yaml` holds no secrets (AD-2), so no caller job needs one.
5. **Gitea 1.27+ ignores `jobs.<job_id>.environment`.**
   - gitea/docs `docs/usage/actions/comparison.md` lists it under "Unsupported workflows
     syntax".
   - Secrets exist only at user, organisation and repository level
     (`docs/usage/actions/secrets.md`; docs main branch fetched 2026-10-09; the latest
     releases are v28.1.0 and v1.27.3).
6. **nektos/act 0.2.89 ignores `environment:`.** I verified this by running it on a throwaway
   repository under `/tmp`. The job had `environment: release` and
   `FLAG: ${{ secrets.PUBLISH_X != '' }}`, run with `-s PUBLISH_X=abc`. act accepted the key
   without error and printed `flag=true`.
7. **zizmor 1.30.1, verified by running it.**
   - On the current tree, `--persona=auditor` reports:
     - 45 `secrets-outside-env` findings.
     - 7 `anonymous-definition` findings, one per unnamed job: `build.yaml` `build`;
       `dev.yaml` `publish-package` and `publish-image`; `release.yaml` `validate-tag`,
       `publish-package`, `publish-image` and `release`.
   - The default persona reports neither.
   - I then ran the same command on a git-initialised copy of `.github/` with two changes:
     - `name: <job-id>` added to those 7 jobs.
     - `environment:` added to the 5 publish jobs.
   - That run printed "No findings to report" and **exited 0**. Its 3 ignored findings are
     the existing inline per-line ignores.
   - So `--persona=auditor` alone, with no severity floor, is a working gate.
   - Setting `name:` equal to the job id leaves check names unchanged: the required check is
     still `build / build`.
8. **Current GitHub state.**
   - `gh api …/environments` returns nothing, and `/rulesets` returns `[]`.
   - The only repository-level Actions secrets are the legacy `DOCKERHUB_TOKEN` and
     `DOCKERHUB_USERNAME`. Running `git grep -nE 'DOCKERHUB_(TOKEN|USERNAME)\b'` over
     `.github`, `justfile` and `docker` finds no reference (exit 1), so both are unused.
   - No `PUBLISH_*` secret is set, so GitHub currently publishes nothing (AD-9).
9. **Gitea package permission scope**, checked in v1.27.3 source
   (`services/context/package.go` `determineAccessMode`).
   - Packages belong to a user or an organisation, not to a repository.
   - **User-owned** packages: only that user gets write. Any other user gets read at most.
   - **Org-owned** packages: a member's write comes from the org-level authorise level, or
     from any team whose **Packages** unit is write. That write covers **every** package of
     the organisation.
   - Neither repository collaboration nor any token setting confines a token to one package
     or one repository's packages.
   - What actually contains the credential is the namespace that owns the packages:
     - A token for the maintainer's own account can write all of the maintainer's packages.
     - A dedicated bot user, or a dedicated organisation that owns only this project's
       packages, limits exposure to that namespace.
   - For releases, a bot that collaborates only on this repository limits a
     `write:repository` token to this repository.
10. **Gitea 1.27 branch protection**, checked in v1.27.3 source.
    - The `models/git/protected_branch.go` `ProtectedBranch` fields used here:
      - `CanPush` with a push allowlist (`EnableWhitelist` / `WhitelistUserIDs` /
        `WhitelistTeamIDs`).
      - `CanForcePush` with a force-push allowlist.
      - `EnableBypassAllowlist`.
      - `EnableMergeWhitelist`.
      - `RequiredApprovals` and the status checks.
    - A protected branch cannot be deleted by push (`routers/private/hook_pre_receive.go`:
      "branch %s is protected from deletion").
    - Gitea has no separate "require a pull request" switch. Disabling push, or allowing push
      only to the maintainer, makes a PR merge the only way for anyone else to change `main`.

**Decisions recorded here:**
- Use two environments for least privilege:
  - `dev` (Branch `main`): `dev.yaml` `publish-package` and `publish-image`.
  - `release` (Tag `v*`): `release.yaml` `publish-package`, `publish-image` and `release`.
- **Maintainer decision (a), AG-20:** a `main` ruleset on GitHub and a protected `main` on
  Gitea are **required** forge settings. Branch protection moves out of the spine's Deferred
  list, as recorded in the new ADR.
- Gitea gets no forge-specific branching. Its residual risk is recorded under Security
  considerations.
- **Sequencing:** this story depends on E013-S02-003. S02-003 creates the
  `## Forge settings the maintainer applies` heading and the `v*` tag protection that
  `release` relies on. This story adds its subsections after that heading and merges after
  S02-003.

## Business acceptance criteria

### Outcome

Once all settings in the checklist are applied (S02-003's included), these statements hold.

**On GitHub:**
- No publish credential is stored at repository level.
- PyPI, the release token and the registry tokens used by releases are readable only by a
  job in `release.yaml` running on a `v*` tag. Only the maintainer, or a bypass actor, can
  create, move or delete such a tag.
- Dev-destination tokens are readable only by a job in `dev.yaml` running on `main`. `main`
  changes only through a pull request, unless the maintainer is on the bypass list, and
  cannot be force-pushed or deleted.
- A collaborator, a stolen write token or a write-capable agent cannot read any publish
  token by pushing a branch or a workflow file.

**On Gitea:**
- Any workflow from any branch pushed by a write-holder still receives every secret stored
  in Gitea. Environments do not exist there.
- The `main` and `v*` protections stop unreviewed code from being **published** through
  `dev.yaml` or `release.yaml`. They do not stop that secret theft.
- Theft is contained only by two measures:
  - Storing just the Gitea-destination tokens in Gitea.
  - Issuing them from a namespace that owns only this project's packages (finding 9).

**In CI:** the "every secret-reading job declares an environment" rule is enforced by
`just check`. Whether the forge settings are applied is not checked, and the docs say so.
Spec: none — l3io-plan run, no spec index bound

### Non-goals

- The dev agent applies no forge setting: no environments, secrets, rulesets or Gitea protection. Those are maintainer steps.
- No OIDC or trusted publishing. ADR-0035 rejects them for forge neutrality.
- No `v*` tag protection and no tag-ancestry check. Both belong to E013-S02-003, which lands first.
- No required reviewers on `release` by default. Adding them is an optional maintainer choice, and it would block unattended releases.
- No Gitea equivalent of environments is built, and no forge-specific YAML or condition is added (AD-6, AD-9).
- No change to `PUBLISH_*` variables (`vars.*`). They stay at repository level, as documented in `docs/operational.md` §Publishing.
- No move of the Gitea package namespace. Moving images or packages to a bot or dedicated organisation is a maintainer choice; the docs state the containment each choice gives.
- No change to `ci.yaml`.

### Error and edge case handling

- **Environment auto-creation (finding 2).** The order creates both environments before the merge (step 2), and step 5 detects any auto-created or misspelt environment. A typo in a workflow would create an empty environment, so its flags would be false and nothing would publish. The failure is loud (destinations skipped), and step 5 lists the environment.
- **Merge before secrets.** Between step 4 and step 6, every GitHub destination is disabled. The runs succeed as no-ops (AD-9). The merge is therefore decoupled from going live.
- **Secret missing or in the wrong environment.** The destination is silently disabled (AD-9). The step-6 verification lists each environment's secrets with `gh api repos/{owner}/{repo}/environments/{env}/secrets --jq '.secrets[].name'` and compares them with the derived list.
- **Ref the policy rejects.** GitHub fails the job before a runner starts, saying the ref "is not allowed to deploy to <env> due to environment protection rules". No secret is exposed.
- **Re-runs.** The policy matches the run's `GITHUB_REF` (a tag or `main`), so re-runs still qualify. ADR-0036 §5 is unchanged.
- **Shared tokens** (GHCR, Docker Hub, Gitea, CA) live in both environments. Rotating one means updating both (`docs/operational.md`).
- **Maintainer on the `main` bypass list.** A direct push by the maintainer still runs `dev`. This is accepted and recorded in the ADR.
- **Gitea and act.** `environment:` and `name:` are ignored or are cosmetic there; act was verified and Gitea is documented. Runs behave as before.

### Security considerations

**GitHub**
- **Threat closed (RT-E013-01).** Nothing is stored at repository level. A branch workflow that references `dev` or `release` is refused by the policy. An invented environment name yields an empty, auto-created environment, which step 5 detects.
- **`release` depends on S02-003.** The Tag `v*` policy admits any `v*` tag. S02-003's tag ruleset restricts creating, moving and deleting `v*` to the maintainer. That is why it is applied (step 3) before the merge and before any secret exists (step 6).
- **`dev` depends on `main` protection (AG-20, now required).** `dev` holds the GHCR, Docker Hub and Gitea registry tokens, which `release` uses too. So `main`'s ruleset must block force-push and deletion, and require changes via PR, with the maintainer allowed on the bypass list.

**Gitea**
- **Residual risk, recorded rather than branched on.** Gitea ignores `environment:` and has only user, org and repository secrets. A branch push by any write-holder gets every secret stored in Gitea.
- **Containment (finding 9):**
  1. Store only Gitea-destination secrets: `PUBLISH_GITEA_TOKEN`, a Gitea `PUBLISH_RELEASE_TOKEN`, and `PUBLISH_CA_CERTIFICATE` if needed. Never store PyPI, TestPyPI, GHCR or Docker Hub tokens in Gitea.
  2. Expect the Gitea package token to expose every package of the namespace that owns the packages, not just this project's. Tight containment needs packages owned by a dedicated bot user, or by an organisation that owns only this project's packages. The maintainer's personal token exposes all of the maintainer's packages.
  3. For releases, use a bot collaborator with write on this repository only. The `write:repository` scope then reaches only this repository.
  4. Keep write collaborators minimal.
- **Revisit** when Gitea gains environment secrets.

**General**
- **Self-hosted runners.** GitHub warns that environment secrets are not isolated on self-hosted runners. GitHub runs here use GitHub-hosted runners. Gitea runner trust is BL-E013-024 and out of scope.
- **Mechanical coverage (global rule 3).** `secrets-outside-env` is enforced. Forge settings are not, and cannot be without forge-specific API calls, which AD-9 forbids. The docs state that gap.
- No secret value appears in the repository, the docs or the logs.

### Decisions and assumptions

- **Ruleset bypass list (open point from S02-003 review).** Verified 2026-10-09: GitHub's guide "Creating rulesets for a repository" → "Granting bypass permissions" lists roles, teams and apps; the REST OpenAPI schema (github/rest-api-description `api.github.com.json`, `components.schemas.repository-ruleset-bypass-actor`) enumerates `actor_type` `Integration`, `OrganizationAdmin`, `RepositoryRole`, `Team`, `DeployKey`, `User`, and states `OrganizationAdmin` is not applicable for personal repositories. S02-003's claim "a ruleset cannot name an individual user" is therefore not supported by the schema; it was replaced (walkthrough and ADR-0038) with: use the Repository admin role, the form the guide documents; the owner is the only admin on this user-owned repo. Both rulesets' verification expects only `RepositoryRole` in `bypass_actors`. The numeric id of the admin role is not documented in the schema, so the docs do not quote one.
- Environment-creation and deployment-branch-policy API shapes (`deployment_branch_policy.custom_branch_policies`, `branch_policies[].{name,type}`) and the ruleset rule type `pull_request` checked against the same REST schema. Gitea branch-protection field names (`rule_name`, `enable_push`, `enable_push_whitelist`, `push_whitelist_usernames`, `enable_force_push`, `enable_force_push_allowlist`, `force_push_allowlist_usernames`, `bypass_allowlist_usernames`) checked against Gitea v1.27.3 `templates/swagger/v1_json.tmpl`.
