## Findings

### F-1 — Medium — kind: claim

- **Location:** `_bmad-output/implementation-artifacts/epic-013/sprint-01/closure/notes-E013-S01-005.md`
  lines 59, 114, 190.
- **Claim:** AC "Error and edge case handling / Install twine without the bypass": "Evidence
  of a passing run (act or forge) goes in the closure notes"; Testability: "run `just act
  dev.yaml` with no secrets. It should show `publish-image` skipping the guard and
  succeeding"; BL-E013-003 "Record a passing `publish-package` run (act or forge) without the
  bypass".
- **Why:** the notes point to "act evidence below" three times, but the file ends at line 190
  on `- act evidence → below.` with no such section. The only behavioural proof that removing
  `POETRY_DYNAMIC_VERSIONING_BYPASS` does not break `Install twine` (the AC's stop condition
  "No tags available") and that the guard is skipped when `PUBLISH_IMAGE` is false is absent.
  Both are claims the story makes and has not evidenced.
- **Fix:** run `just act dev.yaml`, append an "act evidence" section with the command, exit
  code, and the log lines showing `Install twine` succeeding and `Registry configuration
  guard` skipped; or state explicitly that the run was not performed and why.

### F-2 — Medium — kind: claim (doc accuracy: record's reach)

- **Location:** `.gitleaks.toml` header lines ~58-85; `docs/developer.md` ~lines 84-110;
  `docs/adr/0033-secret-scanning-exempts-no-path.md` ADR-0037 amendment.
- **Claim:** the inherited exempt set is recorded "with the gitleaks version that produced
  it", and "a gitleaks upgrade that changes the set must update this list"; developer.md says
  the trace "name[s] exactly these paths".
- **Why:** four of the nine recorded paths are not a function of the gitleaks version but of
  the local install: `.venv/lib/python3.11` (the contributor's interpreter; pyproject allows
  3.10-3.14 and CI uses 3.14) and the three/four `.poetry/plugins/*-<version>.dist-info`
  entries (the locked plugin versions). A contributor on another Python, or any Dependabot
  bump of poetry-dynamic-versioning/dunamai/jinja2/markupsafe, produces a different trace set
  with no gitleaks upgrade. The records name only the gitleaks upgrade as the drift trigger,
  so the documented diff procedure will report spurious drift in other environments and the
  record will go stale silently on routine plugin bumps. Under global rule 4 the record
  understates what determines its scope.
- **Fix:** in both records (and the ADR-0033 note), state that the set also depends on the
  local interpreter version and the installed plugin versions, record those alongside the
  gitleaks version (e.g. "Python 3.11 venv, poetry-dynamic-versioning 1.10.0"), and widen the
  drift trigger to "a gitleaks upgrade or a change to the plugin lock / venv interpreter".
  Optionally record the paths as the pattern class (`.venv/lib/python3.*`,
  `.poetry/plugins/*.dist-info`) with the concrete instance noted.

### F-3 — Low

- **Location:** `CONTRIBUTING.md` "Getting started" code block, first line.
- **Trigger:** a contributor makes a normal `git clone` (full history, tags present) and runs
  the block as written.
- **Why:** `git fetch --tags --unshallow` on a complete repository exits 128 with
  `fatal: --unshallow on a complete repository does not make sense` (reproduced). Run as a
  script under `set -e`, the block stops before `just install`; interactively it prints a
  fatal error on the common, healthy path. The prose below mentions the full-clone variant,
  but the copy-paste block is unconditional.
- **Fix:** keep only `just install` / `pre-commit install` in the block and move
  `git fetch --tags --unshallow` into the recovery sentence, or make it conditional, e.g.
  `git fetch --tags $( [ "$(git rev-parse --is-shallow-repository)" = true ] && echo --unshallow )`.
