## Findings

### F-01: MEDIUM, kind: edge-case / claim. `strict = true` breaks every Poetry command except `run`/`shell` in a tagless or shallow clone, not only `poetry build`
- **Location:** `pyproject.toml:130` (`strict = true`), with consequences at `.pre-commit-config.yaml:24` (`poetry check --lock`) and `justfile` `install`.
- **Claim:** the story says, under Error and edge case handling: "**`strict = true` with no matching tag reachable** (a shallow clone, or a fork without tags). `poetry build` fails rather than emitting `0.0.0`."
- **Observed:**
  - poetry-dynamic-versioning 1.10.0's plugin activates on every command except `run`, `shell` and its own `dynamic-versioning` commands. See `_should_apply` in `.poetry/plugins/poetry_dynamic_versioning/plugin.py:59-64`.
  - I made a scratch clone with `--no-tags --depth 1` and the new `pyproject.toml`/`poetry.lock`. In it, `poetry check --lock` exited 1. After `--unshallow` it still exited 1 with `No tags available and fallbacks disabled by strict mode`. With `POETRY_DYNAMIC_VERSIONING_BYPASS=0.0.0` it exited 0.
  - So the `poetry-lock` pre-commit hook, `poetry install`/`just install` and `poetry lock` all fail without reachable tags.
- **Impact:**
  - A contributor who clones shallow or without tags cannot install or run the hook list.
  - In E013-S01-002, every CI job that runs `poetry install`, `poetry check` or `pre-commit` needs `fetch-depth: 0` and `fetch-tags: true`, or the bypass variable. Configuring this only on `build.yaml`'s build step is not enough, though the story implies it is. That includes publish jobs that run `poetry install`.
  - Dependabot's `pip` updater runs Poetry on its own checkout. Whether it loads `requires-plugins` is **unverified**.
- **Suggested fix:**
  - Correct the edge-case text (story, and AD-7 at next amendment) to say that any plugin-activated Poetry command fails.
  - Add one line to the `install` recipe comment: "needs tags reachable from HEAD (strict); in a shallow/tagless clone run `git fetch --tags --unshallow` first".
  - Hand off to E013-S01-002: every job that invokes Poetry other than through `poetry run` checks out with `fetch-depth: 0` and `fetch-tags: true`, or sets `POETRY_DYNAMIC_VERSIONING_BYPASS` where the version is irrelevant.
  - Do not relax `strict`. AD-7 requires it.

### F-02: LOW, kind: claim. Ignoring `.poetry/` in git does not stop the gitleaks tree hook from scanning it
- **Location:** `.gitignore:14-15`; the hook is at `.pre-commit-config.yaml:60-63`.
- **Claim:** the story says, under Plugin installation: "Add `.poetry/` to `.gitignore` … Otherwise `just release`'s clean-tree check always fails after `poetry install`, and the gitleaks tree hook scans the installed plugin."
- **Observed:**
  - `gitleaks dir . --log-level trace` with the repo's config still scans `.poetry/`. Trace lines matching `.poetry/` occurred 96 times, for example `scanning path path=.poetry/plugins/dunamai/py.typed`. `gitleaks dir` does not read `.gitignore`.
  - The `.gitignore` entry does fix the clean-tree half of the claim. The gitleaks half is false.
  - The gate passes today only because the installed plugin contains nothing secret-shaped.
- **Impact:** the tree hook's scope includes installed third-party code. A plugin upgrade that ships a token-shaped test fixture would turn the gate red both locally and in CI. `.gitleaks.toml` forbids a `paths` allowlist, which rules out that remedy.
- **Suggested fix:**
  - Correct the story claim: only the clean-tree problem is solved.
  - Record that `gitleaks dir .` scans untracked install trees (`.poetry/`, and an in-project `.venv/` if one exists). Then either accept that consciously, or change the tree hook to scan only tracked content. The second option is an AD-3 change and needs an ADR, so it is not done here.

### F-03: LOW, kind: claim. `just release` adds an unrecorded precondition, and the story's re-run test describes a refusal the specified algorithm cannot produce
- **Location:** `justfile`, `release` recipe: the `if [ "$(git rev-parse "$base^{commit}")" = "$head_sha" ]` block.
- **Claim:** the story's Testability step 6 says "a re-run refuses because the tag exists". The Interface contract says "`release <major|minor|patch>` exactly as AD-16 and AD-15 specify".
- **Observed:** with only the 10 specified steps, a re-run after pushing `v0.2.1` picks `v0.2.1` as its base and computes `v0.2.2`, which does not exist. It would then tag the same commit a second time; the developer reproduced this. The added "HEAD is already released as $base" check is therefore what makes the re-run refuse. The code is correct. The story and AD-16 say otherwise and do not list the step.
- **Suggested fix:** record the precondition in the story's step list, and in AD-16 at the next spine amendment: "refuse if the base tag already points at HEAD". Correct the step 6 wording to "a re-run refuses because HEAD is already released". No code change.

## Not findings (checked)

- `git fetch --tags --force origin` still updates `origin/<default>`. Since git 1.9, `--tags` adds to the default refspec instead of replacing it.
- `poetry run pysemver` is unaffected by the versioning plugin, because `run` is on the plugin's exclusion list.
- The unquoted `{{ workflow }}` and `{{ bump }}` interpolation into shell would let a caller inject commands. Not reported: it is a local developer recipe run by the same user, so there is no security boundary.
