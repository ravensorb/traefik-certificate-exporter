# Code review — E013-S01-002

Reviewer: bmad-code-review (read-only). Scope: `.github/workflows/{build,ci,dev,release}.yaml` (read in full), `docker/Dockerfile` diff, deletions.

## Verification performed

- Deletions confirmed: `.github/actions/` is gone, `docker-bake.hcl` is gone, `tests/ci/` is gone. `.github/workflows/` holds exactly `build.yaml`, `ci.yaml`, `dev.yaml`, `release.yaml`.
- `uvx zizmor@1.30.1 --offline .github/workflows` reports "No findings to report (3 ignored, 52 suppressed)". The 3 ignored are the `self-repository` lines. zizmor did not report `use-trusted-publishing`, so the absence of those suppressions is correct ("suppress only the lines zizmor actually reports").
- actionlint was not run because the binary is not on PATH outside pre-commit. The developer reports that `just check` passed.
- Spot greps on the four workflows found no `ref:`/`repository:` on any checkout, no `ACT`, no `pull_request_target` and no `secrets: inherit`. Every `if:` is either `env.PUBLISH_X == 'true'` or the `validate-tag` `is-valid` test.
- `pyproject.toml` has `metadata = false`, so wheel versions carry no `+local` segment. The single `.dev` → `-dev.` substitution therefore always produces a valid Docker tag.
- The Dockerfile `Version()` check fails closed: an unparsable `VERSION` raises, Python exits non-zero, `!` turns that into a mismatch, and the build exits 1. The exact-string match is still accepted. pip, and so its vendored `packaging`, is present at that point because `ensurepip` runs before the check and `pip uninstall` runs after it.
- `.dockerignore` does not exist, so `dist/` is inside the build context and `WHEEL_PATH=dist/<wheel>` resolves through the bind mount.

Everything else matches the story's technical ACs: interface contracts, step order, flags, tag sets, guards before the CA import, token scope and pins.

## Findings

### F-1 — medium — kind: claim — `.github/workflows/ci.yaml:14`, `dev.yaml:23`, `release.yaml:45`

Claim: "zizmor's only suppressions are the per-line `# zizmor: ignore[...]` comments listed below" (Acceptance Criteria). The Technical AC adds: "If it cannot be fixed within the AD rules, record it in the closure notes for the architect; do not suppress it."

The code adds three `# zizmor: ignore[self-repository]` suppressions that are not in the table. The developer recorded the deviation in `closure/notes-E013-S01-002.md` and the backlog, but also suppressed the finding, which the story says not to do.

Assessment of the decision: the substance is sound. The only fix zizmor accepts is `uses: $/...`. That syntax is GitHub-only, and AD-6 requires one workflow that runs on GitHub, Gitea and act, so the finding cannot be fixed within the AD rules. Leaving it unsuppressed would fail the pre-commit gate, and with it `just check` and the `build` job on every run. A per-line suppression with its reason is narrower than disabling the audit in `zizmor.yml`, which the story forbids. The defect is procedural: a story-contract deviation was taken unilaterally rather than ratified.

Suggested fix: no code change. Before this story closes, the architect should ratify the deviation by amending AD-5's suppression list (via ADR-0036 or a successor) to add `self-repository` on `uses: ./.github/workflows/build.yaml`, citing AD-6. If the architect declines, the alternative is a severity floor in `zizmor.yml`, which needs its own decision.

### F-2 — low — kind: edge — `.github/workflows/dev.yaml:109-111,185-188`, `release.yaml:129-131,203-206`

If a registry's `PUBLISH_*_TOKEN` secret is set but its `vars.PUBLISH_*_IMAGE` variable is empty, that registry's image name evaluates to `''`. The login still runs, the metadata action drops the blank line, and the job succeeds without pushing to that registry. A configured destination therefore silently receives nothing. If all enabled registries lack their image variable, `build-push-action` fails with `push: true` and no tags. That failure is loud, but the partial case is not.

This follows the story's mandated expressions, and AD-9 calls the token the switch. The gap is that a half-configured destination is not reported.

Suggested fix: add one unconditional `run:` step after the version guard. It reads `PUBLISH_GHCR`/`GHCR_IMAGE` and the other two pairs through `env:`, and fails naming the registry when the flag is `true` and the image name is empty. It needs no `if:`, so it stays within the two allowed conditional forms. Alternatively, record that this is the accepted behaviour in the walkthrough (E013-S01-003).

### F-3 — low — kind: claim — `.github/workflows/release.yaml:259-264`

Claim: "every step in `release` carries `if: env.PUBLISH_RELEASE == 'true'` … the job succeeds as a no-op when the flag is false."

The CA import step is gated only on `PUBLISH_CA`. When `PUBLISH_CA_CERTIFICATE` is set but `PUBLISH_RELEASE_TOKEN` is not, the `release` job imports the CA and so is not a no-op. The story contradicts itself here, because its step 1 specifies `if: env.PUBLISH_CA == 'true'`, and the implementation follows the more specific text. The effect is harmless: the secret is used only by the step that consumes it, and nothing is published.

Suggested fix: none required. Optionally note in the closure notes that the CA import is the one `release` step not gated on `PUBLISH_RELEASE`, because a step can test only one flag.

## Dimension summary

- **Interface contracts:** conform. Job ids, triggers, outputs, step order, build-args, tag sets and the LiquidLogicLabs inputs match the story and the developer's action.yml reading.
- **Error and edge handling:** conform, except F-2. The count assertion, the guards, the `validate-tag` reject step and the fail-closed PEP 440 check are all present.
- **Observability:** conform. The version step echoes the version, image-version, wheel and SHA-256. The guard and reject steps print the offending value. The `prev` step logs the previous tag.
- **Security:** conform. There are no secrets in `build.yaml` or `ci.yaml`. Every token appears only in its consuming step. Every checkout sets `persist-credentials: false`. No `${{ }}` appears in `run:` bodies. Third-party actions are SHA-pinned.
- **Testability:** conform. There is no bespoke harness; verification uses pre-commit (actionlint and zizmor) and pytest.
- **Existing-library check / reused-before-written:** conform. The only `run:` logic is the set the story justifies: wheel-METADATA read via stdlib, `sha256sum`, the count assertion, the `case`/string guards and the `git tag | awk` previous-tag filter. The Dockerfile uses pip's vendored `packaging` and does not hand-roll a version parser. The `Locate wheel` step re-hashes the wheel that `build` already hashed, but the story mandates that, because those values are step outputs only.
- **Deletion check (`kind: deletion`):** the removed Dockerfile comment referenced the `docker-bake.hcl`↔Dockerfile `BASE_IMAGE` equality test. Both ends of that contract were deleted in this story, and the `BASE_IMAGE` ARG default that Dependabot uses is retained. No contract was dropped (high confidence). The replaced `VERSION` equality check is a deliberate widening per ADR-0036 and keeps the exact-match path and the empty-`VERSION` rejection (high confidence).
