# New workflows: build, ci, dev, release; remove the old workflows and tests/ci

## Context

Core of E013 (ADR-0035). Replaces the five-workflow governed pipeline with four trigger-selected workflows: reusable credential-free `build.yaml`, and thin `ci.yaml`, `dev.yaml`, `release.yaml` (AD-1, AD-2). Implements version hand-off (AD-7), tag ownership (AD-8), credential-gated destinations (AD-9), the one-build image fan-out (AD-10), `twine` package publishing (AD-11), release (AD-12), permissions (AD-13), concurrency (AD-14), the dev-version guard (AD-15), the Dockerfile build contract (AD-17) and private-CA support (AD-18). Because `tests/ci/` asserts the shape of the old workflows, it is removed in this story together with `verify-build.yaml`, `publish-image.yaml` and the three composite actions (`verified-bundle`, `publication-contract`, `setup-poetry-python`).

Design authority: `_bmad-output/planning-artifacts/architecture/architecture-ci-cd-pipeline-2026-10-08/ARCHITECTURE-SPINE.md` (AD-1..AD-18), `docs/adr/0035-standard-ci-cd-pipeline.md`, `docs/ci/pipeline-walkthrough.md`. Rules are cited by AD id; do not re-decide them.

## Acceptance Criteria

- `.github/workflows/` contains exactly `build.yaml`, `ci.yaml`, `dev.yaml` and `release.yaml`, with the triggers, job ids and ordering of AD-1, AD-2 and AD-12.
- `build.yaml` holds no credential, outputs `version` and `image-version`, smoke-tests a single-arch image built per AD-17, and uploads one `dist` artifact with one wheel and one sdist.
- Every destination in AD-9's table publishes only when its `PUBLISH_*_TOKEN` secret is set, using only the two allowed conditional forms; with no secrets set, `dev.yaml` and `release.yaml` succeed and publish nothing.
- `publish-image` performs one multi-arch build pushed to every enabled registry with the AD-8 tag set for its workflow, then tests the pushed image by digest.
- `publish-package` checks out (ref-free) before any `poetry` command and uploads with `twine` per AD-11; dev publish jobs refuse a non-`.dev` version (AD-15); release publish jobs refuse a version that differs from the pushed tag.
- `release` creates the forge release with generated notes and attached wheel and sdist using `PUBLISH_RELEASE_TOKEN`.
- No checkout carries `ref:`/`repository:`, nothing references `env.ACT`, every workflow is `permissions: contents: read`, and actionlint and zizmor pass. zizmor's only suppressions are the per-line `# zizmor: ignore[...]` comments listed below, each citing its AD/ADR (AD-5 as amended by ADR-0036).
- `docker/Dockerfile` checks `VERSION` under PEP 440 normalisation and runs its dependency install with `POETRY_DYNAMIC_VERSIONING_BYPASS=0.0.0` (AD-17 as amended by ADR-0036).
- `just act` (ci.yaml) and `just act dev.yaml` succeed with no secrets, and their logs show the `build` job executed.
- `verify-build.yaml`, `publish-image.yaml`, the three composite actions and `tests/ci/` are deleted; `pytest` and `just check` pass.
- E013-S01-001 and E013-S01-002 land as one change, on the same branch; E013-S01-001 is not closed before this story.

## Business acceptance criteria

### Outcome

The maintainer has four short workflows: a pull request tests, a push to `main` publishes a dev build, and a `vX.Y.Z` tag publishes a release. Each destination is switched on by setting one `PUBLISH_*_TOKEN` secret on either forge.

Contributors get a pull-request check (`build / build`) that runs exactly what `just check` runs. Fork pull requests never reach a credential.

With no secrets configured, every workflow succeeds and publishes nothing, so `act` and a fresh fork are safe by default.

Spec: none — l3io-plan run, no spec index bound

### Non-goals

- No live run on GitHub or Gitea, and no real publish. That is E013-S01-004.
- The remaining legacy surface is not removed here: `src/publication_contract/`, the release/integrity scripts, `vendored-trees.lock`, `docker/act-build.sh` and the CODEOWNERS vendored block all belong to E013-S01-003.
- No docs, README or ADR status changes (E013-S01-003).
- No provenance attestations, SBOM, image vulnerability scan or branch-protection setting (spine Deferred).
- No `workflow_dispatch` trigger, no fifth workflow, and no CHANGELOG file (AD-1, AD-12).
- `pyproject.toml` versioning, `.pre-commit-config.yaml`, `zizmor.yml` and the justfile are not changed here (E013-S01-001).

## Technical acceptance criteria

### Interface contracts

**Conventions every new workflow follows** (derived from the existing `.github/workflows/*.yaml`):
- The extension is `.yaml`.
- A top-level `name:` is set.
- Top-level `permissions: contents: read` (AD-13). No job widens it; jobs may restate it.
- Every job is `runs-on: ubuntu-latest` (AD-6).
- Job ids are exactly `validate-tag`, `build`, `publish-package`, `publish-image` and `release` (Conventions table).
- Third-party `uses:` take the Stack SHA plus a trailing `# vX.Y.Z` comment. `LiquidLogicLabs/*` uses the major tag (AD-5).
- `actions/checkout` sets only `fetch-depth`, `fetch-tags` and `persist-credentials: false`. It never sets `ref:` or `repository:` (AD-6, ADR-0028).
- No expression references `env.ACT`/`ACT`.
- Untrusted or computed values reach a `run:` script only through `env:`, never by inlining `${{ }}` in the script body. This satisfies zizmor's `template-injection` audit.
- Short `#` comments cite the AD id a block implements. The existing workflows' long CI-AR rationale comments are not carried over.

**`build.yaml` (AD-2, AD-6, AD-7, AD-17)**
- Trigger is `on: workflow_call` only.
- `outputs`:
  - `version: ${{ jobs.build.outputs.version }}`
  - `image-version: ${{ jobs.build.outputs.image-version }}`
- It declares no `secrets:` and no `inputs`.
- One job `build`, with `permissions: contents: read` and `outputs` mapped from step `version`. Steps in AD-2 order:
  1. `actions/checkout@3d3c42e5…` (v7.0.1) with `fetch-depth: 0`, `fetch-tags: true`, `persist-credentials: false`.
  2. `actions/setup-python@5fda3b95…` (v7.0.0) with `python-version: "3.14"`, the value the retired workflows used. Then install `poetry==2.4.2` with pip, then `poetry install`, which also installs the `requires-plugins` plugin.
  3. `poetry run pre-commit run --all-files`.
  4. `poetry run pytest`.
  5. `poetry build`, then assert exactly one `dist/*.whl` and one `dist/*.tar.gz`, failing otherwise.
  6. Step `id: version`:
     - Read `Version:` from the wheel's `*.dist-info/METADATA` using stdlib `zipfile` and `email.parser`. No string-guessing from the file name.
     - Write `version=<PEP 440>` and `image-version=<SemVer>` to `$GITHUB_OUTPUT`.
     - Derive `image-version` with the single substitution `.dev` → `-dev.`. A release version passes unchanged.
     - This step is the only version transform in the repository (AD-7).
     - Also output `wheel-path` and `wheel-sha256` (`sha256sum`) for step 7. These are step outputs only, not `workflow_call` outputs.
  7. `docker/setup-buildx-action@f87e5991…` (v4.4.1), then `docker/build-push-action@c3c9e263…` (v7.4.0) with:
     - `context: .`
     - `file: docker/Dockerfile`
     - `push: false`
     - `load: true`
     - no `platforms` (native single-arch)
     - `tags: traefik-certificate-exporter:build`
     - `build-args` exactly `POETRY_VERSION=2.4.2`, `WHEEL_PATH`, `WHEEL_SHA256`, `VERSION=<image-version>`, `REVISION=${{ github.sha }}` (AD-17)

     Then `LiquidLogicLabs/git-action-docker-test@v2` against `traefik-certificate-exporter:build`. Read its `action.yml` for input names and record them in a comment.
  8. `actions/upload-artifact@cf430e03…` (v7.0.2) with `name: dist`, `path: dist/`, `if-no-files-found: error`.

**`ci.yaml` (AD-1)**
- `on: pull_request: branches: [main]`.
- One job `build: uses: ./.github/workflows/build.yaml`, with no `secrets:` and no `with:`. The required check name is `build / build`.
- No concurrency block (AD-14 binds only dev and release).

**`dev.yaml` (AD-1, AD-14, AD-15, AD-9, AD-10, AD-11, AD-18)**
- `on: push: branches: [main]`.
- `concurrency: { group: dev, cancel-in-progress: true }`.
- Jobs, in this order:
  - `build` (`uses: ./.github/workflows/build.yaml`);
  - `publish-package` (`needs: build`);
  - `publish-image` (`needs: build`).

**`release.yaml` (AD-1, AD-12, AD-14)**
- `on: push: tags: ['v*']`.
- `concurrency: { group: release, cancel-in-progress: false }`.
- `validate-tag` steps:
  1. `LiquidLogicLabs/git-action-tag-validate-version@v2` with `id: tag` and `version-regex: '^v\d+\.\d+\.\d+$'`, plus the tag input the action requires (`github.ref_name`; check its `action.yml`).
  2. `if: steps.tag.outputs.is-valid != 'true'` → `run: exit 1`, with an `echo` naming the tag (passed via env).
- `build`: `needs: validate-tag`, `uses: ./.github/workflows/build.yaml`.
- `publish-package` and `publish-image`: `needs: build`.
- `release`: `needs: [build, publish-package, publish-image]`.

**Version guards.** Each publish job starts with one guard step with no `if:`. Values reach the script only through `env:`.
- **dev.yaml (AD-15):** `env: VERSION: ${{ needs.build.outputs.version }}`, then `case "$VERSION" in *.dev*) ;; *) echo "refusing to publish non-dev version $VERSION" >&2; exit 1;; esac`.
- **release.yaml:** `env: VERSION: ${{ needs.build.outputs.version }}` and `TAG: ${{ github.ref_name }}`, then `[ "$VERSION" = "${TAG#v}" ] || { echo "refusing to publish $VERSION from tag $TAG" >&2; exit 1; }`. It catches a build whose version disagrees with the tag that triggered it.

The guard runs before the AD-18 CA import (AD-17 as amended by ADR-0036). It needs no network or secret; the CA import is the first step that touches a credential.

**Destination flags (AD-9).** These are job-level `env` in every publish job, one per destination the job can write. A flag is computed only as `${{ secrets.PUBLISH_X_TOKEN != '' }}` (`PUBLISH_CA` uses `secrets.PUBLISH_CA_CERTIFICATE != ''`).

**`release` job (AD-12)**
- `env:` `PUBLISH_CA: ${{ secrets.PUBLISH_CA_CERTIFICATE != '' }}` and `PUBLISH_RELEASE: ${{ secrets.PUBLISH_RELEASE_TOKEN != '' }}`.
- **Interpretation, recorded:** the Conventions table says the flag is also used at job level. A job-level `if:` cannot read the `env` context, and actionlint rejects it. So every step in `release` carries `if: env.PUBLISH_RELEASE == 'true'`, which is the same single-flag form, and the job succeeds as a no-op when the flag is false.
- Steps:
  1. CA import (`id: ca`, `if: env.PUBLISH_CA == 'true'`), as in `publish-package`, so a private-CA Gitea API is trusted before the changelog and release calls (AD-18);
  2. checkout (`fetch-depth: 0`, `fetch-tags: true`, ref-free, `persist-credentials: false`);
  3. download-artifact `dist` → `dist/`;
  4. a `run:` step `id: prev` that finds the previous release tag and writes `tag=<tag or empty>` to `$GITHUB_OUTPUT`. It is the highest tag reachable from `HEAD^` matching `^v\d+\.\d+\.\d+$`, so floating (`v0`, `v0.2`) and malformed (`v0.1.0.0`) tags are never the range start. Use `git tag --merged HEAD^ --sort=-v:refname | awk '/^v[0-9]+\.[0-9]+\.[0-9]+$/ && !f {print; f=1}'`, which reads all input and exits 0 when nothing matches. On the first release the output is empty;
  5. `LiquidLogicLabs/git-action-release-changelog-builder@v3` (`id: notes`, `token: ${{ secrets.PUBLISH_RELEASE_TOKEN }}`, `from-tag: ${{ steps.prev.outputs.tag }}`). The action has no tag-pattern input (its v3 `action.yml` offers `from-tag`, `to-tag`, `ignore-pre-releases`, but no filter), so the previous tag is computed in step 4. **Decision, recorded:** an empty `from-tag` falls back to the action's own auto-detection, which is acceptable only for the first release; confirm this when reading the action;
  6. `LiquidLogicLabs/git-action-release@v2` with:
     - `token: ${{ secrets.PUBLISH_RELEASE_TOKEN }}`
     - `allow-updates: true`
     - the tag from `github.ref_name`
     - the body from `steps.notes.outputs`
     - artifacts `dist/*.whl` and `dist/*.tar.gz`

     Read both actions' `action.yml` for the exact input names.

### Error and edge case handling

- **No secrets set** (fork, act, or a fresh repo):
  - all flags are `'false'`;
  - every guarded step skips;
  - `publish-image` and `publish-package` succeed having written nothing;
  - `release` succeeds with no forge release.

  This is the AC "with no secrets set, dev and release succeed and publish nothing".
- **Some registries enabled.** `images:` contains blank lines, which the metadata action drops. The `TEST_IMAGE` fallback chain picks the first enabled name.
- **Re-runs are idempotent** (Conventions, as amended by ADR-0036):
  - `twine --skip-existing` skips files already uploaded;
  - the release action's `allow-updates: true` updates the existing release;
  - `publish-image` rebuilds from the same wheel, and every tag that run writes is re-pointed, in every enabled registry, to the one digest that run built. A multi-arch rebuild is not byte-reproducible, so the digest differs from the previous run's; the earlier digest is left untagged. The registries never disagree with each other.

  A re-run of `dev.yaml` after the commit was tagged fails at the version guard, because the version no longer contains `.dev` (AD-15).
- **Malformed or pre-release tag** (`v1.2`, `v1.2.3-rc1`, `v0`). `validate-tag` fails, so `build` and everything after it never runs.
- **Tag and built version disagree** (for example a tag pushed on a commit the plugin resolves differently). The release version guard fails both publish jobs before any credential is used, so nothing publishes and `release` does not run.
- **No previous `vX.Y.Z` tag** (first release). Step `prev` outputs an empty tag and the changelog builder falls back to its own default.
- **Wrong artifact count.** The `build` count assertion fails if `poetry build` yields more than one wheel or sdist. Publish jobs never rebuild (AD-2).
- **Missing tags in a checkout.** `fetch-depth: 0` plus `fetch-tags: true` means `strict = true` always finds the base tag. On act, checkout is skipped (ref-free) and the local `.git` is used. `publish-package` has the same checkout, plus the bypass on its tooling install.
- **Superseding dev push.** `cancel-in-progress: true` cancels the older run. This is the sole ordering protection, which is how BL-E012-009 is dispositioned (AD-14). A release is never cancelled mid-flight.
- **Downstream failure.** `release` needs both publish jobs, so a failed publish leaves no forge release. A partial publish is completed by re-running failed jobs, which is idempotent.
- **arm64 build** runs under QEMU. Build time grows, but no step branches on architecture.
- **`download-artifact` v8 on Gitea** is unverified here. The v7.0.0 fallback (`37930b1c…`) is applied only if E013-S01-004 observes a failure.

Spec: none — l3io-plan run, no spec index bound

### Observability requirements

- `build`'s version step echoes `version=`, `image-version=`, wheel name and wheel SHA-256 to the job log.
- The metadata step logs the resolved tag list.
- `build-push-action` exposes `digest`, which the docker-test step logs as `<image>@<digest>`.
- Each `twine upload` logs the uploaded file URLs.
- The guard and `validate-tag` failure steps print the offending value.
- Correlation is provided by the forge itself, with no custom summary machinery (AD-4):
  - run id and run URL;
  - `github.sha`, carried into the image as `REVISION` and as the metadata-action OCI `revision` label;
  - the `sha-<7>` dev tag.

  An image digest traces back to its commit through the OCI labels.

### Security considerations

- **`build.yaml` holds no credential (AD-2).** Callers pass no `secrets:` (no `secrets: inherit`), and `ci.yaml` runs on `pull_request`, never `pull_request_target`. Fork PRs therefore reach no secret.
- **Permissions (AD-13).** `permissions: contents: read` everywhere, and no job widens it. The ambient `GITHUB_TOKEN`/`GITEA_TOKEN` is never referenced. Releases use `PUBLISH_RELEASE_TOKEN`.
- **Naming (AD-9).** Every secret and variable name starts with `PUBLISH_`; none starts with `GITEA_` or `GITHUB_`.
- **Token scope.** Each token appears only in the one step that consumes it, and never in a job-level `env` (only the boolean flag does).
- **Template injection.** `persist-credentials: false` on every checkout prevents the zizmor `artipacked` finding. No `${{ }}` is interpolated inside `run:` bodies, which prevents `template-injection`.
- **Pin policy (AD-5).** Third-party actions are SHA-pinned per Stack, and zizmor enforces it. `LiquidLogicLabs/*` rides major tags, an accepted risk recorded in ADR-0035.
- **Wheel provenance (AD-17, ADR-0008 as amended).** The image installs only the `dist` wheel whose SHA-256 matches.
- **Private CA (AD-18).** It is imported only when `PUBLISH_CA_CERTIFICATE` is set, and is trusted by the runner, BuildKit (`config`) and `twine` (`REQUESTS_CA_BUNDLE`).

Spec: none — l3io-plan run, no spec index bound

Its log shows the `build` job executed, `publish-package` reached its checkout and `poetry install` (which exercises the AG-1 fix), and every `PUBLISH_*` step skipped with no login or push.
