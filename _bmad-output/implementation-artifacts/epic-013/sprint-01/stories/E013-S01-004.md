# Live verification on GitHub, Gitea 1.27 and local act

## Context

Final story of E013 (ADR-0035): prove the same YAML on all three supported runners before the epic closes (AD-6). The spine defers to this story the live checks that cannot be made from the repository: artifact upload v7 / download v8 on Gitea, `workflow_call` and `concurrency` on Gitea 1.27, and `twine` uploads. Needs the maintainer's runners and secrets, so it carries human-in-the-loop time.

Design authority: `_bmad-output/planning-artifacts/architecture/architecture-ci-cd-pipeline-2026-10-08/ARCHITECTURE-SPINE.md` (AD-1..AD-18), `docs/adr/0035-standard-ci-cd-pipeline.md`, `docs/ci/pipeline-walkthrough.md`. Rules are cited by AD id; do not re-decide them.

## Acceptance Criteria

- `just act` runs `ci.yaml` to success locally, and `just act dev.yaml` runs to success with no secrets and publishes nothing. Both use `--detect-event` (AD-16 as amended by ADR-0036), and the recorded log excerpts show the `build` job executed; exit status 0 alone is not accepted.
- On GitHub: a pull request runs `ci.yaml` green; a push to the default branch publishes a dev build to each configured destination with the AD-7/AD-8 versions and tags; a test tag `vX.Y.Z` (on a disposable version line or test destinations) publishes the release and creates the forge release.
- On Gitea 1.27+: the same three runs succeed with the same YAML, including artifact hand-off between jobs, `concurrency`, and `twine` upload to the Gitea package index.
- If `actions/download-artifact` v8 fails on Gitea, the v7.0.0 fallback recorded in the spine is applied and re-verified.
- Results (run URLs, versions, tags and digests per destination) are recorded in `docs/ci/pipeline-walkthrough.md` or a linked verification note, and any defect found is fixed or filed.
- Once every required cell is recorded, ADR-0035's status becomes `Accepted`, dropping "— implementation pending".

## Business acceptance criteria

### Outcome

The maintainer has recorded evidence that the same four workflows run on all three supported runners (AD-6): GitHub-hosted, Gitea 1.27+ `act_runner`, and local `act`.

That evidence shows, for each of a pull request, a dev push and a release tag:
- the runs are green;
- each enabled destination received the AD-7 version and the AD-8 tags;
- disabled destinations received nothing.

Anyone setting up a new forge or diagnosing a failure can compare against a known-good run: its URL, version, tags and digest.

Spec: none — l3io-plan run, no spec index bound

### Non-goals

- This story makes no planned changes to the pipeline's design. A defect found here is fixed in the workflow, within the AD rules, or filed. It is not redesigned.
- Real PyPI uploads are out of scope. A test tag must not publish to production PyPI. The PyPI step is first exercised by the first real release.
- No branch-protection configuration. That is a forge setting, and spine Deferred names only the required check `build / build`.
- No attestation, SBOM or scanning (Deferred).
- No performance or runtime benchmarking of the workflows.

## Technical acceptance criteria

### Interface contracts

This is a **human-in-the-loop** story. The maintainer supplies runners, forge repositories, secrets and variables. The agent prepares the configuration checklist, runs `act`, triggers or observes runs, and writes the record.

**Run matrix.** Each cell is one recorded run.

| Runner | `ci.yaml` (PR) | `dev.yaml` (push `main`) | `release.yaml` (tag) |
| --- | --- | --- | --- |
| local `act` | `just act` | `just act dev.yaml` (no secrets; from `main`, or with an event file setting `ref: refs/heads/main`) | not required |
| GitHub | PR on `ravensorb/traefik-certificate-exporter` | push to `main` | test tag in a **disposable** repo |
| Gitea 1.27+ | PR on the Gitea mirror | push to `main` | test tag in a **disposable** repo |

**Disposable release target** (assumption, recorded):
- The release run uses a throwaway repository on each forge, a copy of the tree with its tags.
- Its variables point images at test names, for example `<registry>/<owner>/tce-verify`, and `PUBLISH_GITEA_PYPI_URL` at a test owner's index.
- `PUBLISH_PYPI_TOKEN` is unset.
- The tag is the next patch above the copy's latest `vX.Y.Z`.
- This keeps the real version line and production PyPI untouched while still exercising `validate-tag`, `build`, both publish jobs and `release` (AD-12).
- If the maintainer instead chooses a real release on the main repos, record that choice in the evidence note.

**Destinations to enable** (AD-9). Across the GitHub and Gitea dev runs together, set at least these:
- `PUBLISH_GITEA_TOKEN` (Gitea index plus Gitea registry);
- `PUBLISH_TESTPYPI_TOKEN`;
- `PUBLISH_GHCR_TOKEN`;
- `PUBLISH_DOCKERHUB_TOKEN` (optional, if the maintainer has a test repo);
- `PUBLISH_RELEASE_TOKEN` on each forge;
- `PUBLISH_CA_CERTIFICATE` on Gitea, if it uses a private CA.

Each one comes with its variables as in the walkthrough table. At least one run must also leave one destination disabled, to show it is skipped.

**Evidence record — `docs/ci/pipeline-verification.md`**, a new file in the same style as its sibling `docs/ci/pipeline-walkthrough.md`:
- It opens with a heading, a line on what it records, and the date.
- It is linked from the walkthrough's "Requirements" section with one line.
- It holds one table per runner. Each row has:
  - workflow;
  - trigger;
  - run URL;
  - commit SHA;
  - `version` / `image-version` outputs;
  - per destination: published or skipped, plus the package URL or `image@digest` and the tag list;
  - result.
- A "Gitea specifics" subsection records:
  - the Gitea server version;
  - the `act_runner` version;
  - artifact upload v7 / download v8 outcome;
  - `workflow_call` outcome;
  - `concurrency` outcome, shown by two quick pushes with the first cancelled;
  - `twine` upload to the Gitea index;
  - CA import, if used.
- A "local act" subsection records the `act` version, the full `just act` command line (showing `--detect-event`), the summarised exit and skip lines, and the lines showing the `build` job's steps ran (pre-commit, pytest, `poetry build`, image smoke test) and, for `dev.yaml`, `publish-package`'s checkout and `poetry install`.
- A "Known limitations" list records anything the run shows the design does not do, without inventing a fix (see the `0.x` major-tag check below).
- A "Defects" list names each problem found, with a fixed-in commit or a filed backlog key.

**Checks per run:**
- **dev runs:**
  - the package version matches `X.Y.(Z+1).devN` (AD-7);
  - the image carries tags `X.Y.(Z+1)-dev.N`, `sha-<7>` and `dev`, with the same digest across every enabled registry (AD-8, AD-10);
  - TestPyPI and the Gitea index show the dev version.
- **release run:**
  - the tags are `X.Y.Z`, `X.Y`, `X` and `latest`;
  - **`0.x` major tag.** The disposable release is a `0.x` version. Record whether `git-action-docker-metadata@v6`'s `type=semver,pattern={{major}}` produced the `X` (`0`) tag. If it did not, record that as a known limitation for the maintainer in the evidence note. Do not change the workflow to add it;
  - the forge release exists with generated notes and the wheel and sdist attached;
  - the notes' range starts at the previous `vX.Y.Z` tag, never at a floating (`v0`, `v0.2`) or malformed (`v0.1.0.0`) tag: the changelog builder's `from-tag` output equals the `prev` step's tag. Record both;
  - the release version guard passed: the build's `version` equals the tag without its leading `v`;
  - a deliberate re-run of the failed or complete jobs succeeds (Conventions, as amended by ADR-0036): `--skip-existing` skips the packages, `allow-updates` updates the release, and every image tag that run wrote points, in every enabled registry, to the one digest the re-run built. Record both digests. A new digest on re-run is expected; registries disagreeing with each other is a defect.
- **malformed tag:** a pushed `vX.Y` or `vX.Y.Z-rc1` in the disposable repo fails at `validate-tag`, and nothing publishes.

Spec: none — l3io-plan run, no spec index bound

### Error and edge case handling

- **`actions/download-artifact` v8 fails on Gitea** (spine Deferred, ADR-0035 Consequences). Apply the pre-recorded fallback:
  1. Change every `download-artifact` `uses:` in `dev.yaml` and `release.yaml` to `actions/download-artifact@37930b1c2abaa49bbe596cd826c3c89aef350131 # v7.0.0`.
  2. Re-run on all three runners.
  3. Record both the failing v8 run and the passing v7.0.0 run.

  Applying the recorded fallback does not change the design. Do **not** add a Dependabot `ignore` entry, because the spine retires those. Instead the evidence note records that Dependabot will re-propose v8, and that such a PR must be closed until Gitea supports it. Record the Stack-table discrepancy as a finding for the architect, who is the spine owner.
- **`upload-artifact` v7 fails on Gitea.** The spine pre-records no fallback. File a defect and end `BLOCKED` for the Gitea column instead of improvising a pin.
- **`workflow_call` or `concurrency` unsupported** on the maintainer's Gitea. Confirm the server is at least 1.27.0 (Stack). If it is older, the run is out of support, so record it and upgrade rather than change the YAML.
- **One destination fails mid-run** (bad token or URL). Fix the variable or secret and re-run the failed jobs. Record the first failure and the re-run, which exercises the idempotent re-run convention: after the re-run, every registry's tags name the re-run's digest.
- **`just act` exits 0 but the `build` job did not run** (for example `--detect-event` missing, or `dev.yaml` run off `main` with no event file). That is a failed cell, not a pass; fix the invocation and re-run.
- **A dev re-run after tagging** must fail at the AD-15 guard. Record one such re-run as evidence.
- **A secret or variable named with a `GITEA_`/`GITHUB_` prefix** is rejected by Gitea, which confirms the AD-9 naming rule. The fix is to rename it.
- **Human availability.** If the maintainer's runners or secrets are not available in a session, record which cells are complete and end that session's work as `BLOCKED: awaiting maintainer runner/secrets`. Never fabricate a run URL.

Spec: none — l3io-plan run, no spec index bound

### Observability requirements

- Every recorded run is identified by its forge run URL and commit SHA.
- Every published image is identified by `image@sha256:digest`. A `docker buildx imagetools inspect` of each registry's tag shows the same digest and both platforms.
- Every package is identified by its index URL and version.
- The OCI `revision` label on the image equals the run's commit SHA. This is checked once per forge, and is the correlation from artifact back to run.
- The `act` runs keep the act log excerpt (job summary lines and exit status) in the evidence note. Full logs are not committed.

Spec: none — l3io-plan run, no spec index bound

### Security considerations

- Tokens use the least scope that works:
  - package-write for the Gitea index;
  - `write:packages` for GHCR;
  - a repo-scoped token for Docker Hub;
  - release-create on each forge for `PUBLISH_RELEASE_TOKEN`.

  They live only in each forge's secret store.
- No token value, and no screenshot showing one, enters the evidence note. gitleaks runs over it via `just check`.
- **Fork-safety check.** A pull request from a fork (or a branch PR with secrets configured) shows `ci.yaml` with no `PUBLISH_*` value available, because `build.yaml` takes no secrets (AD-2).
- Test tokens and test destinations for the disposable repos are revoked or deleted after verification, and the note records that they were.
- `PUBLISH_CA_CERTIFICATE` is a public certificate, not a key. The note confirms that only the CA certificate was stored.

Spec: none — l3io-plan run, no spec index bound

### Testability approach

This story is itself the post-deploy validation for E013 (CONFIG). There are no new automated tests (AD-4).

Acceptance is the completed `docs/ci/pipeline-verification.md`:
- every cell of the run matrix filled, each with a run URL, except the act release cell, which is not required;
- the Gitea specifics answered;
- defects closed or filed.

`just check` passes on the tree that contains the note and any fixes. ADR-0035's status line reads `- **Status:** Accepted`, with no "pending".

The reviewer spot-checks the evidence:
- opens at least one run URL per runner;
- inspects one digest across two registries;
- confirms the `just act` excerpts show the `build` job ran;
- checks that the TestPyPI dev version and the forge release assets match the recorded version.

Spec: none — l3io-plan run, no spec index bound

### Existing-library check

Verification uses only existing tools:
- the forges' own run UIs and APIs, readable through the Gitea MCP/`gh` CLI;
- `nektos/act` via `just act`;
- `docker buildx imagetools inspect` for digests and platforms;
- `pip download` / `pip index versions` against TestPyPI and the Gitea index to confirm package versions.

No verification script or harness is written. The evidence is a Markdown record (global rule: no custom test harnesses).
